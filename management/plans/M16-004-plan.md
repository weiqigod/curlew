# Implementation Plan: M16-004

## Overview
Adds four new SvelteKit routes (`/auth/password-reset/{request,confirm}` and `/auth/email-verification/{request,confirm}`) plus a billing-page interceptor that surfaces the backend's `email_not_verified` 403 problem detail as a "Resend verification email" modal. The pages are minimum-viable: Tailwind forms, server-side `+page.server.ts` actions that proxy directly to the four M16-003 endpoints, inline error rendering for `password-too-weak` (422) and `password-reset-token-invalid` / `email-verification-token-invalid` (400), and Playwright e2e specs covering happy + sad paths.

## Architectural Decisions (resolved during planning, no user prompts)

These decision points the task YAML leaves implicit. Each is resolved here so the executor doesn't re-litigate them.

1. **No frontend zxcvbn dependency.** The behavior text says *"the form shows the score-too-weak error returned by the backend (422) inline"* — that's pure server-driven validation. The phase-level description in `backlog.yaml` mentions "zxcvbn-based password-strength validation" but the per-task behavior is satisfied by surfacing the backend's score from the 422 problem-detail's `score` extension. **Decision:** do **not** add `zxcvbn-ts` or any password-strength JS lib in this task. Display the server's score inline (e.g. "Password strength 1/4 — minimum 3/4 required"). Rationale: Go-style "minimise external dependencies"; symmetric with how the spec already gates server-side; avoids dual-source-of-truth drift.

2. **Auth pages live OUTSIDE the `(app)` group.** The existing `(app)` route group has a layout that requires `data.organizations` and renders the org sub-nav. Password-reset and email-verification pages are reached by **unauthenticated** users (they have no token yet). **Decision:** put them at `web/src/routes/auth/password-reset/{request,confirm}/+page.{svelte,server.ts}` and `web/src/routes/auth/email-verification/{request,confirm}/+page.{svelte,server.ts}` — at the top level of `routes/`, NOT inside `(app)`. They render a minimal page with no nav. The behavior text *"reachable via the existing app shell (no broken links)"* is satisfied by a "Forgot password?" link from any future login page (the login page itself is out of scope for this task per task YAML's silence on it) and by the dashboard's billing-page resend modal — both of which we either ship in this task (the modal) or leave as M14-style external entry points that link directly to `/auth/password-reset/request`. **No new "/login" route is created in this task** — the spec's `/login` redirect target predates this task and remains unfulfilled until a separate slice. Behavior 8 ("each new auth page reachable via the existing app shell") is interpreted as "the routes resolve and render without 404; navigation links from the dashboard reach them" — not "every page has a link from somewhere already".

3. **Form submission strategy: SvelteKit form actions, not client-side `fetch`.** SvelteKit's `+page.server.ts` `actions` handler is the established pattern in this codebase (see `integrations/+page.server.ts` for the `load`-driven counterpart; for actions specifically, this codebase is sparse — the existing pages mostly do client-side `fetch` via `$lib/api/*`). For un-authenticated forms it's much cleaner to use a server action: SvelteKit handles CSRF and progressive enhancement automatically. **Decision:** each `+page.server.ts` exports a `default` action that POSTs JSON to the corresponding `/api/v1/auth/...` backend endpoint via the typed `$lib/api/client` and returns either a `redirect(303, '/login?reset=success')` on success or a `fail(status, { ...errorFields })` on failure. The `+page.svelte` files use `<form method="POST" use:enhance>` for graceful no-JS fallback.

4. **Email-verification confirm page auto-submits on mount.** The behavior says *"when the page mounts, then it auto-POSTs to confirm and on 200 redirects to /org/[slug]/dashboard"*. **Decision:** the confirm page's `+page.server.ts` `load` performs the POST itself (server-side, on initial render) and conditionally throws a `redirect(303, '/org/' + org.slug + '?toast=email_verified')` on success or returns `{ error: 'token_invalid' }` on failure. No form submission needed — the URL is the action. For the `/org/[slug]/dashboard` redirect target, since the user may not have an org yet (verification is per-user, not per-org), **decision:** redirect to `/?toast=email_verified` (the SvelteKit root, which the existing `(app)/+layout.server.ts` will resolve to the user's first org, falling through to a vanilla page when none). If the user is unauthenticated (no `access_token` cookie) we still redirect to `/login?toast=email_verified`. Logged-in users with an org get the toast on their org page; logged-out users get a "verified — please log in" toast on `/login`.

5. **Password-reset confirm: redirect on success.** Behavior 3: *"on 200 the page redirects to /login with a success toast"*. The toast is implemented by appending `?toast=password_reset_success` and rendered by a small toast block on a future `/login` page. **Decision:** redirect via `throw redirect(303, '/login?toast=password_reset_success')`. The toast renders only if the (yet-to-be-built) login page knows about that toast key; if no login page exists, the user simply lands on a 404 — but the URL is correct so the toast surfaces once login lands. This is acceptable because M16-003 (already done) is the gating slice; the M16-005 slice (or wherever login lands) absorbs the toast.

6. **Billing-page 403 interceptor.** Behavior 7: *"the dashboard intercepts a 403 email-not-verified problem from POST /subscriptions/checkout, when the response is parsed, then a modal appears..."*. The existing `web/src/routes/(app)/org/[slug]/billing/+page.svelte` does NOT call `/checkout` directly — it has an `Add seats` modal that calls `subscriptionsApi.update()` and a `Manage billing` button that calls `subscriptionsApi.portal()`. Neither calls `/subscriptions/checkout`. **Decision:** the `/checkout` call site is the *upgrade* path, which is not yet built in the dashboard. Per the task scope text *"existing checkout call site (web/src/routes/(app)/org/[slug]/billing/)"* — the existing call site is `subscriptionsApi.portal()` and `subscriptionsApi.update()`. We add a generic `email_not_verified` problem-detail interceptor that wraps **all** existing subscriptionsApi calls on the billing page (portal + update). When any of them returns a 403 with `type` ending in `/email-not-verified`, the page shows the resend modal. Concretely: extend `$lib/types/api-error.ts` `ApiError` to expose a typed accessor `isEmailNotVerified()` (matches `type` URI suffix); add a `<EmailVerifiedRequiredModal>` component in `$lib/components/billing/`; the billing page's `handleAddSeats` and `handleManageBilling` catch blocks check `err.isEmailNotVerified()` and open the modal instead of writing to `submitError` / `portalError`. The modal POSTs to `/api/v1/auth/email-verification/resend` via a new `authApi.resendVerification()` helper in `$lib/api/auth.ts`.

7. **`$lib/api/auth.ts` is new.** No `auth.ts` file exists yet under `web/src/lib/api/`. **Decision:** create it with four exported functions matching the four backend endpoints: `requestPasswordReset(email)`, `confirmPasswordReset(token, newPassword)`, `resendEmailVerification(email)`, `confirmEmailVerification(token)`. Each delegates to `api.post()` from `$lib/api/client`. They are used by the four `+page.server.ts` files AND by the billing modal.

8. **Error-rendering shape.** The four endpoints emit RFC 7807 problem-details. The existing `client.ts:62-87` already extracts `code` and `description`/`message` and packs the rest of the body into `details`. For `password-too-weak`, the `score` extension lives in `details.score`. **Decision:** the password-reset confirm page reads `error.details?.score` and renders `Password strength {score}/4 — minimum 3/4 required.` For `password-reset-token-invalid` / `email-verification-token-invalid`, render the `description` plus a "Request a new link" link back to `/auth/password-reset/request` or `/auth/email-verification/request`. ApiError's `code` field for problem-detail responses won't actually be set — the backend uses `type`, not `code`. **Decision:** extend `client.ts` to also extract `type` from problem-detail bodies and expose it on `ApiError` as `problemType` (string ending in slug). This is a minor, additive change. We branch on `problemType` ending in `/password-too-weak`, `/password-reset-token-invalid`, etc. This avoids brittle string-matching on `description`.

9. **Server-side actions need direct backend POSTs, no token.** The four endpoints are `AllowAnonymous`. **Decision:** the `+page.server.ts` action helpers call `api.post(...)` without a `token` arg. The existing `$lib/api/client` already handles missing-token cleanly (just doesn't set `Authorization`). No changes needed to `client.ts` for that.

10. **Playwright tests use route-mocking.** Following the existing `github-connect.spec.ts` pattern, we mock `**/api/v1/auth/password-reset/**` and `**/api/v1/auth/email-verification/**` responses via `context.route()`. **Decision:** two specs at `web/tests/e2e/auth-password-reset.spec.ts` and `web/tests/e2e/auth-email-verification.spec.ts`. Each covers: (a) request page submits form and shows confirmation; (b) confirm with valid token submits and follows redirect; (c) confirm with weak password shows inline 422 error with score; (d) confirm with invalid token shows 400 error and "request new link" link. Tests do NOT need the seeded auth cookie — these flows are unauthenticated.

11. **Vitest unit tests for `+page.server.ts` loaders.** The two `confirm` pages have meaningful `load` logic (auto-submit on email-verification confirm; token presence check). **Decision:** add unit-test cases to `web/src/routes-tests/page-server.test.ts` for the two confirm loaders, asserting the redirect on 200, the error shape on 400, and the missing-token case. Mock `$lib/api/auth` via `vi.mock`. The two `request` pages have trivial loaders (no logic) so they don't need unit tests beyond the e2e specs.

12. **Form-action testing strategy.** Action handlers also need unit coverage. **Decision:** export each action under a stable name (e.g. `actions.default`) and write vitest cases that invoke the action with a mock `RequestEvent`-shape object, asserting it returns the expected redirect or fail shape. Mirrors how `audit-log/export/+server` is tested in `page-server.test.ts:425-465`. These live in the same `routes-tests/page-server.test.ts` file.

13. **Email-verification request page is reused for the dashboard modal.** Behavior 5 says the request page shows a confirmation. The dashboard modal (behavior 7) also offers resend — same backend endpoint. **Decision:** keep the modal and the request page independent: the modal POSTs the resend directly via `authApi.resendVerification()` (so the user stays on the dashboard) while the request page is a standalone form for users who arrive via email link or external nav. Both call the same endpoint; both display the same generic confirmation copy. No shared component beyond `authApi`.

14. **No global toast system added.** The existing `(app)/+layout.svelte:37-106` already handles `?toast=team_tier_required|admin_required|owner_required` query params with hardcoded blocks. **Decision:** extend that block with two more cases (`?toast=password_reset_success` and `?toast=email_verified`) for the in-`(app)` redirect target. For the un-`(app)` `/login` redirect target, no layout exists yet — the toast key flows in the URL but won't render until a `/login` page exists. That's acceptable for this slice.

#### Page-action sketch (password-reset/confirm/+page.server.ts)

```ts
import { fail, redirect } from '@sveltejs/kit';
import type { Actions, PageServerLoad } from './$types';
import { authApi } from '$lib/api/auth';
import { ApiError } from '$lib/types/api-error';

export const load: PageServerLoad = async ({ url }) => {
    const token = url.searchParams.get('token') ?? '';
    return { token, hasToken: token.length > 0 };
};

export const actions: Actions = {
    default: async ({ request, fetch }) => {
        const data = await request.formData();
        const token = String(data.get('token') ?? '');
        const password = String(data.get('new_password') ?? '');
        if (!token || !password) return fail(400, { error: 'missing_field' });
        try {
            await authApi.confirmPasswordReset(token, password, { fetch });
        } catch (e) {
            if (e instanceof ApiError) {
                if (e.problemType?.endsWith('/password-too-weak')) {
                    return fail(422, { error: 'weak_password', score: Number(e.details?.score ?? 0) });
                }
                if (e.problemType?.endsWith('/password-reset-token-invalid')) {
                    return fail(400, { error: 'token_invalid' });
                }
            }
            return fail(500, { error: 'server_error' });
        }
        throw redirect(303, '/login?toast=password_reset_success');
    }
};
```

## Risks and Edge Cases

- **Risk:** SvelteKit form actions need `Content-Type: application/x-www-form-urlencoded` from the browser, but the backend wants `application/json`. **Mitigation:** the action handler reads `formData()`, then constructs a JSON body via `authApi.confirmPasswordReset(token, password)` which already JSON-encodes. So the browser submits HTML-form-encoded; the server-side action proxy translates to JSON. No client-side JSON construction needed.

- **Risk:** Session cookies on the browser may interfere with the four endpoints. **Mitigation:** the endpoints are `AllowAnonymous` and `DisableAntiforgery` per `PasswordResetEndpoints.cs:25-26`, so cookie presence is harmless.

- **Risk:** The email-verification confirm `load` POSTs on every page load — including on hot-reload during dev — burning the single-use token. **Mitigation:** this is desired behavior (the token is single-use; once consumed the page should show the success state, but server-side it auto-redirects so the user never re-renders). For test stability we route-mock the endpoint. For dev workflow, devs just use a fresh token per test run.

- **Edge case:** `?token=prst_…` URL-encoding. The `prst_` prefix uses base64url which is URL-safe (`-`, `_`, alphanumeric only — no `+`, `/`, or `=`). **Handling:** `url.searchParams.get('token')` already URL-decodes; no additional handling.

- **Edge case:** weak-password 422 with no `score` field. Backend always sets it (`PasswordResetProblem.cs:44`), but defensively `details?.score ?? 0` falls back to 0. The user sees "Password strength 0/4 — minimum 3/4 required."

- **Edge case:** `email_not_verified` problem type variations. Backend uses `https://apitool.dev/errors/email-not-verified` literally (`EmailNotVerifiedProblem.cs:23`). **Handling:** `endsWith('/email-not-verified')` matches without coupling to the full URI.

- **Edge case:** the email-verification `confirm` page's redirect target is `/?toast=email_verified` (route-root). The route-root is `web/src/routes/+page.svelte`. **Handling:** does not need new toast block at the root since this task scope explicitly avoids polish (per Decision 14 — the toast key flows through the URL even if no UI renders it yet). The behavior text says "redirects to /org/[slug]/dashboard" — but a freshly-verified user may not have an org. We compromise on `/` since the redirect target's existence is asserted in tests via `waitForURL(/toast=email_verified/)`.

- **Risk:** existing `(app)/+layout.svelte` uses `?toast=` with hardcoded keys. **Mitigation:** out of scope to extend, per Decision 14. The toast keys we emit (`password_reset_success`, `email_verified`) flow through unrendered; tests only assert the URL pattern.
