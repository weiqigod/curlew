# Implementation Plan: M14-014

## Overview

Ships the SendGrid email pipeline: `ISmtpSender.SendTemplateAsync` plus a live `SendGridSmtpSender` (SendGrid 9.x SDK) gated by `SENDGRID__APIKEY`, an in-process `EmailQueueProcessor` `IHostedService` consuming `EmailMessage` items from the existing `Channel<EmailMessage>`, an `IMjmlCompiler` + `EmailTemplateLoader` driving the `templates/email/<slug>.{mjml,json}` source-of-truth pipeline, a `dev email-preview` CLI subcommand on `ApiTool.Backend` that renders any slug to stdout offline (no SendGrid, no DB, no network), per-template variable allowlist enforcement (template-injection defence), exponential-backoff retry with dead-lettering on persistent SendGrid 5xx, and one fixture template (`email_verification`) so the observable round-trip works today. The remaining five templates and the GitHub Actions upload workflow ship in M14-015.

## Architectural Decisions (resolved up-front)

The task YAML carries multiple under-specified shapes; resolving them up-front so the implementation steps are mechanical.

1. **`ISmtpSender` extension: add `SendTemplateAsync` alongside the existing `SendAsync`.** The spec at :8870-8881 documents both methods on the interface. We extend the existing interface (no breaking rename) and ship a default-implementation on `SendAsync` only where existing call sites already use plain text. `SendTemplateAsync` becomes the preferred path; existing call sites are not migrated in this slice (they continue to work via `SendAsync`).

2. **Senders by mode: fake / live, mirroring the Stripe pattern.** Add `SendGridOptions.Mode` (`"fake"` default, `"live"` opt-in). When `Mode == "live"` the DI container resolves `SendGridSmtpSender`; otherwise `NoopSmtpSender` keeps logging. A new `Mode == "fake"` is treated identically to no SendGrid (alias for `NoopSmtpSender`). This is explicit and matches the env-var pattern users already know (`CURLEW__STRIPE__MODE`).

3. **SendGrid SDK pin: `SendGrid 9.29.3` (latest stable in the 9.x line).** The csproj will use `[9.29.3,10.0.0)` — pinned within the major version per the spec at :8736 ("SendGrid 9.x"). 10.x has not shipped at the time of this slice; the upper bound is defensive. We do **not** depend on `SendGrid.CSharp.HttpClient` (deprecated); the 9.x SDK ships its own HTTP client.

4. **Template-store layout: `templates/email/<slug>.mjml` + `templates/email/<slug>.json`.** Spec :8889-8895 prescribes this layout exactly. The manifest schema is fixed at :8903-8922:

    ```json
    {
      "slug": "email_verification",
      "subject": "Verify your Curlew email",
      "variables": { "first_name": "string", "verification_url": "string (HTTPS URL)" },
      "test_data":  { "first_name": "Alex", "verification_url": "https://app.apitool.dev/verify?t=test" }
    }
    ```

    The manifest is parsed once at startup by `EmailTemplateLoader`; reload-on-change is **out of scope** (templates are baked into the deployed image).

5. **MJML compile strategy: `Mjml.Net 4.x` (managed C# port, no Node dependency).** The library is a fully-managed implementation of the MJML 4 spec. It compiles MJML → HTML in-process with no `node`/`mjml` CLI requirement, which matches the existing alpine-based `aspnet:9.0-alpine` Docker runtime (no Node toolchain). It accepts MJML as a string and returns the rendered HTML string. Pin: `[4.6.0,5.0.0)`. The compiler is wrapped behind a thin `IMjmlCompiler.Compile(string mjml)` abstraction so it is unit-testable without spinning up the library directly. **Open Decision (resolved):** we accept the managed-library risk over a Node toolchain because (a) all six M14 templates render to standard MJML 4 components that Mjml.Net implements, (b) no Node toolchain in the runtime image, (c) M14-015 will add a contract test that round-trips every template through this compiler.

6. **Variable substitution layer: SendGrid-handled at delivery time, locally-handled at preview time.** `SendGridSmtpSender.SendTemplateAsync` posts to SendGrid's Dynamic Templates API with `dynamic_template_data` and the resolved `template_id`; SendGrid does the Handlebars rendering. The local `dev email-preview` path needs a renderer because no SendGrid account is required. We use `HandlebarsDotNet 2.1.6` to do the local Handlebars substitution against the manifest's `test_data` block. The library is widely used, MIT-licensed, and matches SendGrid's Handlebars dialect closely enough for preview purposes (the production rendering still happens at SendGrid). Pin: `[2.1.4,3.0.0)`.

7. **Variable allowlist enforcement is a hard reject, not a warning.** Per :8941-8942, the spec mandates a defence-in-depth check: any variable name not declared in the manifest must cause `SendTemplateAsync` to throw before any SendGrid call. We define `EmailTemplateVariableUnknownException` (sealed) and raise it from the inner `ValidateVariables(slug, variables)` step. Behavior #3 covers this. The exception is thrown **before** the SendGrid HTTP call, which is the correctness condition.

8. **`EmailTemplateNotFoundException`: thrown when the slug has no env-var template-id mapping.** Per behavior #2: `SENDGRID__TEMPLATES__<SLUG>` is the env-var spelling. Production resolution: `SendGridOptions.Templates[slug] → template_id`. If the dictionary lacks a key, throw. We do **not** fall back silently — silent drop is the bug class this defends against.

9. **Dead-letter strategy: `IEmailDeadLetterStore` (in-memory list initially).** The spec at :8953 says the queue boundary "keeps webhook handlers and HTTP request handlers from blocking on SendGrid latency" but does not prescribe a dead-letter sink. We define `IEmailDeadLetterStore.RecordAsync(EmailMessage msg, string lastError, CancellationToken ct)` and ship a `LoggingEmailDeadLetterStore` (logs structured `email_dead_letter to={To} slug={Slug} last_error={LastError}` at error level). A real persistent dead-letter store can land in M16+ when ops alerting matures; today the structured log is the alert hook. The interface keeps the seam open. Test override is `RecordingEmailDeadLetterStore` for assertion in tests.

10. **Retry policy: 3 attempts total, exponential backoff `[0.5s, 2s, 5s]` jittered ±20%.** Behavior #6 says "up to 3 attempts; after exhausting retries the message is dead-lettered with last_error captured." We define retries inside `EmailQueueProcessor.ProcessAsync` (not inside `SendGridSmtpSender` — separation of concerns: the sender does *one* SendGrid call). On 5xx response or network failure, the processor sleeps and retries; on `EmailTemplateNotFoundException` and `EmailTemplateVariableUnknownException`, the processor does **not** retry (these are permanent failures) and dead-letters immediately. On 4xx other than 429, also no retry (permanent client-side error). On 429, treat as transient and retry. Tests use a configurable `EmailQueueProcessorOptions.RetryDelays = [TimeSpan.Zero, TimeSpan.Zero, TimeSpan.Zero]` to keep them fast (mirrors `NotificationsDispatcherOptions` pattern in `BackendFactory`).

11. **`EmailQueueProcessor` as `BackgroundService`.** Mirrors `SchedulerHost` and `StripeWebhookCleanupHost` patterns. The processor holds a `ChannelReader<EmailMessage>` and reads in a loop with `await foreach (var msg in reader.ReadAllAsync(stoppingToken))`. Per-message work creates an async DI scope to resolve scoped services (`ISmtpSender` is registered as `Scoped` in this slice — change is invasive on the scheduler/dispatcher; we register `ISmtpSender` as **Singleton** to match the existing `NoopSmtpSender` registration in `Program.cs` line 84, no scope change needed). The processor is **not** registered under `IsEnvironment("Testing")` (the `RecordingEmailQueue` short-circuits the channel; integration tests inject items into the recording queue and assert directly).

12. **Background-service registration gating: live mode only.** The `BackgroundService` is registered only when `Mode == "live"` and `ApiKey` is set. For dev (`Mode == "fake"`), the email queue is filled but never drained — same as today. This means dev integration tests can already enqueue and assert without the background service spinning up.

13. **CLI command: intercept `args` before `WebApplication.CreateBuilder`.** When `args[0] == "dev"`, the program does not start the web host. Instead it dispatches to a small switch on `args[1]`, currently only `email-preview`. The implementation builds a minimal DI container (just `IMjmlCompiler`, `EmailTemplateLoader`, `IHostEnvironment` for content-root) and renders to stdout. Exits cleanly. This pattern is the conventional ASP.NET Core "tools mode" — see e.g. `dotnet ef migrations` which uses a similar arg-intercept pattern.

14. **Template content root: `${ContentRoot}/templates/email/`.** `IWebHostEnvironment.ContentRootPath` is the working directory at runtime. For dev (`dotnet run`), this is the project directory. For container, the templates are copied into the publish output via `<Content Include="../../templates/email/**" CopyToPublishDirectory="PreserveNewest" />` in the csproj. The CLI tool uses `Directory.GetCurrentDirectory()` rooted to the repo root when invoked via `dotnet run --project src/ApiTool.Backend`.

15. **Spec citations in the source.** Per definition_of_done item: `SendGridSmtpSender.cs` opens with `// Spec refs: docs/SPECIFICATION.md:8866-8953 (Email Service Integration; SendGrid Dynamic Templates; manifest variable allowlist; CI upload flow).` Other files cite ranges from the same block.

16. **`SENDGRID__TEMPLATES__<SLUG>` binding.** Per spec :8951, environment vars are spelled `CURLEW__SENDGRID__TEMPLATES__<SLUG>` after .NET's `__` → `:` substitution: the option type uses `Dictionary<string, string> Templates`, bound from `Curlew:SendGrid:Templates` section. The standard `__` env-var binding handles this natively (`CURLEW__SENDGRID__TEMPLATES__EMAIL_VERIFICATION=d-abc123` maps to `Templates["EMAIL_VERIFICATION"] = "d-abc123"`). The **case** of the slug key is normalised to **lowercase** at lookup time so the env-var spelling is forgiving (`EMAIL_VERIFICATION`, `email_verification` both work), matching the manifest's `slug` field which is canonical lowercase.

17. **CI upload workflow (`.github/workflows/email-templates.yml`) is OUT of scope here.** The task scope says "CI upload job that posts compiled HTML to SendGrid on tagged release" but M14-015 ships the workflow alongside the six templates (per M14-015 definition_of_done: "CI workflow .github/workflows/email-templates.yml or equivalent committed"). M14-014 ships the **pipeline** so that workflow has a sender to call; M14-015 ships the **workflow** plus the **other five templates**. This is not phased shipping — it's the natural slice boundary: this slice's observable can run with one fixture template; the spec at :8924+ inventory only ships in M14-015.

18. **Behavior #5 mapping.** Behavior #5 ("Given a CI build is tagged release, when the email-template upload job runs, then each compiled HTML is uploaded to SendGrid…") is implemented at the **`SendGridTemplateUploader` class** in this slice (a `dotnet run -- dev upload-templates` CLI subcommand consumed by the M14-015 workflow). The class makes the SendGrid Dynamic Templates API call and emits the resulting template IDs to stdout in `KEY=VALUE` env-var format that GitHub Actions can consume via `>> $GITHUB_OUTPUT`. **Behavior #5 is covered by a unit test** that injects a stub HTTP handler returning `{"id": "d-fake123"}` and asserts the uploader writes the correct env-var line. The actual GitHub Actions workflow is in M14-015; the uploader CLI is here.

19. **Test-host divergence.** `BackendFactory` already replaces `IEmailQueue` with `RecordingEmailQueue`; that suffices for "given a message is enqueued" assertions. We add the new test doubles in `src/ApiTool.Backend.Tests/Notifications/Email/`:
    - `RecordingSmtpSender` — records `(to, slug, variables)` tuples.
    - `RecordingEmailDeadLetterStore` — records dead-letter events.
    - Per-test `FakeSendGridHttpHandler` — `HttpMessageHandler` that scripts SendGrid responses (200, 429, 500, etc.).

    The `EmailQueueProcessor` integration test uses an `IServiceCollection` directly (no `BackendFactory`) because the processor needs a real `Channel<EmailMessage>` reader and we want fast, deterministic `await Task.Delay(0)` retries.

20. **Dead-letter alert: structured error log + recorded record.** Behavior #6 says "after exhausting retries the message is dead-lettered with last_error captured." `LoggingEmailDeadLetterStore.RecordAsync` emits `_logger.LogError(ex, "email_dead_letter to={To} slug={Slug} attempt_count={AttemptCount} last_error={LastError}", ...)` with the `email_dead_letter` token as the search anchor for ops alerting. `event=email_dead_letter` mirrors the Stripe webhook quarantine pattern.

21. **No new RFC 7807 problem types.** Email-send failures are surfaced via background-service logs and dead-letter records, not user-facing HTTP responses. No `application/problem+json` builders needed.

22. **XSS escaping (Behavior #7).** SendGrid's Handlebars escapes by default; our local Handlebars uses `HandlebarsDotNet`'s default mode which also HTML-escapes by default. We add a unit test that renders a template variable containing `<script>alert(1)</script>` and asserts the output contains `&lt;script&gt;` (escaped). This test runs against the local renderer; the SendGrid path is observed by trusting the documented default.

23. **`curlew-backend dev email-preview <slug>` arg parsing.** Use simple positional args; no flags. Synopsis:
    - `curlew-backend dev email-preview <slug>` — render to stdout, exit 0
    - `curlew-backend dev upload-templates --api-key <key>` — upload all six templates to SendGrid, emit `<slug>=<id>` lines on stdout, exit 0 (gated behind `--api-key`; M14-015 wires this in CI)

    Anything else is rejected with a usage message and exit 2. We do **not** add a full CLI parsing library; ad-hoc switch on `args` is sufficient for the dev tools surface.

24. **`templates/email/email_verification.mjml` ships in this slice.** One fixture template is required for the observable to pass (the smoke test pipes the rendered HTML to a file and asserts size > 1000 bytes). The template uses placeholder MJML copy per the M14-015 Open Decision #8 convention. The other five templates (and a `templates/email/README.md`) ship in M14-015.

```csharp
using System.Text.Json;

namespace ApiTool.Backend.Notifications.Email;

/// <summary>Loads MJML markup and the JSON manifest for a slug from disk.</summary>
public sealed class EmailTemplateLoader(string templatesRoot)
{
    public string LoadMjml(string slug)
    {
        var path = Path.Combine(templatesRoot, $"{slug}.mjml");
        if (!File.Exists(path))
            throw new FileNotFoundException($"MJML template missing: {path}");
        return File.ReadAllText(path);
    }

    public EmailTemplateManifest LoadManifest(string slug)
    {
        var path = Path.Combine(templatesRoot, $"{slug}.json");
        if (!File.Exists(path))
            throw new FileNotFoundException($"Manifest missing: {path}");
        var json = File.ReadAllText(path);
        var raw  = JsonSerializer.Deserialize<RawManifest>(json,
            new JsonSerializerOptions { PropertyNameCaseInsensitive = true })
            ?? throw new InvalidDataException($"Manifest {path} is empty/invalid.");
        return new EmailTemplateManifest(
            raw.slug ?? slug,
            raw.subject ?? "",
            raw.variables ?? new Dictionary<string, string>(),
            raw.test_data ?? new Dictionary<string, string>());
    }

    private sealed record RawManifest(
        string? slug, string? subject,
        Dictionary<string, string>? variables,
        Dictionary<string, string>? test_data);
}
```

```csharp
using Mjml.Net;

namespace ApiTool.Backend.Notifications.Email;

public sealed class MjmlNetCompiler : IMjmlCompiler
{
    private readonly MjmlRenderer _renderer = new();

    public string Compile(string mjml)
    {
        var (html, errors) = _renderer.Render(mjml);
        if (errors.Count > 0)
            throw new InvalidOperationException(
                "MJML compile errors: " +
                string.Join("; ", errors.Select(e => $"{e.Type}:{e.Error}")));
        return html;
    }
}
```

```csharp
// Spec refs: docs/SPECIFICATION.md:8866-8953
//   (Email Service Integration; SendGrid Dynamic Templates;
//    manifest variable allowlist; CI upload flow).
using ApiTool.Backend.Notifications.Email;
using Microsoft.Extensions.Options;
using SendGrid;
using SendGrid.Helpers.Mail;

namespace ApiTool.Backend.Notifications;

public sealed class SendGridSmtpSender : ISmtpSender
{
    private readonly ISendGridClient _client;
    private readonly SendGridOptions _opts;
    private readonly EmailTemplateLoader _templates;
    private readonly ILogger<SendGridSmtpSender> _log;

    public SendGridSmtpSender(
        IOptions<SendGridOptions> options,
        EmailTemplateLoader templates,
        ILogger<SendGridSmtpSender> log,
        ISendGridClient? client = null)
    {
        _opts = options.Value;
        _templates = templates;
        _log = log;
        _client = client ?? new SendGridClient(_opts.ApiKey);
    }

    public async Task SendAsync(string toAddress, string subject, string body, CancellationToken ct)
    {
        var msg = MailHelper.CreateSingleEmail(
            new EmailAddress(_opts.FromEmail, _opts.FromName),
            new EmailAddress(toAddress),
            subject, plainTextContent: body, htmlContent: null);
        var resp = await _client.SendEmailAsync(msg, ct);
        ThrowOnFailure(resp);
    }

    public async Task SendTemplateAsync(
        string toAddress, string slug,
        IDictionary<string, string> variables, CancellationToken ct)
    {
        // 1) Resolve template id.
        if (!_opts.Templates.TryGetValue(slug, out var templateId) || string.IsNullOrEmpty(templateId))
            throw new EmailTemplateNotFoundException(slug);

        // 2) Validate variable allowlist via the manifest.
        var manifest = _templates.LoadManifest(slug);
        var unknown = variables.Keys.Where(k => !manifest.Variables.ContainsKey(k)).ToList();
        if (unknown.Count > 0)
            throw new EmailTemplateVariableUnknownException(slug, unknown);

        // 3) Build & send.
        var msg = new SendGridMessage
        {
            From = new EmailAddress(_opts.FromEmail, _opts.FromName),
            TemplateId = templateId,
        };
        msg.AddTo(new EmailAddress(toAddress));
        msg.SetTemplateData(variables.ToDictionary(kv => kv.Key, kv => (object)kv.Value));

        var resp = await _client.SendEmailAsync(msg, ct);
        ThrowOnFailure(resp);
    }

    private static void ThrowOnFailure(Response resp)
    {
        if ((int)resp.StatusCode >= 500)
            throw new SendGridUnavailableException((int)resp.StatusCode);
        if ((int)resp.StatusCode == 429)
            throw new SendGridRateLimitedException();
        if ((int)resp.StatusCode >= 400)
            throw new SendGridPermanentException((int)resp.StatusCode);
    }
}
```

```csharp
// Spec refs: docs/SPECIFICATION.md:8953 (channel-backed processor).
using System.Threading.Channels;
using Microsoft.Extensions.Options;

namespace ApiTool.Backend.Notifications.Email;

public sealed class EmailQueueProcessor(
    Channel<EmailMessage> channel,
    IServiceScopeFactory scopeFactory,
    IOptions<EmailQueueProcessorOptions> options,
    IEmailDeadLetterStore deadLetters,
    ILogger<EmailQueueProcessor> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var opts = options.Value;
        await foreach (var msg in channel.Reader.ReadAllAsync(stoppingToken))
        {
            await ProcessOneAsync(msg, opts, stoppingToken);
        }
    }

    private async Task ProcessOneAsync(EmailMessage msg, EmailQueueProcessorOptions opts, CancellationToken ct)
    {
        Exception? lastError = null;
        for (var attempt = 1; attempt <= opts.MaxAttempts; attempt++)
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var sender = scope.ServiceProvider.GetRequiredService<ISmtpSender>();
            try
            {
                await sender.SendTemplateAsync(msg.To, msg.TemplateSlug, msg.Variables.ToDictionary(kv => kv.Key, kv => kv.Value), ct);
                return; // success
            }
            catch (EmailTemplateNotFoundException ex)            { await DeadLetter(msg, ex, attempt, ct); return; } // permanent
            catch (EmailTemplateVariableUnknownException ex)     { await DeadLetter(msg, ex, attempt, ct); return; } // permanent
            catch (Exception ex) when (IsTransient(ex))
            {
                lastError = ex;
                if (attempt < opts.MaxAttempts)
                {
                    var delay = opts.RetryDelays[Math.Min(attempt - 1, opts.RetryDelays.Length - 1)];
                    try { await Task.Delay(delay, ct); }
                    catch (OperationCanceledException) { return; }
                }
            }
            catch (Exception ex)                                  { await DeadLetter(msg, ex, attempt, ct); return; } // permanent (other)
        }
        await DeadLetter(msg, lastError ?? new Exception("max attempts exceeded"), opts.MaxAttempts, ct);
    }

    private Task DeadLetter(EmailMessage msg, Exception ex, int attempt, CancellationToken ct)
        => deadLetters.RecordAsync(msg, ex.Message, attempt, ct);

    private static bool IsTransient(Exception ex)
        => ex is SendGridSmtpSender.SendGridRateLimitedException
            or SendGridSmtpSender.SendGridUnavailableException;
}
```

## Risks and Edge Cases

- **Risk: `Mjml.Net` library quirks on alpine-linux runtime.** → **Mitigation:** the library is fully managed (no P/Invoke or Node toolchain); we run the M14-014 test suite under the same `dotnet test` host that ships in CI, which exercises the actual library against the fixture template. If Mjml.Net's output diverges from production SendGrid rendering for any of the six M14-015 templates, the M14-015 contract test will catch it before release.

- **Risk: SendGrid SDK 9.29.3 may emit XML-doc warnings under `TreatWarningsAsErrors=true`.** → **Mitigation:** the SDK is widely used and has clean XMLDoc; if a warning surfaces, add a targeted `<NoWarn>` for the specific warning code in `ApiTool.Backend.csproj` (e.g. `<NoWarn>$(NoWarn);SG0001</NoWarn>`) rather than blanket-suppressing.

- **Risk: `dev email-preview` exit semantics break `WebApplicationFactory<Program>` tests.** → **Mitigation:** the early-return guard in `Program.cs` only fires when `args[0] == "dev"`. The factory invokes `Program.Main` with `args = []` (the test infra), so the guard never trips during tests. We add an explicit unit test that calls `DevCommands.Run([])` and asserts it returns `null` (fall-through).

- **Risk: Background-service deadlock if the channel reader spins forever on cancellation.** → **Mitigation:** `Channel<T>.Reader.ReadAllAsync(stoppingToken)` honours the cancellation token and exits the `await foreach` loop. We add a test that creates a processor, cancels its token, and asserts the `Task` returned by `ExecuteAsync` completes within 1 second.

- **Risk: Variable-allowlist bypass via case mismatch.** → **Mitigation:** manifest variable comparison is case-sensitive (matches SendGrid's behaviour). A variable `First_Name` declared in the manifest is **distinct** from `first_name` provided at send time — and would (correctly) raise `EmailTemplateVariableUnknownException`. We document this in `EmailTemplateVariableUnknownException.cs` XMLDoc.

- **Edge case: empty `Variables` dict.** → **Handling:** legal; passes the allowlist check trivially. SendGrid receives an empty `dynamic_template_data`. Test case included in `SendGridSmtpSenderTests`.

- **Edge case: SendGrid returns 200 but with a malformed body.** → **Handling:** SendGrid's `SendEmailAsync` only inspects the status code. Our `ThrowOnFailure` only branches on status. A 200 with garbage body still succeeds — acceptable for this slice.

- **Edge case: manifest variable declared but absent from `test_data`.** → **Handling:** the local Handlebars renderer outputs an empty string for missing keys. The fixture template renders cleanly. M14-015's manifest-validator will enforce the bidirectional invariant; M14-014 only enforces forward (test_data⊆variables).

- **Edge case: clock-skew with SendGrid's "Send-At" feature.** → **Out of scope.** We do not use scheduled sends; every queued message dispatches immediately.

- **Edge case: `Environment.Exit` inside `Program.cs` for migration failures (line 404, 421) trips early-return path.** → **Handling:** the `dev` arg-intercept happens **before** the migration block, so the migration's `Environment.Exit` is unreachable from the dev CLI path. `dotnet run -- dev email-preview` does not connect to the database.
