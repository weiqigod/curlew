# Implementation Plan: M19-004

## Overview

Add the `assertions: - cel: "<expr>"` shape: parser accepts the new entry form (mutually exclusive with operator assertions), the assertion evaluator runs the expression against the standard activation `{response, previous, vars, env}`, and on failure builds a message that includes the literal expression source plus the resolved value of each top-level named reference, with sensitive values masked via the existing `SensitiveSet`/`RedactBody` pipeline.

## Decisions made during planning (no clarifying questions asked)

1. **Redaction marker.** Task YAML mentions `***`. The project standard (used by `internal/variable/sensitive.go`, `internal/variable/redact.go`, and every output formatter) is `[REDACTED]`. The plan follows the project standard. The smoke fixture / behavior tests assert on `[REDACTED]`. (The observable check in the task YAML is reinterpreted as "the standard redaction marker used by every other surface in the tool".)
2. **Parallel main-phase fallback.** `parallel.Config` has no access to the CEL evaluator, the sensitive set, or the runtime sensitive observer. Threading those four through the parallel executor and through every wave call site is large and unrelated to the slice. Instead, when any item in `col.Requests` carries `cel:` assertions, the runner falls back to sequential main-phase execution (and emits a diagnostics line). This mirrors the M19-001 `if:` fallback at `runner.go:1284`. The fallback is unobservable to users who don't combine `--parallel` with `cel:`.
3. **WebSocket steps.** Spec scope is `assertions:` on HTTP/GraphQL requests. WebSocket expect-step assertions (`BodyAssertions` inside `WebSocketStep.ExpectAssertions` and `AnyOf`) are explicitly out of scope for M19-004. The new `cel:` entry must therefore be rejected if it appears inside a WebSocket expect step — but easiest is to simply not wire CEL into the WebSocket evaluator. Adding `cel:` to a WebSocket expect step will surface as an unknown JSONPath assertion (existing rejection path) since `BodyAssertions.UnmarshalYAML` already requires a path/operator mapping. No code change needed for WS.
4. **Compile cache.** `if:` already maintains a per-run `ifProgCache` keyed by source string. CEL assertions get a parallel cache (`assertProgCache`) on `VarSources`. Same shape, same lifecycle, same lazy init.
5. **Top-level named references in failure messages.** "Top-level named reference" is defined as: every identifier with a top-level prefix from the activation (`response`, `previous`, `vars`, `env`) and the longest selector chain that does not include a `Call` (function/method invocation) in its path. Concretely: walk the AST; for each `Ident` or `Select` whose root is `response|previous|vars|env`, record the receiver expression up to (but not including) the enclosing `Call`. So `response.body.items.map(i, i.price).sum()` records `response.body.items` (the receiver of `.map(...)`), and `response.body.total` records `response.body.total`. The recorded receivers are de-duplicated and rendered in source order.
6. **Resolved value rendering.** Resolved sub-values are stringified via `fmt.Sprintf("%v", value)` to match the existing assertion formatter pattern (`internal/assertion/assertion.go` `formatExpected`/`fmt.Sprintf("%v", val)`). Sensitive scrubbing happens after rendering, via the existing `RedactBody` pipeline (the failure message becomes part of `Result.Actual`, which flows through the same redaction layer as the response body).
7. **Sensitive redaction inside the failure message itself.** Failure messages can contain raw secret values (sub-value of `vars.api_key`). We *cannot* rely solely on `RedactBody` walking the response body — that does not touch `Result.Actual` strings. We therefore apply substring redaction directly in the CEL-assertion message builder: any value registered in the per-run `SensitiveSet` is substring-replaced with `[REDACTED]` before the message is stored in `Result.Actual`. This matches the redaction pass that `internal/variable/redact.go:redactString` performs.
8. **Error code framing.** `ERR_CEL_TYPE` and `ERR_CEL_PARSE` already exist in `internal/cel/errors.go` as `ErrCelType` / `ErrCelParse`. The plan uses the existing `*cel.CelError` shape, sets `FieldPath` to `assertions[N].cel`, and surfaces type errors as assertion failures (`Passed: false`) rather than as runtime errors (per behavior #5 in the task YAML). Parse errors (which can only occur if validate didn't catch them, or if validate wasn't run) surface as assertion failures too, with the parse-error message in `Result.Actual`.
9. **`request` identifier rejection.** The CEL environment in `internal/cel/cel.go:NewEnvironment` only declares `response`, `previous`, `vars`, `env`. Referencing `request` already fails the type-check phase with an "undeclared reference" message → `*CelError{Sentinel: ErrCelParse}`. Behavior #7 is therefore satisfied without code change (just a test).

#### Note on shape collision

The existing `assertions:` block already uses a **map** shape for `body:`:

```yaml
assertions:
  body:
    $.id:
      equals: 1
```

The task requires a **list** shape for the new CEL entries:

```yaml
assertions:
  - cel: "response.body.total == response.body.items.map(i, i.price).sum()"
```

These are *not* the same node — `assertions:` is currently a mapping with keys `status`, `headers`, `body`, `timing`, `schema`. The task YAML's literal text "An assertion entry `- cel: ...`" implies a sibling list. The cleanest fit:

```yaml
assertions:
  status: 200
  body:
    $.id: { equals: 1 }
  cel:
    - "response.body.total == response.body.items.map(i, i.price).sum()"
    - "response.body.status == \"ok\""
```

`cel:` is a top-level key under `assertions:` with a list-of-strings value. Each entry is one CEL expression. This:

- Avoids any breakage to the existing `body:`/`headers:`/`status:`/`timing:`/`schema:` shape.
- Reads naturally as "this collection has these CEL assertions".
- Matches the existing pattern that mutual exclusion is *between operator assertions and CEL assertions on the same entry* — since each entry is one item in the list, "mutual exclusion per entry" reduces to "a list entry cannot also carry operator keys", which is automatically true (list entries are strings, not maps).

But the task explicitly says:

> "Given an assertion entry that contains both `cel:` and an operator key (e.g. `eq:`) on the same entry, when the parser loads the file, then parsing fails..."

This requires the **richer shape** where an entry can carry multiple keys. The reconciliation:

- The `cel:` key under `assertions:` accepts **two forms**: a list of strings (most common) OR a list of mappings where each mapping has exactly one key (`cel: "<expr>"`). The mapping form is what the task's mutual-exclusion behavior addresses.
- Plan: implement the **list-of-strings** form as primary (covers all the smoke-fixture, behavior, and observable test cases), AND implement the **list-of-mappings** form as a secondary parsing path that explicitly rejects entries with extra operator keys.

```go
// internal/parser/collection.go
type CELAssertion struct {
    Source string // the CEL expression
}

type CELAssertions struct {
    Items []CELAssertion
}

func (c *CELAssertions) UnmarshalYAML(value *yaml.Node) error {
    if value.Kind != yaml.SequenceNode {
        return fmt.Errorf("cel assertions must be a list")
    }
    for _, item := range value.Content {
        switch item.Kind {
        case yaml.ScalarNode:
            // simple form: - "<expr>"
            c.Items = append(c.Items, CELAssertion{Source: item.Value})
        case yaml.MappingNode:
            // explicit form: - { cel: "<expr>" } — reject extra keys
            var src string
            extraKey := ""
            for j := 0; j+1 < len(item.Content); j += 2 {
                k := item.Content[j].Value
                if k == "cel" {
                    src = item.Content[j+1].Value
                    continue
                }
                if extraKey == "" {
                    extraKey = k
                }
            }
            if extraKey != "" {
                return fmt.Errorf(
                    "cel assertion entry: cel: and operator key %q are mutually exclusive on the same entry: %w",
                    extraKey, ErrCelAndOperatorMutuallyExclusive,
                )
            }
            if src == "" {
                return fmt.Errorf("cel assertion entry has empty cel: source")
            }
            c.Items = append(c.Items, CELAssertion{Source: src})
        default:
            return fmt.Errorf("cel assertion entry: expected string or mapping, got %v", item.Kind)
        }
    }
    return nil
}

// Assertions struct gains:
//   CEL CELAssertions `yaml:"cel,omitempty"`
```

The "mutual exclusion per entry" behavior is satisfied by the mapping-form rejection. The list-of-strings form simply cannot express the conflict.

func (v *VarSources) ensureAssertProgCache() map[string]apicel.Program {
    if v.assertProgCache == nil {
        v.assertProgCache = make(map[string]apicel.Program)
    }
    return v.assertProgCache
}

func compileAssertProgram(cache map[string]apicel.Program, ev apicel.Evaluator, src string) (apicel.Program, error) {
    if p, ok := cache[src]; ok {
        return p, nil
    }
    p, err := ev.Compile(src, celgo.BoolType)
    if err != nil {
        return nil, err
    }
    cache[src] = p
    return p, nil
}

```go
// internal/assertion/cel.go
package assertion

import (
    apicel "github.com/weiqigod/curlew/internal/cel"
)

// CELInput describes one CEL assertion to evaluate.
type CELInput struct {
    Index  int    // position in assertions.cel list (for error attribution)
    Source string // the CEL expression
}

// CELContext bundles the activation + evaluator + sensitive-value snapshot.
// The snapshot is a sorted slice (longest-first) of values to substring-mask
// in the rendered failure message; the assertion package does not depend on
// internal/variable.
type CELContext struct {
    Evaluator        apicel.Evaluator
    ProgCache        map[string]apicel.Program
    Response         *apicel.Response
    Previous         *apicel.Response
    Vars             map[string]any
    Env              map[string]string
    SensitiveNames   map[string]struct{}
    SensitiveValues  []string // pre-sorted longest-first
    SensitiveObserve func(name, value string) // optional; nil = no-op
}

// CheckCEL evaluates each CELInput and returns one Result per input.
// On runtime errors the result is recorded as failed with ERR_CEL_TYPE /
// ERR_CEL_PARSE framing in the Actual field.
func CheckCEL(inputs []CELInput, ctx CELContext) []Result {
    if len(inputs) == 0 {
        return nil
    }
    out := make([]Result, 0, len(inputs))
    for _, in := range inputs {
        out = append(out, evalCELAssertion(in, ctx))
    }
    return out
}

func evalCELAssertion(in CELInput, ctx CELContext) Result {
    typeName := fmt.Sprintf("assertions[%d].cel", in.Index)

    prog, compileErr := compileCELAssertion(ctx, in.Source)
    if compileErr != nil {
        return Result{
            Type:     typeName,
            Expected: "compiled CEL program",
            Actual:   redactString(compileErr.Error(), ctx.SensitiveValues),
            Passed:   false,
        }
    }

    out, evalErr := prog.Eval(apicel.StandardActivation{
        Response: ctx.Response,
        Previous: ctx.Previous,
        Vars:     ctx.Vars,
        Env:      ctx.Env,
    }, apicel.EvalOptions{
        SensitiveNames:    ctx.SensitiveNames,
        SensitiveObserver: ctx.SensitiveObserve,
    })
    if evalErr != nil {
        return Result{
            Type:     typeName,
            Expected: in.Source,
            Actual:   redactString(formatCELRuntimeError(in.Source, evalErr), ctx.SensitiveValues),
            Passed:   false,
        }
    }

    b, ok := out.(bool)
    if !ok {
        // Defensive: Compile expected bool type — this branch should be unreachable.
        return Result{
            Type:     typeName,
            Expected: "boolean result",
            Actual:   fmt.Sprintf("non-bool %T", out),
            Passed:   false,
        }
    }
    if b {
        return Result{
            Type:     typeName,
            Expected: in.Source,
            Actual:   "true",
            Passed:   true,
        }
    }
    // Failed: enumerate top-level named references and resolve each.
    msg := buildCELFailureMessage(in.Source, ctx)
    return Result{
        Type:     typeName,
        Expected: in.Source,
        Actual:   redactString(msg, ctx.SensitiveValues),
        Passed:   false,
    }
}
```

#### `buildCELFailureMessage`

```go
// buildCELFailureMessage walks the parsed expression, enumerates each
// top-level named reference (a Select/Ident chain rooted at one of the four
// activation identifiers and not interrupted by a Call), and renders one
// line per reference with its resolved value.
//
// Output shape:
//   <source>
//     response.body.total = 9.50
//     response.body.items.map(i, i.price).sum() = 10.50
func buildCELFailureMessage(src string, ctx CELContext) string {
    refs := collectTopLevelRefs(src, ctx.Evaluator) // implemented in internal/cel
    var b strings.Builder
    b.WriteString(src)
    for _, ref := range refs {
        val, err := evaluateSubexpression(ref, ctx)
        var rendered string
        if err != nil {
            rendered = fmt.Sprintf("<eval error: %s>", err)
        } else {
            rendered = fmt.Sprintf("%v", val)
        }
        fmt.Fprintf(&b, "\n  %s = %s", ref, rendered)
    }
    return b.String()
}
```

The receiver-extraction algorithm:

1. Visit the AST in pre-order.
2. For each `Call` node, the receiver (if any) is its target. Record the receiver if its leftmost identifier is in `rootIdents` AND the call's arguments are not in turn rooted at one of those identifiers (or are, but separately).
3. For each top-level `Select` or `Ident` not enclosed in a `Call`, record it.
4. Format each recorded subexpression via `cel.AstToString` (cel-go provides a printer) or via a small `formatRef(expr)` helper.

For the canonical example `response.body.total == response.body.items.map(i, i.price).sum()`:
- The `==` Call has two args: `response.body.total` (no call) → record as-is, and `response.body.items.map(...).sum()` (Call). For the second arg, descend: it's `sum()` whose receiver is `response.body.items.map(...)`, which is itself a Call. Descend: `map`'s receiver is `response.body.items` (no call inside → record as-is, *and skip the lambda arg `i.price`*).

This produces: `["response.body.total", "response.body.items"]` — close to the task's example but with `map(...).sum()` stripped. The task's failure message example shows `response.body.items.map(i, i.price).sum() = 10.50`, which includes the calls. Trade-off: full-call rendering is more informative but harder to evaluate (sub-expressions inside `Call`s are typically the source of the truthy value the user wants to see).

**Resolution:** Record TWO classes of references:
- **Leaf references:** Select/Ident chains containing no Call (e.g., `response.body.total`).
- **Call expressions whose argument set is fully bound to activation values** (e.g., `response.body.items.map(i, i.price).sum()` — the lambda is self-contained, the map/sum chain reads only from `response.body.items`). Render these as the *full* call source.

In practice, the simplest correct rule: record both the *receiver* and the *whole expression* up to (but not including) any binary operator like `==`/`!=`/`<`/`>`/`&&`/`||`. For `response.body.total == response.body.items.map(i, i.price).sum()`, the two operands of `==` are exactly the references we want. Generalising:

```go
// Walk top-level Call/Op nodes; for binary comparison and boolean operators,
// record both operands as references. For unary not (!x), record x.
// Skip references whose root is not in rootIdents.
```

This is straightforward, gives the task's expected output, and degrades gracefully.

func toCELInputs(items []parser.CELAssertion) []assertion.CELInput {
    if len(items) == 0 { return nil }
    out := make([]assertion.CELInput, len(items))
    for i, it := range items {
        out[i] = assertion.CELInput{Index: i, Source: it.Source}
    }
    return out
}

func buildSensitiveNames(col *parser.Collection, item parser.RequestItem) map[string]struct{} {
    out := make(map[string]struct{})
    if col.Variables.Sensitive != nil {
        for _, n := range col.Variables.Sensitive.Names() { out[n] = struct{}{} }
    }
    if item.Variables.Sensitive != nil {
        for _, n := range item.Variables.Sensitive.Names() { out[n] = struct{}{} }
    }
    return out
}

func snapshotSensitiveValues(sets ...*variable.SensitiveSet) []string {
    seen := map[string]struct{}{}
    for _, s := range sets {
        if s == nil { continue }
        for _, v := range s.Values() { seen[v] = struct{}{} }
    }
    out := make([]string, 0, len(seen))
    for v := range seen { out = append(out, v) }
    sort.Slice(out, func(i, j int) bool {
        if len(out[i]) != len(out[j]) { return len(out[i]) > len(out[j]) }
        return out[i] < out[j]
    })
    return out
}

## Risks and Edge Cases

- **Risk: cel-go AST traversal API churn.** → **Mitigation:** Use the same `celast.PostOrderVisit` pattern already established in `internal/cel/observe.go` and `internal/cel/forbid.go`. Pin behavior with unit tests in `internal/cel/refs_test.go`.

- **Risk: substring redaction false positives (e.g., short sensitive value happens to appear in a numeric body).** → **Mitigation:** The existing `internal/variable/redact.go` already accepts this trade-off (`redactString` is exact substring replacement, sorted longest-first). The new failure-message redaction reuses the same algorithm. This is consistent behavior across the project.

- **Risk: parallel main-phase users with CEL assertions silently lose parallelism.** → **Mitigation:** Diagnostics line printed when fallback fires (mirrors `if:` fallback at runner.go:1286). Documented in MANUAL.md by M19-005.

- **Risk: CEL evaluation against a missing/nil response (network error).** → **Mitigation:** The runner only calls `assertion.Evaluate` on the success path (when `execErr == nil && result != nil`); the early-return at runner.go:2110 short-circuits before any CEL evaluation. No change needed.

- **Edge case: empty CEL assertion source after parsing.** → **Handling:** `CELAssertions.UnmarshalYAML` rejects empty strings in the mapping form (`"cel assertion entry has empty cel: source"`). For the scalar form, `item.Value == ""` is a YAML edge case; reject with the same message.

- **Edge case: `cel:` key present but list is empty.** → **Handling:** `len(item.Assertions.CEL.Items) == 0` — `CheckCEL` returns nil, no impact, no compile of the empty list. Treat as "no CEL assertions".

- **Edge case: WebSocket steps using `cel:` under `expect`.** → **Handling:** Out of scope. The WS step has its own `BodyAssertions` parser path that does not recognise `cel:`; the entry would surface as a malformed JSONPath/operator pair and be rejected by the existing parser.

- **Edge case: CEL expression returns nil (e.g., `vars.missing == nil`).** → **Handling:** Compile expects bool. If the expression's type is `null` after type-check, the type-check fails with `ErrCelType` ("got null, expected bool"). Surfaced as assertion failure per behavior #5.
