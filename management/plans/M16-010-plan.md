# Implementation Plan: M16-010

## Overview
Make `scheduled_runs.result_id` actually visible and idempotent end-to-end:
expose the FK in the public `ScheduledRunDto` so the dashboard can join,
turn the result-post endpoint into a true idempotent operation when the
same `claim_token` retries, and lock down both behaviors with new
`ScheduledRunResultLink`-named tests. The schema/FK/EF wiring landed with
M16-009; this slice closes the dashboard linkage and idempotency gaps.

3. No tests under the `ScheduledRunResultLink` filter exist yet — the

The migration step itself is already complete; we therefore don't
generate a new EF migration. The `dotnet ef database update` /
`dotnet ef migrations remove` halves of the observable refer to the
M16-009 migration that carries the `result_id` column.

### Step 2: Make `SubmitResultAsync` idempotent on retried claim_token
**Rationale:** Behavior 6 and the scope are explicit: a network retry
with the same `claim_token` after a successful post must return 200
with the existing linkage, not 409 `AlreadyCompleted`. This is the only
real logic change in the task. We do it after Step 1 so the new
return-value contract has the DTO field that proves the linkage.

The change is constrained by the existing 409 contract for two real
adversarial cases that must keep failing:
- A different worker re-claims after a reap and tries to post for an
  already-terminal row (token mismatch on a terminal row).
- A worker posts twice with **different** payloads after the row was
  re-claimed (token mismatch again).

So the rule becomes: if the row is terminal AND `request.claim_token`
matches the **stored** `run.ClaimToken` AND `run.ResultId` is set, we
return `None` (200) idempotently. Otherwise we keep the existing
`AlreadyCompleted` 409.

| File | Action | Description |
|------|--------|-------------|

#### Current Code

```csharp
// ScheduleExecutorService.cs (SubmitResultAsync, lines 119-135)
var run = await db.ScheduledRuns
    .Where(r => r.Id == runId
             && db.Schedules.Any(s => s.Id == r.ScheduleId && s.OrgId == orgId))
    .SingleOrDefaultAsync(ct);

if (run is null)
    return ScheduleClaimError.NotFound;

if (run.Status == ScheduledRunStatus.Completed || run.Status == ScheduledRunStatus.Failed)
    return ScheduleClaimError.AlreadyCompleted;

// Reap window: claim_token cleared means the reaper already reset this row.
if (run.Status != ScheduledRunStatus.Running || run.ClaimToken is null)
    return ScheduleClaimError.ClaimReaped;

if (run.ClaimToken != token)
    return ScheduleClaimError.StaleClaim;
```

#### New Code

```csharp
// ScheduleExecutorService.cs (SubmitResultAsync)
var run = await db.ScheduledRuns
    .Where(r => r.Id == runId
             && db.Schedules.Any(s => s.Id == r.ScheduleId && s.OrgId == orgId))
    .SingleOrDefaultAsync(ct);

if (run is null)
    return ScheduleClaimError.NotFound;

// Idempotency: same worker posting the same claim_token after a
// successful first post is a benign network retry — return 200 (None)
// without re-inserting.
if ((run.Status == ScheduledRunStatus.Completed
     || run.Status == ScheduledRunStatus.Failed)
    && run.ClaimToken == token
    && run.ResultId is not null)
{
    logger.LogInformation(
        "Schedule executor result idempotent retry for run {RunId} (same claim_token, result_id={ResultId}).",
        RunId.Format(runId), run.ResultId);
    return ScheduleClaimError.None;
}

if (run.Status == ScheduledRunStatus.Completed || run.Status == ScheduledRunStatus.Failed)
    return ScheduleClaimError.AlreadyCompleted;

// Reap window: claim_token cleared means the reaper already reset this row.
if (run.Status != ScheduledRunStatus.Running || run.ClaimToken is null)
    return ScheduleClaimError.ClaimReaped;

if (run.ClaimToken != token)
    return ScheduleClaimError.StaleClaim;
```

## Risks and Edge Cases

- **Risk:** A new EF migration might be auto-generated by `dotnet ef
  migrations add` if the dev runs the command unprompted (since we are
  not adding any new schema changes, it should be a no-op, but a
  designer-file regeneration is wasted churn). **Mitigation:** The
  plan does not invoke `dotnet ef migrations add`. The observable's
  `dotnet ef database update` and `dotnet ef migrations remove` lines
  refer to applying/rolling back the existing M16-009 migration that
  already carries `result_id`.
- **Risk:** The DTO's ASP.NET Core OpenAPI emits `resultId` (camelCase)
  while the snake-case JSON serializer used by some endpoints emits
  `result_id`. **Mitigation:** Snake-case is the Schedules endpoints
  default (see `SchedulesEndpoints.SnakeCaseOptions`); however the
  endpoint actually serializes via `HttpResults.Ok(...)` which uses
  ASP.NET Core's default JsonSerializerOptions (camelCase by default
  unless overridden). Verified by existing test
  `Swagger_json_lists_schedule_executor_endpoints` asserting
  `"claimToken"` (camelCase) in the OpenAPI doc. Plan asserts
  `"resultId"` in OpenAPI schema (Step 4) and the integration tests
  use `JsonSerializerOptions { PropertyNamingPolicy =
  JsonNamingPolicy.SnakeCaseLower, PropertyNameCaseInsensitive = true }`
  to round-trip; we will configure the same in
  `ScheduledRunResultLinkTests` so it matches the wire format already
  used by the dashboard's HTTP client.
- **Edge case (legacy NULL):** Behavior 4 — pre-migration rows with
  `result_id IS NULL`. **Handling:** `Guid?` on the entity, `string?`
  on the DTO, `null` JSON value emitted; covered by
  `ListRuns_returns_null_result_id_for_legacy_completed_row`.
- **Edge case (ON DELETE SET NULL):** Behavior 5 — deleting a row in
  `results` must not orphan the schedule row. **Handling:** Already
  configured by `OnDelete: ReferentialAction.SetNull` in the M16-009
  migration; no new code. We add a unit test in
  `ScheduledRunResultLinkTests` against the SQLite `TestDb` fixture
  (which does enforce FKs) to lock the contract:

  ```csharp
  [Fact]
  public async Task DeletingResult_sets_scheduled_runs_result_id_to_null()
  {
      // arrange: create schedule + run + result, link them, save.
      // act: db.Results.Remove(result); SaveChanges();
      // assert: db.ScheduledRuns.Find(run.Id).ResultId is null
      //         AND the run row still exists.
  }
  ```
- **Edge case (idempotency vs. token rotation):** If between post #1
  and post #2 a reaper resets the row back to Queued (clearing
  `ClaimToken`) and a different worker re-claims, post #2 with the old
  token must NOT match. **Handling:** New idempotency branch requires
  `run.ClaimToken == token` AND `ResultId is not null`. After reap
  + re-claim, the stored `ClaimToken` is the new worker's token, so
  the old token will mismatch → falls through to existing
  `AlreadyCompleted` (or earlier guards). No changes needed; covered
  by `terminal_row_with_DIFFERENT_token_still_returns_AlreadyCompleted`.
- **Risk:** Race between two concurrent retries with the same
  claim_token (worker double-fires before first response returns).
  Both reads see `Status = Running`, both post a Result, both call
  `SaveChangesAsync`. **Mitigation:** Out of scope — same gap M16-009
  documented in its `ScheduleExecutorService` class comment ("retry-on-
  zero-affected-rows hardening is deferred"). The idempotency this
  task adds covers the specified case (sequential retry after first
  succeeds), not concurrent in-flight duplicates.
