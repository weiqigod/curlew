# Implementation Plan: M14-020

## Overview

Adds a top-level `/integrations` web route that lets admin/owner users connect
GitHub via the dashboard-initiated install flow (M14-017's
`GET /api/v1/integrations/github/install-url`), and surfaces install state
(connected slug + repo count, suspended badge, pending-claim button) for the
user's organisation. The slice is bounded per Open Decision #10 to the
GitHub install entry-point and install-state view only — no billing, no SSO,
no other dashboards.

## Architectural Decisions

1. **Top-level `/integrations` route, not nested under `(app)/org/[slug]`.**
   The task scope and DoD are explicit: "No new files outside
   `web/src/routes/integrations/` and `web/tests/e2e/`." This means we cannot
   add a new entry inside the `(app)` layout group, cannot reuse the org
   sub-nav, and cannot add a new `$lib/api/github-installations.ts` API
   client. We create `web/src/routes/integrations/+page.server.ts` and
   `+page.svelte` directly.

2. **Org context resolution.** The page is `/integrations` (no slug). We list
   the authenticated user's organisations via the existing `organizationsApi`
   client and use the first/single org for context. This matches the
   backend's `GET /api/v1/integrations/github/install-url` auto-resolve
   behaviour (single-membership users; multi-org disambiguation is out of
   scope for this slice and produces a clear error).

3. **State-view fetch is inline.** The backend `GET /api/v1/integrations/github`
   state endpoint described at `docs/SPECIFICATION.md:8677` is not yet
   implemented. We call it from `+page.server.ts` using the existing
   `$lib/api/client.ts` `api` helper (imported, not modified). On the live
   stack the call may currently 404 — the loader handles this gracefully and
   shows the "no installation" state. The Playwright spec mocks the endpoint
   to exercise each behaviour deterministically. This is the same pattern
   `org-billing.spec.ts` uses for `/api/v1/subscriptions`.

4. **Connect-button is an `<a>`, not a server action.** Behaviour 1 says it
   "links through `/api/v1/integrations/github/install-url`". The simplest
   shape is an anchor that the loader populates with the resolved
   `install_url` returned by the backend in the SSR `load`. This mirrors the
   billing portal POST pattern, but read-only (GET) so there is no CSRF
   concern.

5. **Toast is inline (no shared component shape change).** Since `/integrations`
   sits outside the `(app)` layout that hosts the existing toasts, we render
   a minimal in-page toast block in `+page.svelte`, dismissible by removing
   the `?installed=true` query param. We do not add to `Toast.svelte`.

6. **Repo count comes from `repo_set.length`.** The mocked state response
   includes `repo_set: [...]` and the page renders
   `"GitHub connected — <account_login>, <repo_set.length> repos covered"`.

7. **`npm run e2e` vs `npm run test:e2e`.** The task observable uses
   `npm run e2e` but `package.json` defines `test:e2e`. We will not modify
   `package.json` (out of scope). The plan documents
   `npm run test:e2e -- tests/e2e/github-connect.spec.ts` as the run command;
   the DoD's `>=4 passing` Playwright assertions is the actual gate.

```ts
// Refs docs/SPECIFICATION.md:8413–8417 (Installation Lifecycle:
// dashboard-initiated vs webhook-first install paths).
import { redirect } from '@sveltejs/kit';
import type { PageServerLoad } from './$types';
import { organizationsApi } from '$lib/api/organizations';
import { api } from '$lib/api/client';
import { ApiError } from '$lib/types/api-error';

interface InstallUrlResponse {
    install_url: string;
    state_expires_at: string;
}

interface RepoRef {
    owner: string;
    name: string;
    id?: number;
}

interface InstallationDto {
    installation_id: number;
    account_login: string;
    account_type: string;
    repo_set: RepoRef[];
    claimed_at: string | null;
    suspended_at: string | null;
}

interface InstallStateResponse {
    installation: InstallationDto | null;
}

/** SSR loader for /integrations. Resolves the user's org, gathers install
 * state and the dashboard-initiated install URL. RBAC: only admin/owner can
 * see the Connect button — members get read-only state. */
export const load: PageServerLoad = async ({ locals, url, fetch }) => {
    if (!locals.accessToken) {
        throw redirect(303, `/login?redirect=${encodeURIComponent(url.pathname + url.search)}`);
    }
    const token = locals.accessToken;

    const orgs = await organizationsApi.list({ token, fetch }).catch(() => []);
    const org = orgs[0] ?? null;
    const isAdmin = !!org && (org.role === 'owner' || org.role === 'admin');

    let installUrl: string | null = null;
    let installation: InstallationDto | null = null;
    let stateError: string | null = null;

    if (isAdmin && org) {
        try {
            const r = await api.get<InstallUrlResponse>(
                '/api/v1/integrations/github/install-url',
                { token, fetch }
            );
            installUrl = r.install_url;
        } catch (e) {
            // Non-fatal — Connect button hidden if we can't mint a URL
            installUrl = null;
            if (e instanceof ApiError && e.status >= 500) stateError = e.description;
        }
    }

    if (org) {
        try {
            const r = await api.get<InstallStateResponse>(
                '/api/v1/integrations/github',
                { token, fetch }
            );
            installation = r.installation;
        } catch (e) {
            if (e instanceof ApiError && e.status === 404) {
                installation = null; // not installed yet — expected
            } else if (e instanceof ApiError) {
                stateError = e.description;
            } else {
                stateError = e instanceof Error ? e.message : 'failed to load install state';
            }
        }
    }

    return {
        org,
        isAdmin,
        installUrl,
        installation,
        stateError,
        showInstalledToast: url.searchParams.get('installed') === 'true'
    };
};
```

## Risks and Edge Cases

- **Risk: Backend `GET /api/v1/integrations/github` does not yet exist.**
  → **Mitigation:** Loader treats 404 as "no install" (the natural empty
  state). Live stack will show the Connect button with no status line until
  M14-021/-022 land the backend state endpoint. Spec mocks the endpoint, so
  CI is deterministic regardless.

- **Risk: Multi-org users.** The loader picks `orgs[0]`. → **Handling:**
  Acceptable for the bounded slice — backend `install-url` already errors
  with `ambiguous_org_id` when memberships > 1; we surface that as
  `stateError`. A multi-org picker is out of scope (no billing/SSO/account
  settings).

- **Risk: User is admin of seat but not admin of the GitHub account named
  in a webhook-first install** → **Handling:** The Claim button is rendered
  for any admin/owner of the Curlew org with a pending install; the actual
  ownership check is enforced server-side in M14-018 (which currently
  returns 501 from `POST /api/v1/integrations/github/claim`). For this
  slice, we render the button but do not wire a click handler beyond
  default form behaviour — leaving the wiring to M14-018's web counterpart.
  This matches the bounded-scope DoD.

- **Edge case: `?installed=true` with `installation: null` (race between
  callback redirect and webhook arrival)** → **Handling:** Toast renders
  regardless; the status line shows the not-connected state until the next
  page load resolves the install row.

- **Edge case: `state_expires_at` already past.** → **Handling:** The
  loader runs on every navigation, so the button always carries a
  fresh-minted state token. We do not render the expiry to the user.

- **Risk: Authentication redirect loop.** The loader does
  `redirect(303, '/login?...')` when `accessToken` is missing.
  → **Handling:** The login page is out of scope; tests seed the cookie
  via `seedAuthCookie` so the loader sees a token.
