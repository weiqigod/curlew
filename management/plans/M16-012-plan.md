# Implementation Plan: M16-012

## Overview

Adds a `timezone TEXT NOT NULL DEFAULT 'UTC'` column to `schedules`, plumbs it through `Schedule` entity / DTO / `CreateScheduleRequest` / `SchedulesService` (including DST-aware `Cronos.GetNextOccurrence(now, TimeZoneInfo)`) and ships a minimum-viable SvelteKit dashboard at `/org/[slug]/schedules` with create/list/run-now/run-history + a client-side cron live-preview.

## Architectural Decisions (resolved upfront)

The task scope/observable contain a few ambiguities. Decisions made during planning:

1. **Endpoint path.** The task observable says `POST /api/v1/schedules`. The existing wired path is `POST /api/v1/organizations/{orgId}/schedules`. The spec line 6028 uses `/api/v1/schedules` as informal shorthand. **Decision:** keep the existing org-scoped path. Update the web `+page.server.ts` and any test assertions accordingly. (We do **not** add a duplicate top-level route — that would duplicate the org-resolution work `ScheduleExecutorEndpoints` already does for worker endpoints.)

2. **PATCH/DELETE.** Task scope mentions `PATCH/DELETE /api/v1/schedules` but no behavior or DoD item requires them, and they do not exist today. **Decision:** out of scope for M16-012. The web page calls only `GET`, `POST`, `POST run-now`, `GET runs` (existing endpoints). PATCH/DELETE can be a follow-up task.

3. **Tier gate on user-facing schedule endpoints.** Today, only `ScheduleExecutorEndpoints` (worker-pull) is tier-gated; `SchedulesEndpoints` is not. The task says "Tier-gated by `ScheduleExecutorTierGate` (the page must handle 402 from the API gracefully)." **Decision:** add `ScheduleExecutorTierGate.EnsureTeamOrAboveAsync` to the user-facing `SchedulesEndpoints` (Create, List, Get, RunNow, ListRuns) so a free-tier org gets the same 402 problem-detail the spec promises. This also matches the M16 v4.3 spec entry at line 10254. The web page handles 402 by surfacing the tier-gate toast (existing `requireTeamTier` guard already does this).

4. **Timezone validation source.** Use `TimeZoneInfo.TryFindSystemTimeZone(name, out _)` (or `TimeZoneInfo.FindSystemTimeZoneById` inside a try/catch). On .NET 8 with the ICU TZ data, both IANA (`Europe/Stockholm`) and Windows (`W. Europe Standard Time`) identifiers resolve. **Decision:** accept any string that resolves via `TimeZoneInfo.FindSystemTimeZoneById` — this is what `Cronos` will use anyway, so validation and execution stay consistent. Empty/null defaults to `"UTC"`.

5. **Cron live preview library.** Spec suggests `cron-parser` (Node). **Decision:** use `cron-parser` (already pure-JS, MIT, runs in browser via Vite). Add as a `web/` dependency.

6. **`scheduled_runs.duration` computation.** Computed in the web `+page.svelte` from `started_at`/`completed_at` (already present on `ScheduledRunDto`), no backend change.

7. **Run-history page navigation.** Per the task: clicking a schedule row goes to `/org/[slug]/schedules/[scheduleId]/`. The backend addresses runs by schedule **name**, not id. **Decision:** use the schedule **name** as the URL segment (`/org/[slug]/schedules/[scheduleName]`) to avoid a name→id resolution round-trip and match the backend route shape. Names are URL-encoded.

8. **Result page link.** Spec says "link to the result page when `result_id` is populated." A results-by-id detail page exists conceptually but isn't yet built. **Decision:** if `result_id` is present render a link to `/org/[slug]/results?run_id=<resultId>` (a query-param-filtered view the existing results page already supports via `range`/list). If the existing page doesn't actually filter by `run_id`, the link is still informational and falls back to the results list. This is acceptable per the "minimum viable" framing in Open Decision 11 and avoids scope-creeping into a results-detail route.

// ScheduleProblem.cs (new)
public static class ScheduleProblem
{
    private const string BaseType = "https://api.apitool.dev/errors";
    private static readonly string[] ValidExamples =
        ["UTC", "Europe/Stockholm", "America/New_York", "Asia/Tokyo", "Australia/Sydney"];

    public static IResult InvalidTimezone(HttpContext http, string? detail)
    {
        var problem = new ProblemDetails {
            Type = $"{BaseType}/invalid-timezone",
            Title = "Invalid IANA timezone",
            Detail = detail ?? "The provided timezone is not a recognized IANA identifier.",
            Status = StatusCodes.Status422UnprocessableEntity,
            Instance = http.Request.Path,
        };
        problem.Extensions["valid_examples"] = ValidExamples;
        return Results.Json(problem,
            contentType: "application/problem+json",
            statusCode: StatusCodes.Status422UnprocessableEntity);
    }
}

#### Loader sketch

```ts
// +page.server.ts
export const load: PageServerLoad = async ({ locals, params, url, fetch }) => {
  const token = requireAuth(locals.accessToken, url.pathname + url.search);
  const org = await organizationsApi.findBySlug(params.slug, { token, fetch });
  const teamOrg = requireTeamTier(org, params.slug);  // throws 303 if not team
  try {
    const schedules = await schedulesApi.list(teamOrg.id, { token, fetch });
    // For each schedule, fetch the most-recent run (limit=1) in parallel.
    const lastRuns = await Promise.all(schedules.map(s =>
      schedulesApi.listRuns(teamOrg.id, s.name, { token, fetch, limit: 1 })
        .then(rs => rs[0] ?? null)
        .catch(() => null)
    ));
    return { org: teamOrg, schedules, lastRuns, error: null };
  } catch (e) {
    return { org: teamOrg, schedules: [], lastRuns: [], error: errorMessage(e) };
  }
};
```

#### Duration helper

```ts
// duration.ts
export function computeDuration(startedAt: string | null, completedAt: string | null): string {
  if (!startedAt || !completedAt) return '—';
  const ms = new Date(completedAt).getTime() - new Date(startedAt).getTime();
  if (ms < 1000) return `${ms}ms`;
  if (ms < 60_000) return `${(ms/1000).toFixed(1)}s`;
  return `${Math.floor(ms/60_000)}m${Math.floor((ms%60_000)/1000)}s`;
}
```

## Risks and Edge Cases

- **Risk:** `TimeZoneInfo.FindSystemTimeZoneById` may behave differently across OSes (Linux ICU vs Windows registry).
  - **Mitigation:** .NET 8 ships with embedded ICU on Linux containers; the test stack runs in Linux containers. Add a sanity test that asserts `Europe/Stockholm` resolves on the test runner.

- **Risk:** Cronos's `GetNextOccurrence(now, tz)` requires `now` to be `Utc` kind.
  - **Mitigation:** `clock.GetUtcNow().UtcDateTime` already returns `DateTime` of kind `Unspecified` — must explicitly `DateTime.SpecifyKind(now, DateTimeKind.Utc)`. Verified via Cronos source.

- **Risk:** DST "spring forward" gap — a cron set to fire at 02:30 in a tz that has no 02:30 that day.
  - **Mitigation:** Cronos handles this by skipping; behavior is documented. Add a regression test for the spring-forward gap.

- **Risk:** DST "fall back" overlap — 02:30 occurs twice.
  - **Mitigation:** Cronos fires once (at the first occurrence) in standard mode. Add a regression test.

- **Risk:** SQLite default-value migration on existing rows with NULL.
  - **Mitigation:** `defaultValue: "UTC"` in the migration is applied at column add time, so existing rows get `'UTC'`. Verified by an integration test that inserts a row before migration applies (we don't have such a row in tests — fresh DB per test — so this is N/A in test, but matters for production). Document in the migration's XML doc comment.

- **Risk:** Adding tier-gate to existing user-facing schedules endpoints may break existing integration tests that don't seed a subscription.
  - **Mitigation:** Update `SchedulesEndpointsTests.InitializeAsync` to seed a `Subscription { OrgId, Tier = Team, Status = Active }` row right after org creation. Mirrors what `ScheduleExecutorEndpointsTests` already does.

- **Risk:** `cron-parser` Node module pulling in Buffer / process polyfills under Vite.
  - **Mitigation:** `cron-parser` v4 is ESM-friendly. If the SSR build complains, mark it `noExternal` in `vite.config.ts`.

- **Edge case:** Schedule name contains URL-unsafe characters.
  - **Handling:** URL-encode the name in all client calls (`encodeURIComponent`) and in route params.

- **Edge case:** A schedule with a deleted/renamed timezone (extremely rare; IANA does occasionally retire identifiers).
  - **Handling:** `EnqueueDueAsync` falls back to UTC if `FindSystemTimeZoneById` throws (best-effort continued execution). Logged at warning level.

- **Edge case:** Empty schedules list for a team-tier org.
  - **Handling:** `EmptyState` component with "Create your first schedule" CTA.
