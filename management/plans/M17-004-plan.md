# Implementation Plan: M17-004

## Overview
Register three new dotted-namespace dynamic functions (`$webhookSign.stripe`, `$webhookSign.github`, `$webhookSign.slack`) that produce provider-specific HMAC-SHA256 webhook signature header values, with sensitive-secret auto-propagation reusing the M12-005 `sensitiveArgIdx` mechanism. No changes to `internal/variable/variable.go` or to the M17 signer registry.

## Architectural Decisions

1. **Three independent registrations, no shared dispatcher.** Each provider has a different signed-payload shape and a different output prefix, so a generic helper would force each registration to pass two non-trivial format strings. Three small closures using a shared internal helper (`hmacHexLower`) is clearer.
2. **Helper file `dynamic_helpers.go`.** The task scope explicitly calls for a new file. It will contain only the three pure string-builder functions plus the shared HMAC helper — keeping `dynamic.go` focused on registration and avoiding a 1,800+ line monolith.
3. **`twoOrThreeArgs` arity helper.** Stripe and Slack share an identical 2-or-3 arity contract (with the third arg being a timestamp; absent → use `r.now()`). Mint a single helper rather than open-coding the same `switch len(args)` twice. GitHub uses the existing `twoArgs`.
4. **`r.now().Unix()` for two-arg form.** Reuses the existing `Registry.now` clock seam. Two-arg tests freeze `r.now` to a fixed instant and assert byte-exact strings. (No new clock plumbing.)
5. **Sensitive-arg index = 1 for all three.** The secret is always the second positional arg (index 1) — same convention as `$hmacSha256`. No changes to the Pass-1 dispatch in `variable.go`.
6. **GitHub v1 (SHA-1) deliberately not shipped.** Per scope: only x-hub-signature-256 (SHA-256). Documented in MANUAL.md.
7. **Cache key already correct.** `cacheKey` joins funcName + NUL + args; the dotted funcName flows through unchanged. Per-request memoization works without changes.
8. **Smoke fixture without network.** Use `--dry-run` so the smoke test never makes a real HTTP call. Render the Stripe header into a `headers:` field, dump via `--format json`, grep for the `t=...,v1=...` shape, and grep that the secret value never appears.

// internal/variable/dynamic_helpers.go
package variable

import (
	"crypto/hmac"
	"crypto/sha256"
	"fmt"
)

// hmacHexLower computes HMAC-SHA256 over msg under key and returns the
// canonical lowercase 64-char hex (matches sha256sum(1) and every webhook
// signature spec we target).
func hmacHexLower(msg, key []byte) string {
	h := hmac.New(sha256.New, key)
	h.Write(msg)
	return fmt.Sprintf("%x", h.Sum(nil))
}

// stripeWebhookSig builds the Stripe-Signature header value
//
//	t=<timestamp>,v1=<hex>
//
// where <hex> is HMAC-SHA256("<timestamp>.<body>", secret) per
// https://stripe.com/docs/webhooks/signatures (signed_payload construction).
// timestamp is the Unix-seconds integer string.
func stripeWebhookSig(body, secret, timestamp string) string {
	signedPayload := timestamp + "." + body
	mac := hmacHexLower([]byte(signedPayload), []byte(secret))
	return "t=" + timestamp + ",v1=" + mac
}

// githubWebhookSig builds the X-Hub-Signature-256 header value
//
//	sha256=<hex>
//
// where <hex> is HMAC-SHA256(body, secret) per
// https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries.
// The legacy x-hub-signature (SHA-1) form is intentionally not produced.
func githubWebhookSig(body, secret string) string {
	mac := hmacHexLower([]byte(body), []byte(secret))
	return "sha256=" + mac
}

// slackWebhookSig builds the X-Slack-Signature header value
//
//	v0=<hex>
//
// where <hex> is HMAC-SHA256("v0:<timestamp>:<body>", secret) per
// https://api.slack.com/authentication/verifying-requests-from-slack
// (the version + colon + timestamp + colon + body construction).
func slackWebhookSig(body, secret, timestamp string) string {
	basestring := "v0:" + timestamp + ":" + body
	mac := hmacHexLower([]byte(basestring), []byte(secret))
	return "v0=" + mac
}
```

// crypto/hmac that exercises the same primitives the production helper
// uses, but written inline at the test call site so a bug in the helper
// cannot mask itself.
func independentHMACHex(msg, key string) string {
	h := hmac.New(sha256.New, []byte(key))
	h.Write([]byte(msg))
	return fmt.Sprintf("%x", h.Sum(nil))

// twoOrThreeArgs wraps a 2-or-3-argument pure function so it conforms
// to DynFunc and returns a structured arity error when called with
// anything other than 2 or 3 args. The wrapped function receives all
// three positional values: when only two args are supplied the third
// is the empty string and the wrapped function is responsible for
// supplying the default. Used by $webhookSign.stripe and
// $webhookSign.slack, where the third arg is an optional timestamp
// that defaults to Registry.now().Unix() when omitted.
func twoOrThreeArgs(funcName string, fn func(a, b, c string) (string, error)) DynFunc {
	return func(_ *rand.Rand, args []string) (string, error) {
		switch len(args) {
		case 2:
			return fn(args[0], args[1], "")
		case 3:
			return fn(args[0], args[1], args[2])
		default:
			return "", &apierrors.Structured{
				Category: apierrors.CategoryInput,
				Code:     "DYNFN_ARITY",
				Message:  fmt.Sprintf("expected 2 or 3 arguments, got %d", len(args)),
				Hint:     fmt.Sprintf("Call $%s with 2 args (body, secret) or 3 args (body, secret, timestamp).", funcName),
			}
		}
	}
}
```

	// $webhookSign.stripe / .github / .slack — M17-004.
	// Each function emits the provider-specific webhook-signature header
	// VALUE (not the header name) shaped per the published spec. All
	// three are HMAC-SHA256 under the secret (arg index 1); the secret
	// is registered in sensitiveArgIdx so a sensitive-named source
	// variable propagates into the run's SensitiveSet via the Pass-1
	// plumbing in internal/variable/variable.go.
	//
	// stripe:  t=<ts>,v1=<hex>           hex = HMAC-SHA256("<ts>.<body>", secret)
	// github:  sha256=<hex>              hex = HMAC-SHA256(body, secret)
	// slack:   v0=<hex>                  hex = HMAC-SHA256("v0:<ts>:<body>", secret)
	//
	// stripe and slack accept an optional 3rd arg (timestamp); when
	// omitted the registry's clock seam r.now().Unix() supplies it.
	r.funcs["webhookSign.stripe"] = twoOrThreeArgs("webhookSign.stripe", func(body, secret, ts string) (string, error) {
		if ts == "" {
			ts = strconv.FormatInt(r.now().Unix(), 10)
		}
		return stripeWebhookSig(body, secret, ts), nil
	})
	r.sensitiveArgIdx["webhookSign.stripe"] = 1

	r.funcs["webhookSign.github"] = twoArgs("webhookSign.github", func(body, secret string) (string, error) {
		return githubWebhookSig(body, secret), nil
	})
	r.sensitiveArgIdx["webhookSign.github"] = 1

	r.funcs["webhookSign.slack"] = twoOrThreeArgs("webhookSign.slack", func(body, secret, ts string) (string, error) {
		if ts == "" {
			ts = strconv.FormatInt(r.now().Unix(), 10)
		}
		return slackWebhookSig(body, secret, ts), nil
	})
	r.sensitiveArgIdx["webhookSign.slack"] = 1

```markdown
**Webhook-signature helpers (`$webhookSign.stripe`, `$webhookSign.github`, `$webhookSign.slack`) — M17-004.**

These three dynamic functions emit the **value** of the provider-specific
webhook-signature header (not the header name). Each is a thin shaping
layer over HMAC-SHA-256 under the second positional argument (the
secret). The signed-payload construction follows each provider's
published spec.

| Function | Arguments | Returns | Example |
|---|---|---|---|
| `{{$webhookSign.stripe('body','secret','timestamp')}}` | 3 strings (or 2 — clock seam supplies timestamp) | `t=<timestamp>,v1=<hex>` — `<hex>` = HMAC-SHA-256(`<timestamp>.<body>`, `secret`) | `{{$webhookSign.stripe('{}','whsec_test','1492774577')}}` → `t=1492774577,v1=<64-char hex>` |
| `{{$webhookSign.github('body','secret')}}` | 2 strings | `sha256=<hex>` — `<hex>` = HMAC-SHA-256(`body`, `secret`) | `{{$webhookSign.github('{"action":"opened"}','whsec_xyz')}}` → `sha256=<64-char hex>` |
| `{{$webhookSign.slack('body','secret','timestamp')}}` | 3 strings (or 2 — clock seam supplies timestamp) | `v0=<hex>` — `<hex>` = HMAC-SHA-256(`v0:<timestamp>:<body>`, `secret`) | `{{$webhookSign.slack('payload','xoxb-...','1531420618')}}` → `v0=<64-char hex>` |

The two-arg forms of `$webhookSign.stripe` and `$webhookSign.slack`
default the timestamp to the current Unix-seconds time (the same clock
seam used by `$timestamp`, `$dateAdd`, `$dateSubtract`); use the three-arg
form when you need to pin the timestamp deterministically (e.g. against
a recorded webhook fixture).

GitHub's legacy SHA-1 form (`x-hub-signature`) is intentionally not
shipped — only the v2 SHA-256 form (`x-hub-signature-256`). New
GitHub integrations must use the SHA-256 header.

**Sensitive-secret auto-redaction.** Like `$hmacSha256`, when the *secret*
argument (the second positional arg) of any of the three functions
resolves from a sensitive-named variable (`secret`, `token`,
`password`, `api_key`, `apikey`, `credential`, `authorization`) or
from a `{{secrets.X}}` token, the resolved secret string is
automatically registered as a redaction trigger for the run. It will
appear as `[REDACTED]` wherever it surfaces in serialised output.

**The literal-secret footgun.** A literal secret passed inline — e.g.
`{{$webhookSign.github('payload', 'whsec_inline_value')}}` — *cannot*
be auto-redacted because there is no source variable to inspect. Always
source webhook secrets from a sensitive-named variable, an env file,
`{{secrets.X}}`, or a `from_command:` block. Mirrors the `$hmacSha256`
documentation above.
```

## Risks and Edge Cases

- **Risk:** Test vectors not literally from provider docs (which often gate behind dashboards). → **Mitigation:** Use `independentHMACHex` reference helper inline in tests so the assertion is a closed mathematical identity (production helper vs. crypto/hmac one-liner) — any HMAC-SHA-256 implementation that disagrees would also fail Stripe's published spec. Provider reference vectors are loosely modelled on docs but verified by the inline reference, not by hard-coded golden hex.
- **Risk:** Two-arg test flakiness from real-time clock. → **Mitigation:** Pin `reg.now` via `frozenClock` (already used by M12-006 date tests).
- **Risk:** Smoke test depends on `--dry-run` not making a network call. → **Mitigation:** Already standard curlew behaviour; existing smoke sections (e.g. AWS SigV4) use real httpbin but our case uses `https://example.invalid` plus `--dry-run` so no DNS resolution is triggered.
- **Risk:** Smoke test secret false-negative — the literal value happens to appear elsewhere. → **Mitigation:** Use a uniquely-suffixed value `whsec_supersecret_donot_leak` that cannot collide with any other smoke fixture.
- **Edge case:** Empty body, empty secret. → **Handling:** Helpers pass through `[]byte("")` to `hmac.New` / `Write` — `crypto/hmac` accepts both; the resulting hex is well-defined (RFC 2104). Covered implicitly by helper unit tests' use of an empty-body scenario for the Stripe vector.
- **Edge case:** Binary body (the dynamic-arg parser returns a Go string, which is byte-clean). → **Handling:** `[]byte(s)` is byte-exact; no UTF-8 normalisation. No special-casing required.
- **Edge case:** `{{secrets.X}}` reference for the secret. → **Handling:** Pass-1 plumbing in `variable.go:321-343` already detects `secretsPattern` matches and flags the arg as sensitive; the existing `$hmacSha256` `_SecretsNamespace` test exercises the same path. We do not duplicate that test for webhookSign — the registration mechanism is identical.
- **Edge case:** Calling `webhookSign` (parent namespace, no leaf) → falls through to the standard unknown-function error from `Evaluate`. Not part of the test matrix; covered transitively by the dotted-namespace-required test.
