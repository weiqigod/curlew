# Implementation Plan: M12-007

## Overview

Adds two layout-aware date dynamic functions — `$formatDate(input, layout)` and `$parseDate(s, layout)` — to `internal/variable/dynamic.go`. Both use Go's reference-time layout convention. `$formatDate` accepts either a Unix-seconds digit string or an RFC3339 string and emits the requested layout; `$parseDate` is the inverse — it parses an arbitrary layout-formatted string and emits the canonical ISO-8601 UTC form (`2006-01-02T15:04:05Z`) used by `$isoTimestamp`, `$dateAdd`, and `$dateSubtract`.

## Architectural Decisions

1. **Two-shape input parser inside `$formatDate`.** The function accepts either a Unix-seconds digit string or an RFC3339 string. The fork is decided by a cheap digits-only scan over the bytes of `input`; on miss, we fall through to `time.Parse(time.RFC3339, input)`. Two specific shapes are deliberate — the spec calls them out, and a wider try-everything heuristic (try ANSIC, RFC822, …) would couple `$formatDate` to an opaque list of layouts and produce confusing error messages when the input is malformed.

2. **Empty-input is its own structured error.** Behavior 8 says `$formatDate('', '2006-01-02')` returns a structured error naming the empty input. Empty string falls through both digits-scan and RFC3339, so we add an explicit early-return with code `DYNFN_FORMATDATE_EMPTY_INPUT`. Same treatment for `$parseDate('', layout)` with code `DYNFN_PARSEDATE_EMPTY_INPUT` — `time.Parse` would surface a confusing internal error message otherwise.

3. **Unrecognised-input error names both accepted shapes and points at the manual.** Behavior 3 says the error must name "the unrecognised input shape" and point the user at MANUAL.md §3.7. Code is `DYNFN_FORMATDATE_BAD_INPUT`; message quotes a 32-char snippet of the offending input (matching the `$base64Decode` precedent at dynamic.go:241). Hint reads: `"$formatDate accepts either a Unix-seconds integer string (e.g. '1713701401') or an RFC3339 string (e.g. '2024-04-21T15:10:01Z'). See MANUAL.md §3.7."`

4. **`$parseDate` parse failure surfaces the layout-as-template footgun in its hint.** When `time.Parse(layout, s)` fails, the error often arises from a malformed layout (e.g. user wrote `'YYYY-MM-DD'` instead of `'2006-01-02'`). The structured error's hint links to the Go reference-time convention: `"layout must be a Go reference-time layout (e.g. '2006-01-02 15:04:05', not 'YYYY-MM-DD'). See MANUAL.md §3.7 'Go reference-time layouts'."`. Code: `DYNFN_PARSEDATE_BAD_INPUT`. The underlying `*time.ParseError` is wrapped via `Inner` for `errors.Is/As` traversal.

5. **Layout-as-template behaviour is documented, not corrected.** Behavior 5 explicitly accepts Go's stdlib quirk: `time.Format("bogus-layout")` returns `"bogus-layout"` because no reference-time tokens appear. We do *not* validate the layout — adding a layout sniffer would diverge from `time.Time.Format` semantics and surprise users who learn the convention from the stdlib. The MANUAL.md callout educates the reader to validate layouts against `time.Parse(layout, "2006-01-02T15:04:05Z")` first when in doubt.

6. **`$parseDate` always converts to UTC before formatting.** Behavior 6 requires `$parseDate('2024-04-21T17:10:01+02:00', time.RFC3339)` → `2024-04-21T15:10:01Z`. `time.Parse` preserves the source location; we explicitly call `.UTC()` before `.Format("2006-01-02T15:04:05Z")`. This matches the existing convention from `$isoTimestamp` (dynamic.go:171) and `applyDateOffset` (dynamic.go:370).

7. **No clock seam required.** Both functions take their timestamp explicitly. The `r.now` seam from M12-006 is not consulted — there is no system-clock dependency in either function. The nested-call test (`$formatDate('{{$timestamp}}', '2006-01-02')`) exercises a real clock via `$timestamp`; we assert only the layout-of-output and the format invariant, not a frozen value (since `$timestamp` is intentionally never seeded — see dynamic.go:166).

8. **Reuse `twoArgs` helper.** Both functions register through the existing `twoArgs` wrapper (introduced in M12-005 for `$hmacSha256`, used by `$dateAdd`/`$dateSubtract`). This gives free arity-2 enforcement, the canonical `DYNFN_ARITY` code, and the single-prefix `err.Error()` formatting.

9. **No sensitive-arg propagation.** Neither function carries credential material. `r.sensitiveArgIdx` is *not* updated for `formatDate` or `parseDate`. (Compare to `$hmacSha256` where the key argument is auto-redaction-marked.)

10. **`Available()` count moves 24 → 26 in the same commit as the registration.** Two new functions are added together so the test suite remains green at the end of each step.

11. **Digits-only scan over `strconv.ParseInt`.** A `len(input) > 0 && all(byte(c) is '0'-'9')` byte scan is allocation-free and zero-error-path. We then call `strconv.ParseInt(input, 10, 64)` to convert. If `ParseInt` fails for an in-bounds digit string (only possible on overflow > `int64` max — 19+ digits), we fall through to `time.Parse(time.RFC3339)`, which will also fail, and we report `DYNFN_FORMATDATE_BAD_INPUT`. This matches the spec: behavior 1 says "string of digits", and 19-digit overflow is not a Unix seconds value.

12. **Negative integers go to the RFC3339 path.** A leading `-` byte is not a digit; the digits scan rejects it, the RFC3339 path also rejects it, and the user sees `DYNFN_FORMATDATE_BAD_INPUT`. We do *not* support negative Unix seconds (pre-1970 timestamps) — the spec lists exactly two input shapes. A future task can add explicit pre-1970 support if real users hit this.

```go
// parseDateToUTC parses s against layout (a Go reference-time layout),
// converts the result to UTC, and formats it as the canonical
// ISO-8601 UTC string (matching $isoTimestamp, $dateAdd, $dateSubtract).
//
// Empty s short-circuits with DYNFN_PARSEDATE_EMPTY_INPUT before
// calling time.Parse — the stdlib's empty-input error message is
// internal and does not name the user-facing function.
func parseDateToUTC(layout, s string) (string, error) {
    if s == "" {
        return "", &apierrors.Structured{
            Category: apierrors.CategoryInput,
            Code:     "DYNFN_PARSEDATE_EMPTY_INPUT",
            Message:  "input string is empty",
            Hint:     "Pass the date string to parse as the first argument, e.g. $parseDate('2024-04-21T15:10:01Z', '2006-01-02T15:04:05Z').",
        }
    }
    t, err := time.Parse(layout, s)
    if err != nil {
        snippet := s
        if len(snippet) > 32 {
            snippet = snippet[:32] + "..."
        }
        return "", &apierrors.Structured{
            Category: apierrors.CategoryInput,
            Code:     "DYNFN_PARSEDATE_BAD_INPUT",
            Message:  fmt.Sprintf("cannot parse %q with layout %q: %v", snippet, layout, err),
            Hint:     "layout must be a Go reference-time layout (e.g. '2006-01-02 15:04:05', not 'YYYY-MM-DD'). See MANUAL.md §3.7 'Go reference-time layouts'.",
            Inner:    err,
        }
    }
    return t.UTC().Format("2006-01-02T15:04:05Z"), nil
}
```

```go
// formatDate parses input as either a Unix-seconds digit string or an
// RFC3339 string, then formats the resulting time with layout.
//
// The two input shapes are deliberate — see MANUAL.md §3.7. layout is
// always a Go reference-time layout; if it contains no reference-time
// tokens, time.Format returns layout verbatim (this is intentional,
// documented stdlib behaviour — the "layout-as-template footgun").
func formatDate(input, layout string) (string, error) {
    if input == "" {
        return "", &apierrors.Structured{
            Category: apierrors.CategoryInput,
            Code:     "DYNFN_FORMATDATE_EMPTY_INPUT",
            Message:  "input string is empty",
            Hint:     "Pass either a Unix-seconds integer string (e.g. '1713701401') or an RFC3339 string (e.g. '2024-04-21T15:10:01Z') as the first argument.",
        }
    }
    if isAllDigits(input) {
        n, err := strconv.ParseInt(input, 10, 64)
        if err == nil {
            return time.Unix(n, 0).UTC().Format(layout), nil
        }
        // Overflow (input > MaxInt64) — fall through to bad-input.
    } else if t, err := time.Parse(time.RFC3339, input); err == nil {
        return t.Format(layout), nil
    }
    snippet := input
    if len(snippet) > 32 {
        snippet = snippet[:32] + "..."
    }
    return "", &apierrors.Structured{
        Category: apierrors.CategoryInput,
        Code:     "DYNFN_FORMATDATE_BAD_INPUT",
        Message:  fmt.Sprintf("cannot interpret %q as a Unix-seconds integer or an RFC3339 string", snippet),
        Hint:     "$formatDate accepts either a Unix-seconds integer string (e.g. '1713701401') or an RFC3339 string (e.g. '2024-04-21T15:10:01Z'). See MANUAL.md §3.7.",
    }
}

// isAllDigits reports whether s is non-empty and every byte is an ASCII digit.
// Allocation-free; matches the digits-only branch of $formatDate's input parser.
func isAllDigits(s string) bool {
    if s == "" {
        return false
    }
    for i := 0; i < len(s); i++ {
        c := s[i]
        if c < '0' || c > '9' {
            return false
        }
    }
    return true
}
```

(Note: in the digits-only branch we call `time.Unix(n, 0).UTC().Format(layout)`. The `.UTC()` ensures consistent zone selection when layout includes a zone token like `MST` — without it the value would render in the local zone of whoever runs the test, breaking the reproducibility contract.)

(The RFC3339 branch does *not* force `.UTC()` — behavior 2 says the result is "that time formatted with `layout`", which preserves the source zone if layout includes `Z07:00` or `MST`. Tests that need UTC pass an already-UTC RFC3339 string. Compare to `$parseDate`, which is always UTC by design — see Decision 6.)

```markdown
**Go reference-time layouts (`$formatDate`, `$parseDate`).** Both
functions interpret their `layout` argument using Go's reference-time
convention — the layout *is itself a literal date* representing
`Mon Jan 2 15:04:05 MST 2006` (Unix time `1136239445`). Each component
of the layout that matches one of these reference values is replaced
by the corresponding component of the actual time; everything else
passes through verbatim. The full grammar is on the stdlib
[`pkg.go.dev/time#pkg-constants`](https://pkg.go.dev/time#pkg-constants)
page. Common layouts:

| Layout | Renders | Example output |
|---|---|---|
| `2006-01-02` | ISO date | `2024-04-21` |
| `02 Jan 2006` | day-month-year | `21 Apr 2024` |
| `Mon Jan _2 15:04:05 2006` | ANSI C | `Sun Apr 21 15:10:01 2024` |
| `2006-01-02T15:04:05Z07:00` | RFC3339 (`time.RFC3339`) | `2024-04-21T15:10:01Z` |
| `02/01/2006 15:04:05` | EU date+time | `21/04/2024 15:10:01` |

`$formatDate` accepts two input shapes for the *first* argument: a
Unix-seconds integer string (e.g. `1713701401`) or an RFC3339 string
(e.g. `2024-04-21T15:10:01Z`). Anything else returns a structured
`[INPUT]` error. To format the current wall-clock time, nest
`{{$timestamp}}`: `{{$formatDate('{{$timestamp}}', '2006-01-02')}}`.

`$parseDate` is the inverse: it parses any layout-formatted string
and returns canonical ISO-8601 UTC. Non-UTC zone-tagged inputs are
converted to UTC before formatting, so `$parseDate('2024-04-21T17:10:01+02:00', time.RFC3339)`
yields `2024-04-21T15:10:01Z`.

**The layout-as-template footgun.** Go's `time.Format` returns the
layout verbatim if it contains no recognised reference-time tokens.
That means `$formatDate('1713701401', 'YYYY-MM-DD')` returns the
literal string `YYYY-MM-DD` — *not* a date. There is no validation
step. Always sanity-check a layout by passing it through
`time.Parse(layout, "2006-01-02T15:04:05Z")` (or a quick `go run`)
before relying on it in production. The valid spelling for ISO date
is `2006-01-02`.
```

## Risks and Edge Cases

- **Risk:** Layout-as-template footgun confuses users who try `'YYYY-MM-DD'`. **Mitigation:** explicit MANUAL.md callout with the spelling guide and a `time.Parse(layout, …)` validation tip. We deliberately do not validate the layout in code — that would fork from `time.Time.Format` and surprise stdlib-literate users. The footgun behaviour is also pinned in `TestRegistry_FormatDate_LayoutAsTemplate`.

- **Edge case:** Whitespace-padded input like `' 1713701401'`. The `isAllDigits` byte scan rejects the leading space; the RFC3339 path also rejects it. The user sees `DYNFN_FORMATDATE_BAD_INPUT` with their input in the message snippet. Pinned in `TestRegistry_FormatDate_BadInput` ("leading-whitespace digits" case).

- **Edge case:** Negative Unix seconds (pre-1970). The `-` byte fails the digit scan; the RFC3339 path fails. User gets `DYNFN_FORMATDATE_BAD_INPUT`. Acceptable: spec lists exactly two input shapes, neither of which includes negative values.

- **Edge case:** Very large digit strings (>19 digits, overflow `int64`). The digit scan succeeds, `strconv.ParseInt` fails with `*strconv.NumError`, and we fall through to the bad-input error. Pinned in `TestRegistry_FormatDate_BadInput` ("int64 overflow digits" case).

- **Edge case:** RFC3339 input with non-UTC offset (e.g. `'2024-04-21T17:10:01+02:00'`) passed to `$formatDate` with layout `'2006-01-02 15:04:05'`. `time.Parse` preserves the source location; `time.Format` renders in that location. Result: `'2024-04-21 17:10:01'` (the local-time wall clock). This is by design — `$formatDate` is not "always UTC". Users who want UTC should pass the input through `$parseDate` first. Documented in MANUAL.md.

- **Edge case:** Empty layout `''` for `$formatDate`. `time.Format("")` returns `""` — no error. We do not special-case empty layouts; the result is the empty string. Acceptable: the user explicitly asked for empty output.

- **Edge case:** Multi-byte UTF-8 in layout (e.g. `'2006年01月02日'`). `time.Format` substitutes the reference tokens and passes the rest through verbatim — Japanese yen-shape characters render correctly. Not pinned by a test (out of scope), but known-safe via stdlib documentation.

- **Risk:** Per-request memoisation could mask subtle differences when the same nested-`$timestamp` call is used twice in the same request. The cache key is `funcName + NUL + args`, where args are the *resolved* values. Both `{{$formatDate('{{$timestamp}}', 'L1')}}` and `{{$formatDate('{{$timestamp}}', 'L2')}}` resolve to the same `$timestamp` value within a request (because `$timestamp` is also memoised per-request), so they share the underlying instant. This matches existing behaviour for `$dateAdd`/`$isoTimestamp` and is intentional.

- **Risk:** `time.Parse(time.RFC3339, …)` is strict about the colon in the offset. Inputs like `'2024-04-21T15:10:01+0200'` (no colon, RFC822-style) fail RFC3339 parsing and fall to bad-input. **Mitigation:** acceptable — the spec calls out RFC3339 specifically; users with other formats should use `$parseDate` with the appropriate layout.

- **Risk:** Test `TestRegistry_FormatDate_Now` exercises the real wall clock via `$timestamp`. **Mitigation:** the assertion is shape-based (regex `^\d{4}-\d{2}-\d{2}$`), not value-based — so it remains reproducible across runs without a clock seam. Compare to other tests in this package that read the wall clock (`TestRegistry_Evaluate` "timestamp" case at dynamic_test.go:166).
