# Implementation Plan: M14-010

## Overview

Replace the `NotImplementedException` body of `StripeGateway.ComputeProration` with a live Stripe.Net `InvoiceService.UpcomingAsync` call (the upcoming-invoice preview), migrate the `IStripeGateway.ComputeProration` interface from a synchronous five-tuple signature to an async `Task<ProrationResult> ComputeProrationAsync(string subscriptionId, string newPriceId, ...)` signature that matches Stripe's server-side proration model, add a new `POST /api/v1/subscriptions/preview-proration` endpoint that returns `amount_due_now` (and a `renewal_date`) shaped from Stripe's preview invoice, and keep the existing `FakeStripeGateway` local-math implementation so unit tests remain network-free with a doc comment that flags the intentional divergence.

## Architectural Decisions (resolved up-front)

These are the design questions surfaced by the task YAML; resolved here to keep the implementation step list mechanical.

1. **A new endpoint `POST /api/v1/subscriptions/preview-proration` is added.** The task observable POSTs to `/preview-proration` with body `{"new_price_id": "..."}` and reads `.amount_due_now` from the response — there is no existing endpoint to repurpose. The legacy `PATCH /api/v1/subscriptions/{id}` route already returns a `proration` block on apply, but that returns the local-math `ProrationResult` and (more importantly) actually *changes* the subscription. Preview is a strictly read-only "what would I be charged?" probe. The new endpoint resolves the bearer's owned org, looks up the active `Subscription`, validates the new `price_id` against the existing `StripePriceAllowlist` (M14-008), and calls the gateway. We keep `PATCH` unchanged for now: the existing `UpdateAsync` continues to use the synchronous fake math via the new sync wrapper (see Decision #4) so we avoid bundling a behaviour change to the apply path into M14-010.

2. **Interface signature: `Task<ProrationResult> ComputeProrationAsync(string subscriptionId, string newPriceId, int newQuantity, DateTimeOffset prorationDate, string? idempotencyKey, CancellationToken ct)`.** The current sync signature `(SubscriptionTier fromTier, int fromSeats, SubscriptionTier toTier, int toSeats, string interval)` operates on tier/seats — abstractions Stripe does not natively understand. Stripe's upcoming-invoice preview takes the Stripe `subscription` id (`sub_*`) and the target `price` id (`price_*`); it computes proration server-side from the live subscription's items. The new signature matches that model directly: caller threads the subscription id through, gateway maps to `UpcomingInvoiceOptions.Subscription` + `UpcomingInvoiceOptions.SubscriptionItems` + `UpcomingInvoiceOptions.SubscriptionProrationDate`. We keep the *old* sync signature on `IStripeGateway` as a transitional default-implementation method (`ComputeProration`) so existing `SubscriptionsService.UpdateAsync` keeps compiling without behaviour change — the new async method is the only deliverable surface for the new endpoint.

3. **The interface gets BOTH methods (transitional).** The task behaviour #2 says "the signature is async (Task<ProrationResult>)" — it is read literally as "the new ComputeProrationAsync is async; the old sync ComputeProration is the legacy fake-math path that continues to live for unit tests / PATCH apply". To avoid a destabilising rewrite of `UpdateAsync` and its endpoint test (`Patch_increases_seats_and_returns_proration_block`) inside M14-010, the live `StripeGateway.ComputeProration` (sync) returns the same simple math the fake uses (delegating to a shared static helper), and the new async method is the gateway's only network-bound proration path. The fake gateway implements both methods identically (the async one wraps the sync one in `Task.FromResult`). This keeps the interface change additive: existing call sites compile unchanged. Decision is documented in the IStripeGateway XML doc comment per behaviour #2.

4. **`ProrationResult` is reused unchanged.** The record `(int Credit, int Charge, int Net)` already expresses everything the new endpoint needs to emit. The endpoint's response shape `{ "amount_due_now": <int>, "renewal_date": <iso8601 or null>, "credit": <int>, "charge": <int> }` is built by the endpoint handler from the gateway's `ProrationResult` plus a new optional `RenewalDate` (the upcoming invoice's `NextPaymentAttempt` or `PeriodEnd`). To avoid changing `ProrationResult` (which other callers rely on), we add a separate **endpoint-only response record `PreviewProrationResponse(int AmountDueNow, DateTime? RenewalDate, int Credit, int Charge)`**. The gateway returns `ProrationResult`; the endpoint maps `Net → amount_due_now`. The renewal date is threaded as a separate out-parameter from the gateway: the new gateway method signature returns a tuple `(ProrationResult Result, DateTime? RenewalDate)` so the wire-protocol shape from Stripe (the upcoming invoice's period end / next payment attempt) is preserved without polluting the internal `ProrationResult` record.

5. **No-op short-circuit for "new price equals current price".** Behaviour #3: when the requested `new_price_id` matches the active subscription's stored Stripe price id, the gateway is **not** called (saves a Stripe round-trip and avoids ambiguous `no_invoice_available` semantics). The service short-circuits with `amount_due_now = 0`, `renewal_date = current_period_end`, `credit = 0`, `charge = 0`. Today the `Subscription` row does **not** store the Stripe price id — it stores `StripeCustomerId` and `StripeSubscriptionId` (which currently holds a checkout session id from M14-008's path; that's a known issue for a later slice). To detect equality without a schema migration, we use a **derived comparison**: extract `(tier, interval)` from the subscription and from the requested price id (via the existing `DerivePlanFromPriceId` helper in `SubscriptionsService`); short-circuit when both match AND the requested seat count (= current seat count if not supplied) matches. **Open question resolved**: behaviour #3 says "new price_id equals the current price". Without a stored price-id-to-row mapping yet, "equality" is a logical equality on (tier, interval, seat_count). This is a defensible interpretation because the existing `StripePriceAllowlist` only emits one price per (tier, interval) combination. A code comment flags the simplification.

6. **No active subscription → 409 `no_active_subscription`.** Behaviour #4. We add `SubscriptionError.NoActiveSubscription` to the existing enum and a `SubscriptionsProblem.NoActiveSubscription` ProblemDetails builder (mirrors the M14-009 `NoBillingSetup` pattern at HTTP 409). The endpoint returns RFC 7807 problem+json on this branch.

7. **Stripe `invoice_upcoming_none` / `no_invoice_available` → HTTP 200 with `amount_due_now=0`, `renewal_date=null`.** Behaviour #5. Stripe's API returns 404 with error code `invoice_upcoming_none` when no upcoming invoice exists for the subscription (e.g. test-mode subs that have never had a real cycle). Per the task this is **not** a client error — preview is best-effort. The gateway catches `StripeException` whose `StripeError.Code == "invoice_upcoming_none"` (or whose HTTP status is 404 on the upcoming-invoice path) and returns a sentinel value: a `ProrationResult` with all zeros plus `RenewalDate = null`. The endpoint surfaces that as 200 OK. **All other** Stripe errors propagate the existing taxonomy (5xx → `STRIPE_UNAVAILABLE` 502, 429 → rate-limited 503).

8. **Idempotency-Key on read endpoints.** Stripe does honour `Idempotency-Key` on `GET /v1/invoices/upcoming` for caching, but this is a read-only preview — replaying with the same key yields the same answer because the underlying subscription state is unchanged within the second-resolution proration date. We thread the `Idempotency-Key` request header through the same way as `CreateBillingPortal` (M14-009): read or synthesize a UUID, echo as `X-Stripe-Idempotency-Key`, pass to the gateway's `RequestOptions.IdempotencyKey`. This keeps the cross-endpoint pattern consistent.

9. **`subscription_proration_date = clock.GetUtcNow()`.** Behaviour #1. The gateway accepts a `DateTimeOffset prorationDate` parameter (so tests can pin it deterministically); the service supplies `clock.GetUtcNow()` from the existing injected `TimeProvider`. Stripe wants epoch seconds; the gateway does the conversion. This makes the fake-vs-live divergence narrow: both functions accept a deterministic time input.

10. **Authorisation: owner only.** The preview endpoint is a billing surface; only org owners see it. This matches `CreateCheckoutByPriceAsync` semantics (which also requires `OrgRole.Owner`). `Admin` role is **not** sufficient — admin/owner dual role applies only to the billing portal (per M14-009 decision #9). The response on member or no-membership is HTTP 403 `permission_denied`.

11. **Stripe 5xx → STRIPE_UNAVAILABLE 502; Stripe 429 → STRIPE_RATE_LIMITED 503.** The same exception types and the same `SubscriptionsProblem` builders introduced in M14-008/M14-009 are reused — no new exception class needed. The gateway throws `StripeRateLimitedException` on 429 and `StripeUnavailableException` on 5xx for the upcoming-invoice path, mirroring how `CreateCheckoutSessionAsync` and `CreatePortalSessionAsync` already handle those status codes.

12. **`SubscriptionsService` exposes a new method `PreviewProrationAsync(Guid userId, string newPriceId, int? newSeatCount, CancellationToken ct)`.** It does NOT live on the existing `UpdateAsync` because preview must run for any owner without changing state, and `UpdateAsync` is destructive and audit-logged. The new method does not write to the audit log (preview is a read-only operation). It returns `(int AmountDueNow, DateTime? RenewalDate, int Credit, int Charge, SubscriptionError Err, string? Msg)` — the shape the endpoint serializes.

13. **The fake gateway's `ComputeProration` semantics are documented as intentionally divergent.** Behaviour #2 + #6 say "FakeStripeGateway.ComputeProration is preserved with its local-math implementation but only used in unit tests (XML doc comment notes the intentional divergence)" and "tests tolerate the documented divergence (test scope is 'shape correct' not 'cents identical')". We add an XML `<remarks>` block on `FakeStripeGateway.ComputeProration` and on the new `FakeStripeGateway.ComputeProrationAsync` (which calls the same simple-math helper) that explicitly states the math is full-month delta, not Stripe's day-prorated math, and that integration tests against stripe-mock cover the wire-protocol shape while smoke against real Stripe covers cents-accuracy.

14. **stripe-mock returns synthetic upcoming invoices.** `stripe-mock` (the OpenAPI-driven mock) responds to `GET /v1/invoices/upcoming` with deterministic placeholder data — typically a non-zero `amount_due` integer regardless of inputs. Tests assert wire-protocol shape correctness ("we got an integer back, line items summed correctly, renewal_date is a parseable date or null") rather than cents-identical math (the latter is the smoke-pass-against-real-Stripe-test-mode contract). We use `[SkippableFact]` + `StripeMockFixture` exactly as `StripeCheckoutIntegrationTests` and `StripeBillingPortalIntegrationTests` do.

15. **No DB migration needed.** `Subscription.StripeSubscriptionId` already exists. The endpoint and service read it from the active subscription row; no schema change. The fact that `StripeSubscriptionId` currently stores a `cs_*` checkout-session id (set by `CreateCheckoutByPriceAsync` from M14-008) rather than a real `sub_*` subscription id is a known cross-slice issue — the live `ComputeProrationAsync` will pass that string straight to Stripe; against stripe-mock that succeeds (stripe-mock accepts any subscription-id-shaped string); against real Stripe it would fail with 404 `resource_missing`. That gap closes when M14-011's webhook handler attaches the real `sub_*` id; until then the `[SkippableFact]` integration tests pass and the real-Stripe smoke pass is what catches regression. We add a code comment in `SubscriptionsService.PreviewProrationAsync` flagging this transitional behaviour.

16. **Spec citation header.** `StripeGateway.cs` already has `// Spec refs: docs/SPECIFICATION.md:6856–6870 (three-layer test strategy), :7322–7345 (POST /api/v1/subscriptions/portal)`. We append `:6860 (Stripe Test Strategy — known limitation: stripe-mock cannot exercise real proration math)` to the file header per definition_of_done item.

17. **`deploy/self-hosted/README.md` gets a one-line note.** Per definition_of_done: "deploy/self-hosted/README.md notes that proration is server-computed in live mode". We append a short subsection under "Stripe Configuration" that says "In `live` mode, proration math is computed server-side by Stripe (via the upcoming-invoice preview); in `fake` mode, a deterministic local approximation is used and dollar amounts will not match real Stripe."

```csharp
/// <inheritdoc/>
/// <remarks>
/// The fake gateway uses a deterministic full-month-delta approximation that intentionally
/// diverges from Stripe's day-prorated math. Unit tests assert *shape* (sign, ordering) only;
/// integration tests against stripe-mock exercise wire-protocol correctness; real-Stripe
/// smoke tests cover cents-accuracy. Do NOT add cents-identical assertions on this path.
/// </remarks>
public Task<(ProrationResult Result, DateTime? RenewalDate)> ComputeProrationAsync(
    string subscriptionId,
    string newPriceId,
    int newQuantity,
    DateTimeOffset prorationDate,
    string? idempotencyKey = null,
    CancellationToken ct = default)
{
    // Approximate using the same local math the sync path uses. The new price id is
    // mapped back to (tier, seats) via the same heuristic SubscriptionsService uses;
    // for tests this is sufficient because the assertions only check sign and shape.
    var (toTier, _, interval) = FakeStripeProrationMath.DerivePlanFromPriceId(newPriceId);
    var result = ComputeProration(toTier, newQuantity, toTier, newQuantity, interval);
    // Renewal date: 30 days out from the proration date (deterministic).
    var renewal = prorationDate.UtcDateTime.AddDays(30);
    return Task.FromResult((result, (DateTime?)renewal));
}
```

```csharp
/// <inheritdoc/>
/// <remarks>
/// Live gateway delegates the sync method to the simple-math helper for the apply path
/// (PATCH); the new <see cref="ComputeProrationAsync"/> talks to Stripe directly for the
/// preview path. Migrating PATCH to the async path is a future slice.
/// </remarks>
public ProrationResult ComputeProration(
    SubscriptionTier fromTier, int fromSeats, SubscriptionTier toTier, int toSeats,
    string interval) =>
    StripeProrationLocalMath.Compute(fromTier, fromSeats, toTier, toSeats, interval);

/// <inheritdoc/>
public async Task<(ProrationResult Result, DateTime? RenewalDate)> ComputeProrationAsync(
    string subscriptionId,
    string newPriceId,
    int newQuantity,
    DateTimeOffset prorationDate,
    string? idempotencyKey = null,
    CancellationToken ct = default)
{
    var requestOptions = new RequestOptions { IdempotencyKey = idempotencyKey };
    if (requestOptions.IdempotencyKey?.Length > 255)
        requestOptions.IdempotencyKey = requestOptions.IdempotencyKey[..255];

    var options = new UpcomingInvoiceOptions
    {
        Subscription = subscriptionId,
        SubscriptionItems = new List<InvoiceSubscriptionItemOptions>
        {
            new() { Price = newPriceId, Quantity = newQuantity },
        },
        SubscriptionProrationDate = prorationDate.UtcDateTime,
        SubscriptionProrationBehavior = "create_prorations",
    };

    Stripe.Invoice invoice;
    try
    {
        invoice = await new InvoiceService(_client).UpcomingAsync(options, requestOptions, ct);
    }
    catch (StripeException ex) when (ex.HttpStatusCode == HttpStatusCode.TooManyRequests)
    {
        _log.LogWarning(
            "Stripe rate-limited during invoice.upcoming; idempotency_key={IdempotencyKey}",
            idempotencyKey);
        throw new StripeRateLimitedException(idempotencyKey, ex);
    }
    catch (StripeException ex) when (
        ex.StripeError?.Code == "invoice_upcoming_none"
        || (ex.HttpStatusCode == HttpStatusCode.NotFound && ex.StripeError?.Code != "resource_missing"))
    {
        // Behaviour #5: no upcoming invoice → 200 OK with zeroed result.
        return (new ProrationResult(Credit: 0, Charge: 0, Net: 0), null);
    }
    catch (StripeException ex) when ((int)ex.HttpStatusCode >= 500)
    {
        _log.LogWarning(
            "Stripe 5xx during invoice.upcoming; idempotency_key={IdempotencyKey} request_id={RequestId} status={Status}",
            idempotencyKey, ex.StripeResponse?.RequestId, (int)ex.HttpStatusCode);
        throw new StripeUnavailableException(idempotencyKey, ex.StripeResponse?.RequestId, ex);
    }

    // Sum line-item amounts: positive amounts are charges, negative are credits.
    int charge = 0, credit = 0;
    if (invoice.Lines is not null)
    {
        foreach (var line in invoice.Lines)
        {
            if (line.Amount >= 0) charge += (int)line.Amount;
            else credit += (int)(-line.Amount);
        }
    }
    var net = charge - credit;
    var renewal = invoice.NextPaymentAttempt ?? invoice.PeriodEnd;
    return (new ProrationResult(credit, charge, net), renewal);
}
```

```csharp
using ApiTool.Backend.Data.Entities;

/// <summary>
/// Maps a Stripe price id (drawn from <see cref="StripePriceAllowlist"/>) to the
/// (tier, default seat count, billing interval) triple it represents.
/// </summary>
public static class StripePriceParser
{
    /// <summary>Parses an allowlisted price id; returns sensible defaults for unknown ids.</summary>
    public static (SubscriptionTier Tier, int DefaultSeatCount, string Interval) Parse(string priceId)
    {
        var tier = priceId switch
        {
            var p when p.StartsWith("price_test_solo_", StringComparison.Ordinal)
                    || p.StartsWith("price_solo_", StringComparison.Ordinal) => SubscriptionTier.Professional,
            var p when p.StartsWith("price_test_pro_", StringComparison.Ordinal)
                    || p.StartsWith("price_professional_", StringComparison.Ordinal) => SubscriptionTier.Professional,
            var p when p.StartsWith("price_test_team_", StringComparison.Ordinal)
                    || p.StartsWith("price_team_", StringComparison.Ordinal) => SubscriptionTier.Team,
            var p when p.StartsWith("price_enterprise_", StringComparison.Ordinal)
                    || p.StartsWith("price_test_enterprise_", StringComparison.Ordinal) => SubscriptionTier.Enterprise,
            _ => SubscriptionTier.Free,
        };
        var interval = priceId.Contains("yearly", StringComparison.OrdinalIgnoreCase) ? "year" : "month";
        var defaultSeatCount = tier == SubscriptionTier.Team ? 3 : 1;
        return (tier, defaultSeatCount, interval);
    }
```

```csharp
/// <summary>
/// Previews proration for swapping the active subscription's price to <paramref name="newPriceId"/>.
/// Read-only — does not modify state and does not write the audit log.
/// Behaviours: allowlist validation, no-op short-circuit when (tier,interval,seats) match,
/// 409 when no active subscription, 200+amount_due_now=0 when Stripe reports no upcoming invoice.
/// </summary>
public async Task<(int AmountDueNow, DateTime? RenewalDate, int Credit, int Charge, SubscriptionError Err, string? Msg)>
    PreviewProrationAsync(Guid userId, string newPriceId, int? newSeatCount, string idempotencyKey, CancellationToken ct)
{
    if (!StripePriceAllowlist.IsAllowed(newPriceId))
        return (0, null, 0, 0, SubscriptionError.InvalidPriceId,
            $"Price '{newPriceId}' is not in the allowlist.");

    // Resolve the user's owned org.
    var ownership = await db.OrganizationMembers
        .FirstOrDefaultAsync(m => m.UserId == userId && m.Role == OrgRole.Owner, ct);
    if (ownership is null)
        return (0, null, 0, 0, SubscriptionError.PermissionDenied,
            "Only org owners can preview proration.");

    var orgId = ownership.OrgId;

    var sub = await db.Subscriptions.FirstOrDefaultAsync(s => s.OrgId == orgId, ct);
    if (sub is null || string.IsNullOrEmpty(sub.StripeSubscriptionId))
        return (0, null, 0, 0, SubscriptionError.NoActiveSubscription,
            "Organization has no active subscription.");

    var seats = newSeatCount ?? sub.SeatCount;
    var (newTier, _, newInterval) = StripePriceParser.Parse(newPriceId);

    // Behaviour #3: short-circuit when the requested target equals the current subscription's
    // (tier, interval, seats). Avoids a Stripe round-trip for pure no-op previews.
    if (sub.Tier == newTier && sub.Interval == newInterval && sub.SeatCount == seats)
        return (0, sub.CurrentPeriodEnd, 0, 0, SubscriptionError.None, null);

    var (result, renewal) = await stripe.ComputeProrationAsync(
        sub.StripeSubscriptionId!, newPriceId, seats,
        clock.GetUtcNow(), idempotencyKey, ct);

    return (result.Net, renewal, result.Credit, result.Charge, SubscriptionError.None, null);
}
```

```csharp
/// <summary>
/// POST /api/v1/subscriptions/preview-proration — previews what changing the active
/// subscription's price would charge or credit, without applying the change.
/// Spec ref: docs/SPECIFICATION.md §"Update Subscription" lines 7274-7278 (proration block shape).
/// </summary>
private static async Task<IResult> PreviewProration(
    [FromBody] PreviewProrationRequest body,
    HttpContext context,
    CurrentUserAccessor users,
    SubscriptionsService svc,
    CancellationToken ct)
{
    var userId = await users.ResolveAsync(ct);
    if (userId is null)
        return Unauthorized401;

    var idempotencyKey = context.Request.Headers["Idempotency-Key"].FirstOrDefault()
                         ?? Guid.NewGuid().ToString();
    context.Response.Headers["X-Stripe-Idempotency-Key"] = idempotencyKey;

    try
    {
        var (amount, renewal, credit, charge, err, msg) = await svc.PreviewProrationAsync(
            userId.Value, body.NewPriceId, body.SeatCount, idempotencyKey, ct);

        return err switch
        {
            SubscriptionError.None => HttpResults.Ok(
                new PreviewProrationResponse(amount, renewal, credit, charge)),
            SubscriptionError.InvalidPriceId => HttpResults.Json(
                new ErrorResponse("invalid_price_id", msg!),
                statusCode: StatusCodes.Status400BadRequest),
            SubscriptionError.PermissionDenied => SubscriptionsProblem.PermissionDenied(context, msg!),
            SubscriptionError.NoActiveSubscription => SubscriptionsProblem.NoActiveSubscription(context),
            SubscriptionError.StripeRateLimited => SubscriptionsProblem.StripeRateLimited(context, idempotencyKey),
            _ => HttpResults.StatusCode(StatusCodes.Status500InternalServerError),
        };
    }
    catch (StripeUnavailableException ex)
    {
        return SubscriptionsProblem.StripeUnavailable(context, ex.RequestId, ex.IdempotencyKey);
    }
    catch (StripeRateLimitedException ex)
    {
        return SubscriptionsProblem.StripeRateLimited(context, ex.IdempotencyKey);
    }
}

private sealed record PreviewProrationResponse(int AmountDueNow, DateTime? RenewalDate, int Credit, int Charge);
```

## Risks and Edge Cases

- **Risk: `StripeSubscriptionId` currently holds a `cs_*` checkout-session id, not a `sub_*` subscription id.** → **Mitigation:** Decision #15. The integration test against stripe-mock passes (mock accepts any subscription-id-shaped string); the smoke pass against real Stripe fails until M14-011 webhooks attach the real `sub_*` id. A code comment in `PreviewProrationAsync` documents this transitional behaviour. The test scope is "shape correct, not cents identical."
- **Risk: Stripe.Net 43.x's exact upcoming-invoice signature drifts.** → **Mitigation:** The signature `InvoiceService.UpcomingAsync(UpcomingInvoiceOptions, RequestOptions, CancellationToken) -> Task<Invoice>` is verified directly against the installed `Stripe.net` 43.0.0 assembly (DLL string-table probe confirms `InvoiceService.UpcomingAsync`, `UpcomingInvoiceOptions`, `Invoice.SubscriptionProrationDate`). If upgrade to 44.x ever happens, the same migration that bumps the package version covers the rename.
- **Risk: stripe-mock returns 401 on any path that does not pass an Authorization header.** → **Mitigation:** The `StripeMockFixture` already documents this and the `StripeGateway` constructor accepts a Stripe API key (in tests we pass `sk_test_stripe_mock_dummy`). Existing `StripeCheckoutIntegrationTests` proves the pattern works.
- **Risk: `Idempotency-Key` truncation.** → **Mitigation:** The existing pattern in `CreateCheckoutSessionAsync` and `CreatePortalSessionAsync` truncates the key to 255 bytes; we replicate the same 4-line guard in `ComputeProrationAsync`.
- **Edge case: empty body / missing `new_price_id`.** → **Handling:** `[FromBody] PreviewProrationRequest` deserializes a missing `new_price_id` as `null`; the service's allowlist check returns `InvalidPriceId` for null/empty, mapping to HTTP 400.
- **Edge case: `new_price_id` is supplied but `seat_count` is absent.** → **Handling:** Service falls back to the active subscription's current `SeatCount` (Decision #2 + service code).
- **Edge case: org has multiple subscriptions (deleted ones).** → **Handling:** `FirstOrDefaultAsync(s => s.OrgId == orgId, ct)` already exists across the codebase; behaviour matches `GetForOrgAsync`. Future subscription-history work refines this guard.
- **Edge case: a `[FromBody]` deserialization failure (malformed JSON) returns 400 from the framework before our handler runs.** → **Handling:** That's the existing ASP.NET Core default; no custom handling required.
- **Edge case: idempotency key longer than 255 bytes.** → **Handling:** Truncated to 255 bytes by the gateway, identical to `CreateCheckoutSessionAsync`.
