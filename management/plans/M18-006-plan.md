# Implementation Plan: M18-006

## Overview

Replace the M18-005 `StubUserAnonymiser` with a concrete `UserAnonymiser` that (a) hard-deletes every InDeletionHard row attributed to the user, (b) anonymises column-level `[GdprAnonymise]` annotations across the audit log and the surviving org-scoped tables (CustomRole, Schedule, CoordinatorJob, TeamVault, NotificationRule, OrganizationMember.InvitedBy) using a deterministic `deleted-user-{first8(sha256(user_id+org_id))}` token, (c) scrubs the user's own PII columns (Email, PasswordHash) while leaving the row as a tombstone for the state machine, and (d) emits a `user.anonymised` audit-of-audit entry per affected org. Adds a last-admin protection check to `POST /api/v1/users/me/deletion-requests` (sole-owner-with-other-members returns 409 `OwnerCannotLeave`; sole-owner-of-empty-orgs cascades the org into PendingDeletion). Lands the corresponding "Delete account" UI on the existing `/account/data` page plus a `/account/data/cancel-deletion` page.

## Architectural Decisions (made without confirmation)

1. **Concrete class name `UserAnonymiser` (not "RealUserAnonymiser" or similar).** Replaces `StubUserAnonymiser`, which is deleted. The interface remains `IUserAnonymiser` so callers are unchanged.
2. **Token derivation:** `deleted-user-{hex}` where `hex` is the first 8 lowercase hex chars of `SHA-256(user_id_bytes || org_id_bytes)`. The user_id and org_id are serialized as their raw 16-byte big-endian (binary) Guid representations to match the GDPR spec wording "first 8 hex chars of sha256(user_id+org_id)". This is collision-proof for any plausible deployment scale (16^8 = 4.3B token-space, only ever sampled per (user, org) pair).
3. **No new `User.Email` GDPR attribute.** The User row's PII columns are scrubbed directly inside `UserAnonymiser.AnonymiseAsync` — adding `[GdprAnonymise(DeletedUserToken)]` would conflict with `User`'s table-level `InExportInDeletionHard` semantics and confuse the manifest. The anonymiser scrubs `Email`, `PasswordHash` explicitly without reflection.
4. **`OrganizationMember.InvitedBy` is scrubbed across the org for every org that referenced the deleted user as inviter** — even though the member's own membership row is hard-deleted (so their own InvitedBy disappears with the row). This honours the column-level `[GdprAnonymise(SetNull)]` for the **inviter** axis.
5. **Per-org anonymisation token + per-org `user.anonymised` audit event.** The token is `(user_id, org_id)`-deterministic per the spec. For each org touched by the anonymisation, one `user.anonymised` audit row is emitted (with `OrgId = <that org's id>`, `Payload = { anonymisation_token: "deleted-user-<8hex>" }`). When `user.anonymised` cannot be attributed to an org (e.g. global user state changes), we DO NOT emit a `Guid.Empty`-scoped row — there's no global audit lane. The user-scoped state-machine cancellation already uses `Guid.Empty`, and we keep that pattern but only for cancellation, not for anonymisation.
6. **Single transaction per anonymisation, not per-org.** `AnonymiseAsync` opens one EF transaction; all hard-deletes, column updates, and audit appends save together. Failure rolls back atomically; the host's retry-on-next-tick logic then re-attempts (idempotent).
7. **Column rename `ActorId` → `actor_id`** in `OrganizationAuditLogEntry` mapping, with a migration to rename the existing column. We also widen it to `nullable Guid?` in the same migration. Same widening migration covers the 6 other `CreatedBy`/`UpdatedBy` columns. Column rename is scoped to `ActorId` only (the other widened columns already follow PascalCase elsewhere in the codebase and there's no observable referring to them).
8. **`audit.Append` writes are ordered after anonymisation queries in the same transaction.** The audit row's own `ActorId` is set to `null` (system event), `ActorEmail` is set to the per-org token. This way the audit-of-audit row is itself anonymised at write-time, preserving the integrity property.
9. **Last-admin protection happens BEFORE re-auth-token consumption.** If the request would be blocked by 409 OwnerCannotLeave, the X-Reauth-Token is NOT consumed — letting the user use the same token after they transfer ownership in another tab. Decision: protection check runs first; if it returns 409, the token is preserved. Implementation places `LastAdminProtectionService.CheckAsync` immediately before `reauthService.ConsumeAsync`.
10. **`LastAdminProtectionService` is a new class in `Organizations/` (next to MembersService), not in `Compliance/Gdpr/`.** The check is a generic "is this user a blocking owner" predicate reusable beyond GDPR (future "transfer & leave" flows can reuse it).
11. **Web `account/data/cancel-deletion` is a server-loaded page that reads `pending_deletion_at` from the status endpoint** and shows a single Cancel button. The page does NOT require re-auth (no destructive action — just clears `pending_deletion_at`).
12. **Re-auth flow in the web UI.** The Delete button triggers a modal that POSTs to `/api/v1/auth/reauth` with the current user's password, receives a `drto_` token, then immediately POSTs to `/api/v1/users/me/deletion-requests` with `X-Reauth-Token`. On 409 OwnerCannotLeave the response body's `blocking_orgs[]` is rendered as a "These orgs block your deletion" preview. The token is held in a JS variable only — never persisted.
13. **Inventory documentation update**: `docs/security/data-inventory.md` already lists the dispositions correctly. We extend the doc with a new section "Anonymisation function (M18-006)" that documents the deterministic token shape and irreversibility property — this is required by definition-of-done.
14. **NotificationRule disposition vs. behavior text discrepancy.** The behavior text says "every row in those tables where UserId=user is hard-deleted (RefreshToken, EmailVerificationToken, PasswordResetToken, NotificationRule per the inventory dispositions)". The inventory disposition for NotificationRule is `ExcludedFromExportAnonymisedInDeletion` (row survives, CreatedBy nulled). We hew to the **inventory** (the explicit source of truth named in the parenthetical "per the inventory dispositions") — NotificationRule rows survive with `CreatedBy` nulled. The behavior text is treated as a drafting error.

```csharp
// AnonymisationToken.cs
namespace ApiTool.Backend.Compliance.Gdpr;

/// <summary>
/// Computes the deterministic <c>deleted-user-{first8(sha256(user_id+org_id))}</c>
/// anonymisation token per spec v4-6. Irreversible — the SHA-256 truncation gives
/// 4.3B-token space, sufficient for any plausible deployment scale.
/// </summary>
public static class AnonymisationToken
{
    public const string Prefix = "deleted-user-";

    /// <summary>
    /// Returns the per-(user, org) deterministic token. Same (userId, orgId) ALWAYS
    /// returns the same string; different orgs yield different tokens.
    /// </summary>
    public static string Compute(Guid userId, Guid orgId)
    {
        Span<byte> buf = stackalloc byte[32];
        userId.TryWriteBytes(buf[..16]);
        orgId.TryWriteBytes(buf[16..]);
        Span<byte> hash = stackalloc byte[32];
        SHA256.HashData(buf, hash);
        return $"{Prefix}{Convert.ToHexString(hash[..4]).ToLowerInvariant()}";
    }
}
```

#### Implementation outline (AnonymiseAsync)

1. Load the User by id; if anonymised already (`AnonymisedAt != null`), return (idempotent).
2. Snapshot the user's PII fields needed downstream (email already captured by the host).
3. Open EF transaction (`db.Database.BeginTransactionAsync(ct)`).
4. **Step 4a — Find all orgs the user is attributable to**, by union over all InExport-Anonymise / Excluded-Anonymise tables that have UserAttribution columns OR whose ColumnsToAnonymise reference this user. For practical efficiency we read directly: `affectedOrgIds = union(audit_log.OrgId where ActorId=userId, schedule.OrgId where CreatedBy=userId, ...)`.
5. **Step 4b — Anonymise OrganizationAuditLogEntry rows** scoped per affected org:
   - For each `org_id` in `affectedOrgIds`:
     - `token = AnonymisationToken.Compute(userId, org_id)`
     - `await db.OrganizationAuditLog.Where(x => x.OrgId == org_id && x.ActorId == userId).ExecuteUpdateAsync(s => s.SetProperty(x => x.ActorId, _ => null).SetProperty(x => x.ActorEmail, _ => token), ct);`
6. **Step 4c — Anonymise the 6 `CreatedBy`/`UpdatedBy` columns** in CustomRole/Schedule/CoordinatorJob/TeamVault/NotificationRule:
   - Use `ExecuteUpdateAsync` on each table for rows where `CreatedBy == userId` → set to NULL.
   - TeamVault: also `UpdatedBy`.
   - `OrganizationMember.InvitedBy` for the deleted user (other members' rows where the deleted user invited them) → set to NULL.
7. **Step 4d — Hard-delete the InDeletionHard rows attributed to the user:** (NOT the User row itself)
   - `await db.RefreshTokens.Where(x => x.UserId == userId).ExecuteDeleteAsync(ct);`
   - `await db.EmailVerificationTokens.Where(x => x.UserId == userId).ExecuteDeleteAsync(ct);`
   - `await db.PasswordResetTokens.Where(x => x.UserId == userId).ExecuteDeleteAsync(ct);`
   - `await db.DeletionReauthTokens.Where(x => x.UserId == userId).ExecuteDeleteAsync(ct);`
   - `await db.OrganizationMembers.Where(x => x.UserId == userId).ExecuteDeleteAsync(ct);`
8. **Step 4e — Scrub the user row's PII:**
   - `user.Email = AnonymisationToken.Compute(userId, Guid.Empty);` (per-user token, org-less)
   - `user.PasswordHash = null;`
   - `user.IsAdmin = false;`
   - `user.EmailVerified = false;`
   - `user.PendingDeletionAt = null;`
   - `user.AnonymisedAt = clock.GetUtcNow().UtcDateTime;`
9. **Step 4f — Emit one `user.anonymised` audit row per affected org:**
   - For each `org_id` in `affectedOrgIds`:
     - `audit.Append(new AuditEvent(OrgId: org_id, ActorId: Guid.Empty, EventType: "user.anonymised", TargetType: "user", TargetId: null, Payload: new { anonymisation_token = AnonymisationToken.Compute(userId, org_id) }));`
10. `await db.SaveChangesAsync(ct);` + `await tx.CommitAsync(ct);`.

```markdown
## Anonymisation function (M18-006)

The `UserAnonymiser` concrete implementation finalises GDPR account deletions. Its
contract is **deterministic, irreversible, and per-(user, org)-scoped**.

**Token shape:** `deleted-user-{first8(sha256(user_id||org_id))}` — lowercase
hex, total length 21 chars. The same `(user_id, org_id)` pair always derives the
same token; different orgs derive different tokens; given just the token,
recovering the user_id is computationally infeasible. The `users.email` column
uses `(user_id, Guid.Empty)` as the org axis.

**What is hard-deleted:** rows in tables whose disposition is
`InExportInDeletionHard` attributed to the user (refresh_tokens,
email_verification_tokens, password_reset_tokens, deletion_reauth_tokens,
organization_members for the user).

**What is anonymised in place:** `organization_audit_log.actor_id` → NULL,
`organization_audit_log.actor_email` → per-(user, org) token; `*_by` columns on
`custom_roles`, `schedules`, `coordinator_jobs`, `team_vaults`,
`notification_rules` → NULL; `organization_members.invited_by` → NULL (for
inviter-axis on other members' rows).

**Audit-of-audit trail:** for each affected org, exactly one
`user.anonymised` audit row is emitted with `payload.anonymisation_token`
carrying the per-org token. The audit row's own `actor_id` is NULL and
`actor_email` is the token, so the audit row itself is anonymised at write-time.

**User row tombstone:** the `users` row survives with `anonymised_at` set,
`email` replaced by `deleted-user-{first8(sha256(user_id||0x00...))}`,
`password_hash` NULL, `email_verified` and `is_admin` cleared. The row is
retained for state-machine accountability; no PII remains.
```

## Risks and Edge Cases

- **Risk: Schema rename `ActorId → actor_id` breaks SQL queries that reference the column by name.** **Mitigation:** the column is only referenced via EF Core LINQ everywhere in the codebase. The migration uses `RenameColumn` (reversible). Smoke + e2e covers production-shaped queries.
- **Risk: Existing audit-log rows with `ActorId == Guid.Empty` (representing "no actor", per `AuditEvent.cs` doc) become indistinguishable from "anonymised" once we widen to nullable + introduce NULL semantics.** **Mitigation:** keep the `Guid.Empty` convention for "no actor" and use NULL only for "anonymised away". The two semantics differ. The migration does NOT mass-rewrite existing `Guid.Empty` rows to NULL.
- **Risk: `OrganizationAuditLogEntry.ActorId == Guid.Empty` is used in some existing tests as a sentinel.** **Mitigation:** grep `ActorId == Guid.Empty` and confirm no test asserts non-nullability; only the existing semantics survive.
- **Risk: `ExecuteUpdateAsync` and `ExecuteDeleteAsync` are not supported on EF Core InMemory provider.** **Mitigation:** anonymiser tests use SQLite in-memory (same pattern as `UserDeletionFinalizerHostTests`); endpoint tests use InMemory (which is fine because they only assert via `Find` which works on InMemory). The anonymiser must therefore tolerate the InMemory provider's lack of `ExecuteUpdateAsync` — but production runs against Postgres/SQLite. **Decision:** the anonymiser uses `ExecuteUpdateAsync` exclusively (no per-row tracking); endpoint tests do NOT directly call the anonymiser (they call the request endpoint which only writes `PendingDeletionAt`). Finalizer tests provide their own SQLite-based stub anonymiser already. Production wiring uses Postgres → `ExecuteUpdateAsync` works.
- **Risk: A user owns many orgs (thousands).** **Mitigation:** `affectedOrgIds` query and the per-org loop are linear in the count; for practical scale (single-digit owned orgs per user) this is fine. Documented as a known scaling limit. If a user owns >1000 orgs the anonymisation runs longer but still within the 03:00 maintenance window.
- **Risk: Two concurrent finalizer ticks process the same user.** **Mitigation:** anonymisation is idempotent — second call short-circuits on `AnonymisedAt != null`. Race is benign.
- **Risk: Pre-existing audit-log row's `ActorEmail` was set to a real email at write-time (e.g. login failures); the anonymiser overwrites with the token. Distinguishability between "anonymous user" rows (Guid.Empty ActorId from spec) and "anonymised user" rows.** **Mitigation:** by spec v4-6 we MUST overwrite the email column. Inability to distinguish post-anonymisation is the intentional irreversibility property.
- **Risk: `LastAdminProtectionService` runs on the request path → adds N+1 queries.** **Mitigation:** a single grouped query: `SELECT m.OrgId, COUNT(*) AS members, SUM(CASE WHEN role='Owner' THEN 1 ELSE 0 END) AS owners FROM organization_members WHERE OrgId IN (SELECT OrgId FROM organization_members WHERE UserId=@user AND Role='Owner') GROUP BY OrgId`. One round trip total. Join with `organizations` for slug/name in a follow-up query.
- **Edge case: User has `pending_deletion_at` set (existing pending request) and POSTs again.** **Handling:** existing `AlreadyPending` 409 fires before the last-admin check, preserving prior semantics.
- **Edge case: User cancels deletion AFTER `cascade` orgs were marked PendingDeletion in the initial request.** **Handling:** `CancelDeletion` endpoint clears `users.pending_deletion_at` only — the cascade orgs remain in `PendingDeletion`. The cancel endpoint should ALSO reverse the cascade. **Decision for this slice:** the cancel endpoint additionally clears `OrgStatus.PendingDeletion` for any orgs that were cascade-marked in the same window (identified by querying `Organizations` where the deletion was scheduled by this user within the deletion-request window). Implement via emitting an `org.deletion_canceled` audit event and resetting status. Documented in the plan; covered by a new test `POST_cancel_with_cascade_orgs_unwinds_them`.
- **Edge case: A blocking org's owner is the deleted user, but the org has only the deleted user as owner AND zero other members.** **Handling:** falls into `cascade` (not blocking). The check is "other members > 0" for blocking; otherwise cascade applies.
- **Edge case: A blocking org's owner is the deleted user, who is also the sole member.** **Handling:** falls into `cascade`. The user is the only member; no human is left behind to "block".
