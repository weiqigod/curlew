### How the existing `$faker.ssn` auto-sensitive pattern works

The task YAML pins `$faker.ssn` (`dynamic.go:474-480`) as the model.
Two cooperating pieces:

1. **Registration body** is a normal `noArgs` closure that produces
   the value (no manual `AddValue` call inside the body).
2. **Policy hook** `r.sensitiveReturn["faker.ssn"] = true` (line
   480) tells the registry the function's return value is
   auto-sensitive.
3. **Dispatch hook** in `Scope.Interpolate` (`variable.go:440-444`):
   after a successful `Evaluate`, if `IsSensitiveReturn(funcName)`
   is true and the scope has a `runtimeSensitive` set attached,
   the produced value is `AddValue`-registered as a redaction
   trigger.

This means **the registration body itself does NOT call
`r.runtimeSensitive.AddValue`** — that plumbing happens in
`variable.go` after the value is returned. Despite the task YAML
phrasing ("Each registration body must call
r.runtimeSensitive.AddValue(generated)"), the cleaner and tested
approach used by `$faker.ssn` is the indirect `sensitiveReturn`
table — and it is what we follow here. The behavior contract from
the YAML ("the registration calls SensitiveSet.AddValue with the
produced number at generation time") is satisfied: `AddValue` IS
called at evaluation time, by the Interpolate hook, immediately
after the closure returns. The verifying tests check for the
observable effect (value present in `runtimeSet.Values()` and
`[REDACTED]` in body output), not the mechanism, so this
implementation choice is invisible to the contract.

### How `$faker.price` argument parsing flows

Per M13 Open Decision #6 and the M12-001 reuse contract:

1. The placeholder `{{$faker.price('5', '50')}}` is captured by
   `dynPattern` (`variable.go:101`) — the inner-group `(.*?)`
   captures `'5', '50'` as the raw arg list.
2. `parseDynArgs("faker.price", "'5', '50'")` (`variable.go:112`)
   produces `args = []string{"5", "50"}`. Whitespace around the
   comma is ignored; both args are stripped of their enclosing
   single quotes.
3. The dispatch flows into the registry's `Evaluate` →
   `funcs["faker.price"]` closure with `args = []string{"5", "50"}`.
4. The closure validates arity (0 or 2), `strconv.ParseFloat`
   -converts each arg, validates `min <= max`, and emits a 2-decimal
   float in `[min, max]` via `float64InRange(rng) * (max-min) + min`.

Three arity branches:
- `len(args) == 0` → use `(1.0, 1000.0)` defaults per
  SPECIFICATION.md:829.
- `len(args) == 2` → parse each as float; validate range.
- `len(args) == 1` or `>= 3` → `DYNFN_ARITY` (the existing
  `arityError` helper produces `"expected 2 arguments, got N"`).
  We lift the message to "expected 0 or 2 arguments" by raising a
  custom structured error rather than calling `arityError` for the
  `1` and `>=3` cases — see Step 2.

### Currency pool design (1:1:1 parallel slices)

Per the task's behavior 5: "$faker.currencyName and
$faker.currencySymbol are evaluated independently, then each returns
the documented shape from a pool aligned 1:1:1 with currencyCode by
index". This is the same parallel-slice contract `stateNames` /
`stateAbbrs` already use. Three slices at file scope:

```go
var currencyCodes   = []string{"USD", "EUR", "GBP", "JPY", ...}
var currencyNames   = []string{"US Dollar", "Euro", "British Pound", "Japanese Yen", ...}
var currencySymbols = []string{"$", "€", "£", "¥", ...}
```

`TestFakerFinancial_CurrencyPoolAlignment` enforces
`len(currencyCodes) == len(currencyNames) == len(currencySymbols)`
and spot-checks the canonical USD/EUR/GBP/JPY entries by index.

The functions themselves call them independently with three
independent `intn(rng, len(...))` draws — i.e. a single
`{{$faker.currencyCode}}` followed by `{{$faker.currencyName}}` does
NOT necessarily produce a coherent (USD, US Dollar) pair. The 1:1:1
alignment is a future-proofing invariant for a possible "matched
triple" function (out of scope here) and a guarantee that anyone
relying on parallel-index access gets coherent data. Behavior 5 only
asserts the pool-length-equality and the by-index correspondence.

### Credit card generation (Visa-like, Luhn-valid)

Per task scope: "pick a Visa-like prefix ('4'), generate 14 random
digits, compute the Luhn check digit, append" → 16-digit total.

Algorithm:
1. Initialise `digits := []byte{'4'}` (the BIN prefix).
2. Append 14 random ASCII digit bytes via `intn(rng, 10) + '0'`.
3. Compute the Luhn check digit:
   - Walk right-to-left over the 15-digit prefix.
   - Double every other digit starting from the rightmost; sum the
     digits of any product > 9.
   - Sum all touched and untouched digits.
   - Check digit is `(10 - sum % 10) % 10`.
4. Append the check digit. Result: 16-digit string.

The Luhn helper is a small private function `luhnCheckDigit(prefix
[]byte) byte` (returns `'0'..'9'`). A separate
`isLuhnValid(s string) bool` helper supports the test (it walks
right-to-left over all 16 digits, doubles every second-from-right,
and verifies `sum % 10 == 0`).

### IBAN generation (mod-97-valid, country-length-aware)

IBAN structure (ISO 13616): `<2-letter country><2-digit checksum><BBAN>`,
total length is per-country (Germany 22, GB 22, France 27, etc.).
Algorithm:

1. Pick a country from a small pool: `{DE: 22, GB: 22, FR: 27,
   ES: 24, IT: 27, NL: 18, BE: 16, CH: 21}` (8 entries — diverse
   lengths, all alphanumeric BBAN). Stored as two parallel slices
   `ibanCountries` and `ibanLengths`.
2. Generate the BBAN: a `(totalLen - 4)`-character string of random
   uppercase alphanumerics (`A-Z0-9`) — drawn via `intn` from the
   36-char alphabet.
3. Compute the mod-97 check digits:
   - Build the rearranged string: `BBAN + country + "00"`.
   - Convert each letter to its A=10..Z=35 numeric form, producing
     a long decimal numeral.
   - Compute `numeral mod 97` using the iterative chunked algorithm
     (process 9 digits at a time to avoid `big.Int`).
   - Check digits are `98 - (numeral mod 97)`, formatted as `%02d`.
4. Final IBAN is `country + checkDigits + BBAN`.

A separate `isIBANValid(s string) bool` helper supports the test (it
runs the same rearrange-and-mod-97 over the full IBAN and checks the
result is 1). The rearrangement places the original country and
check digits at the end; if the check digits were correct,
`numeral mod 97 == 1` per the IBAN standard.

### BIC generation (no auto-sensitivity)

BIC (ISO 9362, also "SWIFT code") structure:
`<4-letter bank><2-letter country><2-alphanum location>[<3-alphanum branch>]`
— total 8 or 11 chars. Random uppercase letters + random uppercase
alphanumerics. Per behavior 9, `^[A-Z]{6}[A-Z0-9]{2}([A-Z0-9]{3})?$`
is the structural assertion. The first 6 chars (bank + country) are
always letters; the location code can be alphanumeric.

`$faker.bic` is **not** auto-sensitive (BIC identifies a bank, not
an account).

// luhnCheckDigit returns the Luhn checksum digit (ASCII '0'..'9')
// for the digits-only prefix. The prefix must be all ASCII digits;
// caller's contract (the only call site is the credit-card
// generator that builds prefix from intn(rng, 10) + '0').
//
// Algorithm: walk right-to-left over the prefix, doubling every
// other digit (starting with the rightmost — which becomes
// position 1 from the right of the final number, so it is NOT
// doubled when the check digit is appended; the doubling-from-right
// pattern starts at position 2). The check digit is chosen so the
// total sum (including the check digit at position 1) is divisible
// by 10.
func luhnCheckDigit(prefix []byte) byte {
    sum := 0
    // After we append the check digit, prefix[i] sits at position
    // (len(prefix) - i + 1) from the right. We double when that
    // position is even, i.e. when (len(prefix) - i) is odd.
    n := len(prefix)
    for i := 0; i < n; i++ {
        d := int(prefix[i] - '0')
        if (n-i)%2 == 1 {
            d *= 2
            if d > 9 {
                d -= 9
            }
        }
        sum += d
    }
    return byte((10 - sum%10) % 10) + '0'
}

// isLuhnValid reports whether s is a non-empty digit-only string
// that satisfies the Luhn checksum (sum of doubled-and-folded
// digits divisible by 10). Used by TestRegistry_FakerFinancial to
// validate generated card numbers; also exported within-package
// for any future card-validation helpers.
func isLuhnValid(s string) bool {
    if s == "" {
        return false
    }
    sum := 0
    n := len(s)
    for i := 0; i < n; i++ {
        c := s[i]
        if c < '0' || c > '9' {
            return false
        }
        d := int(c - '0')
        if (n-i)%2 == 0 {
            d *= 2
            if d > 9 {
                d -= 9
            }
        }
        sum += d
    }
    return sum%10 == 0
}

// ibanCheckDigits computes the two ISO 13616 check digits for an
// IBAN with the given country code and BBAN. The result is a
// zero-padded two-digit string in "00".."98".
//
// Algorithm (per ISO 13616-1):
//   1. Rearrange: bban + country + "00"
//   2. Convert letters to numbers: A=10, B=11, ..., Z=35
//   3. Treat the result as one large decimal numeral; compute
//      numeral mod 97 via the iterative chunked algorithm
//      (process digits left-to-right, 9 at a time, to stay within
//      int64 precision — no big.Int dependency).
//   4. Check digits = 98 - (numeral mod 97).
func ibanCheckDigits(country, bban string) string {
    var b strings.Builder
    b.Grow(len(bban) + len(country) + 2)
    b.WriteString(bban)
    b.WriteString(country)
    b.WriteString("00")
    rearranged := b.String()

    // Stream through, replacing letters with their two-digit numeric
    // form, and computing mod 97 as we go using int math.
    var rem int64
    flush := func(digits string) {
        for i := 0; i < len(digits); i++ {
            rem = (rem*10 + int64(digits[i]-'0')) % 97
        }
    }
    for i := 0; i < len(rearranged); i++ {
        c := rearranged[i]
        if c >= '0' && c <= '9' {
            rem = (rem*10 + int64(c-'0')) % 97
        } else if c >= 'A' && c <= 'Z' {
            // Two-digit numeric form.
            v := int(c-'A') + 10
            flush(strconv.Itoa(v))
        }
        // (Other characters never appear — caller's contract.)
    }
    check := 98 - int(rem)
    return fmt.Sprintf("%02d", check)
}

// isIBANValid reports whether s is a structurally valid IBAN whose
// mod-97 checksum is 1 (the ISO 13616 validity criterion).
// Length is not asserted against any country-specific table — only
// the generic shape (ASCII letters + digits, length >= 5) and the
// mod-97 result.
func isIBANValid(s string) bool {
    if len(s) < 5 {
        return false
    }
    // Move the first 4 characters to the end (country code + check digits).
    rearranged := s[4:] + s[:4]
    var rem int64
    for i := 0; i < len(rearranged); i++ {
        c := rearranged[i]
        if c >= '0' && c <= '9' {
            rem = (rem*10 + int64(c-'0')) % 97
        } else if c >= 'A' && c <= 'Z' {
            v := int(c-'A') + 10
            // Two-digit form.
            rem = (rem*10 + int64(v/10)) % 97
            rem = (rem*10 + int64(v%10)) % 97
        } else {
            return false
        }
    }
    return rem == 1
}

// TestFakerFinancial_CurrencyPoolAlignment proves the parallel-slice
// invariant for currency pools (behavior 5 prerequisite). Catches
// index-skew regressions where someone reorders one slice but forgets
// the others.
func TestFakerFinancial_CurrencyPoolAlignment(t *testing.T) {
    if len(currencyCodes) != len(currencyNames) ||
        len(currencyNames) != len(currencySymbols) {
        t.Fatalf("currency pools length mismatch: codes=%d names=%d symbols=%d",
            len(currencyCodes), len(currencyNames), len(currencySymbols))
    }
    if len(currencyCodes) == 0 {
        t.Fatal("currency pools are empty")
    }
    // Spot-check canonical pairings.
    cases := []struct {
        idx                  int
        code, name, symbol   string
    }{
        {0, "USD", "US Dollar", "$"},
        {1, "EUR", "Euro", "€"},
        {2, "GBP", "British Pound", "£"},
        {3, "JPY", "Japanese Yen", "¥"},

    for _, c := range cases {
        if currencyCodes[c.idx] != c.code ||
            currencyNames[c.idx] != c.name ||

    }
}

// TestLuhnCheckDigit_KnownVectors validates the Luhn helper against
// well-known test card numbers (Visa "4111111111111111" is canonical).
func TestLuhnCheckDigit_KnownVectors(t *testing.T) {
    valid := []string{
        "4111111111111111", // canonical Visa test
        "5555555555554444", // canonical Mastercard test
        "378282246310005",  // canonical Amex test (15 digits)
    }
    for _, s := range valid {
        if !isLuhnValid(s) {
            t.Errorf("isLuhnValid(%q) = false, want true", s)
        }
    }
    invalid := []string{
        "4111111111111112",
        "1234567890123456",
        "0000000000000001",
    }
    for _, s := range invalid {
        if isLuhnValid(s) {
            t.Errorf("isLuhnValid(%q) = true, want false", s)
        }
    }
    // Round-trip: building "4" + 14 zeros + check digit produces a
    // valid Luhn number.
    prefix := []byte("400000000000000")
    cd := luhnCheckDigit(prefix)
    full := string(prefix) + string(cd)
    if !isLuhnValid(full) {
        t.Errorf("luhnCheckDigit round-trip failed for %q (built %q)",
            string(prefix), full)
    }
}

                    Hint:     "Pass two single-quoted decimal strings, e.g. {{$faker.price('5', '50')}}.",
                    Inner:    err,
                }

    // redaction trigger via the IsSensitiveReturn hook.

        prefix := append([]byte{'4'}, randomDigits(rng, 14)...)
        return string(append(prefix, luhnCheckDigit(prefix)))

        n := 3
        if intn(rng, 2) == 1 {
            n = 4
        }
        return string(randomDigits(rng, n))
    })
    r.sensitiveReturn["faker.creditCardCVV"] = true

    // check digits. AUTO-SENSITIVE.
    r.funcs["faker.iban"] = noArgs("faker.iban", func(rng *rand.Rand) string {
        idx := intn(rng, len(ibanCountries))
        country := ibanCountries[idx]
        totalLen := ibanLengths[idx]
        bbanLen := totalLen - 4
        bban := make([]byte, bbanLen)
        for i := 0; i < bbanLen; i++ {
            bban[i] = ibanBBANChars[intn(rng, len(ibanBBANChars))]
        }
        bbanStr := string(bban)
        return country + ibanCheckDigits(country, bbanStr) + bbanStr
    })
    r.sensitiveReturn["faker.iban"] = true

    // $faker.bic — 6 uppercase letters (bank+country) + 2 alphanum
    // (location) + optional 3 alphanum (branch). NOT auto-sensitive
    // — BIC identifies a bank, not an account (per
    // SPECIFICATION.md:849-857).
    r.funcs["faker.bic"] = noArgs("faker.bic", func(rng *rand.Rand) string {
        const upper = "ABCDEFGHIJKLMNOPQRSTUVWXYZ"
        var b strings.Builder
        b.Grow(11)
        for i := 0; i < 6; i++ {
            b.WriteByte(upper[intn(rng, len(upper))])
        }
        for i := 0; i < 2; i++ {
            b.WriteByte(ibanBBANChars[intn(rng, len(ibanBBANChars))])
        }
        // 50/50 between 8-char and 11-char BIC.
        if intn(rng, 2) == 1 {
            for i := 0; i < 3; i++ {
                b.WriteByte(ibanBBANChars[intn(rng, len(ibanBBANChars))])
            }
        }
        return b.String()
    })
}

// randomDigits returns n ASCII-digit bytes (each '0'..'9') drawn via
// intn. Caller must pass n >= 1; the function trusts its input. Used
// by the credit-card and CVV generators.
func randomDigits(rng *rand.Rand, n int) []byte {
    out := make([]byte, n)
    for i := 0; i < n; i++ {
        out[i] = byte(intn(rng, 10)) + '0'
    }
    return out
}

## Risks and Edge Cases

- **Risk: `parseDynArgs` accidentally modified.** Definition_of_done
  forbids any change to `internal/variable/variable.go`'s
  `parseDynArgs`. **Mitigation:** Steps 1 + 2 modify only
  `dynamic.go` and test files; the `parseDynArgs` function and
  `dynPattern` regex stay untouched. Verified by code review and
  CI test pass.
- **Risk: IBAN mod-97 numeric overflow in int64.** A naive
  implementation would build the full numeric string (~30+ digits)
  before computing mod-97 — that overflows int64. **Mitigation:**
  the implementation processes the rearranged string left-to-right,
  one character at a time, applying `rem = (rem*10 + digit) % 97`
  after each digit — staying well within int64 (max value of
  `rem*10 + 9 < 1000` per iteration). The
  `TestIBANCheckDigits_KnownVectors` test exercises a 28-character
  IBAN (FR) which would overflow naive math.
- **Risk: Luhn check digit algorithm subtleties.** The doubling
  pattern is "double every second digit from the right", but
  whether the rightmost-after-appending-the-check-digit is included
  depends on parity. **Mitigation:** the helper is tested against
  three canonical industry test cards (Visa, Mastercard, Amex) and
  a round-trip test that builds a number with `luhnCheckDigit` and
  immediately validates it with `isLuhnValid`. Both helpers must
  agree, ruling out off-by-one errors.
- **Risk: $faker.creditCard generates a value that, by chance,
  matches a real credit card number.** **Mitigation:** the
  generated number is auto-sensitive — it is automatically redacted
  in body output, so even if it accidentally matched a real card
  it would not be displayed. The Visa-like prefix '4' plus 14
  random digits gives a 1-in-10^14 chance of hitting any specific
  number; this is no different from any test data generator.
- **Risk: $faker.price seeded-determinism breaks under default vs
  args path.** The default branch and the args branch both call
  `float64InRange(rng)` once per evaluation, so seeded RNG state
  consumption is symmetric. **Mitigation:** the
  `TestRegistry_FakerFinancial_Seeded` test exercises both
  `(args=nil)` and `(args=['5','50'])` paths under the same seed
  and asserts byte-equality across two independent registries.
- **Risk: shared currency pool drift breaks 1:1:1 alignment.** A
  contributor adding a currency to `currencyCodes` but forgetting
  the matching entries in `currencyNames` and `currencySymbols`
  would silently produce mismatched data. **Mitigation:**
  `TestFakerFinancial_CurrencyPoolAlignment` enforces the
  length-equality invariant and spot-checks canonical pairings
  (USD/Euro/GBP/JPY).
- **Risk: $faker.iban country pool drift.** Adding a country to
  `ibanCountries` without the matching length in `ibanLengths` (or
  with a wrong length) would generate invalid IBANs.
  **Mitigation:** `TestFakerFinancial_IBANCountriesAlignment`
  enforces length equality and per-country-length validity (each in
  `[15, 34]` per ISO 13616). The
  `TestRegistry_FakerFinancial`'s `iban` case validates every
  generated IBAN against `isIBANValid`.
- **Risk: per-request memoization makes auto-sensitive functions
  produce the same value within a request.** `Registry.Evaluate`
  caches results per (name, args) within a request — two
  `{{$faker.creditCard}}` placeholders in the same request resolve
  to the same number. **Mitigation:** this is documented behaviour
  (MANUAL.md memoization rules) and is the property we want for
  reproducibility. It does not undermine redaction — the cached
  value is still added to `runtimeSensitive` once, and that one
  entry triggers redaction wherever it appears.
- **Risk: auto-sensitive value AddValue happens AFTER the value is
  already substituted into the surrounding string.** The
  `IsSensitiveReturn` hook in `Scope.Interpolate` calls `AddValue`
  immediately after `Evaluate` returns; the substituted string is
  built up using `ReplaceAllStringFunc`. Importantly, the final
  redaction pass happens later (in the runner / output sinks) over
  the **already-substituted** string + the populated
  `runtimeSensitive` set — so the order is correct and fully
  asserted by `TestRegistry_FakerSSN_Sensitive` (the existing
  M13-002 test) and the new
  `TestRegistry_FakerFinancial_AutoSensitive`.
- **Risk: BIC validation strictness.** A real BIC's first 4 chars
  must be the bank code (any uppercase letters), the next 2 must
  be a valid ISO 3166-1 alpha-2 country code, and the optional
  branch is "XXX" for the head office. Per task scope ("Not in
  scope: BIC validation against a registry"), we only assert the
  structural shape — `^[A-Z]{6}[A-Z0-9]{2}([A-Z0-9]{3})?$` — not
  semantic validity. The BIC generator emits a random sequence
  matching this regex; the test asserts the same.
- **Edge case: `$faker.price('5.5', '5.5')`.** min == max (not >);
  the implementation accepts this (no inverted-range error) and
  returns `5.50` deterministically. The behavior YAML uses "min <=
  max" wording, so this is the documented behaviour.
- **Edge case: `$faker.price('-5', '5')`.** Negative min is
  accepted; the result is a 2-decimal float in `[-5.00, 5.00]`. The
  spec does not forbid negative prices; we don't add a guard.
  `TestRegistry_FakerFinancial` does not exercise this case
  explicitly but `TestRegistry_FakerFinancial_PriceArgs` would
  cover it if a future test added it.
- **Edge case: `$faker.creditCard` first digit is '4' (Visa BIN).**
  Per task scope: "pick a Visa-like prefix ('4')". Spec-aligned;
  the test asserts shape (`^\d{16}$`) and Luhn validity, not
  brand. Future enhancements could rotate brands.
- **Edge case: empty arg via `{{$faker.price('','50')}}`.**
  `parseDynArgs` returns `args = []string{"", "50"}`;
  `strconv.ParseFloat("", 64)` fails; we return
  `DYNFN_FAKER_PRICE_BAD_INPUT`.
  `TestRegistry_FakerFinancial_PriceBadInput` includes the empty
  string case.
