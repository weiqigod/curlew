## Architectural Decisions

The task observable references several capabilities the codebase does not actually expose end-to-end yet. Documented decisions (no clarifying questions per pipeline mode):

1. **No `/auth/register` page exists.** The web app ships `/auth/password-reset/*` and `/auth/email-verification/*` but no registration page or `POST /api/v1/auth/register` endpoint. Per Open Decision 9 (happy-path only, "the scenario does not assert on individual cluster failure modes — it only proves the parts wire together"), and following the precedent set by M14-021 which uses `POST /internal/test/seed-refresh` to side-step a real login flow, this plan uses `seed-refresh` as the "register" step. `seed-refresh` already (a) upserts the user with `EmailVerified=false`, (b) invokes `TrialSeederService.SeedFullInitialAsync` (which creates `kind=full_initial` trial rows — exactly what real registration would produce), and (c) returns a refresh token. The behavior assertion "rows per feature appear in trials with kind=full_initial" is satisfied by this existing path.

2. **No real Stripe checkout flow.** Open Decision 9 forbids asserting on Stripe webhook handling failure modes. Tier-upgrade is performed via the existing `POST /internal/test/seed-m14` endpoint (which idempotently sets `subscription.Tier = Team`). This is the same pattern M14-021 uses and mirrors the convergence-spec contract.

3. **No `sendgrid-fake` sidecar service.** The task scope mentions "a sendgrid-fake assertion harness that confirms the `password_reset` and `trial_expiring` emails arrive". The backend already has this capability: `IRecentlySentEmailLog` + `GET /internal/test/email-audit` was built for M14-021 for exactly this purpose. No new docker service is needed.

4. **Email queue processor must run in fake-SendGrid mode.** `Program.cs:467` currently gates `EmailQueueProcessor` registration on `sendGridMode == "live"`. With the default `"fake"` mode used by the docker stack, enqueued emails sit in `ChannelEmailQueue` forever and never reach `IRecentlySentEmailLog`. This means assertions like `waitForEmailAuditEntry('billing_receipt', ...)` cannot pass against the docker stack as-shipped. The fix: change the gate so the processor runs whenever the audit log is present (Dev+Testing), which is exactly when `NoopSmtpSender` is wired — calling `NoopSmtpSender.SendTemplateAsync` succeeds, which causes `EmailQueueProcessor` to record into the audit log. This is a tiny, isolated change and a prerequisite for both M14-021 and this task to function against the docker stack.

5. **TrialExpiryNotifier needs a way to force a tick from the e2e script.** The hosted service is registered with `RunAtUtc=09:00` by default and only fires once per day; tests use `RunAtUtc=now` plus direct `TickOnceAsync` calls. From the e2e script we need a one-shot trigger. Approach: add a new `POST /internal/test/trial-expiry-tick` Dev+Testing-only endpoint that resolves the registered `TrialExpiryNotifier` from DI and invokes `TickOnceAsync(new TrialExpiryNotifierOptions { RunAtUtc = "now", BatchSize = 100 }, ct)`. (Side note: `TickOnceAsync` is currently `internal` to its assembly — accessible from `ApiTool.Backend` itself, so the new endpoint can call it directly without a visibility change.)

6. **Seeding a near-expiry trial.** The `trials` table has no exposed PUT/PATCH endpoint. Add a new `POST /internal/test/seed-near-expiry-trial` Dev+Testing-only endpoint that inserts a `kind=full_initial` row with `expires_at = now + 2 days` (inside the 3-day window) for a given `user_id` and `feature`, setting `notified_3day_at = null`. This is the smallest surface that lets the e2e script drive the assertion "trial_expiring email is queued after TrialExpiryNotifier ticks".

7. **No `psql`.** The docker stack uses SQLite (per `Program.cs:71`), so the observable's mention of `psql` is replaced with `curl` against existing REST endpoints. Specifically: `GET /api/v1/organizations/{orgId}/results/stats?window=30d` for the dashboard cross-cluster invariant, `GET /api/v1/organizations/{orgId}/schedules/{name}/runs` for the `scheduled_runs` transition check, and `GET /internal/test/email-audit` for the email assertions.

8. **`scripts/m16-e2e.sh` orchestrates; Playwright spec drives web interactions.** Per task scope: the Playwright spec navigates the dashboard, the password-reset web pages, and the email-verification flow; the shell script orchestrates CLI invocations (`apitest worker --schedule-pull --once`, `apitest license trial start`) and back-end state queries via `curl`. The Playwright spec is invoked from the shell script with `npx playwright test`. Final summary line is printed by the shell script: `M16 e2e PASS in <duration>s`.

```csharp
// InternalTrialTickEndpoint.cs
public static class InternalTrialTickEndpoint
{
    public static IEndpointRouteBuilder MapInternalTrialTickEndpoint(
        this IEndpointRouteBuilder app, IWebHostEnvironment env)
    {
        if (!env.IsDevelopment() && !env.IsEnvironment("Testing")) return app;

        app.MapPost("/internal/test/trial-expiry-tick", async (
            IServiceProvider services, CancellationToken ct) =>
        {
            // The hosted service instance is registered via AddHostedService; resolve it.
            var notifier = services.GetServices<IHostedService>()
                .OfType<TrialExpiryNotifier>()
                .FirstOrDefault();
            if (notifier is null)
                return Results.StatusCode(StatusCodes.Status503ServiceUnavailable);

            var opts = new TrialExpiryNotifierOptions { RunAtUtc = "now", BatchSize = 500 };
            await notifier.TickOnceAsync(opts, ct);
            return Results.Ok(new { ticked = true });
        })
        .AllowAnonymous()
        .DisableAntiforgery()
        .AddEndpointFilter<InternalAccessFilter>()
        .WithName("InternalTrialExpiryTick")
        .WithTags("Internal");

        return app;
    }
}
```

```csharp
// InternalSeedNearExpiryTrialEndpoint.cs
internal sealed record SeedNearExpiryTrialRequest(
    Guid UserId, string Feature, int DaysUntilExpiry = 2);

public static class InternalSeedNearExpiryTrialEndpoint
{
    public static IEndpointRouteBuilder MapInternalSeedNearExpiryTrialEndpoint(
        this IEndpointRouteBuilder app, IWebHostEnvironment env)
    {
        if (!env.IsDevelopment() && !env.IsEnvironment("Testing")) return app;

        app.MapPost("/internal/test/seed-near-expiry-trial", async (
            SeedNearExpiryTrialRequest? body, AppDbContext db, TimeProvider clock,
            CancellationToken ct) =>
        {
            if (body is null || body.UserId == Guid.Empty || string.IsNullOrWhiteSpace(body.Feature))
                return Results.BadRequest("user_id and feature are required");

            var now = clock.GetUtcNow().UtcDateTime;
            // Idempotent: delete any existing row for (user, feature) first to allow re-seeding.
            var existing = await db.Trials.Where(
                t => t.UserId == body.UserId && t.Feature == body.Feature).ToListAsync(ct);
            db.Trials.RemoveRange(existing);

            var trial = new Trial
            {
                Id = Guid.NewGuid(),
                UserId = body.UserId,
                Feature = body.Feature,
                Kind = TrialKind.FullInitial,
                GrantedAt = now.AddDays(-12),
                ExpiresAt = now.AddDays(body.DaysUntilExpiry),
                Notified3DayAt = null,
                Notified1DayAt = null,
                ConsumedAt = null,
                CreatedAt = now,
                UpdatedAt = now,
            };
            db.Trials.Add(trial);
            await db.SaveChangesAsync(ct);

            return Results.Ok(new { trial_id = trial.Id, expires_at = trial.ExpiresAt });
        })
        .AllowAnonymous()
        .DisableAntiforgery()
        .AddEndpointFilter<InternalAccessFilter>()
        .WithName("InternalSeedNearExpiryTrial")
        .WithTags("Internal");

        return app;
    }
}
```

## Risks and Edge Cases

- **Risk:** TrialExpiryNotifier's `TickOnceAsync` is `internal` to the `ApiTool.Backend` assembly. → **Mitigation:** The internal endpoint lives in `ApiTool.Backend` itself, so visibility is fine. No `InternalsVisibleTo` needed.

- **Risk:** Resolving the `TrialExpiryNotifier` singleton from `IServiceProvider.GetServices<IHostedService>()` returns it only because it was registered via `AddHostedService`. In tests this works the same way. → **Mitigation:** Test the resolution path explicitly in the new endpoint tests.

- **Risk:** The `EmailQueueProcessor` registration change opens a previously-dormant code path in Development. NoopSmtpSender doesn't throw, but if a template variable allowlist is violated, the processor dead-letters via `LoggingEmailDeadLetterStore` — quiet logging only. → **Mitigation:** All templates used in this scenario (`password_reset`, `trial_expiring`, `email_verification`, `billing_receipt`) are already covered by manifest-allowlist tests.

- **Risk:** SQLite WAL contention between the worker writing scheduled_runs heartbeats and the dashboard query reading them. → **Mitigation:** None — SQLite serializes writes; reads are non-blocking with WAL. The 1-second poll interval the script uses is well below any contention threshold.

- **Risk:** The script's "register a new user" step uses a per-run unique email (`m16-e2e-$(date +%s)@example.com`). The org is shared (`acme`) — adding the new user as an owner of `acme` would be wrong. → **Mitigation:** Create a per-run org slug `m16-e2e-$RANDOM` and add the user as its owner via existing endpoints, so re-runs don't pile up rows under `acme`. The existing seed pattern in `seed-test-data.sh` shows the idempotent create-or-fetch flow.

- **Edge case:** The schedule's cron is `0 9 * * *` (daily 09:00 UTC); the script must use `run-now` rather than wait for cron. → **Handling:** `POST /api/v1/organizations/{orgId}/schedules/{name}/run-now` is used directly.

- **Edge case:** The CLI `apitest license trial start <feature>` requires a cached refresh token in `~/.config/apitesttool/`. → **Handling:** Set `APITESTTOOL_CONFIG_DIR=$(mktemp -d)` and pre-seed `license.json` + `device.json` + the refresh-token entry, mirroring `worker_schedule_test.go:184-193`. Or, do the same via `apitest login` against an internal helper. Simplest: write the files directly from the shell using the response of `seed-refresh` + the License JWT from `/api/v1/auth/refresh`.

- **Edge case:** Wall-clock budget (< 5 min DoD). → **Handling:** `ci-local.sh --full` already takes the majority of that time on the developer laptop; the new orchestration script should run in ~30-60 seconds.
