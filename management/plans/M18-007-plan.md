# Implementation Plan: M18-007

## Overview
Deliver the backend half of the Telemetry Phase 3 pipeline: an anonymous, idempotency-keyed
`POST /api/v1/telemetry/events` endpoint (64KB cap, per-`install_id` 60/min rate limit),
two new tables (`telemetry_events`, `telemetry_daily_aggregates`), a daily
`TelemetryAggregatorHost`, a 90-day `TelemetryPurgeHost`, and two Dev/Testing-only test
hooks. Locks the wire contract that M18-008 (CLI emitter) will implement against.

## Architectural Decisions

The Plan agent was not invoked because the surface is well-bounded and every reused
pattern already exists in the codebase. The decisions below resolve open questions in
pipeline mode rather than blocking on confirmation.

1. **`event_payload` storage:** `jsonb` on Postgres, `TEXT` on SQLite — mirrors the
   `GithubWebhookEvent.PayloadJson` pattern at AppDbContext.cs:476-498. We store the raw
   JSON the CLI sent; we do not project payload fields into columns. The aggregator reads
   payload via `jsonb_path_query` on Postgres and `json_extract` on SQLite, gated by
   `Database.IsNpgsql()`.

2. **Idempotency strategy:** `idempotency_key` is a non-nullable `varchar(64)` with a
   `UNIQUE` index. The endpoint inserts via `db.SaveChangesAsync`; a `DbUpdateException`
   wrapping a unique-constraint violation is caught and converted to a 202 no-op. This
   mirrors the Stripe webhook insert-then-handle-collision pattern.

3. **64KB body cap:** Enforce **before** model binding via the endpoint route's
   `app.MapPost(..., handler).Add(b => b.Metadata.Add(new RequestSizeLimitAttribute(65536)))`
   and a defensive read of `context.Request.ContentLength` returning 413 early. Reading the
   body manually (like StripeWebhookEndpoint) lets us return 413 before deserializing.

4. **Rate limiting:** Add a new ASP.NET Core `RateLimiter` policy `telemetry-ingest`
   partitioned by `install_id` (60/min). Register in `Program.cs:582`'s `AddRateLimiter`
   block alongside the existing policies. The Testing-environment no-op block already
   reflects this pattern — extend it with `"telemetry-ingest"`.

5. **`install_id` as partition key:** Per the rate-limit policy spec we need the
   `install_id` available at policy time. The cleanest approach is to peek the body once
   in a small `IEndpointFilter` (`TelemetryIngestRequestFilter`) that buffers the body,
   parses install_id, sticks it onto `HttpContext.Items["telemetry.install_id"]`, then
   the policy reads it. Body buffering is enabled via `context.Request.EnableBuffering()`
   so the endpoint handler can re-read. This avoids reading the body twice in user code.

6. **Aggregator schema:** `telemetry_daily_aggregates` columns:
   - `day` (`date`)
   - `event_type` (`varchar(64)`)
   - `event_count` (`bigint`)
   - `distinct_install_count` (`bigint`)
   - `numeric_sums_json` (`jsonb`/text) — sum/min/max/avg of common numeric payload fields
     (e.g. `duration_ms`, `collection_size`) discovered by scanning the day's rows. The
     stored JSON shape: `{ "duration_ms": {"sum": 12345, "min": 1, "max": 999, "avg": 41.2, "n": 300}, ... }`.
   - Composite PK `(day, event_type)`.

7. **Aggregator scheduling:** Daily at 04:00 UTC per task YAML. Reuse the
   `BackgroundService` with an `ExecuteAsync` loop that computes the delay to the next
   04:00 UTC and sleeps until then — same shape as
   `UserDeletionFinalizerHost.ExecuteAsync` (03:00 UTC). The host re-runs idempotently:
   each tick processes any complete UTC day that has no aggregate row yet, so a missed
   tick catches up next run. Already-aggregated days are skipped via the `(day, event_type)`
   PK guard.

8. **Purge host:** A second `BackgroundService` (`TelemetryPurgeHost`) ticks daily and
   `ExecuteDeleteAsync`s `telemetry_events` where `received_at < now - 90d`. Could fold
   into the aggregator, but separating keeps each host single-responsibility and lets
   the two test hooks be triggered independently.

9. **OpenAPI:** Annotate the endpoint with `Produces(202)`, `ProducesProblem(413)`,
   `ProducesProblem(429)`, document the `Idempotency-Key` header via
   `Microsoft.OpenApi.Models.OpenApiParameter`. Existing pattern: see
   `AuditLogSwaggerSurfaceTests` and `SubscriptionsSwaggerSurfaceTests`.

10. **Forward-compat for unknown `event_type`:** No allow-list. Behavior 8 explicitly
    asks us to accept future event types. The endpoint validates only the JSON
    structure: `install_id` is a UUID, `event_type` is a non-empty string ≤ 64 chars,
    `event_payload` is a JSON object.

11. **Spec edit:** The task DoD requires "Wire-shape contract recorded in
    docs/SPECIFICATION.md so M18-008 can implement against a stable surface." Add a new
    `## Telemetry Phase 3 Implementation Pipeline` section to `docs/SPECIFICATION.md`
    documenting the wire shape, idempotency contract, rate-limit policy, retention, and
    aggregator schema. The M18 changelog at line 16 already names this section.

12. **`:6604` retention reference:** Spec line 6604 reads "Telemetry data … 2 years" in
    the policy table; line 6616 reads "Archive telemetry data older than 90 days to cold
    storage." The task YAML is explicit ("hard-deleted") so we implement 90-day hard
    delete of **raw events** (the daily aggregates persist), and the new spec section
    will spell out the asymmetry. This is the only interpretation that satisfies both
    the task YAML and the privacy posture (raw events are the high-detail surface).

## Risks and Edge Cases

- **Risk:** Body buffering doubles memory pressure. → **Mitigation:** 64KB cap is the
  buffer cap; reads beyond return 413 before allocation; `EnableBuffering(bufferThreshold:
  65536, bufferLimit: 65536)`.
- **Risk:** Rate-limit policy partitioner cannot see body-derived install_id because
  endpoint filters run *after* the rate limiter middleware. → **Mitigation:** Move the
  body-buffering pre-read into a small middleware registered before `UseRateLimiter()`,
  scoped only to `POST /api/v1/telemetry/events`. Pattern: inspect
  `HttpContext.GetEndpoint()?.Metadata.GetMetadata<RouteNameMetadata>()` or check the
  path prefix.
- **Risk:** Unique-constraint exception varies by provider. → **Mitigation:** Catch
  `DbUpdateException` and inspect inner exception type for `SqliteException.SqliteErrorCode
  == 19` (SQLITE_CONSTRAINT) and `PostgresException.SqlState == "23505"`. Cover both
  in tests.
- **Risk:** Aggregator double-counts on re-runs. → **Mitigation:** Composite PK
  `(day, event_type)` rejects duplicates; the host wraps each day in `INSERT ... ON
  CONFLICT DO NOTHING` (Postgres) / `INSERT OR IGNORE` (SQLite) — provider-conditional.
- **Risk:** Numeric-field aggregation explodes when payloads contain unbounded keys. →
  **Mitigation:** Aggregate only a whitelist of known numeric keys
  (`duration_ms`, `collection_size`, `request_count`, `failure_count`,
  `success_count`); list lives in `TelemetryAggregatorHost` constants and the spec
  section names it. Forward-compat: unknown numeric keys are ignored, not failing.
- **Risk:** `TimeProvider` injection inconsistency. → **Mitigation:** Tests inject
  `FakeClock` (already in TestInfrastructure) so 04:00 scheduling is deterministic.
- **Edge case:** Empty `event_payload`. → **Handling:** Accept `{}`; aggregator gracefully
  skips numeric-key extraction.
- **Edge case:** `event_type` containing path-separator characters. → **Handling:**
  Stored verbatim; column is varchar(64); validator rejects anything outside `[A-Za-z0-9._-]`.
- **Edge case:** Clock skew between CLI and backend pushing events with future
  timestamps. → **Handling:** Backend stamps `received_at` server-side; CLI-supplied
  timestamp lives in `event_payload`.
