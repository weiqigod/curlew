# Implementation Plan: M16-015

## Overview

Adds the inbound `POST /webhooks/gitlab` endpoint with `X-Gitlab-Token` constant-time verification against each `gitlab_installations.webhook_secret_ciphertext` (decrypted via `IGitLabKeyProvider`), `X-Gitlab-Event-UUID` idempotency on `gitlab_webhook_events`, two quarantine surfaces (per-row dispatcher-failure → schema's `failure_count`/`quarantined_at`; in-memory per-source-IP verification-failure → HTTP 429), a `Pipeline Hook` dispatcher that reconciles status into `pr_checks` (lookup by `gitlab_status_id`), pass-through storage for `Push Hook` and `Merge Request Hook` (no business logic per spec :9263), and a daily retention pruning hosted service that mirrors `GithubWebhookCleanupHost`. Single-secret-per-installation only — multi-secret rotation via `GITLAB__WEBHOOK_SECRETS_<installation_id>` is a documented follow-up (Open Decision 3).

## Key Architectural Decisions (resolved up-front)

These resolve under-specified parts of the task YAML so the implementation steps are mechanical. Each decision is anchored to docs/SPECIFICATION.md or to a precedent in the GitHub side (M14-019) so cross-provider consistency is preserved.

### Decision A — Verification flow: iterate `gitlab_installations` rows, constant-time compare against each decrypted secret

GitHub's HMAC verifier reuses a single byte buffer for the computed digest across N secrets in a comma-separated env var. GitLab is fundamentally different: the secret lives *per installation* in `gitlab_installations.webhook_secret_ciphertext` (encrypted via `IGitLabKeyProvider`). The handler therefore cannot pre-load the secret list. It must:

1. Read the raw `X-Gitlab-Token` header value (the secret itself — no HMAC).
2. Query `gitlab_installations` for all rows where `webhook_secret_ciphertext IS NOT NULL AND deleted_at IS NULL`.
3. For each row, decrypt the ciphertext via `IGitLabKeyProvider.DecryptAsync(...)` and compare to the header value using `CryptographicOperations.FixedTimeEquals(...)`.
4. On the *first* match, the request is authenticated to that installation.
5. If no row matches, return 401.

Because the comparison itself is constant-time per-row but the *iteration* leaks information (a request matching the first row returns faster than one matching the last), we order rows by `created_at ASC` and always iterate every row before emitting a result (no short-circuit on match). The expected installation count per backend is small (single-digit to dozens), so the cost is acceptable. Spec :9257 ("constant-time compared against `webhook_secret_ciphertext`") is satisfied by `FixedTimeEquals` plus full-iteration.

**Why not a per-org dispatch hint?** GitLab does not include an installation identifier in the request headers — only the token. Without iterating, we cannot know which installation sent the event. (GitHub's `X-GitHub-Hook-Installation-Target-ID` provides this directly; GitLab does not have an equivalent.)

### Decision B — Per-event quarantine via `failure_count`/`quarantined_at` matches the schema and mirrors GitHub

The schema (entity `GitLabWebhookEvent` in M16-013) carries `FailureCount INT NOT NULL DEFAULT 0` and `QuarantinedAt DateTime?` columns. The semantics map cleanly onto the GitHub side: dispatcher throws → increment `failure_count`, set `last_error` (not in schema — we omit, log via structured log instead), and when `failure_count >= 5` set `quarantined_at = now` and `status` (in-row sense) → return 200 to break GitLab's retry storm. Subsequent retries of the same `event_uuid` return 200 immediately (the existing idempotency path).

### Decision C — Per-source-IP verification quarantine is an in-memory tracker (singleton), not a new DB table

The YAML behaviour reads: *"5 consecutive verification failures from the same source IP / installation, when the next request arrives, then it is quarantined (HTTP 429 + a quarantined_at timestamp) until manual reset."* The schema has no `webhook_verification_failures` table and the spec does not define one. We resolve this as follows:

- A new `GitLabWebhookSourceTracker` singleton holds `IDictionary<string, SourceState>` keyed on source IP (per-installation isn't possible until verification succeeds — see Decision A).
- `SourceState` is `(int Failures, DateTime? QuarantinedAt)`. After 5 consecutive verification failures, `QuarantinedAt` is set. While `QuarantinedAt` is non-null, *every* request from that IP returns HTTP 429 *before* signature verification.
- Successful verification resets `Failures` to 0 (but does not clear `QuarantinedAt` — the quarantine must be cleared explicitly via a future admin endpoint, not specified in this slice; documented as a TODO).
- The tracker is in-memory (process-local); state is lost on restart. This is acceptable for DoS protection: an attacker would need to remount the attack post-restart, and a backend restart is rare. **Persistence is not required by the spec.**
- A 5-minute idle window resets a "warm" failure count: if 4 failures occur and then 5 minutes pass with no requests, the 5th failure resets to 1, not 5. This prevents long-tail false positives from legitimate operators with intermittent misconfiguration.

`HTTP 429` returns include a `quarantined_at=<ISO>` response body field (a small JSON object) and a `Retry-After: 0` header (since the quarantine is until manual reset — there's no automatic expiry).

### Decision D — Pipeline Hook reconciliation: lookup by `(provider='gitlab', gitlab_installation_id, head_sha)`, NOT `gitlab_status_id`

The YAML observable describes "lookup the matching `pr_checks` row by `gitlab_status_id`". This is the wrong join key in practice. The flow is:

1. Backend posts to GitLab → GitLab returns a status id we persist into `pr_checks.gitlab_status_id`.
2. CI runs (or fails / cancels / times out) → GitLab fires Pipeline Hook events for *the pipeline itself*, not for our commit-status row.
3. The Pipeline Hook payload includes `object_attributes.id` (the pipeline id), `object_attributes.status` (the pipeline state), `project.id` (the project), and `object_attributes.sha` (the commit SHA).

The `pipeline_id` from the Pipeline Hook is *not* our `gitlab_status_id`. They are distinct identifiers in two unrelated tables on GitLab's side.

What the YAML actually wants (and what spec :9263 says — "for re-run / status reconciliation"): when a Pipeline Hook arrives, find any `pr_checks` rows for the same `(gitlab_installation_id, head_sha)` pair whose status hasn't yet been reconciled — i.e. the most-recently-posted one for that commit — and update `pr_checks.status` to reflect the *pipeline state*.

We resolve the join as `(provider='gitlab', gitlab_installation_id == installation.Id, head_sha == payload.sha)`. Multiple rows matching is rare but possible (multiple test collections per commit) — we update every matching row. Mapping pipeline state → `pr_checks.status`:

| GitLab pipeline state | `pr_checks.status` |
|---|---|
| `success` | `posted` (no change — was already terminal) |
| `failed` | `posted` (state was already failed; reconciliation is a no-op) |
| `running` | `posting` |
| `pending` | `queued` |
| `canceled` | `failed` (set `last_error = "Pipeline cancelled in GitLab UI"`) |
| `skipped` | `posted` |
| (other / unknown) | (no change; log warning) |

Reconciliation is **purely informational** in M16 — we are not re-running collections on Pipeline Hook events (re-run pipeline is out of milestone scope, identical to the GitHub `check_run.rerequested` handling). The handler exists, is wired, and is the documented extension point.

If no `pr_checks` row matches, the handler logs `gitlab_pipeline_hook_no_match` at Info and returns success. The event row is still marked processed.

### Decision E — Push Hook and Merge Request Hook: stored only, dispatcher logs and returns

Per task YAML behavior 5 + spec :9263: "`Push Hook` and `Merge Request Hook` are stored for debugging but no business logic acts on them in M16." The dispatcher receives these envelopes, emits `LogInformation("gitlab_webhook_stored_only event_type={EventType} event_uuid={EventUuid}", ...)`, and returns success. The idempotency row gets `processed_at`; daily pruning eventually removes it.

### Decision F — Top-level path and endpoint structure mirror M14-019 GitHub side exactly

Endpoint path: `POST /webhooks/gitlab` (top-level, no `/api/v1` prefix). Registered with `AllowAnonymous` (verification is the gate), no rate-limit policy (GitLab is a trusted source; we have our own per-IP quarantine). File: `src/ApiTool.Backend/GitLab/Webhooks/GitLabWebhookEndpoint.cs`. Endpoint extension: `MapGitLabWebhookEndpoint`. Wired in `Program.cs` next to `MapGithubWebhookEndpoint`.

### Decision G — Single-secret per installation (Open Decision 3); multi-secret rotation deferred and documented

The task YAML behavior #8 reads: *"M16-015 ships with single-secret support per Open Decision 3, when documentation is read, then it explicitly states multi-secret rotation via `GITLAB__WEBHOOK_SECRETS_<installation_id>` is a follow-up."* The schema confirms: `webhook_secret_ciphertext` is a single (nullable) column — no "secrets" list. M16-015 implements:

- One ciphertext per installation. Verification compares the header value against the single decrypted plaintext per row.
- A doc comment on `GitLabWebhookEndpoint` and a clear paragraph in `docs/SPECIFICATION.md` (under "GitLab Inbound Webhook Handler") flag the deferred multi-secret support.
- Add an entry to `CHANGELOG.md` noting this.

The future shape (not implemented): a row could carry `webhook_secret_ciphertext` + `webhook_secret_ciphertext_previous` for rotation; or the env-var `GITLAB__WEBHOOK_SECRETS_<installation_id>` could supply an out-of-band secret list. Both designs are equally valid; the choice is deferred to the rotation-implementation slice.

### Decision H — Daily retention pruning: 30 days, mirrors `GithubWebhookCleanupHost`

Spec :10943: "*Identical pattern to `github_webhook_events`: 5-failure quarantine, daily retention pruning of rows older than 30 days where `quarantined_at IS NULL`.*" Note: spec says **30 days** for GitLab, not GitHub's 90. We honor the spec. New `GitLabWebhookCleanupHost : BackgroundService` with 24-hour tick deleting `processed_at IS NOT NULL AND quarantined_at IS NULL AND received_at < (now - 30 days)`. Quarantined rows retained indefinitely. Skipped under `IsEnvironment("Testing")`. New `GitLabWebhookCleanupOptions { RetentionDays = 30; Section = "ApiTool:GitLab:Webhook:Cleanup"; }`.

### Decision I — Raw body preservation and JSON parse order

Same pattern as GitHub side: read raw body via `MemoryStream`, *then* verify, *then* parse JSON. For GitLab the token compare doesn't need the raw body (token is in a header, not signed over the body), so we could parse before verification — but defense-in-depth says verify before parsing. We keep raw-body-first to preserve the symmetry. Cost is small (one extra stream allocation per request).

### Decision K — InMemory test provider compatibility

EF Core InMemory (used by `BackendFactory`) does not support `ExecuteUpdateAsync`/`ExecuteDeleteAsync`. The store implements two branches: an Npgsql/SQLite fast path using bulk `ExecuteUpdateAsync` + raw SQL `INSERT … ON CONFLICT DO NOTHING RETURNING *`, and a slow LINQ path for InMemory (FirstOrDefaultAsync → Add → SaveChangesAsync with DbUpdateException catch). Mirrors `GithubWebhookStore`.

namespace ApiTool.Backend.GitLab.Webhooks;

public interface IGitLabWebhookDispatcher
{
    Task DispatchAsync(GitLabWebhookEnvelope envelope, CancellationToken ct);
}

public sealed record GitLabWebhookEnvelope(
    string EventUuid, string EventType, Guid InstallationId, JsonDocument Payload);

public sealed record GitLabPipelineHookPayload(
    long PipelineId, string Status, string Sha, long ProjectId);

public sealed class GitLabWebhookDispatcher(
    GitLabPipelineHookHandler pipelineHandler,
    ILogger<GitLabWebhookDispatcher> log) : IGitLabWebhookDispatcher
{
    public async Task DispatchAsync(GitLabWebhookEnvelope envelope, CancellationToken ct)
    {
        switch (envelope.EventType)
        {
            case "Pipeline Hook":
                await pipelineHandler.HandleAsync(
                    GitLabWebhookPayloadParser.ParsePipelineHook(envelope.Payload),
                    envelope.InstallationId, ct);
                break;
            case "Push Hook":
            case "Merge Request Hook":
                log.LogInformation(
                    "gitlab_webhook_stored_only event_type={EventType} event_uuid={EventUuid} installation_id={InstallationId}",
                    envelope.EventType, envelope.EventUuid, envelope.InstallationId);
                break;
            default:
                log.LogInformation(
                    "gitlab_webhook_unhandled event_type={EventType} event_uuid={EventUuid}",
                    envelope.EventType, envelope.EventUuid);
                break;
        }
    }
}

public sealed class GitLabPipelineHookHandler(
    AppDbContext db, TimeProvider clock, ILogger<GitLabPipelineHookHandler> log)
{
    public async Task HandleAsync(
        GitLabPipelineHookPayload payload, Guid installationId, CancellationToken ct);
}
```

public static class GitLabWebhookEndpoint
{
    public static IEndpointRouteBuilder MapGitLabWebhookEndpoint(this IEndpointRouteBuilder app)
    {
        app.MapPost("/webhooks/gitlab", HandleAsync)
            .AllowAnonymous()
            .WithName("GitLabWebhook")
            .WithTags("Webhooks");
        return app;
    }

    private static async Task<IResult> HandleAsync(
        HttpContext context,
        GitLabWebhookStore store,
        IGitLabWebhookDispatcher dispatcher,
        GitLabWebhookSourceTracker sourceTracker,
        IGitLabKeyProvider keyProvider,
        AppDbContext db,
        ILoggerFactory loggerFactory,
        CancellationToken ct)
    {
        // 1) Source-IP quarantine check (pre-everything)
        // 2) Read raw body
        // 3) Read X-Gitlab-Token, X-Gitlab-Event, X-Gitlab-Event-UUID headers
        // 4) Validate headers (event-uuid non-empty, event-type non-empty)
        // 5) Iterate gitlab_installations → find token match (constant-time, no short-circuit)
        // 6) On match: record success on tracker; parse JSON; idempotency insert; dispatch
        // 7) On no match: record failure on tracker → if 5th, return 429; else 401
    }
}
```

Endpoint pseudocode (canonical):

```
ip = context.Connection.RemoteIpAddress?.ToString() ?? "unknown";
var (quarantined, quarantinedAt) = sourceTracker.GetState(ip);
if (quarantined)
    return Results.Json(new { quarantined_at = quarantinedAt }, statusCode: 429);

var rawBody = await ReadRawBodyAsync(...);

var token = context.Request.Headers["X-Gitlab-Token"].FirstOrDefault();
var eventUuid = context.Request.Headers["X-Gitlab-Event-UUID"].FirstOrDefault();
var eventType = context.Request.Headers["X-Gitlab-Event"].FirstOrDefault();

if (string.IsNullOrEmpty(token) || string.IsNullOrEmpty(eventUuid) || string.IsNullOrEmpty(eventType))
    return Results.Unauthorized();  // or BadRequest for missing event headers — see test cases

// Try to match the token against any installation's webhook_secret_ciphertext
var matchedInstallationId = await TryFindMatchingInstallationAsync(db, keyProvider, token, ct);
if (matchedInstallationId is null)
{
    var failures = sourceTracker.RecordFailure(ip);
    if (failures >= GitLabWebhookSourceTracker.QuarantineThreshold)
        return Results.Json(new { quarantined_at = clock.GetUtcNow() }, statusCode: 429);
    return Results.Unauthorized();
}

sourceTracker.RecordSuccess(ip);

// Parse JSON
JsonDocument payload;
try { payload = JsonDocument.Parse(rawBody); }
catch (JsonException) { return Results.BadRequest(); }

// Idempotency insert
var result = await store.TryInsertPendingAsync(eventUuid, eventType, matchedInstallationId.Value,
    Encoding.UTF8.GetString(rawBody), ct);
if (!result.Inserted)
{
    payload.Dispose();
    return Results.Ok();  // duplicate — no-op
}

// Dispatch
try
{
    var envelope = new GitLabWebhookEnvelope(eventUuid, eventType, matchedInstallationId.Value, payload);
    await dispatcher.DispatchAsync(envelope, ct);
    await store.MarkProcessedAsync(eventUuid, ct);
    return Results.Ok();
}
catch (Exception ex)
{
    var attempts = await store.RecordFailureAsync(eventUuid, ex.Message, ct);
    if (attempts >= GitLabWebhookStore.QuarantineThreshold)
    {
        logger.LogError(ex, "gitlab_webhook_quarantined event_uuid={Uuid} event_type={EventType} attempt_count={Count}",
            eventUuid, eventType, attempts);
        return Results.Ok();  // break retry storm
    }
    logger.LogWarning(ex, "gitlab_webhook_handler_failed event_uuid={Uuid} event_type={EventType} attempt_count={Count}",
        eventUuid, eventType, attempts);
    return Results.StatusCode(500);
}
finally { payload.Dispose(); }
```

`TryFindMatchingInstallationAsync` is a private helper on the endpoint that loads all installations (`webhook_secret_ciphertext IS NOT NULL AND deleted_at IS NULL`), decrypts each via `IGitLabKeyProvider`, and `FixedTimeEquals`-compares against the token bytes. Returns the matching `installation.Id` or null. Iterates every row even after a match (per Decision A).

## Risks and Edge Cases

- **Risk:** Verifying via "iterate all installations" leaks information about how many installations exist (the response time correlates with installation count). **Mitigation:** Accepted — installation count is not sensitive (the dashboard shows it to the org admin), and the alternative (a single-secret env-var fallback) would conflict with Decision G's single-secret-per-installation model.

- **Risk:** With many installations, the per-request decrypt cost (one `IGitLabKeyProvider.DecryptAsync` per installation) becomes the verification critical path. For `FileGitLabKeyProvider` this is a sync in-process AES-GCM decrypt — negligible (<1ms per row). For `GoogleKmsGitLabKeyProvider` this is an HTTP round-trip to KMS per row — **potentially expensive at high installation counts**. **Mitigation:** Out of scope for this slice. The follow-up (a separate task) is a per-process LRU cache of `(InstallationId → SecretPlaintext)` invalidated on `WebhookSecretRotatedAt` change. We document this in a TODO comment on the endpoint helper.

- **Risk:** Source-IP tracker grows unbounded under attack (one entry per attacking IP). **Mitigation:** The tracker uses `ConcurrentDictionary<string, SourceState>`. Periodic cleanup (every N minutes, remove entries idle > 30 minutes without quarantine) is added to the tracker class. Memory is O(active attackers); a sustained DoS would push memory but not crash — the Kestrel front already has connection limits. Documented limitation.

- **Risk:** In-memory source-IP quarantine state is lost on backend restart, defeating "until manual reset". **Mitigation:** Accepted per Decision C. The state is DoS protection, not audit; an attacker would have to restart their attack and accrue 5 fresh failures, by which time normal alerting catches them. Persistence is a follow-up if real-world incidents warrant it.

- **Risk:** Pipeline Hook arrives before the outbound `pr_checks` row is fully committed (race window: backend posts to GitLab → GitLab fires Pipeline Hook → backend hasn't yet committed `posted_at`). **Mitigation:** The handler logs `gitlab_pipeline_hook_no_match` at Info and returns success; the row will catch up on the next pipeline state change. We do not implement an explicit retry.

- **Risk:** Pipeline Hook reconciliation operates on `head_sha` but `pr_checks.HeadSha` was nullable in M14-018 (defaulted to empty). M16-014 made it `IsRequired().HasDefaultValue(string.Empty)`. **Mitigation:** The reconciliation join filters out rows with empty `HeadSha`. Rows without a head_sha cannot be reconciled — correctly so. No data loss.

- **Risk:** Multiple `pr_checks` rows might match `(installation, head_sha)` if the same commit had multiple PR-check uploads. **Mitigation:** Per Decision D, update all matching rows. No deduplication needed.

- **Risk:** `X-Gitlab-Event-UUID` is documented as "an attempt UUID" by GitLab but the format is not strictly UUID v4 in older self-managed instances. **Mitigation:** Store as `string` (already in the entity), not `Guid`. The schema's `event_uuid TEXT NOT NULL` is the right shape. Unique-index uniqueness still works on string equality.

- **Risk:** Empty / whitespace-only `X-Gitlab-Token` could match an empty/whitespace `webhook_secret_ciphertext` if a misconfigured installation has one. **Mitigation:** Defense in depth: the endpoint rejects empty tokens (returns 401) before any DB lookup. The `gitlab_installations` row also has `webhook_secret_ciphertext nullable` and we filter `WHERE webhook_secret_ciphertext IS NOT NULL` in the query.

- **Edge case:** Quarantined event row receives a retry. **Handling:** The existing idempotency path returns 200 immediately (`!result.Inserted` → return Ok). The quarantine breaks the dispatch loop without changing wire behavior.

- **Edge case:** Backend has zero installations with a webhook secret configured. **Handling:** The verification iteration returns null → 401 → tracker increments. After 5 such requests from the same IP, 429. This is correct: a request to a backend not yet provisioned for any GitLab integration is unauthorised.

- **Edge case:** Source IP is null (Kestrel quirk under reverse proxy). **Handling:** Default to the string `"unknown"` for the tracker key. All "unknown"-keyed requests share the same quarantine counter, which is the intended pessimistic behaviour under upstream misconfiguration.
