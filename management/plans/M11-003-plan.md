# Implementation Plan: M11-003

## Overview

Two additive changes to the TAP formatter that close IMPROVEMENT.md
§2.4 bullets 1 (TAP half) and 2: (a) explicitly contract per-iteration
TAP test points for data-driven runs (one `ok N - BaseName [i/N]` per
iteration, plan `1..N` matching the actual count) by locking the
contract with new tests; (b) emit a TAP YAML diagnostic block carrying
`speedup_factor`, `wave_count`, and `max_parallelism` after the test
points when the run was parallel and produced more than one wave —
mirroring the existing `output.ParallelExecutionJSON` data.

## Architectural Decisions (resolved during planning)

1. **Per-iteration TAP test points already exist.** Audit of
   `internal/runner/runner.go` (lines 2118, 2326, 2519–2523) and
   `cmd/apitest/main.go::buildTAPOutput` (line 2123) confirms the runner
   emits one `RequestResult` per data-driven iteration with `Name` set
   to `BaseName [i/N]`. `buildTAPOutput` produces one `TAPResult` per
   `RequestResult`. The existing test
   `TestRunCmdDirect_DataDriven_TAPFormat` (line 6690) already asserts
   `1..2` for a 2-row CSV. The task scope wording "Replace the single
   TAP test point that currently represents an entire data-driven
   request" describes a state that does **not** match the live binary —
   the historical fix already happened. **Plan adopts this finding:** we
   do **not** alter `buildTAPOutput`; instead we (a) add explicit
   regression tests (`TestTAPOutput_DataDrivenIterations`) that lock the
   contract — `[i/N]` suffix on every test-point line and `plan ==
   actual count` invariant — and (b) keep the existing
   `# Data-Driven: BaseName (M iterations)` group marker comment as a
   section header above the iteration block. This matches every behavior
   bullet in the task verbatim (the wording is descriptive, not
   prescriptive of a code change).

2. **Speedup YAML diagnostic block is a new addition to `WriteTAP`.**
   Today `WriteTAP` emits, in order: header `TAP version 13`, plan line
   `1..N`, per-result test points (with optional `# Data-Driven:` and
   `# Wave M` group comments and inline retry diagnostics), and a
   trailing summary comment `# Summary: P passed, F failed`. We insert
   the new block **after the last test point and before the summary
   comment**, gated on a new optional argument carrying parallel
   metadata. The block conforms to TAP 13 YAML diagnostic conventions:
   a `# Parallel execution:` header line on the line above, then a
   YAML block bracketed by `  ---` / `  ...` (two-space indent matches
   the existing `writeTAPDiagnostics`), holding three keys —
   `speedup_factor`, `wave_count`, `max_parallelism`. The block is
   emitted only when `wave_count > 1` (single-wave parallel runs have
   speedup ≈ 1.0 by definition, and the per-result `# Wave M` comments
   already convey wave structure). This matches the JSON formatter's
   speedup population guard: `cmd/apitest/main.go:1997`
   (`summary.WaveCount > 1 && summary.Duration > 0`).

3. **`speedup_factor` is computed identically to the JSON path.** The
   formula is `sum(WaveDurations) / Duration`, rounded to one decimal
   via `math.Round(x*10) / 10`. We keep the rounded float (not raw)
   because parity with `ParallelExecutionJSON.SpeedupFactor` is a task
   behavior (the parity test compares the two values byte-equal after
   round-trip). The arithmetic stays in `cmd/apitest/main.go::buildTAPOutput`
   (passed in as a struct field), not duplicated in `internal/output`.

4. **API shape: optional struct on `WriteTAP` rather than a new
   exported writer function.** Two viable patterns:
   - **Option A (rejected):** new `WriteTAPWithParallel(w, results, passed, failed, parallel *ParallelTAP) error`. Adds API surface but keeps existing two-arg form unchanged.
   - **Option B (chosen):** add a struct `ParallelTAP` to `internal/output` and a fifth optional argument by introducing variadic options OR by changing `WriteTAP`'s signature and migrating call sites.

   Final choice: **add a 5th positional parameter `parallel *output.ParallelTAP`** to `WriteTAP`. Rationale: (a) only two call sites in `cmd/apitest/main.go` (lines 815, 1479) — small migration; (b) no variadic options pattern exists elsewhere in the package (compare `WriteJSON`/`WriteJUnit` which take a single `*JSONOutput` carrying everything); (c) the symmetric pattern with `JSONOutput.ParallelExecution` works for JSON because JSON is a single-argument blob, but TAP has historically taken multiple args (`results`, `passed`, `failed`); (d) callers who don't run parallel pass `nil`. The migration is a one-line change at each call site (`output.WriteTAP(stdout, nil, 0, 0, nil)` and `output.WriteTAP(stdout, tapResults, passed, failed, parallelInfo)`). Tests that currently call `WriteTAP(&buf, results, passed, failed)` are updated to pass the new `nil` arg — pure mechanical fix.

   Alternative considered: option C — keep `WriteTAP` as-is and add `WriteTAPParallel(w, results, passed, failed, parallel *ParallelTAP)`. Rejected because it doubles surface and requires both call sites in main.go to switch on `summary.IsParallel`. Option B keeps the call paths uniform: the 5th argument is `nil` when not parallel, populated when parallel. Cleaner.

5. **Type lives in `internal/output/tap.go`.** New `ParallelTAP` struct
   matches `ParallelExecutionJSON` field names (snake_case in YAML/JSON
   wire form, CamelCase in Go) so the parity test reads naturally. Field
   types: `WaveCount int`, `MaxParallelism int`, `SpeedupFactor float64`.
   No JSON tags needed — this is a pure-emission helper, never marshaled
   directly.

6. **YAML block format matches existing TAP diagnostic style.** Compare
   `writeTAPDiagnostics` (line 123 of `tap.go`) which writes two-space-
   indented `  ---` / `  ...`. The new block follows the same convention
   so TAP parsers (prove, tappy) treat it as a free-floating diagnostic
   between the last test point and the trailing comment. Specifically:

   ```
   # Parallel execution:
     ---
     speedup_factor: 1.5
     wave_count: 3
     max_parallelism: 2
     ...
   ```

   The `# Parallel execution:` comment line is a free comment (TAP
   ignores it); the `---`/`...` block is parsed as YAML. We format
   `speedup_factor` with `%.1f` (one decimal — same as the terminal
   `Speedup: %.1fx`).

7. **Iteration name uses `r.Name` verbatim.** The runner has already
   produced names of the form `BaseName [i/N]` at
   `internal/runner/runner.go:2118` and 2326. `buildTAPOutput` already
   passes through `r.Name` to `TAPResult.Name`. The existing
   `sanitizeTAPName` strips `#` and collapses whitespace; the `[i/N]`
   suffix survives intact (no `#`, no embedded whitespace).

8. **Observable testdata fixtures.** The task observable references
   two fixtures:
   - `cmd/apitest/testdata/datadriven_simple.yaml` — **already exists**
     (created in M11-002, points at `httpbin.org/get?name={{name}}`).
     We reuse it verbatim.
   - `cmd/apitest/testdata/parallel_simple.yaml` — **does not exist**.
     We create a minimal collection with two independent requests so
     dependency analysis schedules them into a single wave and the
     `--parallel` flag triggers the parallel pipeline. To produce
     **`wave_count > 1`** (the speedup-block guard), we add a third
     request that depends on the first two via a `{{var}}` reference
     extracted from request 1. Final shape: 3 requests, 2 waves
     (wave 1 = req1+req2 in parallel, wave 2 = req3 sequentially),
     `max_parallelism = 2`. Targets `httpbin.org` for the same reason
     M11-002 used it (no local server, deterministic 200 OK).
   - The observable command requires `APITEST_TIER=professional` for
     both `--parallel` and the data-driven path. The plan adds the
     env-var note to the observable instructions and to `docs/MANUAL.md`
     (mirrors M11-002 documentation pattern).

9. **`parallel_simple.yaml` design choices.**
   - Two leaves + one downstream consumer is the minimum to provoke
     `wave_count = 2`. A single-wave layout would skip the diagnostic
     block (per Decision 2), defeating the test.
   - We reuse `httpbin.org` because the existing M11-002 fixture
     already does. Yes, this means observable verification is
     network-dependent — same trade-off accepted in M11-002.
   - The `extract:` line in request 1 captures `$.url` (always present
     on `/get`) and the consumer references it through a query string
     so dependency analysis sees the variable edge.
   - The fixture is byte-light (~12 lines) and doesn't introduce any
     new schema features.

10. **Test signatures: `TestTAPOutput_DataDrivenIterations` and
    `TestTAPOutput_ParallelSpeedup`.** The task observable runs:
    ```bash
    go test -run 'TestTAPOutput_DataDrivenIterations|TestTAPOutput_ParallelSpeedup' -v ./cmd/apitest/...
    ```
    so both tests must live in `cmd/apitest/`. We place them in
    `cmd/apitest/main_test.go` next to the existing
    `TestRunCmdDirect_DataDriven_TAPFormat` (line 6690) for proximity.
    The naming differs from the per-package `TestWriteTAP_*` series in
    `internal/output/tap_test.go` (which we also extend with
    `TestWriteTAP_ParallelSpeedup` to cover the unit-level emission
    contract).

11. **Existing tests stay green.** Mechanical updates only:
    - `internal/output/tap_test.go::TestWriteTAP*` — every existing
      `WriteTAP(&buf, results, passed, failed)` call gets an extra
      `nil` arg (decision 4). 4 such test functions × ~25 cases. All
      mechanical; no logic changes.
    - `cmd/apitest/main.go` — two call sites (lines 815, 1479) get the
      extra arg. The line-1479 call passes a non-nil
      `parallelInfo` when `summary.IsParallel && summary.WaveCount > 1`.
    - `cmd/apitest/main_test.go::TestRunCmdDirect_DataDriven_TAPFormat`
      (line 6690) continues to pass — its assertions on `1..2` and
      `# Data-Driven: ...` are untouched. We **extend** this test to
      also assert `[i/N]`-suffixed test-point lines (locking the
      iteration contract).

12. **No changes to `MultiJSONOutput`-style multi-collection TAP.**
    `apitest run <glob>` on TAP currently iterates per-collection (no
    multi-doc TAP). Out of scope.

13. **The `# Wave M` comment is preserved.** The existing
    `# Wave 1` / `# Wave 2` markers above each wave's test points are
    visual aids for humans reading TAP. The new YAML diagnostic block
    is the structured-data answer to the same question. Both stay —
    parallel runs of >1 wave will show wave headers AND the trailing
    YAML diagnostic.

// writeTAPParallelDiagnostic writes a free-comment header line followed
// by a TAP 13 YAML diagnostic block (two-space indented, bracketed by
// `  ---` and `  ...`) carrying speedup_factor, wave_count, and
// max_parallelism. (M11-003)
func writeTAPParallelDiagnostic(w io.Writer, p *ParallelTAP) error {
	if _, err := fmt.Fprintln(w, "# Parallel execution:"); err != nil {
		return err
	}
	if _, err := fmt.Fprintln(w, "  ---"); err != nil {
		return err
	}
	if _, err := fmt.Fprintf(w, "  speedup_factor: %.1f\n", p.SpeedupFactor); err != nil {
		return err
	}
	if _, err := fmt.Fprintf(w, "  wave_count: %d\n", p.WaveCount); err != nil {
		return err
	}
	if _, err := fmt.Fprintf(w, "  max_parallelism: %d\n", p.MaxParallelism); err != nil {
		return err
	}
	_, err := fmt.Fprintln(w, "  ...")
	return err
}

// internal/output/tap_test.go — new test function next to TestWriteTAP_WaveAnnotations.
func TestWriteTAP_ParallelSpeedup(t *testing.T) {
	tests := []struct {
		name     string
		results  []TAPResult
		passed   int
		failed   int
		parallel *ParallelTAP
		check    func(t *testing.T, out string)
	}{
		{
			name: "speedup block emitted when wave_count > 1",
			results: []TAPResult{
				{Name: "A", Passed: true, DurationMs: 10, WaveIndex: intPtr(0)},
				{Name: "B", Passed: true, DurationMs: 20, WaveIndex: intPtr(1)},
			},
			passed:   2,
			failed:   0,
			parallel: &ParallelTAP{WaveCount: 2, MaxParallelism: 1, SpeedupFactor: 1.5},
			check: func(t *testing.T, out string) {
				t.Helper()
				if !strings.Contains(out, "# Parallel execution:\n") {
					t.Errorf("missing parallel header comment, got: %q", out)
				}
				if !strings.Contains(out, "  speedup_factor: 1.5\n") {
					t.Errorf("missing speedup_factor line, got: %q", out)
				}

// buildParallelMetadata extracts wave count, max parallelism, and
// speedup factor from a runner.Summary. SpeedupFactor mirrors the JSON
// formatter's computation: sum(WaveDurations) / Duration rounded to one
// decimal, zero when WaveCount <= 1 or Duration <= 0. (M11-003)
func buildParallelMetadata(summary *runner.Summary) (waveCount, maxParallelism int, speedup float64) {
	if summary == nil {
		return 0, 0, 0
	}
	waveCount = summary.WaveCount
	maxParallelism = summary.MaxParallelism
	if summary.WaveCount > 1 && summary.Duration > 0 {
		var seqEstimate time.Duration
		for _, d := range summary.WaveDurations {
			seqEstimate += d
		}
		speedup = float64(seqEstimate) / float64(summary.Duration)
		speedup = math.Round(speedup*10) / 10
	}
	return waveCount, maxParallelism, speedup
}

## Risks and Edge Cases

- **Risk:** TAP parsers (prove, tappy) reject the new YAML diagnostic
  block as invalid. → **Mitigation:** TAP 13 specifies that YAML
  diagnostic blocks are valid anywhere between the plan and the trailing
  comment, so long as they sit at indentation greater than zero. Our
  block uses two-space indent (matching `writeTAPDiagnostics` style)
  and is bracketed by `  ---`/`  ...`. Tested locally with `prove` if
  available; behaviour parallels existing `not ok` diagnostic blocks
  which already round-trip through `prove`. The free-comment header
  `# Parallel execution:` is ignored by all TAP parsers (TAP comments
  start with `#`).
- **Risk:** Existing snapshot-style tests doing exact byte comparison
  of TAP output break. → **Mitigation:** Survey of `tap_test.go`
  asserts via `strings.Contains` and `strings.Count`; no exact byte
  comparison found. Confirmed during planning.
- **Edge case:** Parallel run with `wave_count == 1`. → **Handling:**
  `parallel != nil && parallel.WaveCount > 1` guard ensures no block
  emitted. Tested in `TestWriteTAP_ParallelSpeedup` case
  "no speedup block when wave_count == 1".
- **Edge case:** Parallel run with `Duration == 0` (theoretically
  impossible — execution always takes nonzero time). → **Handling:**
  `buildParallelMetadata` returns `speedup = 0` in that branch, so the
  emitted block reads `speedup_factor: 0.0`. Defensive only.
- **Edge case:** `summary == nil` in the TAP path. → **Handling:**
  `parallelInfo` stays `nil`, branch is skipped. Tested implicitly via
  the bailout-call site (`WriteTAP(stdout, nil, 0, 0, nil)`).
- **Edge case:** Sequential collection with `--parallel` flag (only one
  wave possible because of dependency chain). → **Handling:** Same as
  `wave_count == 1`. No diagnostic emitted; users see only `# Wave 1`
  comment + test points. The exit-0 contract is preserved.
- **Edge case:** Data-driven request inside a parallel run. →
  **Handling:** Each iteration becomes its own TAPResult with its own
  `WaveIndex`. Both `# Data-Driven:` group markers and `# Wave M`
  markers can appear. The plan count counts all iterations. The
  parallel diagnostic block is independent and reports run-level
  metrics. Tested implicitly via the existing data-driven-parallel
  runner machinery.
- **Edge case:** httpbin.org slow / down during observable verification.
  → **Mitigation:** Same trade-off accepted for M11-002. The unit
  tests in `internal/output/tap_test.go` are network-free; the
  integration tests in `cmd/apitest/main_test.go` use
  `httptest.NewServer`. Only the shell-level observable verification
  hits the public network.
- **Edge case:** `regexp` and `strconv` not previously imported in
  `cmd/apitest/main_test.go`. → **Handling:** `goimports` will add
  them; `golangci-lint` flags missing imports. Mitigated by running
  `goimports` after writing the new tests.
- **Risk:** `golangci-lint` flags the new `buildParallelMetadata`
  helper for cyclomatic complexity. → **Mitigation:** The helper has
  one early return + one nested loop — well under any reasonable
  threshold. Existing `buildJSONOutput` is far more complex without
  trip-wire violations.
- **Risk:** Coverage drops below 80% in `cmd/apitest` or
  `internal/output`. → **Mitigation:** Two new helpers
  (`buildParallelMetadata`, `writeTAPParallelDiagnostic`) and one new
  struct (`ParallelTAP`); each fully covered by the new tests
  (`TestWriteTAP_ParallelSpeedup`, `TestTAPOutput_ParallelSpeedup`).
  Net-positive coverage.
