# Implementation Plan: M14-013

## Overview
Add `invoice.{payment_succeeded,payment_failed,finalized}` and `payment_method.{attached,detached}` handlers to the Stripe webhook dispatcher, persist invoice and payment-method state to two new EF tables, and enqueue `billing_receipt` / `billing_payment_failed` emails — each variable name validated against the manifest at compose time. Re-fetch every Stripe object before writing per the order-defense rule.

## Task Details
- **ID:** M14-013
- **Title:** Backend: Stripe invoice + payment-method event handlers
- **Phase:** M14: Revenue plumbing
- **Priority:** 2
- **Complexity:** high

| Task | Title | Status |

| M14-011 | Stripe webhook ingest pipeline | done |

Both dependencies are merged. ## Architectural Decisions

The task YAML is partly aspirational. These are the resolutions baked into the plan, decided unilaterally per pipeline auto-mode rules:

1. **`/api/v1/me` does not exist.** The observable's `curl /api/v1/me | jq '.last_invoice.status'` cannot be satisfied without a new endpoint. Building one is out of scope (no behavior in the YAML calls for it; M4-005 web dashboards already render results from elsewhere). We satisfy the equivalent observable via the **email queue** and a **direct DB read against the new `invoices` table** — i.e. the integration test asserts the same outcome by reading state the handler wrote rather than via a JSON projection. The runbook in CHANGELOG / smoke test will use a direct DB query. The behavior under test — that the handler persists `status=paid` and the URL after `invoice.payment_succeeded` — is unchanged.

2. **`scripts/replay-stripe-event.sh` is extended.** Today it has cases for `customer.subscription.*` and `customer.updated` only; we add `invoice.*` (object: invoice, with id/customer/amount_paid/total/hosted_invoice_url/period_start/period_end/attempt_count/status) and `payment_method.*` (object: payment_method, with id/customer/type=card and card.last4/card.brand). The shape mirrors what the gateway's `GetInvoiceAsync` / `GetPaymentMethodAsync` will re-fetch to assert order-defense.

3. **New tables: `invoices` and `payment_methods`.** SPECIFICATION.md:6803 references "store invoice URL for user access" but no `invoices` schema is defined elsewhere. Decision: create lean tables tied to the existing `subscriptions.OrgId` foreign key:

   - `invoices(Id PK guid, OrgId FK, StripeInvoiceId unique, StripeCustomerId, StripeSubscriptionId nullable, Status string(20), AmountPaid long-cents, AmountTotal long-cents, Currency string(3), HostedInvoiceUrl string(500) nullable, PeriodStart DateTime, PeriodEnd DateTime, CreatedAt DateTime, UpdatedAt DateTime)` — `Status` is the Stripe invoice status string lowercased: `paid|open|void|uncollectible|draft`.
   - `payment_methods(Id PK guid, OrgId FK, StripePaymentMethodId unique, StripeCustomerId, Brand string(20), Last4 char(4), ExpMonth long, ExpYear long, AttachedAt DateTime, DetachedAt DateTime nullable, CreatedAt DateTime, UpdatedAt DateTime)` — soft-delete via `DetachedAt` per behavior #5 ("removed (or soft-deleted with detached_at)"). We pick the soft-delete option because it preserves audit history and makes idempotent replay trivial.

   Migration: `20260507120000_AddInvoicesAndPaymentMethods`. Both tables get a unique index on the Stripe id and an index on `OrgId, CreatedAt` for dashboard queries. EF model snapshot is regenerated.

4. **Re-fetch contract additions to `IStripeGateway`.** Add two methods symmetric to the existing `GetSubscriptionAsync` / `GetCustomerAsync`:
   - `Task<Stripe.Invoice?> GetInvoiceAsync(string invoiceId, CancellationToken ct)` — `null` on 404, throws on other StripeExceptions. Uses `new Stripe.InvoiceService(_client).GetAsync(invoiceId, …)`.
   - `Task<Stripe.PaymentMethod?> GetPaymentMethodAsync(string paymentMethodId, CancellationToken ct)` — same null-on-404 contract; `new Stripe.PaymentMethodService(_client).GetAsync(…)`.
   `FakeStripeGateway` mirrors with two new dictionaries and `SetInvoiceForTest` / `SetPaymentMethodForTest` helpers. This is consistent with M14-012's approach.

5. **Two handler types, not one file.** The task scope says "Adds handlers in `Webhooks/Handlers/InvoiceAndPaymentHandlers.cs`". We follow that path naming but split into **two sibling sealed classes** (`StripeInvoiceHandler`, `StripePaymentMethodHandler`) co-located in that one file — same pattern as `SubscriptionHandlers.cs` (which only has `StripeSubscriptionHandler`) and `CustomerHandlers.cs`. Two handlers means cleaner DI registration and dispatcher routing.

6. **Manifest-contract enforcement at compose time.** Behavior #6 says the handler must fail when a variable not in the manifest is enqueued. We don't push that into the runtime path of `StripeInvoiceHandler` (the SendGrid sender already enforces it at send time per :8941). Instead we add a **dedicated unit test** (`InvoiceHandlerManifestContractTests`) that loads `templates/email/billing_receipt.json` + `billing_payment_failed.json` via `EmailTemplateLoader`, runs the handlers against fakes that capture the `EmailMessage`, and asserts every variable name in the captured `Variables` dict is a key in the manifest's `variables`. This makes the contract a CI gate without coupling production code to manifest loading. (Behavior #6 says "fails its unit test" — that is exactly this assertion.)

7. **Idempotent replay (behavior #7) is satisfied by the existing M14-011 idempotency store.** The dispatcher is invoked only once per event because `StripeWebhookStore.TryInsertPendingAsync` short-circuits duplicates. We add one focused test on `StripeInvoiceHandler` to prove that **applying the same logical event twice** (e.g. two calls to `HandlePaymentSucceededAsync` with the same invoice id) is itself idempotent — upserts not inserts, no double email. This guards against any code path that bypasses the store (e.g. cron-driven reconciliation in a future slice).

8. **Dunning grace timer (behavior #2) is data-only.** The spec mentions "starts the dunning grace timer". We do not introduce a hosted service or cron in this slice — that lives in M16. Today, "starts the timer" means: persist `subscription.Status=PastDue` and let the existing time-based licence-status check (already used by the org's tier resolution) treat it as past-due. No timer field is added to the entity in this slice; M16's trial cron will own that.

9. **`update_payment_url` for `billing_payment_failed`.** The manifest declares it. We compose it as `{App:WebAppUrl}/billing/update-payment` using the existing `IOptions<AppOptions>` already injected for the cancellation handler. No new option key.

10. **`first_name` derivation reuses the local-part rule.** Same as `StripeSubscriptionHandler.HandleDeletedAsync`: `email[..email.IndexOf('@')]` (lowercase). Skip the email enqueue with a warning log when no org owner is found, matching the existing handler pattern.

11. **`billing_period` for `billing_receipt`.** Compose from `Invoice.PeriodStart`/`PeriodEnd` as `"<MonthYear>"` when one calendar month is covered (`"May 2026"`), otherwise the date range `"2026-05-01 – 2026-05-15"`. Default culture `en-US` to match the manifest's example. Same approach used for the canceled `effective_date` in M14-012.

12. **`amount_total` formatting.** Stripe amounts come in the smallest currency unit (cents for USD). Format as `"$<dollars>.<cents>"` with two-decimal places when `Currency == "usd"`; otherwise emit `"<cents> <CURRENCY>"` (e.g. `"4900 EUR"`) — defensive and unambiguous. Locale-bound currency formatting is out of scope.

13. **Step ordering (smallest blast radius first):** entity scaffolding → migration → DbContext sets → gateway re-fetch methods (interface, fake, live) → invoice handler with tests → payment-method handler with tests → dispatcher routing → integration test → DI wiring. Each step compiles green on its own.

```csharp
public sealed class StripeInvoiceHandler(
    AppDbContext db,
    IStripeGateway gateway,
    IEmailQueue emailQueue,
    TimeProvider clock,
    IOptions<AppOptions> appOptions,
    ILogger<StripeInvoiceHandler> log)
{
    public async Task HandlePaymentSucceededAsync(string invoiceId, CancellationToken ct);
    public async Task HandlePaymentFailedAsync(string invoiceId, CancellationToken ct);
    public async Task HandleFinalizedAsync(string invoiceId, CancellationToken ct);

    // shared helpers
    private async Task<Invoice?> UpsertInvoiceFromStripeAsync(Stripe.Invoice stripe, CancellationToken ct);
    private static string FormatBillingPeriod(DateTime start, DateTime end);
    private static string FormatAmount(long amount, string currency);
```

#### Behavior outlines

- **`HandlePaymentSucceededAsync`** —
  1. `gateway.GetInvoiceAsync(id)`; null → log + return (Stripe 404, can't reconcile).
  2. Upsert local `invoices` row.
  3. Find subscription by `StripeSubscriptionId` (or `StripeCustomerId` if subscription id null) and set `Status=Active`.
  4. Look up org owner via the same query pattern as `StripeSubscriptionHandler.HandleDeletedAsync`. If found, enqueue `billing_receipt` with `{first_name, billing_period, amount_total, invoice_url}`.
  5. `SaveChangesAsync`.

- **`HandlePaymentFailedAsync`** —
  1. Re-fetch invoice; null → return.
  2. Upsert invoice row.
  3. Find subscription, set `Status=PastDue`.
  4. Compose `update_payment_url = $"{appOptions.Value.WebAppUrl}/billing/update-payment"`.
  5. Enqueue `billing_payment_failed` with `{first_name, amount_total, update_payment_url, attempt_count}`.

- **`HandleFinalizedAsync`** —
  1. Re-fetch invoice; null → return.
  2. Upsert invoice row (specifically persisting `HostedInvoiceUrl`).
  3. **No email**, **no subscription state change**.

```csharp
    public async Task HandleDetachedAsync(string paymentMethodId, CancellationToken ct);
}
```

#### Behavior outlines

- **`HandleAttachedAsync`** —
  1. `gateway.GetPaymentMethodAsync(id)`; null → log + return.
  2. Pull `Customer` from PM. Look up subscription row by `StripeCustomerId` to find `OrgId`. If none, log + return (PM with no org context).
  3. Upsert `payment_methods` row by `StripePaymentMethodId` (UNIQUE). Set `Brand=stripePm.Card?.Brand`, `Last4=stripePm.Card?.Last4`, `ExpMonth/ExpYear`, `AttachedAt=clock.UtcNow`, clear `DetachedAt`.

- **`HandleDetachedAsync`** —
  1. Re-fetch via `GetPaymentMethodAsync`. (Stripe still serves a recently-detached PM for a window.) Null → fall through to local-only.
  2. `db.PaymentMethods.FirstOrDefaultAsync(pm => pm.StripePaymentMethodId == id)`. If row exists, set `DetachedAt=clock.UtcNow`. Don't physically delete (audit + replay).

## Risks and Edge Cases

- **Risk: `Stripe.Invoice.Subscription` type is `string` (id) on some versions, an expandable object on others.** → **Mitigation:** Use `invoice.SubscriptionId` (Stripe.Net 43.x exposes both `Subscription` (object) and `SubscriptionId` (string)). Stick to the string id for matching local rows. Verified via the Stripe.Net 43.0 reference DLL during exploration.

- **Risk: `Invoice.HostedInvoiceUrl` may be missing on `invoice.payment_succeeded` if the invoice was created via subscription-cycle billing.** → **Mitigation:** Persist `null` when missing; the column is nullable. The `billing_receipt` email's `invoice_url` variable falls back to `App:WebAppUrl + /billing/invoices/<stripe-id>` so the manifest contract is satisfied. This is the only place the test scaffold needs a fallback string.

- **Risk: `PaymentMethod.Card` is null for non-card types (SEPA, ACH, etc.).** → **Mitigation:** Defensive null-check; if `Card == null`, log and skip with `payment_method_unsupported_type` warning. Behavior #4 specifies the four-digit card last4 — non-card types are out of M14 scope per spec.

- **Risk: An invoice arrives without a corresponding local subscription row.** → **Mitigation:** Persist the invoice row with `StripeSubscriptionId` populated but no matching `OrgId` linkage available. Decision: skip the invoice persistence (return early with a log) when no `OrgId` resolves — `invoices.OrgId` is non-nullable. M14-021's E2E test seeds the subscription before the invoice event so this path is not exercised in happy-path coverage.

- **Risk: Currency-formatting edge cases (zero-decimal currencies like JPY).** → **Mitigation:** `FormatAmount` falls through to `"<cents> <CURRENCY>"` for any non-USD path; spec is en-US-only for M14 (line :8937).

- **Risk: Replay race causes duplicate `invoices` insert before unique index commits.** → **Mitigation:** The handler does an explicit `FirstOrDefaultAsync` by `StripeInvoiceId` before insert. Concurrent webhook deliveries are serialized by the M14-011 idempotency store (one row per `event_id`); two events with the same invoice id cannot run concurrently because the second short-circuits at `TryInsertPendingAsync`.

- **Edge case: `invoice.payment_failed` with `attempt_count > 1`.** → **Handling:** Pass the live `attempt_count` from Stripe straight into the `billing_payment_failed` email's variables. Stripe increments it; we never compute it locally.

- **Edge case: `customer` field on the invoice is an expandable object, not a string id.** → **Handling:** Use `invoice.CustomerId` (string) per Stripe.Net 43 conventions.

- **Edge case: `payment_method.detached` arrives with no prior `attached` (out-of-order).** → **Handling:** Re-fetch returns the PM from Stripe (still queryable for a window). Local `payment_methods` row absent → log and return.
