## Key Architectural Decisions

1. **No code in the slice except the consistency test.** The five files are policy artefacts (Markdown only). The only executable surface is one new xUnit test that mirrors `GdprInventoryDocConsistencyTests.cs` so the matrix and inventory cannot silently drift. This keeps the blast radius minimal and satisfies the DoD line "A docs-consistency test (run as part of CI) asserts every table named in docs/security/data-classification-matrix.md also appears in docs/security/data-inventory.md (and vice versa)."

2. **Asymmetric consistency:** the data-classification matrix covers all 32 tables from the SPECIFICATION.md schema appendix; the GDPR data inventory only covers the 14 user-attributable tables. A strict equality test would fail by construction. The reasonable interpretation of "no table appears in one without the other" is that **every table in `data-inventory.md` MUST have a row in `data-classification-matrix.md`** (the asymmetric direction), and any table in the classification matrix that is *also* user-attributable (i.e. carries one of the GDPR dispositions) MUST appear in the inventory. The test enforces the first half strictly (`inventory ⊆ classification`) and asserts the inventory's 14-table list is a subset of the classification matrix's table set. The reverse direction is unenforceable without re-deriving "user-attributable" — that signal already lives in the EF attributes and is enforced by `GdprInventoryCoverageTests`.

3. **markdownlint:** the task observable invokes `npx markdownlint-cli` ad hoc. We do *not* add it as a `web/package.json` dev-dep (it has no runtime use), and we do *not* wire it into `scripts/ci-local.sh`. The author runs the command from the observable when verifying; CI does not run markdownlint in this slice. This keeps the blast radius scoped to the five new docs.

4. **No `README.md` exists at repo root.** The DoD line "docs/COMPLIANCE.md linked from README.md and top-level docs index" is unsatisfiable for README.md. Decision: interpret "top-level docs index" as the existing CHANGELOG `[Unreleased]` entry plus an `Added` line in the changelog naming `docs/COMPLIANCE.md` and the five new files. The cross-link FROM `docs/COMPLIANCE.md` TO the policies and to `data-inventory.md` / `vendor-inventory.md` is the umbrella's own TOC (already in scope and load-bearing). Documented in the plan; this is the pragmatic resolution.

5. **Forward references to M18-011 are explicit and labelled.** `vendor-inventory.md` and `data-flow-customer.md` / `data-flow-internal.md` ship in M18-011. The umbrella TOC lists them with `(M18-011)` annotations and either omits the link or marks it `(forthcoming)` so markdownlint does not see a broken relative link.

6. **The COMPLIANCE.md umbrella file already exists** (10 lines, links to the GDPR inventory). This slice extends it rather than creating it from scratch.

1. `# Data Classification Matrix`
2. `## Classification Tiers` — define the four tiers with examples and handling rules:
   - **Public** — marketing copy, documentation, OpenAPI specs.
   - **Internal** — engineering-team-only operational data with no individual user attribution (e.g. webhook event metadata, aggregated telemetry).
   - **Confidential** — customer-attributable business data: audit logs, schedules, results, org settings, custom roles.
   - **Restricted** — auth credentials, secrets, payment data, personally-identifiable information: `users.password_hash`, `signing_keys`, `team_vaults` encrypted templates (M18-009), `schedules.env_vars` encrypted blobs (M18-009), Stripe payment-method tokens.
   (Observable greps `Public\|Internal\|Confidential\|Restricted`.)
3. `## Per-Table Classification` — Markdown table mirroring the inventory's table-row format so it is machine-parseable by the consistency test. Columns: `Table | Classification | Encryption-at-Rest | Rationale`. Includes all 32 tables from `docs/SPECIFICATION.md` schema appendix (lines 10500–11258):
   - Auth: `users`, `magic_link_tokens`, `oauth_state_tokens`, `user_audit_log`, `signing_keys`, `refresh_tokens`, `device_authorization_codes`, `sessions`, `devices`, `service_tokens`, `auth_audit_log`, `password_reset_tokens`, `email_verification_tokens`, `deletion_reauth_tokens` (added in M18-005).
   - Billing: `subscriptions`, `payment_methods`, `invoices`, `subscription_audit_log`, `stripe_webhook_events`.
   - Integrations: `github_installations`, `github_webhook_events`, `pr_checks`, `gitlab_installations`, `gitlab_webhook_events`.
   - Workspace: `team_vaults`, `trials`, `schedules`, `scheduled_runs`, `organizations`, `organization_members`, `organization_invitations`, `organization_audit_log`, `license_validations`, `organization_custom_roles`, `notification_rules`, `coordinator_jobs`.
4. `## Encryption-at-Rest Posture` — table mapping each Restricted table to its envelope-encryption mechanism:
   - `team_vaults.template_jsonb` → AES-256-GCM envelope (M18-009; `ITeamVaultKeyProvider`).
   - `schedules.env_vars` → AES-256-GCM envelope (M18-009; `IScheduleEnvKeyProvider`).
   - `signing_keys.private_key` → KMS-wrapped per-row (v3-10; CI lint enforced by `scripts/check-signing-keys.sh`).
   - `github_installations.encrypted_pat` / `gitlab_installations.encrypted_pat` → AES-256-GCM (existing).
   - `users.password_hash` → argon2id (existing; not envelope, hash function).
   (Observable greps `team_vaults\|schedules.env_vars\|envelope`.)
5. `## Consistency with GDPR Data Inventory` — explicit pointer: every table in `data-inventory.md` appears in this matrix; the reverse is not required because the matrix is the broader superset covering non-user-attributable tables.
6. `## Review Cadence` — reviewed each time the schema appendix changes (event-driven, not date-driven). Stated next-review trigger.

## Risks and Edge Cases

- **Risk: forward-reference markdown links to M18-011 files break markdownlint** → **Mitigation:** annotate them as `(M18-011 — forthcoming)` plain text without a `[text](path)` link to a non-existent file. The observable `npx markdownlint-cli` only inspects the five new files; it does not check link targets resolve. The DoD also mentions `npx markdown-link-check` — relative links to *unwritten* files would fail. Resolution: in `docs/COMPLIANCE.md`, M18-011 references are bare text, not links. The links that are present (to the four new policy files + `data-inventory.md`) all resolve.

- **Risk: classification-matrix table count drifts from schema appendix** → **Mitigation:** `Matrix_lists_all_32_schema_appendix_tables` test hardcodes the 32-table list. When a future migration adds a new table, both the schema appendix AND the matrix must be updated, or the test fails naming the missing table.

- **Risk: inventory file gains a row that the matrix doesn't know about** → **Mitigation:** `Every_inventory_table_appears_in_matrix` enforces the asymmetric subset.

- **Risk: markdownlint default rules reject reasonable prose patterns (line length, bare URLs, etc.)** → **Mitigation:** use markdownlint-cli defaults; if a specific rule triggers, fix the doc rather than disable the rule (compliance artefacts should be lint-clean). If a rule is genuinely unreasonable, a `.markdownlint.json` config file may be added scoped to `docs/security/**` — out of scope for this slice unless required.

- **Edge case: existing `docs/COMPLIANCE.md` is 10 lines and the GDPR test asserts the file exists and links to `data-inventory.md`** → **Handling:** rewrite preserves the GDPR cross-link as required by `ComplianceMd_links_to_data_inventory`.

- **Edge case: no README.md exists** → **Handling:** documented in Architectural Decision 4. CHANGELOG `[Unreleased]` entry is the discoverability mechanism; the COMPLIANCE.md umbrella is self-discoverable from `docs/`.

- **Edge case: review cadence dates** → **Handling:** state explicit "next review: 2027-05-19" (annual policies) or "next review: at next schema-appendix change" (classification matrix). No mechanical enforcement — the cadence belongs to M19+.
