# Implementation Plan: M18-005

## Overview

Add the GDPR account-deletion state machine: two new TIMESTAMPTZ columns on `users` (`pending_deletion_at`, `anonymised_at`), three new endpoints under `/api/v1/users/me/deletion-requests` (request/cancel/status), a reauth-token sub-system (`drto_` prefix, 5-minute single-use, lifted from the existing password-reset token pattern), `UserDeletionFinalizerHost : BackgroundService` running daily at 03:00 UTC, two new MJML email templates (`account_deletion_initiated`, `account_deletion_completed`), and a test-only `/api/v1/internal/test-hooks/run-deletion-finalizer` hook. The anonymisation work itself is stubbed behind `IUserAnonymiser` — this slice asserts only the state-machine transitions and host wiring; the concrete implementation ships in M18-006.

## Code Exploration Findings

**Auth/token issuance baseline.** `AuthTokenIssuer` (`src/ApiTool.Backend/Auth/AuthTokenIssuer.cs`) mints opaque prefixed tokens — 32 random bytes base64url-encoded, persisted as SHA-256 hash. The `password_reset_tokens` table (entity at `Data/Entities/PasswordResetToken.cs`, migration `20260507174354_AddPasswordResetAndEmailVerificationTokens.cs`) is the canonical shape: `id`, `user_id`, `token_hash` (unique), `issued_at`, `expires_at`, `consumed_at`, `revoked_at`, with active/hash/user indexes. We reuse this shape verbatim for `deletion_reauth_tokens` (new table, prefix `drto_`).

**User entity.** `Data/Entities/User.cs` has `Id`, `Email`, `CreatedAt`, `PasswordHash?`, `IsAdmin`, `EmailVerified`. `AppDbContext.OnModelCreating` configures the `users` table at lines 106–115 (no `[Index]`, no `[Timestamp]`). Adding two nullable DateTime columns is a strictly additive migration. The `[GdprIncluded(InExportInDeletionHard)]` annotation on `User.Id` means the user row is hard-deleted by M18-006; this slice doesn't touch that path.

**Compliance.Gdpr namespace.** Existing files: `UserDataExportEndpoints.cs`, `UserExportBuilderHost.cs`, `UserExportBundleAssembler.cs`, `UserExportRequestDto.cs`, `GdprAttributeScanner.cs`, `GdprBundleManifest.cs`, `GdprManifestEntry.cs`. All new GDPR files for this slice land in the same folder.

**Email pipeline.** `IEmailQueue.EnqueueAsync(EmailMessage, CancellationToken)` accepts `(To, TemplateSlug, Variables, EnqueuedAt)`. Slugs are registered in `EmailTemplateInventory.Slugs`. The MJML+JSON template pair lives at `templates/email/<slug>.{mjml,json}`. `EmailTemplateLoader` validates that every JSON-declared variable is present at enqueue time — adding a template requires both files plus the slug entry in `EmailTemplateInventory` and a corresponding `EmailTemplateInventoryDocConsistencyTests` update if one exists. (Verified the inventory list is the single source of truth.)

**Test infrastructure.** `BackendFactory` (`src/ApiTool.Backend.Tests/TestInfrastructure/BackendFactory.cs`) registers `RecordingEmailQueue` in place of `IEmailQueue`, runs against EF Core InMemory, and registers `FakeKeyProvider` so JWTs are deterministic. `TestTokens.Create(userId, email)` mints a Bearer token. The factory skips registration of hosted services for test isolation by gating registration on `env != "Testing"` (see `Program.cs:446–451`); the test-hook endpoint pattern (`MapInternalRunExportBuilderEndpoint`) lets tests drive the host's `TickOnceAsync` synchronously.

**Internal endpoint pattern.** `InternalRunExportBuilderEndpoint` registers only in `Development` + `Testing` and wears `InternalAccessFilter` as belt-and-braces gating. `Program.cs:807–814` shows the canonical wiring location for `MapInternal*` test hooks. We follow the same shape for `MapInternalRunDeletionFinalizerEndpoint`.

**Audit writer.** `IAuditWriter.Append(AuditEvent)` enqueues an audit row but the caller must still call `SaveChangesAsync`. For `account_deletion_cancelled` we emit `OrgId = Guid.Empty` (user-scoped event with no org), `ActorId = userId`, `EventType = "account.deletion_cancelled"`, `TargetType = "user"`, `TargetId = userId`. (Spec doesn't pin the dot-namespace string; we adopt `account.*` to match `account_security_alert` email slug convention.)

**Re-auth header model.** The task spec says the client obtains a re-auth token via "the existing re-auth flow" and presents it as `X-Reauth-Token`. There is no existing re-auth flow in code — only password-reset (which is unauthenticated, email-driven). Decision: ship a minimal re-auth-token issuer in this slice — `POST /api/v1/auth/reauth` (requires Bearer + password in body), mints a `drto_` token, returns `{ "reauth_token": "drto_..." }`, single-use, 5-minute TTL. This is the smallest surface that lets a logged-in user prove they still own their password before requesting account deletion. The endpoint is reusable for future destructive operations.

## Architectural Decisions (made without confirmation)

1. **Reauth scope: dedicated subsystem, not piggyback on password-reset.** Password-reset tokens are 30-minute, email-delivered, and have different threat assumptions (out-of-band proof of email ownership). Re-auth tokens are 5-minute, API-delivered, prove current-session password ownership. Different lifetimes + different delivery channels = different table.
2. **`drto_` prefix.** Matches the `prst_` / `evtk_` pattern (4 lowercase letters + underscore). `drto` = **D**eletion **R**eauth **TO**ken.
3. **Audit-event namespace.** `account.deletion_initiated`, `account.deletion_cancelled`, `account.deletion_finalized` — dot-namespaced per existing convention (see `Audit/AuditEvent.cs` doc-comment example `sso.login`).
4. **`OrgId = Guid.Empty` for user-scoped events.** This is consistent with `AuditEvent.ActorId = Guid.Empty` meaning "no actor". The `OrganizationAuditLogEntry.OrgId` column is non-nullable (per existing migration); using `Guid.Empty` rather than the user's primary org avoids leaking deletion intent into a third-party org's audit log.
5. **No org-scoped notifications in this slice.** "Last-admin protection" is explicitly deferred to M18-006 (per task description). This slice does NOT check whether the user is the sole owner of any org.
6. **Test-hook test-only.** Like `run-export-builder`, the `run-deletion-finalizer` hook registers only in `Development`+`Testing`. CURLEW_INTERNAL=1 is the existing `InternalAccessFilter` gate.
7. **Concurrency token on `users`.** Not added — additive nullable columns don't require optimistic-concurrency rotation, and adding a Version column to `users` would be a wide-blast-radius change that breaks every existing user-update site. The deletion-request path uses a single conditional UPDATE (`SET pending_deletion_at = now() WHERE id = @id AND pending_deletion_at IS NULL`) for idempotency.
8. **`anonymised_at` is set by this slice's stub.** The task says "the host invokes a (stub) IUserAnonymiser when the cooldown is past." To make the state-machine transition observable, the stub `IUserAnonymiser` registered in this slice DOES set `anonymised_at = now()` on the user row but does NOT touch any other table. The real anonymiser in M18-006 will overwrite this stub implementation.
9. **Cancel-URL host.** The `account_deletion_initiated` email's `{{cancel_url}}` is `{WebAppUrl}/account/data/cancel-deletion` (matches the GET-status `cancel_url` field in the response body). `WebAppUrl` comes from `AppOptions.WebAppUrl`.
10. **`account_deletion_completed` email destination.** The user's `Email` column is still present when the finalizer runs (anonymisation hasn't happened in this slice's stub). M18-006 will need to capture the email BEFORE anonymising. Documented as a M18-006 prerequisite in the plan but not implemented here.

#### Host signature

```csharp
public sealed class UserDeletionFinalizerHost(
    IServiceScopeFactory scopeFactory,
    TimeProvider clock,
    ILogger<UserDeletionFinalizerHost> logger,
    TimeSpan? tickInterval = null) : BackgroundService
{
    private static readonly TimeSpan CooldownDuration = TimeSpan.FromDays(30);
    private static readonly TimeSpan DefaultInterval = TimeSpan.FromHours(24); // daily

    public async Task TickOnceAsync(CancellationToken ct) { /* see logic below */ }
    protected override async Task ExecuteAsync(CancellationToken stoppingToken) { /* loop */ }
}
```

`TickOnceAsync` logic:

1. `now = clock.GetUtcNow().UtcDateTime`
2. `threshold = now - CooldownDuration`
3. `var users = await db.Users.Where(u => u.PendingDeletionAt != null && u.PendingDeletionAt <= threshold && u.AnonymisedAt == null).ToListAsync(ct);`
4. For each user:
   - capture `email = user.Email` (snapshot before anonymisation)
   - `await anonymiser.AnonymiseAsync(user.Id, ct);` (stub sets `AnonymisedAt = now`)
   - enqueue `account_deletion_completed` email
   - log `account_deletion_finalized userId={...}`
5. Catch+log per-user exceptions; don't abort the loop on one user's failure.

The daily-at-03:00 schedule is implemented via `tickInterval ?? TimeSpan.FromHours(24)` plus a one-shot delay-until-03:00 at startup. For test parity, the test-hook calls `TickOnceAsync` directly so the schedule logic is untested in this slice (covered by smoke against the running stack).

### Added (M18-005)

- Reauth-token subsystem — `POST /api/v1/auth/reauth` mints a 5-minute single-use `drto_` token presented as `X-Reauth-Token` for sensitive operations.
- Email templates `account_deletion_initiated` and `account_deletion_completed`.

## Risks and Edge Cases

- **Risk:** Adding a re-auth subsystem could be considered out of scope. **Mitigation:** Task spec mandates "the existing re-auth flow" but no such flow exists in code. Building the smallest possible re-auth (one endpoint, dedicated table, no UI) keeps the surface minimal and reuses every existing primitive (AuthTokenIssuer, PasswordHasher). Documented as architectural decision #1 above.
- **Risk:** `UserDeletionFinalizerHost` daily-at-03:00 schedule with a 24h `Task.Delay` is sensitive to clock skew and host restarts (a restart at 02:59 means the host could tick at 02:59 once then 02:59+24h). **Mitigation:** Production-grade scheduling is out of scope for this slice — the test hook drives `TickOnceAsync` directly. Production scheduling correctness is covered by smoke + the M18-006 follow-up.
- **Risk:** `account_deletion_completed` email enqueue references `user.Email` which the M18-006 anonymiser will scrub. **Mitigation:** The plan documents that M18-006 must snapshot the email BEFORE invoking the anonymiser. Our stub does NOT scrub the email, so this slice's tests pass without the snapshot.
- **Edge case:** User initiates deletion → cancels → initiates again. **Handling:** The cancel endpoint clears `PendingDeletionAt`, so a second `POST` is a fresh request (re-auth needed again).
- **Edge case:** User initiates deletion, then a stale GET-status arrives after the host anonymises. **Handling:** GET returns `{anonymised_at: <ts>}` with 200; cancel returns 404 (`no_pending_request` — the row no longer has `PendingDeletionAt` because the anonymiser stub clears the column when it sets `AnonymisedAt`).
- **Edge case:** Two concurrent `POST /deletion-requests` from the same user. **Handling:** Both consume the same X-Reauth-Token; the second `ConsumeAsync` returns `TokenConsumed` → 401. EF's `SaveChangesAsync` on `consumed_at = now()` is the single source of truth.
- **Edge case:** Re-auth issued for User A, presented by User B (token theft). **Handling:** `ConsumeAsync(userId, token)` requires the JWT-authenticated `userId` to match the token's `UserId`; mismatch returns `TokenInvalid`. Test: `ConsumeAsync_with_other_users_token_returns_TokenInvalid` in Step 2.
- **Risk:** EF Core InMemory provider in test factory doesn't enforce unique indexes — the `token_hash` unique index is only verified at the SQLite schema level (Step 1's `AppDbContextSchemaTests`). **Mitigation:** Documented; matches the existing pattern for `password_reset_tokens`.
