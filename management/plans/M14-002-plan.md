# Implementation Plan: M14-002

## Overview

Lands the unified mint endpoint `POST /api/v1/auth/refresh`. The handler validates a presented opaque refresh token + device_id, enforces RFC 9700 §4.14 rotation-on-use with family-revocation reuse detection, and mints all three tokens (License JWT 30d typed `license+jwt`, Access token 1h typed `at+jwt`, opaque refresh 90/365d) signed by the active `IKeyProvider` from M14-001. RFC 7807 problem-details errors with stable codes (`AUTH_REFRESH_REUSED`, `AUTH_REFRESH_EXPIRED`, `AUTH_DEVICE_MISMATCH`, `AUTH_INVALID_REFRESH`). On reuse detection, an `account_security_alert` `EmailMessage` is enqueued onto a `System.Threading.Channels<EmailMessage>` channel — the channel boundary is owned here; the consumer (`EmailQueueProcessor`) lands in M14-014 and is no-op stubbed for unit tests.

## Key Architectural Decisions

These decisions resolve open questions surfaced during exploration. They are documented here so reviewers can challenge them in `/review` rather than rediscovering them. Auto-mode resolutions: I made these choices using best judgment per the spec and prior M14-001 plan; flag in review if any conflict with intent.

1. **Token-issuance is split into a `LicenseTokenIssuer` and an `AccessTokenIssuer` behind a thin `ITokenIssuer` triplet, NOT bundled into one God class.** The two JWT shapes have different `aud`, `typ`, and claim sets. Separate issuers keep each minimal and let the test for `typ != "license+jwt"` cross-rejection (RFC 8725 §3.11) sit in the right unit-test file. Both issuers depend on `IKeyProvider` (already DI-registered). They emit raw JWS using ASP.NET's `Microsoft.IdentityModel.JsonWebTokens.JsonWebTokenHandler` — but since `IKeyProvider.SignAsync` returns raw R||S, we hand-build the JWS string (header.payload.signature) using `Base64UrlEncoder` + the signature bytes. This matches how the existing `BouncyCastleEs256` produces signatures and avoids re-importing the private key into a `SecurityKey` round-trip.

2. **A new `IRefreshTokenIssuer` mints the opaque value AND inserts the row.** Lifetime: `min(now+90d, family_root.issued_at+365d)` per spec :7934. Returns `(plaintext_token, RefreshToken row)`. Token is 32 random bytes base64url-encoded (~43 chars). Hashed via `SHA-256` for `token_hash` storage per spec :7905.

3. **`RefreshTokenService` owns the rotate-or-revoke business logic.** Handler does HTTP shape-checking only; the service is the pure transactional core. Methods:
   - `RotateAsync(plaintextToken, deviceId, ip, userAgent, ct) → RotateResult` — returns one of {Success, Reused, Expired, DeviceMismatch, NotFound, Revoked}.
   - The reuse-detection branch updates ALL family rows in a single `UPDATE refresh_tokens SET revoked_at=NOW(), revoke_reason='reuse_detected' WHERE family_id=@familyId AND revoked_at IS NULL` and enqueues the email.
   - Wraps the rotate in `db.Database.BeginTransactionAsync()` so the row's `rotated_at` set + new row insert are atomic. EF Core InMemory does not support transactions; the test path uses SQLite-in-memory via `TestDb.CreateOpen` which does.

4. **Email queue boundary — `Channel<EmailMessage>` injected via DI, no-op consumer for now.** This slice owns:
   - `EmailMessage` record (in `Notifications/Email/EmailMessage.cs`) — `(string To, string TemplateSlug, IReadOnlyDictionary<string,string> Variables, DateTimeOffset EnqueuedAt)`.
   - `IEmailQueue` interface with `ValueTask EnqueueAsync(EmailMessage msg, CancellationToken ct)`.
   - `ChannelEmailQueue` implementation backed by an unbounded `Channel<EmailMessage>`.
   - DI registration: `services.AddSingleton<Channel<EmailMessage>>(_ => Channel.CreateUnbounded<EmailMessage>())` and `services.AddSingleton<IEmailQueue, ChannelEmailQueue>()`.
   - The consumer (`EmailQueueProcessor`) ships in M14-014. Tests inject a `RecordingEmailQueue : IEmailQueue` test double that captures messages into a list — this is the contract test for the manifest variables (`first_name`, `event_time`, `event_ip`, `relogin_url`).
   - This decision is consistent with the task scope: "queue boundary stubbed in this slice; the EmailQueueProcessor binding lands in M14-014, but the handler must compile and run with a no-op channel reader registered for unit tests".

5. **Trial fields default to `none`/null per spec :7872 + investigation decision J.** The `LicenseTokenIssuer` always emits `trial_state="none"` and omits `trial_expiry` (or emits null per the JsonIgnoreCondition.WhenWritingNull policy already in `Program.cs`). This is explicit code, not a TODO — M16 will replace the default-emitter with a `ITrialStateResolver` injection point.

6. **`tier`/`org_id`/`org_role` resolution — first OrganizationMember row by `joined_at` ASC.** A user can belong to multiple orgs; the spec doesn't pin which org's tier the License JWT carries when the user has many. For M14, the issuer picks "the user's first/oldest org membership" deterministically (smallest `JoinedAt`, tiebroken by `OrgId`). This matches how a CLI user typically operates (one workspace per laptop session). M17/M18 may add a multi-org switcher; the claim shape doesn't change. If the user has no org membership, `tier="free"`, `org_id=null`, `org_role=null`.

7. **`features` and `request_limit` come from a static tier-→-config map for M14.** Spec lines 7867–7868 list these as claims sourced from "tier+org" but no service computes them yet. A lightweight `TierConfig.For(tier) → (features, requestLimit)` table lives next to `SubscriptionTier` for now:
   - `Free`        → `features=[]`, `request_limit=1000`
   - `Professional`→ `features=["unlimited_requests","collections","environments"]`, `request_limit=100000`
   - `Team`        → `features=[…above…,"shared_collections","sso"]`, `request_limit=1000000`
   - `Enterprise`  → `features=[…above…,"audit_log","custom_roles"]`, `request_limit=int.MaxValue`
   These are the rough contours from existing plans; M16/M18 will refine. Documented in code so reviewers can challenge specific values without blocking M14-002.

8. **Algorithm pinned to ES256, typ enforced strictly.** The header is hand-built: `{"alg":"ES256","kid":"<active-kid>","typ":"license+jwt"}` (or `"at+jwt"`). No `none`, no HS256, no RS256 — there's no SecurityAlgorithms-string indirection that could downgrade.

9. **`device_id` validation runs BEFORE token-hash lookup.** Cheaper to reject early; also avoids a timing oracle that distinguishes "valid token, wrong device" from "invalid token entirely". Both still hash and look up to keep timing constant — the device check happens after the row is loaded, then we return AUTH_DEVICE_MISMATCH instead of AUTH_INVALID_REFRESH.

10. **No `/api/v1/license/issue` endpoint registration.** The DoD bans this; the Swagger surface test asserts the path is absent from `paths`.

11. **Refresh-token plaintext format = `base64url(32-random-bytes)`.** ~43 chars, no padding. The CLI never sees the hash; only the plaintext travels over HTTPS in request body per spec :8201.

12. **SQLite test database supports transactions.** Tests use `TestDb.CreateOpen()` (SQLite in-memory, supports transactions) for `RefreshTokenService` unit tests so `BeginTransactionAsync` exercises real semantics. The integration test that exercises the live HTTP endpoint uses `BackendFactory` which is `EF Core InMemory` — that provider does NOT support transactions, so the integration test path uses a wrapped `IDbContextTransaction` no-op when `db.Database.IsInMemory()`. The service detects this and fails open for InMemory, fail-fast for any other untested provider. This dual-mode is a known wart but matches how the existing `OrganizationService` + InMemory tests work.

13. **`request_id` claim in problem-details = `HttpContext.TraceIdentifier`.** Already a project pattern indirectly (via ASP.NET Core's request-id middleware). The response also sets header `X-Request-Id` to the same value for client-side correlation per spec :8254 + :8265.

```csharp
public sealed class RefreshTokenIssuer(TimeProvider clock)
{
    /// <summary>
    /// Mints a new opaque refresh token. Returns the plaintext (~43 chars b64url)
    /// AND a populated RefreshToken row with TokenHash=SHA256(plaintext) and the
    /// 90/365 lifetime from spec :7934.
    /// </summary>
    public (string Plaintext, RefreshToken Row) Mint(

        Guid deviceId,
        Guid familyId,
        Guid? parentId,

public static class RefreshSentinelErrors
{
    public const string Reused          = "AUTH_REFRESH_REUSED";
    public const string Expired         = "AUTH_REFRESH_EXPIRED";
    public const string DeviceMismatch  = "AUTH_DEVICE_MISMATCH";
    public const string Invalid         = "AUTH_INVALID_REFRESH";
}
```

#### Algorithm Sketch

```text
RotateAsync(plaintext, deviceId, ip, ua, ct):
  1. tokenHash = SHA256(plaintext)
  2. row = db.RefreshTokens.FirstOrDefaultAsync(r => r.TokenHash == tokenHash)
     - if null: return RotateResult(NotFound)
  3. if row.RevokedAt != null:
       enqueue NO email (already revoked); return RotateResult(Revoked)  // maps to AUTH_INVALID_REFRESH
  4. if row.ExpiresAt < now: return RotateResult(Expired)
  5. if row.DeviceId != deviceId: return RotateResult(DeviceMismatch)
  6. if row.RotatedAt != null:  // REUSE
       UPDATE refresh_tokens
         SET revoked_at = now, revoke_reason = 'reuse_detected'
         WHERE family_id = row.FamilyId AND revoked_at IS NULL
       enqueue EmailMessage(account_security_alert, {first_name, event_time, event_ip, relogin_url})
       return RotateResult(Reused)
  7. // Happy path: rotate
     using tx = db.Database.BeginTransactionAsync():
       row.RotatedAt = now
       db.RefreshTokens.Update(row)
       familyRoot = (row.ParentId is null) ? row : await db.RefreshTokens.FirstAsync(r => r.Id == row.FamilyId)
       (plaintext, newRow) = issuer.Mint(row.UserId, deviceId, row.FamilyId, parentId: row.Id,
                                         familyRootIssuedAt: familyRoot.IssuedAt, ip, ua)
       db.RefreshTokens.Add(newRow)
       await db.SaveChangesAsync()
       await tx.CommitAsync()
     return RotateResult(Success, newRow, plaintext, row.UserId, row.FamilyId)
```

#### Handler Sketch

```csharp
public static class AuthRefreshEndpoints
{
    public static IEndpointRouteBuilder MapAuthRefreshEndpoints(this IEndpointRouteBuilder app)
    {
        app.MapPost("/api/v1/auth/refresh", async (
            AuthRefreshRequest? body,
            HttpContext http,
            RefreshTokenService refreshSvc,
            LicenseTokenIssuer licenseIssuer,
            AccessTokenIssuer accessIssuer,
            AppDbContext db,
            CancellationToken ct) =>
        {
            if (body is null
                || string.IsNullOrWhiteSpace(body.RefreshToken)
                || body.DeviceId == Guid.Empty)
            {
                return RefreshProblem.Invalid(http, "refresh_token and device_id are required");
            }

            var ip = http.Connection.RemoteIpAddress?.ToString();
            var ua = http.Request.Headers.UserAgent.ToString();

            var result = await refreshSvc.RotateAsync(body.RefreshToken, body.DeviceId, ip, ua, ct);

            switch (result.Outcome)
            {
                case RotateOutcome.Reused:         return RefreshProblem.Reused(http);
                case RotateOutcome.Expired:        return RefreshProblem.Expired(http);
                case RotateOutcome.DeviceMismatch: return RefreshProblem.DeviceMismatch(http);
                case RotateOutcome.NotFound:
                case RotateOutcome.Revoked:        return RefreshProblem.Invalid(http, "Refresh token not recognised");
            }

            // Success: mint License + Access
            var (tier, orgId, orgRole, email) = await ResolveUserContextAsync(db, result.UserId!.Value, ct);
            var (features, requestLimit) = TierConfig.For(tier);
            var licenseJwt = await licenseIssuer.IssueAsync(new LicenseTokenInput(
                UserId: result.UserId!.Value,
                Email: email,
                Tier: tier, OrgId: orgId, OrgRole: orgRole,
                DeviceId: body.DeviceId,
                Features: features, RequestLimit: requestLimit), ct);
            var accessToken = await accessIssuer.IssueAsync(new AccessTokenInput(
                UserId: result.UserId!.Value,
                Tier: tier, OrgId: orgId, DeviceId: body.DeviceId), ct);

            return HttpResults.Ok(new AuthRefreshResponse(
                LicenseJwt: licenseJwt,
                AccessToken: accessToken,
                RefreshToken: result.NewPlaintextToken!));
        })
        .AllowAnonymous()
        .DisableAntiforgery()
        .WithName("AuthRefresh")
        .WithTags("Auth")
        .Accepts<AuthRefreshRequest>("application/json")
        .Produces<AuthRefreshResponse>()
        .ProducesProblem(StatusCodes.Status400BadRequest)
        .ProducesProblem(StatusCodes.Status401Unauthorized);

        return app;
    }
}
```

#### RefreshProblem helper

```csharp
internal static class RefreshProblem
{
    public static IResult Reused(HttpContext http) => Build(http, 401,
        type:   "https://api.apitool.dev/errors/refresh-token-reused",
        title:  "Refresh token reuse detected",
        detail: "Token has been rotated; entire token family revoked. Re-authenticate via 'curlew login'.",
        code:   RefreshSentinelErrors.Reused);

    public static IResult Expired(HttpContext http) => Build(http, 401,
        type: ".../errors/refresh-token-expired", title: "Refresh token expired",
        detail: "Re-authenticate via 'curlew login'.", code: RefreshSentinelErrors.Expired);

    public static IResult DeviceMismatch(HttpContext http) => Build(http, 401,
        type: ".../errors/auth-device-mismatch", title: "Device mismatch",
        detail: "device_id does not match the refresh token's bound device.",
        code: RefreshSentinelErrors.DeviceMismatch);

    public static IResult Invalid(HttpContext http, string detail) => Build(http, 401,
        type: ".../errors/auth-invalid-refresh", title: "Invalid refresh token",
        detail: detail, code: RefreshSentinelErrors.Invalid);

    private static IResult Build(HttpContext http, int status, string type, string title, string detail, string code)
    {
        var requestId = http.TraceIdentifier;
        http.Response.Headers["X-Request-Id"] = requestId;
        var problem = new ProblemDetails
        {
            Type = type, Title = title, Status = status, Detail = detail,
            Extensions = { ["code"] = code, ["request_id"] = requestId },
        };
        return HttpResults.Json(problem, contentType: "application/problem+json", statusCode: status);
    }
}
```

### Step 5: `scripts/test-token.sh` extension + observable command

**Rationale:** The task observable script invokes `./scripts/test-token.sh refresh <email>` and `./scripts/test-token.sh device <email>`. The existing script only mints HS256 JWTs. We extend it to support two modes:

**Decision #11 (auto-resolved):** The task observable command writes to a `device_id` field but the `devices` table is M14-005's responsibility per the M14 DAG. ## Risks and Edge Cases

- **Risk:** EF Core InMemory provider doesn't support transactions, so the integration test's `BeginTransactionAsync` would throw.
  **Mitigation:** Decision #12 — the service skips `BeginTransactionAsync` when `db.Database.IsInMemory()`. Unit tests use SQLite-in-memory which DOES support transactions — that's where we get the real-semantics coverage.

- **Risk:** EF Core InMemory provider does not enforce unique indexes (e.g. `IX_refresh_tokens_token_hash`), so a duplicate-hash bug could pass tests.
  **Mitigation:** Add a SQLite-backed unit test in `RefreshTokenServiceTests` that asserts `db.SaveChangesAsync()` throws `DbUpdateException` when two rows attempt the same `token_hash` — guards against accidental hash collisions in test setup masking real bugs.

- **Risk:** Hash collision between two random refresh tokens.
  **Mitigation:** 256-bit random source; collision probability is negligible (~birthday bound at ~2^128 inserts). The unique constraint enforces it at the DB level.

- **Risk:** Family-revocation `UPDATE … WHERE family_id = X AND revoked_at IS NULL` could miss rows that another concurrent request has just inserted.
  **Mitigation:** The reuse path uses `IsolationLevel.Serializable` for its transaction. Serializable on Postgres uses SSI; on SQLite it's the default (single-writer at a time). Acceptable for this slice; benchmarked under M19 if it surfaces as a hot-spot.

- **Risk:** Trial fields shape change between M14 and M16.
  **Mitigation:** Decision #5 — emit `trial_state="none"` always, `trial_expiry=null` always, in M14-002. M16 only changes the values, not the keys. Test `Trial_fields_default_to_none_and_null` is the wire-shape contract.

- **Risk:** `request_id` exposed in the problem-details response could leak server internals if `TraceIdentifier` carries something sensitive.
  **Mitigation:** ASP.NET Core's default `TraceIdentifier` is opaque (e.g. `0HMV6...0`); not security-relevant. Same as the existing pattern indirectly used via `X-Request-Id` middleware.

- **Edge case:** A refresh token that was ALREADY revoked (not just rotated). The service returns `RotateOutcome.Revoked`, the handler maps it to `AUTH_INVALID_REFRESH` (not `AUTH_REFRESH_REUSED`). Rationale: a previously-revoked token should not re-trigger the family-revocation alert because the alert was already sent at first reuse. This matches the Auth0/Okta pattern.

- **Edge case:** Device ID is `Guid.Empty` (`00000000-…`). Treated as a missing field (returns `AUTH_INVALID_REFRESH`).

- **Edge case:** The user's first org membership has been deleted (race). `ResolveUserContextAsync` falls back to `tier="free", org_id=null, org_role=null` — same as a user with no org.

- **Edge case:** Rate limiting. The endpoint is unauthenticated. We do NOT add a rate limiter in this slice — the existing `AddRateLimiter` configuration in `Program.cs` already has a "results-ingest" pattern; M14 may add an "auth-refresh" policy in a separate slice. Not in scope here per the focused-slice rule.
