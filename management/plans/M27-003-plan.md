## The narrowing decision

The task lists four candidate surfaces and asks for a choice, not a menu. The
unifying criterion it sets is **prefer surfaces where a defect produces a wrong
result over surfaces where it produces an error.**

### Selected: stateful sequences and the report they produce

Chosen because a probe found a real defect on the first attempt, and because it
is the only candidate that is both unreached and deterministic.

**The defect, measured.** A collection of one plain request plus one
`data_driven` request over the 3-row `testapi/collections/data/bulk.csv`:

```
summary: {'total': 2, 'passed': 4, 'failed': 0, 'skipped': 0}
requests[] length: 4
run status: passed          exit code: 0
```

`total` is 2. `passed` is 4. `len(requests)` is 4. The run reports success and
exits 0, and a consumer computing `passed/total` gets 200%.

`docs/MANUAL.md:1879` documents the contract this violates — its worked example
is `{"total": 3, "passed": 1, "failed": 1, "skipped": 1}` against exactly three
`requests[]` entries, so `total == passed + failed + skipped == len(requests)`.

**Root cause, located.** `internal/runner/runner.go:1375`:

```go
total := len(col.Setup.Items) + len(col.Requests.Items) + len(col.Teardown.Items)
summary := &Summary{Total: total}
```

`Total` counts *declared* items. `computeSummary` (runner.go:3364) increments
`Passed`/`Failed`/`Skipped` while ranging over *executed* results. A
`data_driven` request expands one declared item into N results, and the two
numbers part company.

**Why no existing test catches it.** `internal/runner/runner_test.go:7275`
already asserts exactly this invariant:

```go
if len(results) != summary.Total {
    t.Errorf("summary counts %d requests but %d were reported", summary.Total, len(results))
}
```

but only inside a GraphQL test built from three plain requests, where nothing
expands. The guard exists and has a hole in it. That is precisely the class this
phase is for: the arithmetic is checked, but not where it breaks.

**Why the surface is unreached today.** `data_driven` appears exactly once in
the whole dogfood suite (`testapi/collections/20-extraction.yaml:72`), with no
`store_results`, no `parallel`, no `rate_limit`. Nothing in `testapi/` has ever
asserted anything about curlew's *summary arithmetic* against a server-side
account of what actually happened.

### Rejected: long-running and streaming

Already reached by Phase 3. §9.M plus `/sse`, `/sse/reconnect`, `/stream/{n}`,
`/stream/json/{n}`, `/ndjson/{n}`, `/stream/infinite` and the nine `/ws/*`
endpoints are exercised by `92-streaming.yaml` and `91-websocket.yaml`, and
`/stream/infinite` is already exempted in `parity_test.go` with a stated reason.
Building it again would re-answer an answered question.

### Rejected: adversarial-but-legal servers

Already reached by Phase 2. The raw layer (§9.E) is 16 endpoints on a second
listener that uses no HTTP library, with 15 hand-reviewed golden transcripts
covering enormous headers (`header-huge`), many headers (`header-many`),
duplicate and mismatched `Content-Length` (`content-length-duplicate`, `-over`,
`-under`, `-with-chunked`), and `crosscheck.sh` proving curl agrees. This is the
best-covered surface in the repository.

### Rejected as a bare gate step: concurrency under contention

Real, but **measured nondeterministic**. A three-request collection (create A,
create B, list asserting `total == 2`) run with `--parallel`:

```
parallel_execution: {'wave_count': 1, 'max_parallelism': 3}
over 12 runs: passed=2  failed=10
```

Dependency analysis in `internal/parallel` is driven by variable references, so
it cannot see that the list depends on the creates *server-side*; all three land
in one wave and race. A 2-in-12 pass rate is a flaky gate step, and this
repository has already deleted one wall-clock flake (M21-003) and says so in
`60-barrier.yaml`'s own header. The deterministic half of this surface — *is
`--parallel` actually parallel* — is already proven by the existing barrier
rendezvous.

**Carried forward instead:** the finding itself is worth recording in §11D as an
observation with its measurement, not built into a gate step.

## The oracle: how a wrong result is detected

The whole difficulty is that curlew reports success. Detection needs a source of
truth curlew does not author. Phase 4 uses two, and **the machinery already
exists** — no new mudflat endpoint is required, which also keeps §16 anti-bloat
and `testapi/parity_test.go` satisfied for free.

**Oracle A — internal consistency (curlew against itself).** The results
document must satisfy its own documented invariant:

```
summary.total == summary.passed + summary.failed + summary.skipped == len(requests[])
```

No server needed. This is the one the measured defect violates.

**Oracle B — external agreement (mudflat against curlew).** mudflat keeps
per-session state and will report it, independently of anything curlew claims.
All three were verified working during planning:

| Endpoint | Returns | Measured |
|---|---|---|
| `GET /s/{sid}/concurrency` | `{"current","max_observed","total"}` | `total: 4` after 4 requests — a server-side count of what curlew actually sent |
| `GET /s/{sid}/resources` | `{"total", "items": [...]}` | `total: 3` after a 3-row `data_driven` POST |
| `GET /s/{sid}/flaky/fail-then-succeed?times=N` | `{"attempt": n, ...}` | server `attempt: 3` agreeing with curlew's `attempt_details` length 3 (affirmative) |

The harness asserts that curlew's count of what it did equals mudflat's count of
what happened. A retry that is silently dropped, an iteration that never fires,
or a summary that miscounts shows up as a numeric disagreement rather than as an
error — which is the point.

### Step 5: The ledger harness

**Rationale:** The collection can only assert things a collection can express.
The harness asserts what no collection can: that curlew's *own report* is
arithmetically sound and agrees with the server.

#### Files to Modify

| File | Action | Description |
|------|--------|-------------|
| `testapi/harness/ledger.sh` | create | Runs `25-ledger.yaml`, then checks Oracle A and Oracle B |

Follows the conventions read off `gaps.sh` exactly: `set -euo pipefail`, a
`--url` argument, `mktemp -d` with a cleanup `trap`, the `run_bounded` helper
(macOS has no GNU `timeout(1)`), `python3` for JSON, `FAILURES`/`CHECKED`
counters, and — critically — the **zero-check guard**, because `gaps.sh` states
the rule this repository already learned: *a harness that reports zero checks as
success is worse than no harness.*

```bash
#!/usr/bin/env bash
# ledger.sh — check curlew's account of a run against mudflat's.
#
# Specification §18 Phase 4. Every other harness asks whether a request
# succeeded or failed. This one asks whether the NUMBERS are right, because a
# wrong number is what a passing run looks like from the outside.
#
# Two oracles:
#   A. Internal — summary.total == passed+failed+skipped == len(requests[]).
#      docs/MANUAL.md:1879 documents this; §11D.1 is where it was broken.
#   B. External — mudflat's per-session counters agree with curlew's report.
#      The server is the independent witness; it does not read curlew's output.
#
# Usage:
#   testapi/harness/ledger.sh [--url http://127.0.0.1:8080]
#
# Exit codes:
#   0 — every count agreed
#   1 — a count disagreed, or nothing could be evaluated
#   2 — usage or setup error
```

The failure message carries promotion instructions, as every harness here does:

```
  LEDGER MISMATCH: summary.total=2 but requests[] holds 4
    curlew's report does not add up. If this is now correct, the defect is
    fixed: keep this check (it is the guard that proves it stayed fixed) and
    record the change in specification §11D.
```

#### Tests to Write FIRST (RED phase)

The harness is the test. Its RED state is demonstrable and must be demonstrated
before Step 3's fix is kept:

#### The promotion procedure, for any defect found during the work

Restating the rule so the execute phase cannot improvise: a reproduction is
**moved, never deleted**. Exactly one of:

1. **Into a passing collection** (`testapi/collections/`) — when the request now
   succeeds and the assertion is the guard.
2. **Into `testapi/gaps/expected-failures.yaml`, inverted** — when the request
   still cannot succeed but the *message or classification* is what changed.
   `gaps.sh` then fails on an unexpected pass.
3. **Into a unit test** — when the claim is about curlew's own output rather than
   about a response, so there is no failing request to record. §11D.1 takes this
   route, as §11C.6/§11C.9/§11C.10 did.

Each promotion adds a row to the §11D table naming where the evidence now lives.

## Risks and Edge Cases

- **Risk: a flaky gate step.** → **Mitigation:** the contention surface is
  measured at 2/12 and is explicitly *not* built as a gate step. Everything in
  `25-ledger.yaml` is deterministic: fixed CSV rows, `times=2` failure injection
  with no clock, and counters rather than timings. No wall-clock comparison
  appears anywhere, per M21-003.

- **Risk: gate runtime cost.** → **Mitigation:** the harness reuses the
  already-running mudflat from the dogfood block (no new server, no new port) and
  issues roughly a dozen requests against a local listener. Budget: under 5
  seconds. The execute phase must measure the before/after wall time of
  `ci-local.sh --go` and record it; if it exceeds ~10s, trim the collection.

- **Risk: port collision.** → **Mitigation:** none introduced — the harness takes
  `--url` and is handed `${MUDFLAT_URL}` (port 18080) exactly as the four
  existing harnesses are.

- **Risk: `§16` anti-bloat / parity failure.** → **Mitigation:** the design adds
  **zero new endpoints**. If the execute phase finds one is genuinely needed, it
  must also add a §9 entry and collection coverage in the same commit, or
  `testapi/parity_test.go` fails the build.

- **Risk: the `Total` fix changes an exit code somewhere.** → **Mitigation:**
  exit status derives from `Failed`, not `Total`; `computeSummary` does not touch
  `Failed`. The guard rail's use of the declared count is deliberately left
  alone. Confirm with the full suite plus `./smoke/run.sh`.

- **Edge case: an empty collection.** → **Handling:** `len(results) == 0` gives
  `Total = 0`, and `0 == 0+0+0` holds. Covered by the `"edge case - empty
  collection"` table row.

- **Edge case: a fatal error mid-run.** → **Handling:** the four early-return
  call sites pass the partial `all` slice, so `Total` reflects what was actually
  reported rather than what was planned — which is the documented contract.
  Covered by the teardown row.

- **Edge case: guard rail truncates the run.** → **Handling:** `LimitExceeded`
  still compares `counter` against the *declared* `total`, which is left in
  place precisely so this keeps working.

- **Risk: the phase finds nothing further.** → **Mitigation:** it already found
  one defect during planning, so §11D is non-empty regardless. Affirmative
  results (the retry-attempt agreement measured during planning) are recorded
  too, as §11C did — a checked claim that came out right is a finding.
