# Implementation Plan: M17-005

## Overview
Register two new dynamic functions (`$jwtDecodeHeader`, `$jwtDecodeClaims`) that split a JWT on `.`, base64-url-decode the requested segment, and JSON-roundtrip the bytes to produce a canonical compact JSON string. Pure standard-library work (`encoding/base64.RawURLEncoding` + `encoding/json`); no signature verification (out of scope, documented as a security-relevant caveat).

## Architectural Decisions

The exploration of `internal/variable/dynamic.go`, `dynamic_helpers.go`, `dynamic_test.go`, the M17-004 plan, and the M12-002 (`$base64Decode`) precedent surfaces seven design choices worth recording up front. Each is the lowest-risk option that satisfies the behaviors and reuses existing wiring without modification.

1. **Two registrations sharing a private helper `decodeJWTSegment`.** Both functions take exactly one arg (the token), differ only by which segment index they decode (0 = header, 1 = claims), and otherwise behave identically — same error codes, same truncation, same JSON roundtrip. A shared helper keeps the registration call sites to two lines each and concentrates the error-shaping logic in one place. The helper lives in `dynamic_helpers.go` next to the existing webhook-sig helpers (the file already exists; M17-004 created it for exactly this kind of cross-call shared logic).

2. **Use `encoding/base64.RawURLEncoding` (URL-safe alphabet, NO padding).** JWTs deliberately omit the `=` padding per RFC 7515 §2 / RFC 4648 §5, and use `-` and `_` instead of `+` and `/`. `RawURLEncoding` is the exact match. `URLEncoding` would reject the unpadded input; `StdEncoding` (used by `$base64Decode`) would reject the URL-safe alphabet. This is the single most important decision — using the wrong encoding silently produces a `DYNFN_JWT_DECODE_BAD_BASE64` error on every real JWT.

3. **Use `encoding/json.Unmarshal` into `interface{}` then `json.Marshal` for canonicalisation.** This is what the task scope explicitly calls for. Side effect (and feature): the marshaller sorts map keys alphabetically — so the header roundtrip `{"alg":"HS256","typ":"JWT"}` is order-preserved (alg < typ alphabetically) but claims like `{"sub":"x","name":"y","iat":1}` come out as `{"iat":1,"name":"y","sub":"x"}`. This is **not a bug** — it is the canonicalisation guarantee that makes downstream `$jsonpath`, `$regex`, and equality assertions deterministic regardless of source-side key ordering. The task observable's expected claim string (`{"sub":"1234567890","name":"John Doe","iat":1516239022}`) is a *description of which fields are present*, not a byte-exact contract — the actual `Vector` test will assert the alphabetical output. This decision is documented in MANUAL.md §3.7 so users are not surprised.

4. **Three CategoryInput error codes — `DYNFN_JWT_DECODE_BAD_FORMAT`, `_BAD_BASE64`, `_BAD_JSON`.** Distinguishes the three failure modes per Open Decision #7 / behavior list. Codes are stable, machine-readable, and follow the existing `DYNFN_BASE64_DECODE` convention. Each error is wrapped via `fmt.Errorf` indirectly (the registry's `Evaluate` adds the `$jwtDecodeXxx:` prefix), so the inner `apierrors.Structured` does NOT include the function name in its `Message` (matches the noArgs/oneArg/twoArgs conventions and avoids `$jwtDecodeHeader: $jwtDecodeHeader: …` doubling).

5. **Truncate offending input to 32 chars in error messages — inlined, not exported.** Mirrors the exact pattern used by `$base64Decode` at `dynamic.go:276-279`. JWTs can be hundreds of bytes; surfacing a full token in an error message is both noisy and a credential-leak risk if the token is sensitive. The truncation snippet is 4 lines at the top of `decodeJWTSegment`; promoting it to a package-level helper would force a name + doc + tests for one caller and inflate the diff. If a third decoder lands later, that becomes the moment to extract.

6. **No `sensitiveArgIdx` registration.** The single argument is the JWT *token* — typically a public bearer credential, not a secret to be auto-redacted as a side effect of this call. If the token resolves from a sensitive-named variable, the existing M12-005 plumbing already redacts the *token* itself wherever it surfaces. The decoded segments contain whatever claims the issuer chose to embed; whether those are themselves sensitive is the caller's concern (use `extract:` + `sensitive:` if needed). Marking `sensitiveArgIdx[name] = 0` would *also* redact the decoded JSON output — an over-reach the task scope explicitly rules out. This decision matches the scope: "Sensitive-secret propagation: NOT applicable."

7. **No signature verification — explicit non-goal, security callout in MANUAL.md.** The task scope rules out a `$jwtVerify` companion. The signature segment is **not even examined** by either function — a deliberately-mangled signature still decodes both header and claims successfully. The `TestRegistry_JwtDecode_NoSignatureVerification` test asserts this contract. MANUAL.md §3.7 carries a security callout: "Both functions decode WITHOUT verifying the signature. If you trust the contents of `header` or `claims`, you must verify the signature via a separate mechanism (e.g. an OAuth-validated session, an upstream API gateway, or a future `$jwtVerify` helper)."

8. **`Available()` count assertion bumps from 84 to 86.** `dynamic_test.go:301` hard-codes `len(avail) != 84`. Adding two functions makes that test fail; bumping the literal in the same step keeps the build green between RED and GREEN cycles.

```go
// decodeJWTSegment splits token on '.', base64-url-decodes the segment at
// segIdx (0 = header, 1 = claims), JSON-roundtrips the bytes via the
// standard encoding/json marshaller (alphabetical key sort), and returns
// the canonical compact JSON string. funcName is the user-facing function
// name ("jwtDecodeHeader" or "jwtDecodeClaims") used to shape the Hint
// field of any structured error.
//
// On failure returns a *apierrors.Structured with Category=CategoryInput
// and one of three stable codes:
//
//   - DYNFN_JWT_DECODE_BAD_FORMAT  — token does not split into exactly 3
//     dot-separated segments (zero, one, two, or four+).
//   - DYNFN_JWT_DECODE_BAD_BASE64  — target segment is not valid
//     base64-url (RFC 4648 §5, no padding).
//   - DYNFN_JWT_DECODE_BAD_JSON    — base64 decode succeeded but the
//     bytes are not valid JSON.
//
// The Message field carries the offending input truncated to 32 chars
// (with "..." marker when truncated) so long tokens neither flood logs
// nor leak in full. Signature segment (segments[2]) is intentionally
// NOT examined — this is decode-only, not verification. See MANUAL.md
// §3.7 for the security caveat.
func decodeJWTSegment(funcName, token string, segIdx int) (string, error) {
	snippet := token
	if len(snippet) > 32 {
		snippet = snippet[:32] + "..."
	}
	parts := strings.Split(token, ".")
	if len(parts) != 3 {
		return "", &apierrors.Structured{
			Category: apierrors.CategoryInput,
			Code:     "DYNFN_JWT_DECODE_BAD_FORMAT",
			Message:  fmt.Sprintf("expected 3 dot-separated segments, got %d; input prefix=%q", len(parts), snippet),
			Hint:     fmt.Sprintf("Pass a JWT (three '.'-separated base64-url segments) to $%s.", funcName),
		}
	}
	decoded, err := base64.RawURLEncoding.DecodeString(parts[segIdx])
	if err != nil {
		return "", &apierrors.Structured{
			Category: apierrors.CategoryInput,
			Code:     "DYNFN_JWT_DECODE_BAD_BASE64",
			Message:  fmt.Sprintf("segment %d is not valid base64-url: %v; input prefix=%q", segIdx, err, snippet),
			Hint:     "JWT segments must use the URL-safe base64 alphabet (RFC 4648 §5) without '=' padding.",
			Inner:    err,
		}
	}
	var v interface{}
	if err := json.Unmarshal(decoded, &v); err != nil {
		return "", &apierrors.Structured{
			Category: apierrors.CategoryInput,
			Code:     "DYNFN_JWT_DECODE_BAD_JSON",
			Message:  fmt.Sprintf("segment %d is not valid JSON: %v; input prefix=%q", segIdx, err, snippet),
			Hint:     "Each JWT segment must base64-url-decode to a JSON object.",
			Inner:    err,
		}
	}
	out, err := json.Marshal(v)
	if err != nil {
		// json.Marshal of an interface{} populated by json.Unmarshal cannot
		// fail in practice — interface{} only holds JSON-representable values.
		// Report defensively rather than panic.
		return "", &apierrors.Structured{
			Category: apierrors.CategoryInput,
			Code:     "DYNFN_JWT_DECODE_BAD_JSON",
			Message:  fmt.Sprintf("segment %d failed JSON re-marshal: %v; input prefix=%q", segIdx, err, snippet),
			Hint:     "Each JWT segment must base64-url-decode to a JSON object.",
			Inner:    err,
		}
	}
	return string(out), nil
}
```

	// $jwtDecodeHeader / $jwtDecodeClaims — M17-005.
	// Each function takes a single arg (the JWT token), splits on '.', and
	// returns the requested segment as canonical compact JSON via an
	// encoding/json roundtrip. Header is segment 0, claims is segment 1.
	// Signature (segment 2) is NOT examined — these helpers do NOT verify
	// the signature; that is explicitly out of scope. See MANUAL.md §3.7
	// for the security caveat. The shared helper decodeJWTSegment lives
	// in dynamic_helpers.go and shapes the three CategoryInput error codes
	// (DYNFN_JWT_DECODE_BAD_FORMAT / _BAD_BASE64 / _BAD_JSON).
	//
	// No sensitiveArgIdx registration: the single arg is the token (a
	// public bearer credential by convention), not a secret to be
	// auto-redacted as a side effect of this call. The token's own
	// sensitivity is preserved by the existing M12-005 plumbing wherever
	// it surfaces in serialised output.
	r.funcs["jwtDecodeHeader"] = oneArg("jwtDecodeHeader", func(token string) (string, error) {
		return decodeJWTSegment("jwtDecodeHeader", token, 0)
	})
	r.funcs["jwtDecodeClaims"] = oneArg("jwtDecodeClaims", func(token string) (string, error) {
		return decodeJWTSegment("jwtDecodeClaims", token, 1)
	})
}
```

#### Content to Add (after line 1367, before line 1369 `**MD5 caveat.**`)

```markdown
**JWT decode helpers (`$jwtDecodeHeader`, `$jwtDecodeClaims`) — M17-005.**

These two dynamic functions split a JWT on `.` and base64-url-decode the
requested segment, returning the decoded JSON as a canonical compact
string. The third segment (the signature) is **never examined** — these
helpers are decode-only.

| Function | Arguments | Returns | Example |
|---|---|---|---|
| `{{$jwtDecodeHeader('token')}}` | 1 string (the JWT) | The header segment as compact JSON | `{{$jwtDecodeHeader('eyJ...JWT...')}}` → `{"alg":"HS256","typ":"JWT"}` |
| `{{$jwtDecodeClaims('token')}}` | 1 string (the JWT) | The claims segment as compact JSON | `{{$jwtDecodeClaims('eyJ...JWT...')}}` → `{"iat":1516239022,"name":"John Doe","sub":"1234567890"}` |

The output is always **canonical compact JSON** with map keys sorted
alphabetically — this is the standard `encoding/json` round-trip
guarantee. The original key order in the source token is **not**
preserved; downstream `$jsonpath`, `$regex`, and equality assertions
should not rely on input ordering. Values are byte-exact (UTF-8 strings
round-trip unchanged, including multi-byte sequences).

Example — extract a claim from an opaque bearer token:

```yaml
- name: read-current-user
  request:
    method: GET
    url: "{{base_url}}/me"
    headers:
      Authorization: "Bearer {{access_token}}"
  extract:
    # The 'sub' (subject) claim is the user-id encoded in the JWT.
    user_id: "{{$jsonpath('$.sub', $jwtDecodeClaims('{{access_token}}'))}}"
    # The signing algorithm — useful for audit / debug only.
    token_alg: "{{$jsonpath('$.alg', $jwtDecodeHeader('{{access_token}}'))}}"
```

**Errors.** Three structured `[INPUT]` codes distinguish the failure modes:

- `DYNFN_JWT_DECODE_BAD_FORMAT` — token does not split into exactly three
  `.`-separated segments.
- `DYNFN_JWT_DECODE_BAD_BASE64` — the target segment is not valid
  URL-safe base64 (RFC 4648 §5, no padding).
- `DYNFN_JWT_DECODE_BAD_JSON` — the segment base64-url-decodes
  successfully but the bytes are not valid JSON.

Each error message includes the offending input truncated to 32 chars
(with `...` marker) so long tokens cannot flood logs or leak in full.

**Security caveat — no signature verification.** Both functions decode
**without verifying the signature**. Calling `$jwtDecodeHeader` or
`$jwtDecodeClaims` does **not** prove the token was issued by anyone
trusted; an attacker can forge an arbitrary header and claims and the
decode will succeed. If your test asserts on a claim value as a
*security boundary* — for example, "the token is for user 42" — the
correctness of that assertion depends on the token's signature having
been verified by the API server (or a separate mechanism) before it was
returned to you. Curlew does not ship a `$jwtVerify` helper; if you
need cryptographic verification within a test, generate the expected
signature with `$hmacSha256` over the canonicalised header.claims
prefix and compare with `equals`.
```

## Risks and Edge Cases

- **Risk:** Go `encoding/json` sorts map keys alphabetically, so claims output may surprise users expecting source-side key order. → **Mitigation:** Documented explicitly in MANUAL.md §3.7 ("canonical compact JSON ... not preserved"); claim values themselves are byte-exact; downstream `$jsonpath` and equality assertions are order-agnostic.
- **Risk:** A JWT whose payload is a JSON *array* or *number* (not an object) would still decode cleanly via `interface{}` → not strictly compliant with RFC 7519 §4 (claims set must be a JSON object) but the helper does not enforce this. → **Mitigation:** Out of scope; this slice intentionally does not validate the JSON shape beyond "is JSON". The downstream `$jsonpath('$.claim', ...)` against a non-object would naturally surface as a path-not-found error. Documented in the broader MANUAL.md tone (we decode, the caller asserts).
- **Risk:** A token containing ` ` or other control chars in its claims could cause display weirdness in error messages. → **Mitigation:** The error path uses `%q` formatting which escapes control chars; the success path returns whatever `json.Marshal` produces (which itself escapes per RFC 8259).
- **Risk:** Smoke test depends on `python3` availability. → **Mitigation:** The existing `webhook-sign Stripe` smoke block already uses `python3 -m http.server` and `python3 -c "import json"` — same prereq, no new dependency.
- **Risk:** Smoke test port conflict with the webhook-sign block (9181). → **Mitigation:** New port 9182 chosen explicitly; webhook-sign block already cleans up its server before reaching this section.
- **Edge case:** Empty token (zero `.` chars → 1 segment). → **Handling:** `strings.Split("", ".")` returns `[""]` (length 1), triggering `DYNFN_JWT_DECODE_BAD_FORMAT`. Covered by `TestRegistry_JwtDecode_BadFormat` first case.
- **Edge case:** Token with empty header segment (e.g. `.eyJ...sig`). → **Handling:** `RawURLEncoding.DecodeString("")` returns `[]byte{}` with no error; `json.Unmarshal([]byte{}, &v)` returns "unexpected end of JSON input" → `DYNFN_JWT_DECODE_BAD_JSON`. Covered transitively.
- **Edge case:** Token with JSON `null` as the payload (segment decodes to `null`). → **Handling:** `json.Unmarshal` succeeds with `v = nil`; `json.Marshal(nil)` returns `"null"`. The function returns the literal string `null`. Not a behavior tested; this is an obscure input and the current behavior is the natural Go-stdlib path.
- **Edge case:** Token with extremely long claims (megabyte-scale). → **Handling:** No size limit imposed; `encoding/base64` and `encoding/json` handle arbitrary sizes. The error truncation only affects error messages; success-path output is full-size. Not a behavior tested.
- **Edge case:** Two-arg form. → **Handling:** `oneArg` returns `DYNFN_ARITY` with message "expected 1 arguments, got 2" — covered by `TestRegistry_JwtDecode_ArityErrors`.
- **Edge case:** UTF-8 multi-byte values in claims (e.g. `"日本語"`). → **Handling:** `encoding/base64` and `encoding/json` are byte-exact through UTF-8; the round-trip preserves the original bytes. Covered by `TestRegistry_JwtDecode_UTF8Roundtrip`.
