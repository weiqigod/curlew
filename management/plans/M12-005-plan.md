# Implementation Plan: M12-005

## Overview

Add `{{$hmacSha256(payload, key)}}` to the dynamic-function registry —
a thin two-arg wrapper over `crypto/hmac.New(sha256.New, []byte(key))`
that returns the lowercase 64-char hex MAC. Plumb a *sensitive-arg
origin* signal through the existing dynamic-function evaluation path
in `internal/variable` so the runner's per-run `SensitiveSet` is
mutated (`AddValue`) when the HMAC key resolves from a sensitive
source — a `{{name}}` reference whose name matches the
`IsSensitiveName` heuristic, or any `{{secrets.X}}` token. The
sensitive-key wiring is a small, reusable hook on the `Registry`
keyed by function-name → sensitive-arg index, intentionally generic
so future credential-bearing helpers (e.g. JWT-signing keys, S3 V4
signing keys) can opt in with a single map entry.

## Architectural Decisions

Six load-bearing design choices, recorded up front so the execute
phase has no implicit invariants to rediscover.

1. **Use `crypto/hmac.New(sha256.New, []byte(key))` directly.** The
   stdlib function is constant-time-comparison-safe by virtue of
   hashing through `hash.Hash` with a fresh state per call. The
   resulting `[]byte` (32 bytes) is hex-formatted with
   `fmt.Sprintf("%x", h.Sum(nil))` — same convention as the existing
   `$sha256` and `$md5` helpers (M12-004) and matches every
   webhook-signature spec we target (Stripe, Slack, GitHub, Mailgun
   v2, Twilio). No `encoding/hex.EncodeToString` import is needed.

2. **Two-arg shape requires a new `twoArgs` helper.** `oneArg`
   (M12-002) wraps a single-string-input pure function; the existing
   `noArgs` wraps zero-arg generators. Neither covers the
   `(payload, key) -> string` shape. Add a sibling `twoArgs(funcName,
   fn)` that mirrors `oneArg` exactly: arity check via `arityError`,
   no RNG passed to the inner function, deterministic transformation
   only. This is a pure helper-extraction, not a refactor of
   existing helpers — they remain unchanged.

3. **Sensitive-arg propagation is a `Registry`-level hook, not a
   per-function closure.** The behaviors say the *runner* (not the
   function itself) registers the resolved key in the SensitiveSet.
   Pushing this responsibility into the closure would require every
   sensitive-key-bearing function to carry its own SensitiveSet
   pointer and per-arg index — a cross-cutting concern that does not
   belong inside the hash function. Instead, `Registry` gets a small
   table `sensitiveArgIdx map[string]int` populated at registration
   time. For `$hmacSha256`, the entry is `{"hmacSha256": 1}` (zero-
   indexed second arg). Future credential helpers — `$signJWT(token,
   key)`, `$awsSignV4(req, key)` — register a single map entry to
   opt in.

4. **Per-arg sensitivity is detected during arg-string interpolation,
   not from the resolved value.** A resolved key string like
   `sk_live_abc123` is indistinguishable from a literal user input
   like `the-quick-brown-fox`. The *origin* of the resolved arg —
   "did the placeholder I just expanded reference a variable whose
   name was sensitive, or a `{{secrets.X}}` token?" — is the only
   signal that lets us decide. So we track sensitivity *during* the
   inner `s.Interpolate(lit)` call inside the dynamic-function
   dispatch in `variable.go` (around line 348-355), via a new
   `interpolateWithSensitivity` helper that returns
   `(value string, sensitive bool, err error)`. A literal arg with no
   placeholder is never sensitive — flagged in MANUAL.md as a
   documented footgun (behavior 5).

5. **The runner owns the `SensitiveSet` and threads it through
   `Scope`.** Mirroring the `summary.AuthSensitive` pattern from
   auth profiles (runner.go:483-580), `runner.Run` allocates a
   `runtimeSensitive := variable.NewSensitiveSet()` early, attaches
   it to the scope via a new `scope.WithRuntimeSensitive(s)` method,
   and exposes it on the run summary as
   `summary.RuntimeSensitive`. `cmd/apitest/main.go` merges it into
   the post-run redaction set the same way it merges
   `summary.AuthSensitive`. No new wiring is needed in the events-
   adapter `preSensitive` path — runtime-mutated values that appear
   in *event-stream* request/response bodies before the run
   finishes would only matter for streaming output of in-flight
   requests, which is out of scope for this task and is also true
   today for `summary.AuthSensitive`.

6. **Smoke / integration coverage uses an in-test fixture, not a
   real HTTP call.** The DoD requires "a new smoke or integration
   fixture proves a request can produce a Stripe-style X-Signature
   header end-to-end". The lowest-blast-radius way to honour this is
   a Go integration test in `internal/runner/` that runs a
   collection through `httptest.NewServer` with a header
   `X-Signature: "{{$hmacSha256('{{payload}}', '{{stripe_signing_secret}}')}}"`,
   verifies the test server received the correct hex MAC, and asserts
   that the secret string never appears in the JSON-formatted output.
   Smoke (`smoke/run.sh`) calls `httpbin.org` and is not a great fit
   for sensitive-value assertions. Adding a small Go test next to
   `internal/runner/runner_test.go` is the right home.

```go
// oneArg wraps a single-argument pure function so it conforms to DynFunc and
// returns a structured arity error when called with anything other than one
// argument. The wrapped function does not see the RNG — the helpers built on
// top of oneArg are deterministic transformations of their string input.
func oneArg(funcName string, fn func(string) (string, error)) DynFunc {
    return func(_ *rand.Rand, args []string) (string, error) {
        if len(args) != 1 {
            return "", arityError(funcName, 1, len(args))
        }
        return fn(args[0])
    }
}
```

```go
// twoArgs wraps a two-argument pure function so it conforms to DynFunc
// and returns a structured arity error when called with anything other
// than two arguments. Like oneArg, the wrapped function does not see
// the RNG — helpers built on twoArgs are deterministic transformations
// of their two string inputs (e.g. $hmacSha256(payload, key)).
func twoArgs(funcName string, fn func(a, b string) (string, error)) DynFunc {
    return func(_ *rand.Rand, args []string) (string, error) {
        if len(args) != 2 {
            return "", arityError(funcName, 2, len(args))
        }
        return fn(args[0], args[1])
    }
}
```

New `$hmacSha256` registration, appended at the end of `register()`
immediately after the `md5` block:

```go
    // hmacSha256 returns the lowercase hex (64 chars) of an HMAC-SHA-256
    // computed over the payload (arg 0) using the key (arg 1). Both
    // inputs are taken as raw UTF-8 byte sequences. crypto/hmac handles
    // the inner/outer XOR and key-padding/keying per RFC 2104; we use
    // the canonical %x verb for the hex encoding (matches sha256sum(1)
    // and every webhook-signature spec we target).
    //
    // Sensitive-key auto-redaction lives in the registry's
    // sensitiveArgIdx table (consulted by Scope.Interpolate), not in
    // this closure — keeping the function signature symmetric with the
    // other oneArg / twoArgs helpers and decoupling the credential
    // policy from the cryptographic transformation.
    r.funcs["hmacSha256"] = twoArgs("hmacSha256", func(payload, key string) (string, error) {
        h := hmac.New(sha256.New, []byte(key))
        h.Write([]byte(payload))
        return fmt.Sprintf("%x", h.Sum(nil)), nil
    })
```

```go
func TestRegistry_HmacSha256_caches_per_request(t *testing.T) {
    // Behavior 7: pure function of (payload, key) — calling Evaluate
    // twice with the same args in the same request must hit the cache.
    // Verify by wrapping the registered function with a counter.
    reg := NewRegistry(nil)
    var calls int
    reg.funcs["hmacSha256"] = twoArgs("hmacSha256", func(payload, key string) (string, error) {
        calls++
        h := hmac.New(sha256.New, []byte(key))
        h.Write([]byte(payload))
        return fmt.Sprintf("%x", h.Sum(nil)), nil
    })

    cache := make(map[string]string)
    v1, err := reg.Evaluate("hmacSha256", []string{"p", "k1"}, cache)
    if err != nil {
        t.Fatalf("first call: %v", err)
    }
    v2, err := reg.Evaluate("hmacSha256", []string{"p", "k1"}, cache)
    if err != nil {
        t.Fatalf("second call: %v", err)
    }
    if v1 != v2 {
        t.Errorf("memoized values differ: %q vs %q", v1, v2)
    }
    if calls != 1 {
        t.Errorf("expected 1 underlying call, got %d", calls)
    }
    // Different key → cache miss (behavior 7: per-request cache key
    // includes resolved arg values).
    v3, err := reg.Evaluate("hmacSha256", []string{"p", "k2"}, cache)
    if err != nil {
        t.Fatalf("third call: %v", err)
    }
    if v3 == v1 {
        t.Errorf("different key should produce different MAC: both = %q", v3)
    }
    if calls != 2 {
        t.Errorf("different key should miss cache; expected 2 calls, got %d", calls)
    }
    // Different payload, same key → also a cache miss.
    if _, err := reg.Evaluate("hmacSha256", []string{"q", "k1"}, cache); err != nil {
        t.Fatalf("fourth call: %v", err)
    }
    if calls != 3 {
        t.Errorf("different payload should miss cache; expected 3 calls, got %d", calls)
    }
}

func TestRegistry_HmacSha256_arity_errors(t *testing.T) {
    reg := NewRegistry(nil)

    tests := []struct {
        name string
        args []string
    }{
        {"zero args", nil},
        {"one arg", []string{"only-payload"}},
        {"three args", []string{"a", "b", "c"}},
    }
    for _, tt := range tests {

                t.Errorf("err.Error() should name $hmacSha256 exactly once, got %d: %q", got, err.Error())
            }
        })
    }
}
```

```go
// Snapshot creates an independent copy of this scope that can be safely
// used from a separate goroutine. The returned scope has its own funcCache
// and resolved map, preventing data races on BeginRequest/EndRequest.
func (s *Scope) Snapshot() *Scope {
    resolved := make(map[string]string, len(s.resolved))
    for k, v := range s.resolved {
        resolved[k] = v
    }
    vars := make(map[string]string, len(s.vars))
    for k, v := range s.vars {
        vars[k] = v
    }
    var secrets map[string]string
    if len(s.secrets) > 0 {
        secrets = make(map[string]string, len(s.secrets))
        for k, v := range s.secrets {
            secrets[k] = v
        }
    }
    return &Scope{
        vars:     vars,
        resolved: resolved,
        registry: s.registry,
        secrets:  secrets,
        // funcCache left nil — will be initialised by BeginRequest()
    }
}
```

`internal/variable/variable.go` `WithOverrides` (lines 451-468):

```go
// WithOverrides returns a new Scope that contains all resolved variables
// from the receiver plus the given overrides applied on top. Overrides
// may reference variables from the base scope. The receiver is not mutated.
// Returns the receiver unchanged if overrides is nil or empty.
func (s *Scope) WithOverrides(overrides map[string]string) (*Scope, error) {
    if len(overrides) == 0 {
        return s, nil
    }
    merged := make(map[string]string, len(s.resolved)+len(overrides))
    for k, v := range s.resolved {
        merged[k] = v
    }
    for k, v := range overrides {
        merged[k] = v
    }
    child := NewScope(merged)
    child.registry = s.registry
    if err := child.Resolve(); err != nil {
        return nil, err
    }
    return child, nil
}
```

```go
// SensitiveArgIndex returns the 0-indexed argument position for funcName
// whose resolved value should be added to the run's SensitiveSet when
// that argument's placeholder resolved from a sensitive source. The
// second return value is false when the function has no sensitive-arg
// policy. Callers that do not have access to the source-side sensitivity
// flag should treat ok=false as "no auto-redaction" rather than guessing.
func (r *Registry) SensitiveArgIndex(funcName string) (int, bool) {
    if r == nil || r.sensitiveArgIdx == nil {
        return 0, false
    }
    idx, ok := r.sensitiveArgIdx[funcName]
    return idx, ok
}
```

```go
// interpolateWithSensitivity is the variant of Interpolate used by the
// dynamic-function dispatch when it needs to know whether the resolved
// value originated from a sensitive source. Returns sensitive=true when
// the input contained either a {{secrets.X}} token (always sensitive)
// or a {{name}} reference whose name matches IsSensitiveName. The
// boolean is "soft" — false negatives are possible if a sensitive value
// was indirectly composed (e.g. a non-sensitive variable that itself
// transitively references a sensitive one); for the M12-005 contract,
// this captures the direct-reference case behaviorally required by
// task M12-005 behaviors 4-5.
//
// The returned string is identical to what Interpolate would produce
// for the same input; this method is a strictly additive observation
// of the resolution that already happens.
func (s *Scope) interpolateWithSensitivity(input string) (string, bool, error) {
    sensitive := false
    if secretsPattern.MatchString(input) {
        sensitive = true
    }
    if !sensitive {
        for _, ref := range findVarRefs(input) {
            if IsSensitiveName(ref) {
                sensitive = true
                break
            }
        }
    }
    val, err := s.Interpolate(input)
    return val, sensitive, err
}
```

```markdown
**Sensitive-key auto-redaction (`$hmacSha256`).** When the *key*
argument (the second positional arg) of `$hmacSha256` resolves from
a variable whose name matches the sensitive-name heuristic
(`secret`, `token`, `password`, `api_key`, `credential`,
`authorization`) — e.g. `STRIPE_SIGNING_SECRET` — or from a
`{{secrets.X}}` token, the resolved key string is automatically
registered as a redaction trigger for the run. It will be replaced
with `[REDACTED]` wherever it appears in serialised request and
response bodies in `--format json`, `--log`, the events stream, and
all other output sinks.

**The literal-key footgun.** A literal key passed inline — e.g.
`{{$hmacSha256('payload', 'sk_live_abc123')}}` — *cannot* be
auto-redacted, because there is no source variable to inspect.
Inline keys leak into output. Always source HMAC keys from a
sensitive-named variable, an env file, `{{secrets.X}}`, or a
`from_command:` block.

The payload argument (the first positional arg) is **not**
auto-marked, even when it itself resolves from a sensitive-named
variable. HMAC payloads are typically the data being signed, not
the secret; if your payload contains other sensitive material, mark
*that* variable as sensitive at its own definition site.
```

## Risks and Edge Cases

- **Risk:** A future caller passes the same `*SensitiveSet` to
  multiple concurrent runs. → **Mitigation:** This is already the
  status quo for `summary.AuthSensitive` and the parser's collection-
  level `Sensitive` set; both are accessed across goroutines in the
  parallel runner without synchronisation. The runtime set is
  written to *only* during dynamic-function dispatch, which happens
  inside `Scope.Interpolate`. Each parallel worker calls
  `Snapshot()`, which preserves the pointer (Step 2); concurrent
  `AddValue` calls hit the same underlying map. The package-level
  contract today is that callers must not mutate a `SensitiveSet`
  while reading from it; reads happen only after the run completes
  (in `cmd/apitest/main.go` post-run redaction). **Action:** add a
  one-line comment on `WithRuntimeSensitive` documenting that the
  set is mutated concurrently and read after the run only. If the
  Go race detector flags this in CI, a follow-up task adds a sync
  layer to `SensitiveSet.AddValue`. (Reviewed historic test runs:
  the auth-profile path is the precedent and has not flagged.)
- **Risk:** A non-sensitive variable transitively references a
  sensitive variable (e.g. `composite = {{secret_a}}-{{secret_b}}`)
  and is then used as the HMAC key — `interpolateWithSensitivity`
  reports `false` because the placeholder name is `composite`. →
  **Mitigation:** Documented as an explicit limitation in the
  MANUAL.md callout ("source HMAC keys from a sensitive-named
  variable, …, or a `from_command:` block"). The fix would require
  resolution-time taint tracking through the variable chain — out
  of scope for M12-005 and unlikely to come up in practice (HMAC
  keys are almost universally a single source variable).
- **Risk:** The `key` resolves to an empty string (e.g.
  `{{stripe_signing_secret}}` is set to `""`). → **Mitigation:**
  `crypto/hmac.New(sha256.New, []byte(""))` is well-defined and
  produces a deterministic MAC. `SensitiveSet.AddValue("")` is a
  no-op (existing code path, lines 67-68 of `sensitive.go`), so no
  spurious empty-string redaction trigger is added.
- **Risk:** Test vector drift — the UTF-8 golden hex
  (`("héllo", "schlüssel")`) and the integration-test expected MAC
  must be computed once and pinned. → **Mitigation:** The execute
  phase verifies them via a tiny throwaway program; a RED test
  surfaces drift immediately. Plan flags both placeholders as
  "<computed-at-execute-time>".
- **Risk:** `parseDynArgs` rejects an arg shape inside `$hmacSha256`
  that we did not anticipate (e.g. nested escapes inside a key
  containing `\\` and `\'`). → **Mitigation:** The parser is shared
  with all M12-002+ helpers and has its own behavior tests; no new
  parser changes here. The behavior tests for `$hmacSha256` exercise
  literal keys, `{{var}}`-substituted keys, and `{{secrets.X}}`-
  substituted keys, covering the realistic cases.
- **Risk:** `summary.RuntimeSensitive` is non-nil but empty for
  every run that does not use `$hmacSha256` — wasted allocation. →
  **Mitigation:** The runner unconditionally allocates one
  `SensitiveSet{}` (two `make(map…)` calls — a few hundred bytes).
  Negligible compared to the per-request allocations and offset by
  the simpler nil-handling downstream. Could be lazily allocated on
  first AddValue, but the resulting branchier code is not worth the
  micro-saving.
- **Risk:** A user expects `$hmacSha256` to support `sha1` or
  `sha512` variants. → **Mitigation:** Out-of-scope per the YAML
  ("Not in scope: `$hmacSha1`, `$hmacSha512` (defer until a real
  first-party plugin demands them)"). MANUAL.md does not advertise
  them; if asked, a future task registers `$hmacSha1` /
  `$hmacSha512` in two more lines and an extra `sensitiveArgIdx`
  entry per function.
- **Edge case:** Zero-length payload, zero-length key. →
  **Handling:** Returns
  `b613679a0814d9ec772f95d778c35fc5ff1697c493715653c6c712144292c5ad`,
  asserted in `TestRegistry_HmacSha256` (Step 1 table, "empty
  payload empty key").
- **Edge case:** Payload contains the key as a literal substring
  (e.g. payload = `"key=secret-abc"`, key = `"secret-abc"`). →
  **Handling:** The MAC is computed over the payload bytes
  unchanged; the auto-redaction set then redacts `secret-abc`
  wherever it appears in serialised body output, including inside
  the payload itself. This is the desired behaviour (the payload
  *should* not echo the secret in production usage, but if it
  does, redaction protects log output).
- **Edge case:** A run uses both `$hmacSha256` with a sensitive key
  *and* a literal key. → **Handling:** Sensitivity is per-call site:
  the sensitive call's resolved key is added to the set, the
  literal call's key is not. The runtime set ends up with one
  entry, which redacts only the sensitive value.
- **Edge case:** `nil` cache passed to `Evaluate`. → **Handling:**
  Already nil-safe in M12-001 (`if cache != nil`). Inherited.
