# Implementation Plan: M14-017

## Overview

Adds the `github_installations` table, the dashboard-initiated install-URL endpoint with signed-state callback, the webhook-first claim path, repo-set reconciliation handlers, and a daily reconciliation hosted service. Closes the cross-tenant isolation guardrail at the schema level via a partial UNIQUE index on `(org_id) WHERE deleted_at IS NULL AND org_id IS NOT NULL`. Bounded scope: no Checks-API outbound (M14-018), no `/webhooks/github` signature verification (M14-019).

## Key Architectural Decisions

1. **Row PK is `installation_id` (BIGINT), not a synthesized GUID.** Spec :10009 declares `installation_id BIGINT PRIMARY KEY`. The table is keyed on GitHub's natural ID; `(app_id, installation_id)` is the de-facto compound key when multiple Apps exist (today: one App per backend deployment, distinguished by `app_id`).
2. **Repo-set is stored as `JSONB` on Postgres / `TEXT` (JSON-serialized) on SQLite.** Spec :10014 uses `JSONB DEFAULT '[]'`. EF Core's `HasColumnType("jsonb")` is conditional on `Database.IsNpgsql()` (mirrors the `StripeWebhookEvent.PayloadJson` pattern). Each repo entry is `{ owner, name, id }`.
3. **Signed-state token is a self-contained HMAC-SHA256 token (no DB row).** Encodes `{org_id, user_id, expires_at, nonce}` as Base64URL JSON, separator `.`, with HMAC over the body using the GitHub App webhook-secret-style key derived from `ApiTool:GitHubApp:StateSigningKey` (env: `APITOOL__GITHUBAPP__STATESIGNINGKEY`). 15-minute expiry per behavior. Nonce prevents identical-payload reuse. Stateless tokens avoid an extra table for a 15-minute window.
4. **Cross-tenant unique index is conditional on Postgres only at the EF level**, but expressed as a `HasFilter("\"deleted_at\" IS NULL AND \"org_id\" IS NOT NULL")`. SQLite's partial-index syntax is identical, so the migration's raw SQL works on both. This mirrors the M14-002 `signing_keys` `idx_signing_keys_current` precedent.
5. **Webhook handlers are wired in this slice but the inbound endpoint signature verification is M14-019.** The handler classes (`GitHubInstallationCreatedHandler`, `GitHubInstallationRepositoriesHandler`) are public, fully unit-tested with payload fixtures, and live under `internal/GitHub/Webhooks/`. M14-019 wires them into the `/webhooks/github` route once verification is in place. This keeps test coverage on the row-mutation logic without prematurely shipping an unverified inbound surface.
6. **Daily reconciliation uses a `BackgroundService` mirroring `StripeWebhookCleanupHost`.** Tests inject a fake `IGitHubInstallationsApi` (interface introduced in this slice) and assert `repo_set` converges. The real HTTP implementation against `api.github.com` is deferred to M14-018 — this slice ships a stub that throws `NotImplementedException` registered only when `ASPNETCORE_ENVIRONMENT != "Testing"` and `GitHubApp.AppId != 0`, so tests bind to a fake without modification.
7. **Authorization: owner OR admin** can call `GET /api/v1/integrations/github/install-url`. Members are 403'd. Pulled from spec :8413 ("Customer clicks 'Connect GitHub' in the ApiTool dashboard while logged in") and the standard pattern in `MembersService` where admins manage integrations. The endpoint requires the user to belong to exactly one org via membership lookup; the org_id baked into the state token is the org they're admin/owner of. Multi-org users specify via query parameter `?org_id=org_<hex>`.
8. **Webhook-first row uses `org_id = NULL` and `claimed_at = NULL`.** Per behavior #5 and spec :8416-8417: GitHub posts `installation.created` with no state; we insert a row with `org_id = NULL`. The dashboard later shows pending installs and lets the user claim them — this slice writes the schema and the install-create handler; the claim verification (admin-of-account check) is a stretch goal documented but not implemented in the bounded scope (no GitHub API call wired yet — that's M14-018). The `POST /api/v1/integrations/github/claim` endpoint is implemented as a stub returning 501 in this slice; full implementation lands with M14-018's GitHub API client.

namespace ApiTool.Backend.Data.Entities;

/// <summary>
/// Registry of customer GitHub App installations. Primary cross-tenant isolation surface.
/// Refs docs/SPECIFICATION.md:8409-8427 (lifecycle), :10006-10025 (schema).
/// </summary>
public sealed class GithubInstallation
{
    /// <summary>GitHub's installation ID (primary key per spec :10010).</summary>
    public long InstallationId { get; set; }

    /// <summary>Our GitHub App's numeric App ID — one per ApiTool product (spec :8387).</summary>
    public long AppId { get; set; }

    /// <summary>NULL until the customer claims the install (webhook-first path).</summary>
    public Guid? OrgId { get; set; }

    /// <summary>e.g. 'acme-corp' (display only).</summary>
    public string AccountLogin { get; set; } = string.Empty;

    /// <summary>'Organization' or 'User'.</summary>
    public string AccountType { get; set; } = string.Empty;

    /// <summary>'all' or 'selected'.</summary>
    public string RepoSelection { get; set; } = "selected";

    /// <summary>JSON array of {owner, name, id}. JSONB on Postgres, TEXT on SQLite.</summary>
    public string RepoSetJson { get; set; } = "[]";

    /// <summary>Insert timestamp (UTC).</summary>
    public DateTime InstalledAt { get; set; }

    /// <summary>Set when the user claims the install (or instantly on dashboard-initiated path).</summary>
    public DateTime? ClaimedAt { get; set; }

    /// <summary>Non-null while suspended via installation.suspend.</summary>
    public DateTime? SuspendedAt { get; set; }

    /// <summary>Soft-delete marker; never hard-deleted (spec :8423).</summary>
    public DateTime? DeletedAt { get; set; }

    /// <summary>Last time the daily reconciler synced repo_set against the GitHub API.</summary>
    public DateTime LastReconciledAt { get; set; }
}
```

### 6. App-Installation Runbook (M14-017)

Once the GitHub App is registered and the backend is configured (steps 1–5), end users
install the App on their org and link it to their ApiTool org via either the
dashboard-initiated flow or the webhook-first claim flow.

**Required env var (in addition to M14-016):**

```dotenv
APITOOL__GITHUBAPP__STATESIGNINGKEY=<32+ char random secret>
```

**Dashboard-initiated install flow:**

1. The user clicks "Connect GitHub" in the dashboard.
2. Dashboard fetches `GET /api/v1/integrations/github/install-url` → returns
   `https://github.com/apps/<slug>/installations/new?state=<signed-token>`.
3. The user installs on GitHub; GitHub redirects back to
   `GET /api/v1/integrations/github/callback?installation_id=...&state=...`.
4. Backend verifies the signed state, looks up `org_id`, and writes the
   `github_installations` row.

**Webhook-first install flow** (the user installed via GitHub UI directly): the
`installation.created` event arrives at `/webhooks/github`; backend writes a row with
`org_id = NULL`. The user claims the install in the dashboard later (full claim
endpoint lands with M14-018 — until then, dashboard surfaces the pending row).

**Daily reconciliation:** `GithubInstallationReconcilerHost` runs every 24h, calling
`GET /installation/repositories` for each non-deleted, non-suspended row, correcting
any drift between `repo_set` and the GitHub-side reality.
```

## Risks and Edge Cases

- **Risk:** UNIQUE-index violation surfaces as a generic `DbUpdateException` on EF Core, not a typed Postgres-only `PostgresException` with code `23505`. → **Mitigation:** Service catches `DbUpdateException` whose inner `Microsoft.Data.Sqlite.SqliteException` (test) or `Npgsql.PostgresException` (prod) message contains `idx_github_installations_org` (or SqlState `23505` on Postgres) and translates to `InstallClaimError.AlreadyLinked`. The migration test exercises both paths.
- **Risk:** EF Core InMemory provider does not enforce partial unique indexes, so the "already-linked" behavior cannot be tested via `BackendFactory` (which uses InMemory). → **Mitigation:** Endpoint tests for the 409 path use a SQLite-backed factory variant (drop-in: spin up `TestDb.CreateOpen()` and inject directly into the service test, OR use the established pattern from `AppDbContextSchemaTests` where SQLite is used for schema-level guarantees and InMemory for endpoint flow). The 409 endpoint test uses a SQLite override.
- **Risk:** `RepoSetJson` is stored as `TEXT` on SQLite and `JSONB` on Postgres; serialization must round-trip identically. → **Mitigation:** Always `JsonSerializer.Serialize/Deserialize` with `JsonSerializerDefaults.Web`. `NpgsqlDbType.Jsonb` accepts a textual JSON string verbatim. Migration test verifies an array round-trips.
- **Edge case:** Webhook-first row exists with `org_id = NULL`, then the same `installation_id` arrives via dashboard callback. → **Handling:** `ClaimAsync` first looks up by `installation_id`. If found with `org_id = NULL`, set `org_id` and `claimed_at` (path that satisfies behavior #5 retroactively). If found with a different `org_id` set, → 409. If the org already has a different active install, the UNIQUE index fires → 409.
- **Edge case:** Duplicate `installation.created` deliveries (GitHub retries). → **Handling:** `UpsertFromWebhookAsync` is idempotent — if the row exists, it leaves `org_id` alone (preserves any prior claim) and refreshes `last_reconciled_at` only.
- **Edge case:** `installation_repositories.removed` for a repo not currently in `repo_set`. → **Handling:** Set-difference is naturally idempotent; no error.
- **Edge case:** State token signed with one key, server rotates `StateSigningKey`. → **Handling:** This slice supports a single signing key; rotation is a future enhancement (we'd accept either `StateSigningKey` or `StateSigningKeyPrevious`). Documented but not implemented — out of scope for the bounded slice.
- **Edge case:** Multi-org user calls `/install-url` without `?org_id=`. → **Handling:** If user is in exactly one org, use that. If 0 orgs, 404. If 2+ orgs, 400 ambiguous_org_id with a list of resolvable orgs.
