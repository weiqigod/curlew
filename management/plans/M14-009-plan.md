# Implementation Plan: M14-009

## Overview

Replace the `NotImplementedException` body of `StripeGateway.CreatePortalSessionAsync` with a live Stripe.Net integration, add a new `POST /api/v1/subscriptions/billing-portal` endpoint that resolves the org's `stripe_customer_id` (409 `no_billing_setup` when missing), accepts an empty body and defaults `return_url` to `App:WebAppUrl + '/billing'`, allows admin or owner roles, propagates `Idempotency-Key`, maps Stripe 5xx to RFC 7807 `STRIPE_UNAVAILABLE` 502 with the Stripe `request_id`, and fails fast on boot when `App:WebAppUrl` is unset.

## Architectural Decisions (resolved up-front)

1. **A new route `POST /api/v1/subscriptions/billing-portal` is added; the existing `POST /api/v1/subscriptions/portal` is preserved for backward compatibility and to satisfy the spec wording at SPECIFICATION.md:7324.** The task observable POSTs to `/billing-portal` with empty body and reads `.url` from the response. The existing endpoint requires a body containing `org_id`+`return_url` and returns `portal_url`. Removing it breaks `SwaggerSurfaceTests` (which asserts `/api/v1/subscriptions/portal` is published) and `SubscriptionsEndpointsTests.Portal_returns_portal_url`. We therefore keep both endpoints. The existing `/portal` endpoint continues to call the same underlying service path; the new `/billing-portal` endpoint adds the empty-body, defaulted-return-url, role-relaxed (admin|owner), customer-id-required behaviour. The new endpoint's handler is the M14-009 deliverable.

2. **A new `AppOptions` config block carries `WebAppUrl`.** No equivalent option exists today (`grep -rn WebAppUrl src/ApiTool.Backend` returns nothing). The task scope explicitly references "App:WebAppUrl" per Open Decision #2 in milestone-mapping.md. We introduce `ApiTool.Backend.AppOptions` (section name `Curlew:App`, env var `CURLEW__APP__WEBAPPURL`) with a single `string WebAppUrl` property. The `Program.cs` builder validates at startup via `AddOptions<AppOptions>().Validate(...).ValidateOnStart()` so misconfiguration is visible immediately. The `Testing` environment (BackendFactory) sets a deterministic value (`"http://web.test"`) so existing endpoint tests continue to boot. Production/dev uses the real value.

3. **`SubscriptionsService.CreatePortalAsync` gains a customer-id-required branch and an admin-or-owner role check.** Today it requires `OrgRole.Owner` and unconditionally calls `stripe.CreatePortalSessionAsync` even when the org has no `stripe_customer_id`. The new logic: (a) verify `member.Role is Owner or Admin` (returns `PermissionDenied` otherwise); (b) look up the most recent `Subscriptions` row for the org and read its `StripeCustomerId`; (c) when that value is null/empty, return a new `SubscriptionError.NoBillingSetup` (HTTP 409 `no_billing_setup`); (d) otherwise call the gateway with the customer id. This means the gateway signature must carry a `customerId` parameter — see Decision #4. The legacy `/portal` endpoint with the body-supplied `return_url` keeps its current owner-only role check; only the new `/billing-portal` endpoint uses the relaxed admin|owner check (per task behaviours #5).

4. **`IStripeGateway.CreatePortalSessionAsync` signature gains an explicit `customerId` parameter and an `idempotencyKey` parameter.** Today the signature is `(Guid userId, Guid orgId, string returnUrl, CancellationToken ct)`. Stripe's billing portal session API requires a customer id (`cus_*`) — without it the SDK call cannot construct the request. Rather than have the gateway re-query the database for the customer id (a layer-mixing anti-pattern), the service resolves the customer id and passes it down. Both the live gateway (Stripe.BillingPortal.SessionService.CreateAsync) and the fake gateway accept the new parameters. `idempotencyKey` follows the same pattern as `CreateCheckoutSessionAsync` from M14-008. Existing callers — `SubscriptionsService.CreatePortalAsync` is the only one — get updated to thread the new arguments through. The fake gateway's `Portal_returns_portal_url` test (in `FakeStripeGatewayTests.cs`) currently calls without `customerId`/`idempotencyKey`; we keep both new parameters as optional with `null` defaults so the test compiles unchanged. The fake gateway ignores the values and returns its deterministic URL.

5. **STRIPE 5xx maps to RFC 7807 `STRIPE_UNAVAILABLE` 502, preserving Stripe's `request_id`.** This mirrors the M14-008 STRIPE_RATE_LIMITED 503 mapping shape but with a distinct code. `Stripe.StripeException` carries `RequestId` (the `Stripe-Request-Id` header value) and `HttpStatusCode`. We add a new `StripeUnavailableException` (parallel to `StripeRateLimitedException`) carrying both `RequestId` and `IdempotencyKey`; the gateway throws it for any `StripeException` whose `HttpStatusCode` is 5xx (or where the inner `HttpRequestException` indicates a network failure). The endpoint maps the exception to a `ProblemDetails` with `code=STRIPE_UNAVAILABLE`, `status=502`, `extensions["request_id"]=<stripe request id>`, `extensions["idempotency_key"]=<key>`, content-type `application/problem+json`. We follow the existing `RefreshProblem` pattern from `Auth/Refresh/RefreshProblem.cs`.

6. **`Idempotency-Key` propagation matches M14-008.** The endpoint reads the `Idempotency-Key` request header, generates a v4 UUID server-side when absent, echoes it on the response as `X-Stripe-Idempotency-Key`, and passes it down through the service to the gateway. Stripe's billing portal API itself does not enforce idempotency at the same level as Checkout sessions, but stripe-mock does record the header per-request, so the behaviour test ("replay creates exactly one session") asserts the gateway produces equivalent results across two calls with the same key. **Open question resolved**: behaviour #3 says "exactly one billing-portal session is created (verified against stripe-mock)". Stripe's actual API returns a fresh session per call even with the same idempotency key for billing-portal (different from Checkout); however, stripe-mock's idempotency replay logic DOES return the same response on duplicate keys. We assert the stripe-mock behaviour via the integration test, and document the divergence in a comment so future readers don't expect identical behaviour against the real Stripe API.

7. **The new endpoint returns `{"url": "..."}` (snake-case `url`), matching the observable's `jq .url`.** The existing `/portal` endpoint returns `{"portal_url": "..."}`. We keep both shapes — the new `BillingPortalResponse` record uses `Url` (which serializes as `url` per the existing snake-case naming policy in `Program.cs`'s JSON options) and the legacy `PortalResponse` keeps `PortalUrl` (serializes as `portal_url`). No breaking change for existing clients.

8. **The fake gateway's `Portal_returns_portal_url` test contract is preserved.** That test asserts the URL starts with `https://billing.stripe.test/`. The fake's signature gets the extra `customerId`/`idempotencyKey` parameters as optional (defaults to null), so the existing call site (no extra args) continues to work. The new behaviour test for "no_billing_setup" lives at the service level and uses a seeded `Subscription` with `StripeCustomerId == null`.

9. **Authorisation: the new endpoint accepts admin OR owner.** The behaviour says "member-role user (not admin/owner) hits the endpoint, when authorized, then 403 permission_denied because billing portal access is admin/owner-only". The legacy `/portal` endpoint stays owner-only — changing it would break the existing `Portal_returns_portal_url` test which uses the org owner; but the test does not exercise an admin user, so no observable conflict. We document in the route handler XML doc the role requirement.

10. **Spec citation header on `StripeGateway.cs`.** Per definition_of_done item: "docs/SPECIFICATION.md (Subscription endpoints subsection) cited in handler header". We add `// Spec refs: docs/SPECIFICATION.md:7322–7345 (POST /api/v1/subscriptions/portal)` to the new endpoint handler XML doc and to the file header of `StripeGateway.cs`.

11. **The `App:WebAppUrl` boot-time fail-fast applies only to non-Testing environments.** `BackendFactory` sets the `Testing` environment via `UseEnvironment("Testing")`. We gate `ValidateOnStart` so it only runs when `WebAppUrl` validation matters (i.e., the new endpoint is registered). Two implementation paths considered: (a) gate the `Validate` predicate on `Mode != "Testing"`; (b) seed the test config with a real value. We pick (b) — the `BackendFactory` adds `["Curlew:App:WebAppUrl"] = "http://web.test"` to the in-memory configuration. This keeps the production config-validation strict and tests deterministic without env-specific branches.

12. **No DB migration needed.** `Subscription.StripeCustomerId` already exists (M14-008's migration `20260417123128_AddBillingAndInvitations`). The portal endpoint reads from this column; no schema change required.

```csharp
namespace ApiTool.Backend.Subscriptions;

/// <summary>
/// Thrown when the Stripe API returns an unrecoverable 5xx response or the request
/// fails to reach Stripe (network failure). Maps to RFC 7807 STRIPE_UNAVAILABLE 502.
/// </summary>
public sealed class StripeUnavailableException : Exception
{
    /// <summary>The idempotency key from the failed request, for correlation in logs.</summary>
    public string? IdempotencyKey { get; }

    /// <summary>The Stripe-Request-Id header value from the failing response, when available.</summary>
    public string? RequestId { get; }

    /// <summary>Initialises a new <see cref="StripeUnavailableException"/>.</summary>
    public StripeUnavailableException(string? idempotencyKey, string? requestId, Exception inner)
        : base("Stripe is unavailable (HTTP 5xx or network failure).", inner)
    {
        IdempotencyKey = idempotencyKey;
        RequestId = requestId;
    }
}
```

```csharp
/// <inheritdoc/>
// Spec refs: docs/SPECIFICATION.md:7322-7345 (POST /api/v1/subscriptions/portal).
public async Task<PortalSession> CreatePortalSessionAsync(
    Guid userId, Guid orgId, string returnUrl,
    string? customerId = null,
    string? idempotencyKey = null,
    CancellationToken ct = default)
{
    if (string.IsNullOrEmpty(customerId))
        throw new InvalidOperationException(
            "StripeGateway.CreatePortalSessionAsync requires a non-empty customerId; " +
            "SubscriptionsService must resolve the org's stripe_customer_id before calling the gateway.");

    var requestOptions = new RequestOptions { IdempotencyKey = idempotencyKey };
    if (requestOptions.IdempotencyKey?.Length > 255)
        requestOptions.IdempotencyKey = requestOptions.IdempotencyKey[..255];

    var options = new Stripe.BillingPortal.SessionCreateOptions
    {
        Customer = customerId,
        ReturnUrl = returnUrl,
    };

    try
    {
        var session = await new Stripe.BillingPortal.SessionService(_client)
            .CreateAsync(options, requestOptions, ct);
        return new PortalSession(session.Url);
    }
    catch (StripeException ex) when (ex.HttpStatusCode == HttpStatusCode.TooManyRequests)
    {
        _log.LogWarning(
            "Stripe rate-limited during billing portal session.create; idempotency_key={IdempotencyKey}",
            idempotencyKey);
        throw new StripeRateLimitedException(idempotencyKey, ex);
    }
    catch (StripeException ex) when ((int)ex.HttpStatusCode >= 500)
    {
        _log.LogWarning(
            "Stripe 5xx during billing portal session.create; idempotency_key={IdempotencyKey} request_id={RequestId} status={Status}",
            idempotencyKey, ex.StripeError?.RequestId, (int)ex.HttpStatusCode);
        throw new StripeUnavailableException(idempotencyKey, ex.StripeError?.RequestId, ex);
    }
}
```

```csharp
/// <summary>
/// Creates a Stripe Billing Portal session for the authenticated user's owned/admin'd organization.
/// Returns <see cref="SubscriptionError.NoBillingSetup"/> when the org has no <c>stripe_customer_id</c> on file.
/// </summary>
public async Task<(string portalUrl, SubscriptionError err, string? msg)>
    CreateBillingPortalAsync(Guid userId, string returnUrl, string idempotencyKey, CancellationToken ct)
{
    // Resolve the user's owned/admin'd org (any membership at admin or owner role).
    var membership = await db.OrganizationMembers
        .Where(m => m.UserId == userId && (m.Role == OrgRole.Owner || m.Role == OrgRole.Admin))
        .OrderBy(m => m.JoinedAt) // deterministic when user belongs to multiple orgs
        .FirstOrDefaultAsync(ct);
    if (membership is null)
        return (string.Empty, SubscriptionError.PermissionDenied,
            "Only org owners or admins can access the billing portal.");

    var orgId = membership.OrgId;

    // Look up the most recent stripe_customer_id for the org.
    var customerId = await db.Subscriptions
        .Where(s => s.OrgId == orgId && s.StripeCustomerId != null)
        .OrderByDescending(s => s.CreatedAt)
        .Select(s => s.StripeCustomerId)
        .FirstOrDefaultAsync(ct);

    if (string.IsNullOrEmpty(customerId))
        return (string.Empty, SubscriptionError.NoBillingSetup,
            "Organization has no Stripe customer on file. Complete checkout first.");

    PortalSession session;
    try
    {
        session = await stripe.CreatePortalSessionAsync(
            userId, orgId, returnUrl,
            customerId: customerId,
            idempotencyKey: idempotencyKey,
            ct: ct);
    }
    catch (StripeRateLimitedException)
    {
        return (string.Empty, SubscriptionError.StripeRateLimited,
            "Stripe rate-limited; retry with the same idempotency key.");
    }
    // StripeUnavailableException is intentionally NOT caught here — the endpoint layer
    // maps it to a 502 ProblemDetails so the StripeException's RequestId is preserved.

    return (session.PortalUrl, SubscriptionError.None, null);
}
```

#### New Code (SubscriptionsProblem.cs)

```csharp
// RFC 7807 problem-details responses for subscription/billing failures.
// Spec refs: docs/SPECIFICATION.md:7322-7345.
using Microsoft.AspNetCore.Mvc;
using HttpResults = Microsoft.AspNetCore.Http.Results;

namespace ApiTool.Backend.Subscriptions;

internal static class SubscriptionsProblem
{
    private const string BaseType = "https://api.apitool.dev/errors";

    public static IResult StripeUnavailable(HttpContext http, string? requestId, string? idempotencyKey) =>
        Build(http, 502,
            type:   $"{BaseType}/stripe-unavailable",
            title:  "Stripe API is unavailable",
            detail: "The Stripe API returned a 5xx response or is unreachable. Retry with the same Idempotency-Key.",
            code:   "STRIPE_UNAVAILABLE",
            extensions: new Dictionary<string, object?>
            {
                ["stripe_request_id"] = requestId,
                ["idempotency_key"]   = idempotencyKey,
            });

    public static IResult NoBillingSetup(HttpContext http) =>
        Build(http, 409,
            type:   $"{BaseType}/no-billing-setup",
            title:  "No billing setup",
            detail: "Organization has no Stripe customer on file. Complete checkout first.",
            code:   "no_billing_setup");

    public static IResult PermissionDenied(HttpContext http, string detail) =>
        Build(http, 403,
            type:   $"{BaseType}/permission-denied",
            title:  "Permission denied",
            detail: detail,
            code:   "permission_denied");

    public static IResult StripeRateLimited(HttpContext http, string? idempotencyKey) =>
        Build(http, 503,
            type:   $"{BaseType}/stripe-rate-limited",
            title:  "Stripe rate-limited",
            detail: "Stripe returned HTTP 429. Retry with the same Idempotency-Key.",
            code:   "stripe_rate_limited",
            extensions: new Dictionary<string, object?>
            {
                ["idempotency_key"] = idempotencyKey,
            });

    private static IResult Build(
        HttpContext http,
        int status,
        string type,
        string title,
        string detail,
        string code,
        IReadOnlyDictionary<string, object?>? extensions = null)
    {
        var requestId = http.TraceIdentifier;
        http.Response.Headers["X-Request-Id"] = requestId;

        var problem = new ProblemDetails
        {
            Type   = type,
            Title  = title,
            Status = status,
            Detail = detail,
            Extensions =
            {
                ["code"]       = code,
                ["request_id"] = requestId,
            },
        };
        if (extensions is not null)
            foreach (var (k, v) in extensions)
                if (v is not null) problem.Extensions[k] = v;

        return HttpResults.Json(problem, contentType: "application/problem+json", statusCode: status);
    }
}
```

#### New Code (SubscriptionsEndpoints.cs additions)

```csharp
// In MapSubscriptionsEndpoints:
group.MapPost("billing-portal", CreateBillingPortal)
    .WithName("CreateBillingPortal")
    .Produces<BillingPortalResponse>()
    .Produces<ProblemDetails>(StatusCodes.Status403Forbidden)
    .Produces<ProblemDetails>(StatusCodes.Status409Conflict)
    .Produces<ProblemDetails>(StatusCodes.Status502BadGateway);

// Handler:
/// <summary>
/// POST /api/v1/subscriptions/billing-portal — creates a Stripe Billing Portal session for the
/// authenticated user's owned/admin'd organization.
/// Spec refs: docs/SPECIFICATION.md:7322-7345.
/// </summary>
private static async Task<IResult> CreateBillingPortal(
    [FromBody] BillingPortalRequest? body,
    HttpContext context,
    CurrentUserAccessor users,
    SubscriptionsService svc,
    IOptions<AppOptions> appOptions,
    CancellationToken ct)
{
    var userId = await users.ResolveAsync(ct);
    if (userId is null)
        return Unauthorized401;

    var idempotencyKey = context.Request.Headers["Idempotency-Key"].FirstOrDefault()
                         ?? Guid.NewGuid().ToString();
    context.Response.Headers["X-Stripe-Idempotency-Key"] = idempotencyKey;

    var returnUrl = !string.IsNullOrWhiteSpace(body?.ReturnUrl)
        ? body!.ReturnUrl!
        : appOptions.Value.WebAppUrl.TrimEnd('/') + "/billing";

    try
    {
        var (portalUrl, err, msg) = await svc.CreateBillingPortalAsync(
            userId.Value, returnUrl, idempotencyKey, ct);

        return err switch
        {
            SubscriptionError.None => HttpResults.Ok(new BillingPortalResponse(portalUrl)),
            SubscriptionError.PermissionDenied => SubscriptionsProblem.PermissionDenied(context, msg!),
            SubscriptionError.NoBillingSetup => SubscriptionsProblem.NoBillingSetup(context),
            SubscriptionError.StripeRateLimited => SubscriptionsProblem.StripeRateLimited(context, idempotencyKey),
            _ => HttpResults.StatusCode(StatusCodes.Status500InternalServerError),
        };
    }
    catch (StripeUnavailableException ex)
    {
        return SubscriptionsProblem.StripeUnavailable(context, ex.RequestId, ex.IdempotencyKey);
    }
}
```

- **Risk:** Adding `ValidateOnStart` to `AppOptions` makes every existing test boot-fail unless the test config seeds `App:WebAppUrl`. → **Mitigation:** Add the seed (`["Curlew:App:WebAppUrl"] = "http://web.test"`) to `BackendFactory.ConfigureWebHost` in Step 1, in the same commit as the `AppOptions` addition. Verified by running `dotnet test` after Step 1 only.

- **Risk:** Stripe.Net's `Stripe.BillingPortal.SessionCreateOptions` and `SessionService` may have slightly different namespaces between 43.x and 44.x. → **Mitigation:** csproj already pins `Stripe.net` to 43.x (per M14-008). Verify by running `dotnet build` after Step 3.

- **Risk:** stripe-mock's idempotency replay for billing portal sessions may behave differently from real Stripe (real Stripe does not idempotency-replay portal sessions). → **Mitigation:** The integration test asserts the stripe-mock semantic only; the unit test for the gateway 5xx mapping does not depend on it. A code comment in `StripeBillingPortalIntegrationTests` documents the divergence.

- **Risk:** The new `/billing-portal` route may collide with the existing `/portal` route in OpenAPI if both are tagged identically. → **Mitigation:** Both routes use `WithName(...)` with distinct names (`CreatePortal` vs `CreateBillingPortal`); Swashbuckle generates distinct operationIds. SwaggerSurfaceTests asserts both paths are present.

- **Risk:** `App:WebAppUrl` may have a trailing `/` (e.g., `https://app.apitool.dev/`). Concatenating `+ "/billing"` would produce `https://app.apitool.dev//billing`. → **Mitigation:** The endpoint uses `.TrimEnd('/')` before appending `/billing`.

- **Risk:** The `OrderBy(m => m.JoinedAt).FirstOrDefault` for resolving the user's owned/admin org is non-deterministic when the user belongs to multiple orgs at the same admin/owner role. → **Mitigation:** Document this in the XML doc on `CreateBillingPortalAsync`. Future enhancement (out of scope for M14-009): require the request to specify which org via `org_id` body field. The current behaviour is acceptable for the single-org-per-user mainstream case.

- **Risk:** `StripeException.StripeError` may be null on certain network failures (e.g., DNS resolution failure → `HttpRequestException` wrapped in `StripeException` with no error body). → **Mitigation:** The catch clause guards `ex.StripeError?.RequestId` — null is acceptable in the `StripeUnavailableException` and the RFC 7807 response then omits the `stripe_request_id` extension via the null-skip in `SubscriptionsProblem.Build`.

- **Edge case:** Empty body `{}` deserializes to `BillingPortalRequest(null)` — handled. Bodyless POST (no Content-Type) — ASP.NET model binding returns the default record, also handled. The endpoint accepts `[FromBody] BillingPortalRequest? body` so a fully-omitted body becomes `null`.

- **Edge case:** A user belonging to multiple orgs as Owner of one and Admin of another — `OrderBy(m => m.JoinedAt)` picks the earliest-joined; both roles satisfy the predicate. Documented in step 4 (Decision in service method).

- **Edge case:** Idempotency-Key header longer than 255 bytes — gateway truncates defensively (mirrors M14-008's `CreateCheckoutSessionAsync`).

- **Edge case:** `App:WebAppUrl = "https://app.apitool.dev"` (no trailing path) → final return URL = `https://app.apitool.dev/billing`. Matches the spec example at SPECIFICATION.md:7329 (`https://apitesttool.com/billing`).

## Open Questions Resolved

- **Q:** Is the new endpoint route `/billing-portal` or `/portal`? **A:** `/billing-portal` per the task observable's curl path. The existing `/portal` route is preserved for backward compatibility with the spec body at SPECIFICATION.md:7324 and to avoid breaking `SwaggerSurfaceTests` and `Portal_returns_portal_url`. Decision #1.

- **Q:** Where does `App:WebAppUrl` config live? **A:** New `AppOptions` class binding `Curlew:App` section, env var `CURLEW__APP__WEBAPPURL`. Decision #2.

- **Q:** Should `ComputeProration` and `CreateCheckoutSessionAsync` change in this slice? **A:** No — task scope is `CreatePortalSessionAsync` only. M14-010 covers proration. Decision #3.

- **Q:** What HTTP code does `STRIPE_UNAVAILABLE` map to? **A:** 502 Bad Gateway per task behaviour #4 ("STRIPE_UNAVAILABLE 502"). RFC 7807 ProblemDetails preserves Stripe's `request_id`. Decision #5.

- **Q:** Is `Idempotency-Key` propagation observable in stripe-mock? **A:** Yes, stripe-mock records it per-request and replays the same response for duplicate keys (within a single container lifetime). Decision #6.

- **Q:** Field name in response — `url` or `portal_url`? **A:** `url` per the observable's `jq .url`. The legacy `/portal` endpoint keeps `portal_url`. Decision #7.

- **Q:** Should the legacy `/portal` endpoint also accept admin role? **A:** No — keeping its owner-only contract preserves the existing test (`Portal_returns_portal_url` uses an owner). The new `/billing-portal` endpoint is the surface where admin|owner relaxation lives. Decision #9.

- **Q:** Does the integration test count toward the ">=5 tests pass" threshold? **A:** Yes — but even excluding the 2 SkippableFact integration tests, we have 13 unit + service + endpoint tests. The DoD threshold is comfortably exceeded.
