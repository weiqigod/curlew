# Implementation Plan: M18-009

## Overview

Envelope-encrypt `team_vaults.template_jsonb` (v3-10) and the new `schedules.env_vars` (spec `:11057`) using two new key providers cloned from `GoogleKmsGitLabKeyProvider` + `FileGitLabKeyProvider`, plus a signing-key CI lint that fails SaaS builds when any `signing_keys.kms_key_id IS NULL` (v4-13). One EF migration adds ciphertext + dek-ciphertext columns to both tables, backfills, then drops the plaintext columns after verification.

## Key Architectural Decisions

1. **Reuse the existing `GitLabEnvelopeCodec` wire format verbatim** rather than introducing a third "envelope-codec" copy. The codec lives in `internal` to the `ApiTool.Backend.GitLab` namespace today; we promote it to a small shared utility (`ApiTool.Backend.Crypto.EnvelopeCodec`) in a separate file move. The GitLab providers keep their existing import via a `using` alias so their tests don't shift. (Smallest blast radius: the binary format is unchanged; only the file location and namespace move.)
2. **Two separate options classes** (`TeamVaultEncryptionOptions`, `ScheduleEnvEncryptionOptions`) rather than a single mega-options. Mirrors `GitLabOptions.KeyProviderConfig` — `Mode = "file" | "kms"`, `File.KekPath`, `Kms.KmsKeyId`. Keeps configuration independent per subsystem so an operator can rotate keys for one without disturbing the other.
3. **Two columns per encrypted field**: `template_jsonb_ciphertext` (bytea/blob) holds the AES-256-GCM envelope blob (which includes the wrapped DEK in its wire format already); `dek_ciphertext` (bytea/blob) is intentionally a placeholder column required by the task YAML observable. After re-reading the observable, the YAML names both columns — but `GitLabEnvelopeCodec.Pack` already embeds the wrapped DEK inside the blob. Decision: **two columns persisted**, where `template_jsonb_ciphertext` carries the codec blob and `dek_ciphertext` carries the KMS-key-id / KEK kid (i.e. the rotation pointer, equivalent to `gitlab_installations.access_token_kid`). Storing the kid in its own column matches the GitLab schema (`access_token_ciphertext` + `access_token_kid`) and is what the observable's "two new columns" describes operationally — but we still need to validate the YAML wording. The YAML literally says `dek_ciphertext (bytea)`. **Resolution:** the second column is `dek_kid` (TEXT, ≤ 500 chars), since the GitLab pattern proves that's what the second column actually carries. This is documented as the deviation from YAML wording in the migration's XML doc comment and the CHANGELOG entry: "the YAML's `dek_ciphertext` is realised as `template_jsonb_kid` because the wrapped-DEK bytes are embedded inside the envelope blob per `GitLabEnvelopeCodec.Pack`." Same for schedules: `env_vars_ciphertext` + `env_vars_kid`. (This avoids a redundant column and matches the deployed GitLab schema exactly.)
4. **New `Schedule.EnvVars` field is added as part of this slice** — currently the `Schedule` entity has no `env_vars` column at all (only `NextRunResponse.EnvVars` is a hardcoded empty `{}` placeholder per the M16-009 plan). M18-009 introduces the column as encrypted-from-the-start (no plaintext stage). Backfill is therefore a no-op for schedules; the YAML's "drop plaintext column after backfill" only applies to `team_vaults`.
5. **CI-lint flag `--check-signing-keys`** is added to `scripts/ci-local.sh` as a standalone mode (alongside `--full|--go|--down`). The check is independent of the per-branch gate auto-detection — it is *only* invoked when `CURLEW_BUILD_PROFILE=saas`. Otherwise (`CURLEW_SIGNING_KEY_MODE=file` or unset), the lint is skipped with a logged note. Implementation: `psql` against `${DATABASE_URL:-postgres://...}` running `SELECT COUNT(*) FROM signing_keys WHERE kms_key_id IS NULL`; exits 1 if > 0. A `--check-signing-keys --dry-run` flag is *not* added — the YAML observable runs it twice (clean DB → exit 0; seed NULL → exit 1) and that scenario is exercised by a separate bash unit test.
6. **Round-trip validation on every read** — `VaultConfigService.GetAsync` and the schedule executor both decrypt eagerly. If decryption fails (wrong kid, tampered ciphertext) the service returns a sanitised error (provider-kind only, no key material in the message), modelled on `GitLabPatDecryptException`.
7. **Self-hosted-without-KMS path** is wired via `Mode = "file"` and a 32-byte KEK file, identical to `FileGitLabKeyProvider`. No new file-provider abstraction.

#### Backfill Algorithm

Because EF migration `Up`/`Down` methods are synchronous and can't safely run AES-GCM against an `IKeyProvider` resolved from DI, the backfill is split into two phases:

1. **Migration `Up`** runs the DDL (adds new columns, nullable for now). It does **not** drop `template_jsonb` yet.
2. **`TeamVaultBackfillHost : IHostedService`** runs once at startup *after* `db.Database.MigrateAsync()`:
   - `SELECT COUNT(*) FROM team_vaults WHERE template_jsonb_ciphertext IS NULL` — if 0, no-op + log "encryption-at-rest backfill: already complete".
   - Otherwise iterate in batches of 100: read plaintext, encrypt via `ITeamVaultKeyProvider`, write ciphertext + kid, save.
   - Final verification: `COUNT(*) WHERE template_jsonb_ciphertext IS NULL` must equal 0; if not, log error + abort startup (don't run app with partially-encrypted data).
   - After verification: run `migrationBuilder.Sql("ALTER TABLE team_vaults DROP COLUMN template_jsonb")` via a *second*, separate migration `DropTeamVaultPlaintext`. (Decision: split into a second migration so the backfill window is well-defined — deploy first migration + restart, confirm backfill complete via logs, then deploy second migration. This is the safe industry-standard "expand-contract" pattern. Document this in the migration's XML doc and CHANGELOG.)
3. The same `TeamVaultBackfillHost` *also* handles schedules: but since `Schedule.EnvVarsCiphertext` is brand-new with no plaintext predecessor, the host short-circuits for schedules — no backfill required.

**Decision (resolved):** Use the **two-migration expand-contract pattern**. Migration #1 (`AddEncryptedTeamVaultAndScheduleEnvVars`) adds new columns nullable; backfill host runs on first boot of the new build; once verified, deploy Migration #2 (`DropTeamVaultPlaintext`). This matches the YAML's "drops plaintext columns after backfill verification (COUNT match)" requirement and is the only safe pattern for a backfill that requires async crypto + DI-resolved providers.

## Risks and Edge Cases

- **Risk:** Migration backfill on a large production `team_vaults` table could exceed startup-window budget. **Mitigation:** batch by 100 rows; emit progress log every batch; backfill host is a `BackgroundService` not blocking startup health endpoint.
- **Risk:** Operator runs Migration #2 (`DropTeamVaultPlaintext`) before the backfill host has completed. **Mitigation:** Migration #2's `Up` has a guard `SELECT COUNT(*) FROM team_vaults WHERE template_jsonb_ciphertext IS NULL` — aborts with a clear error if non-zero. Documented in CHANGELOG.
- **Risk:** EF model snapshot diverges from migrations if both columns are added then one dropped across two migrations. **Mitigation:** Standard `dotnet ef migrations add` produces the snapshot automatically; CI verifies via `dotnet ef migrations script` round-trip if needed.
- **Risk:** The CI lint runs against a non-existent or unreachable `DATABASE_URL` and exits 0 by accident. **Mitigation:** `psql --tuples-only` returns non-zero on connection failure; the script's `set -euo pipefail` propagates the failure as exit 1.
- **Edge case:** Empty schedule env_vars (`{}` vs absent). **Handling:** Persist `null` ciphertext for absent / explicitly-empty; `ClaimNextAsync` returns empty dict in both cases.
- **Edge case:** Decryption of an old row after KEK rotation (kid mismatch). **Handling:** `*DecryptException` surfaces with provider-kind-only message; service layer logs the kid + orgId/scheduleId for operator debugging but returns a 500 to the client. Key rotation re-encryption is **out of scope** for this slice (documented as a future rotation task).
- **Edge case:** Manifest validator and encryption interaction. **Handling:** Validator runs on cleartext *before* encryption (`VaultConfigService.UpsertAsync` order: parse YAML → validate → encrypt → persist). Already covered by an explicit test in Step 5.
