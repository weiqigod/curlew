# Implementation Plan: M14-001

## Overview

Lands the backend signing-key infrastructure for v4.2 ES256 token issuance: a new `signing_keys` registry table, an `IKeyProvider` abstraction with two implementations (`FileKeyProvider` for self-hosted, `GoogleKmsKeyProvider` for SaaS), the parallel v4.2 `refresh_tokens` schema (decoupled from M14-002 which will use it), an internal `GET /internal/keys/active` health-style probe, and the emergency-rotation entry point. This is the foundation slice the rest of the M14 token-issuance track (`M14-002` mint endpoint, `M14-003` JWKS endpoint) is built on.

## Key Architectural Decisions

These decisions resolve open questions surfaced during exploration. They are documented here so reviewers can challenge them in `/review` rather than rediscovering them.

1. **JSON column type — string + `jsonb` via Postgres column type.**
   The existing project stores JSON as plain `string` properties (e.g. `OrganizationAuditLogEntry.PayloadJson`, `CoordinatorShard.RequestsJson`) without any provider-specific column type. Same pattern here: `SigningKey.PublicKeyJwkJson` is a `string` property mapped to column `public_key_jwk`. Under the SQLite test provider this is a `TEXT` column; under Postgres production it is a `jsonb` column via `.HasColumnType("jsonb")` set inside an `if (Database.IsNpgsql())` branch in `OnModelCreating`. EF Core honours the provider-specific type at migration generation time; the SQLite test path uses `TEXT`. (No reflection of EF Core models is provider-specific outside of `OnModelCreating`, which already sees `Database.IsNpgsql()` from prior work — verified by `Program.cs:31-48` which selects the provider at runtime.)

2. **Partial unique indexes — Postgres-only; SQLite tests skip.**
   `idx_signing_keys_current` and `idx_signing_keys_next` are partial indexes (`WHERE status = 'current'`). Postgres supports them natively; SQLite supports them too (since 3.8). EF Core's `HasFilter("\"status\" = 'current'")` produces partial indexes on both providers. The behavior test for "two rows attempt status='current' simultaneously" runs against the SQLite test DB and asserts `DbUpdateException` with constraint name fragment matching either `IX_signing_keys_status_current` or `idx_signing_keys_current`. The behavior_8 test "Postgres returns 23505 SQLSTATE" is gated `[Trait("Category", "PostgresOnly")]` and runs only when `POSTGRES_TEST_CONN` env var is set (consistent with the existing `BackendCollection`/`BackendFactory` pattern).

3. **Migration name — `0014_signing_keys_and_refresh_tokens`.**
   Uses the EF Core timestamp prefix from the migration tool, not a literal `0014`. The DoD's "0014_signing_keys_and_refresh_tokens" naming maps to a migration class named `SigningKeysAndRefreshTokens` in the `Migrations/` folder, generated by `dotnet ef migrations add SigningKeysAndRefreshTokens`. The resulting filename is `<YYYYMMDDHHMMSS>_SigningKeysAndRefreshTokens.cs` — the timestamp prefix is the EF convention, not a contract violation. The DoD's "0014" reflects ordering (this is the 14th migration in sequence, after `20260420193328_AddUserBootstrapColumns`).

4. **Refresh-tokens table — created in this slice but FK to `devices(id)` deferred.**
   The v4.2 `refresh_tokens` table references `devices(id)`. The `devices` table does NOT exist yet (verified: `grep "devices" Migrations/AppDbContextModelSnapshot.cs` returns empty). M14-001 creates `refresh_tokens` with `device_id UUID NOT NULL` as a plain column (no FK constraint), with an inline migration comment marking the foreign-key add as M14-002's responsibility (M14-002 will create the `devices` table and add the FK in the same migration). This avoids a circular dependency — M14-002 needs the refresh_tokens table to call `INSERT INTO refresh_tokens` from the mint endpoint, and we don't want M14-002 to also have to drop+recreate this table to add the FK. Decision #5 (Open Decisions) confirms there are no rows to preserve, so the `DROP TABLE refresh_tokens; CREATE TABLE refresh_tokens` framing in the task scope is academic — there is no existing table to drop. We just `CREATE TABLE refresh_tokens (...)` with the v4.2 schema; the migration's `Down()` issues a clean `DropTable` for both tables in reverse order.

5. **`IKeyProvider` is split into `IKeyProvider` (signing surface) and `ISigningKeyStore` (DB I/O).**
   The spec mandates `IKeyProvider` exposes `SignAsync`, `GetActiveKidAsync`, `GetVerificationJwksAsync` only. Repository-style DB access (`InsertAsync`, `LoadCurrentAsync`, etc.) goes on a separate `ISigningKeyStore` injected into both providers. This keeps `IKeyProvider` minimal (per spec) and lets us mock just the DB in unit tests without re-implementing crypto.

6. **Emergency rotation — exposed as `ISigningKeyRotator.RotateAsync(emergency: bool, reason: string, ct)`.**
   Behavior #7 ("apitest-backend keys rotate --emergency") cannot be wired to a binary because `apitest-backend` does not exist yet. M14-001 ships the rotation logic on a separate `ISigningKeyRotator` interface; the runbook entry in `deploy/self-hosted/README.md` documents calling a small admin-only HTTP endpoint `POST /internal/keys/rotate` (auth: localhost only, gated by `Allow:Internal=true` in non-Production environments) for now. A future `apitest-backend` CLI can wrap this endpoint. The HTTP endpoint is in scope (it is needed for the integration test that asserts JWKS reflects the change).

7. **`GoogleKmsKeyProvider` does NOT call live KMS in tests.**
   The hard rule "Never take an action that may incur real-world cost" forbids live KMS calls in CI. The provider depends on an injected `IKmsClient` interface. The production registration uses `Google.Cloud.Kms.V1.KeyManagementServiceClient` (added as a transitive dependency only — see Risks). Tests inject a `FakeKmsClient` that returns deterministic signatures derived from a locally-generated EC key. Behavior #3 ("dispatches to KMS asymmetricSign API and the signing_keys row records the kms_key_id") asserts the call shape (`kms_key_id` value passed, signature returned, row stored) without ever hitting GCP.

8. **RFC 6979 deterministic signing — use BouncyCastle (`Org.BouncyCastle.Cryptography`).**
   Per spec line 7992 / M14_INVESTIGATION.md:262, ES256 must use RFC 6979 deterministic ECDSA. .NET's `ECDsa.SignData` uses random nonces (it is NOT RFC 6979 by default in .NET 9). The vetted choice is `Org.BouncyCastle.Cryptography 2.5.x` (managed code, BSD-style licence, FIPS-track). KMS path is inherently deterministic by KMS contract (Google Cloud KMS `EC_SIGN_P256_SHA256` is RFC 6979). Tests assert determinism by signing the same payload twice and asserting byte-equal signatures (FileKeyProvider path; KMS path is fake, deterministic by fake construction).

9. **`kid` format — `<env>-es256-<YYYYMM>-<6char-uuid-suffix>`.**
   Per spec line 8060. Environment value comes from `APITOOL__KEYPROVIDER__ENV` config (default `dev`). Generated at key-mint time. The 6-character suffix is the first 6 hex chars of `Guid.NewGuid().ToString("N")`. Validation regex `^[a-z0-9-]{1,64}$` is enforced in `KeyId.IsValid(string)` and re-checked at every `IKeyProvider.GetKeyAsync(kid)` boundary before any DB lookup.

// src/ApiTool.Backend/Licensing/Keys/KeyId.cs
// Refs docs/SPECIFICATION.md:7990-8090 (Signing-Key Storage, kid format).
namespace ApiTool.Backend.Licensing.Keys;

using System.Text.RegularExpressions;

/// <summary>
/// Static helpers for the kid (key identifier) format defined in
/// docs/SPECIFICATION.md:8060 — <c>&lt;env&gt;-&lt;alg&gt;-&lt;YYYYMM&gt;-&lt;6char-uuid&gt;</c>.
/// All callers MUST validate untrusted kid input via <see cref="IsValid"/>
/// before any database lookup or filesystem access (RFC 8725 §3.10).
/// </summary>
public static class KeyId
{
    /// <summary>Allowlist regex from spec line 7999 / RFC 8725 §3.10.</summary>
    public static readonly Regex Allowlist = new(@"\A[a-z0-9-]{1,64}\z",
        RegexOptions.CultureInvariant | RegexOptions.Compiled);

    /// <summary>Returns true when the kid matches the allowlist regex.</summary>
    public static bool IsValid(string? kid) => kid is not null && Allowlist.IsMatch(kid);

    /// <summary>Generates a new kid using <paramref name="clock"/> for the YYYYMM segment.</summary>
    public static string Generate(string env, string alg, TimeProvider clock)
    {
        var month = clock.GetUtcNow().ToString("yyyyMM");
        var suffix = Guid.NewGuid().ToString("N")[..6];
        var kid = $"{env}-{alg}-{month}-{suffix}";
        if (!IsValid(kid))
            throw new InvalidOperationException($"Generated kid '{kid}' fails allowlist regex");
        return kid;
    }
}

// FileKeyProvider.cs — refs docs/SPECIFICATION.md:8040, 8060
public sealed class FileKeyProvider(
    ISigningKeyStore store,
    IOptions<KeyProviderOptions> opts,
    TimeProvider clock,
    ILogger<FileKeyProvider> logger) : IKeyProvider
{
    public async Task<SignatureResult> SignAsync(byte[] payload, CancellationToken ct = default)
    {
        var current = await store.LoadCurrentAsync(ct)
            ?? await BootstrapAsync(ct);
        var pem = await ReadPrivatePemAsync(current.Kid, ct);
        var sig = BouncyCastleEs256.SignDeterministic(pem, payload);  // RFC 6979
        return new SignatureResult(current.Kid, sig);
    }

    public async Task<string> GetActiveKidAsync(CancellationToken ct = default)
    {
        var current = await store.LoadCurrentAsync(ct) ?? await BootstrapAsync(ct);
        return current.Kid;
    }

    public async Task<JsonWebKeySet> GetVerificationJwksAsync(CancellationToken ct = default)
    {
        var rows = await store.LoadCurrentAndVerifyingAsync(ct);
        var jwks = new JsonWebKeySet();
        foreach (var row in rows)
            jwks.Keys.Add(JsonSerializer.Deserialize<JsonWebKey>(row.PublicKeyJwkJson)!);
        return jwks;
    }

    private async Task<SigningKey> BootstrapAsync(CancellationToken ct)
    {
        var kid = KeyId.Generate(opts.Value.Env, "es256", clock);
        var (pem, jwk) = BouncyCastleEs256.GenerateKeyPair(kid);
        await WritePrivatePemAsync(kid, pem, ct);  // mode 0600 enforced via File.SetUnixFileMode
        var row = new SigningKey
        {
            Kid = kid,
            Algorithm = "ES256",
            Status = "current",
            PublicKeyJwkJson = JsonSerializer.Serialize(jwk),
            CreatedAt = clock.GetUtcNow().UtcDateTime,
            PromotedAt = clock.GetUtcNow().UtcDateTime,
        };
        await store.InsertAsync(row, ct);
        logger.LogInformation("signing-key: bootstrapped current kid={Kid}", kid);
        return row;
    }

    public Task<SignatureResult> SignWithKidAsync(string kid, byte[] payload, CancellationToken ct = default)
    {
        if (!KeyId.IsValid(kid))
            throw new InvalidKidFormatException(kid);
        // ... reads <kid>.pem, signs ...
    }

// InternalKeysEndpoints.cs
public static class InternalKeysEndpoints
{
    public static IEndpointRouteBuilder MapInternalKeysEndpoints(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/internal/keys").RequireInternalAccess();

        group.MapGet("/active", async (IKeyProvider kp, CancellationToken ct) =>
        {
            var kid = await kp.GetActiveKidAsync(ct);
            return HttpResults.Json(new { kid });
        });

        group.MapPost("/rotate", async (
            [FromQuery] bool emergency,
            [FromBody] RotateRequest req,
            ISigningKeyRotator r,
            CancellationToken ct) =>
        {
            var newKid = await r.RotateAsync(emergency, req.Reason, ct);
            return HttpResults.Json(new { kid = newKid });
        });

        return app;
    }
}

## Risks and Edge Cases

- **Risk: `Google.Cloud.Kms.V1` package size / transitive dependency surface.**
  → Mitigation: confined to `GoogleKmsKeyProvider` only; behind the `keyMode == "kms"` branch. Self-hosted operators never load it. Add `<PackageReference>` with `<IncludeAssets>` constrained.

- **Risk: BouncyCastle vs .NET native crypto incompatibility.**
  → Mitigation: keep BouncyCastle ONLY for the `RFC 6979 deterministic nonce` step. Public-key export and signature verification use .NET's native `ECDsa` and `JsonWebKey` so JWKS round-trips through `Microsoft.IdentityModel.Tokens`.

- **Risk: SQLite test DB partial-unique-index semantics differ from Postgres.**
  → Mitigation: assert on `DbUpdateException` shape only; skip the SQL-state-23505 check on SQLite. Add `[Trait("Category", "PostgresOnly")]` for the explicit 23505 test, gated by env-var `POSTGRES_TEST_CONN`.

- **Risk: Concurrent first-boot bootstrap creates two `current` rows.**
  → Mitigation: bootstrap path uses `INSERT ... ON CONFLICT DO NOTHING` (Postgres) or wraps `LoadCurrentAsync` + `InsertAsync` in a `SERIALIZABLE` transaction. SQLite lacks `INSERT ... ON CONFLICT` for partial unique indexes — fallback is the partial unique index itself rejecting the second insert with `DbUpdateException`, which the bootstrap path catches and re-reads.

- **Risk: Internal endpoint exposed publicly.**
  → Mitigation: `RequireInternalAccess()` extension on the endpoint group — checks `Connection.RemoteIpAddress` for loopback OR matches `X-Internal-Secret` header against `APITOOL__INTERNAL__SECRET` env var. Returns 404 (not 403) so external probes can't fingerprint the endpoint.

- **Edge case: `kid` collision (Guid suffix collision under same YYYYMM).**
  → Handling: 16^6 = 16,777,216 possible suffixes per month. With ~3 keys/month, collision probability is negligible. But guarded: bootstrap retries on DB unique-constraint failure.

- **Edge case: Empty `Keys/signing/` directory but DB row says `current` exists.**
  → Handling: `FileKeyProvider.SignAsync` falls through to `BootstrapAsync` after logging a warning ("signing-key: db says kid={Kid} but file missing — re-bootstrapping"). Operator runbook in `deploy/self-hosted/README.md` warns about this state.

- **Edge case: Kid format passed to `SignWithKidAsync` from CLI/API request header.**
  → Handling: Behavior #4 — validate via `KeyId.IsValid` before any DB lookup or filesystem access. Throw `InvalidKidFormatException`; endpoint maps to RFC 7807 with `code: AUTH_INVALID_KID`.
