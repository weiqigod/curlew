## Architectural Decisions Recorded

The Plan agent surfaced four ambiguities; the resolutions below are committed in this plan and must be honoured by the executor.

1. **File placement.** Task scope says "under `src/ApiTool.Backend/Health/Dashboard/`". `Health/` is the readiness/liveness folder. Dashboard endpoints belong with the Results feature area. **Decision:** place new files under `src/ApiTool.Backend/Results/Dashboard/`. This keeps endpoints at `/api/v1/organizations/{orgId}/results/...` co-located with `ResultsEndpoints.cs` and avoids polluting the health-probe namespace.
2. **Path-template source field.** The current `result_items` table has only `Name` (free-form). The spec's grouping key `(method, path_template)` cannot be derived from the existing rows. **Decision:** extend the upload-item wire shape and `ResultItem` entity with optional `method` (varchar 10) and `request_url` (varchar 1000) columns. A new `PathTemplateExtractor` parses `request_url` → `path_template` at ingest time and writes the templated form to `path_template` (varchar 500). Rows with NULL `path_template` (legacy or non-HTTP test items) are EXCLUDED from the failures listing — documented in the helper. This is forward-compatible with the spec language ("the same path-template extraction the result-ingest pipeline already uses") and lets the existing CLI keep working unmodified.
3. **Path-template algorithm.** Replace path segments that match any of (a) 32-char hex (UUID without hyphens), (b) RFC 4122 UUID with hyphens, (c) all-digits, (d) hex strings of length ≥ 8 with `{id}`. Query string is dropped. Trailing slash trimmed. Empty path becomes `/`. Documented in XML doc on the helper, with a table of examples.
4. **Failures `sample_run_ids` ordering.** The spec example shows 3 sample run ids per group. **Decision:** select up to 3 most-recent `result_items.id` values (formatted via `ResultId`-like prefix `res_<hex>` — but these are the parent **result** id, not the item id, per the spec's "sample_run_ids" naming — confirmed by the `res_` prefix in the spec example). Use a `DISTINCT` projection of the parent `Result.Id` of the 3 most recent failing items per group.

5. **Limit clamp Warning header.** Spec says "a Warning header (or response field) notes the clamp". **Decision:** emit BOTH — `Warning: 299 - "limit_clamped: requested=N, applied=50"` header (per RFC 7234 §5.5 standard format) AND a `limit_clamped: true` field in the JSON body so SDK clients see the signal without parsing headers.

6. **`?window=` parsing.** Allowed values: `7d`, `30d`, `90d`. Case-sensitive. Whitespace not stripped. Empty/missing → default `30d`. Anything else → 400 `unsupported-window` per Open Decision 10.

7. **Date boundaries.** `window_start = window_end - <N> days`, `window_end = now(UTC)`. Trend `date` field is the UTC calendar date (`YYYY-MM-DD`) at which `created_at` falls. Days with zero rows produce no entry (sparse array — caller fills gaps client-side). Confirmed by spec example showing only days with activity.

8. **p50 / p95 latency.** Computed over `Result.DurationMs` (run-level total duration), not per-item. Use Postgres `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY duration_ms)` and `PERCENTILE_CONT(0.95)`. EF Core does not translate percentile functions natively — use `FromSqlRaw` for the totals query. For EF Core InMemory in tests, fall back to a C#-side computation when the provider is InMemory (detected via `db.Database.IsInMemory()`).

9. **Permission check ordering.** Tier gate first (402 on Free), then `dashboard.view` permission (403 on member with custom role that excludes it), then handler. Matches the existing `VaultConfigEndpoints.cs` ordering except we add the permission check between gate and handler (vault config uses RBAC at service-layer; dashboards are read-only and the endpoint should reject early).

10. **Latency budget verification.** The 800ms-on-5M-rows behavior is verified by an `[Fact(Skip = ...)]` benchmark test gated by an env var (`APITOOL_RUN_DASHBOARD_LATENCY_BENCH`) — not part of normal `dotnet test`. Documents the index and the EXPLAIN ANALYZE expectation. Out-of-scope for CI; in-scope for plan completeness.

```csharp
/// <summary>
/// Extracts a normalised <c>path_template</c> from a request URL by replacing
/// id-shaped segments with <c>{id}</c>. Documented per spec line 10239:
/// path templates collapse <c>/users/4f3a...</c> and <c>/users/9c1e...</c>
/// into <c>/users/{id}</c>.
/// </summary>
/// <remarks>
/// Rules:
/// <list type="bullet">
///   <item>Segment is all-digits ⇒ <c>{id}</c></item>
///   <item>Segment matches RFC 4122 UUID (with hyphens) ⇒ <c>{id}</c></item>
///   <item>Segment is 32-char lowercase hex ⇒ <c>{id}</c></item>
///   <item>Segment is hex-only and length ≥ 8 ⇒ <c>{id}</c></item>
///   <item>Query string is stripped</item>
///   <item>Trailing slash trimmed (except root)</item>
///   <item>Empty / unparseable input ⇒ <c>null</c> path_template (caller excludes)</item>
/// </list>
/// </remarks>

    /// <param name="requestUrl">Full URL or path-only string.</param>
    /// <returns>Normalised <c>path_template</c>, or <c>null</c> when input is empty/invalid.</returns>
    public static string? Extract(string? method, string? requestUrl) { /* impl */ }
}
```

```csharp
/// <summary>Allowed dashboard time windows per spec ("7d | 30d (default) | 90d"). Open Decision 10.</summary>
public enum DashboardWindow
{
    /// <summary>7-day window.</summary>
    SevenDays,
    /// <summary>30-day window (default).</summary>
    ThirtyDays,
    /// <summary>90-day window.</summary>
    NinetyDays,
}

/// <summary>Parsing and conversion helpers for <see cref="DashboardWindow"/>.</summary>
public static class DashboardWindowExtensions
{
    /// <summary>Default window when <c>?window=</c> is omitted.</summary>
    public const DashboardWindow Default = DashboardWindow.ThirtyDays;

    /// <summary>Allowed wire values, for error messages.</summary>
    public static readonly IReadOnlyList<string> AllowedValues = ["7d", "30d", "90d"];

    /// <summary>
    /// Parses a wire value (<c>"7d"</c>, <c>"30d"</c>, <c>"90d"</c>, or null/empty for default).
    /// Returns false for any other value (caller emits 400 unsupported-window).
    /// </summary>
    public static bool TryParse(string? value, out DashboardWindow window) { /* impl */ }

    /// <summary>Returns the window's span as a <see cref="TimeSpan"/> (7, 30, or 90 days).</summary>
    public static TimeSpan ToTimeSpan(this DashboardWindow window) => window switch
    {
        DashboardWindow.SevenDays   => TimeSpan.FromDays(7),
        DashboardWindow.ThirtyDays  => TimeSpan.FromDays(30),
        DashboardWindow.NinetyDays  => TimeSpan.FromDays(90),
        _ => throw new ArgumentOutOfRangeException(nameof(window)),
    };

    /// <summary>Returns the wire form (e.g. <c>"30d"</c>).</summary>
    public static string ToWire(this DashboardWindow window) => window switch
    {
        DashboardWindow.SevenDays   => "7d",
        DashboardWindow.ThirtyDays  => "30d",
        DashboardWindow.NinetyDays  => "90d",
        _ => throw new ArgumentOutOfRangeException(nameof(window)),
    };
}
```

#### Handler control flow (both endpoints)

1. Resolve `userId` from token (401 if absent).
2. Resolve `orgGuid` via `OrgResolver.ResolveAsync` (403 on not-found, mirroring other endpoints).
3. `DashboardTierGate.EnsureTeamOrAboveAsync` → 402 via `TierGateProblemFactory.AuthenticatedTierIneligibleAsync` with `featureCode: "dashboard"`, 404 via `AuthenticatedOrgNotFound` on `OrgNotFound`.
4. `RoleResolver.HasPermissionAsync(userId, orgGuid, Permissions.DashboardView, ct)` → 403 if false.
5. Parse `?window=` via `DashboardWindowExtensions.TryParse` → 400 `unsupported-window` problem-detail if rejected.
6. Call service.
7. For failures: emit `Warning: 299 - "limit_clamped..."` header when clamped.

#### DashboardProblem (RFC 7807 unsupported-window)

```csharp
public static class DashboardProblem
{
    private const string BaseType = "https://api.apitool.dev/errors";

    public static IResult UnsupportedWindow(HttpContext http, string? received)
    {
        var requestId = http.TraceIdentifier;
        http.Response.Headers["X-Request-Id"] = requestId;
        var problem = new ProblemDetails
        {
            Type   = $"{BaseType}/unsupported-window",
            Title  = "Unsupported window",
            Status = StatusCodes.Status400BadRequest,
            Detail = $"Allowed values: {string.Join(", ", DashboardWindowExtensions.AllowedValues)}.",
            Extensions =
            {
                ["code"]            = "unsupported_window",
                ["request_id"]      = requestId,
                ["allowed_values"]  = DashboardWindowExtensions.AllowedValues,
                ["received"]        = received,
            },
        };
        return Results.Json(problem, contentType: "application/problem+json", statusCode: 400);
    }
}
```

## Risks and Edge Cases

- **Risk:** EF Core InMemory does not support `PERCENTILE_CONT` or `date_trunc`. **Mitigation:** `DashboardResultsService` branches on `db.Database.IsInMemory()` — InMemory pulls rows and computes percentiles in C#; Postgres uses `FromSqlInterpolated` with `PERCENTILE_CONT(0.5/0.95) WITHIN GROUP (ORDER BY duration_ms)` and `DATE_TRUNC('day', created_at AT TIME ZONE 'UTC')`. Both code paths produce the same wire shape; both are tested.
- **Risk:** Failures `sample_run_ids` returns the parent `Result.Id`, but the spec example shows three string values. **Mitigation:** Format as `res_<32hex>` via `ResultId.Format` so the wire shape matches the existing `GET /results/{id}` route.
- **Risk:** Clock drift when test fixtures span the trend boundary. **Mitigation:** Service injects `TimeProvider` (already in `Program.cs` DI). Tests use a `FakeClock` to pin `now` deterministically.
- **Risk:** Index `(Status, Method, PathTemplate)` may not be the best query plan for the failures aggregation. **Mitigation:** Real-Postgres latency benchmark (skipped unless env var set) verifies EXPLAIN ANALYZE uses the index. If Postgres prefers a different plan, the index is still a no-cost addition and can be tuned in a follow-up.
- **Edge case:** Window crosses DST boundary. **Handling:** All `created_at` values are UTC; trend grouping is by UTC calendar date. No DST handling needed.
- **Edge case:** Limit param is negative or zero. **Handling:** `Math.Clamp(limit, 1, MaxFailuresLimit)`. Clamp from `0` or negative is NOT reported as `limit_clamped: true` — that field is reserved for "above max" clamps per spec language. The lower-bound clamp is silent.
- **Edge case:** Org slug vs `org_<hex>` in path. **Handling:** Reuse `OrgResolver.ResolveAsync` — exactly the pattern used by `ResultsEndpoints.IngestResult` / `ListResults`.
- **Edge case:** Race between window calculation and result write. **Handling:** `window_end = clock.GetUtcNow().UtcDateTime` captured once at request start; passed to both stats and failures queries.
- **Edge case:** `Result.DurationMs` is `long` but spec totals use `avg_duration_ms` as integer. **Handling:** `AvgDurationMs = (long)Math.Round(avg)`. Same for p50/p95.
- **Risk:** Existing CLI clients won't populate `method`/`request_url` immediately; failures listing will be empty until CLI adoption. **Mitigation:** Documented behavior. The endpoint still returns `200 OK` with an empty `items` array — not an error.
