## Overview

(`firstName`, `lastName`, `fullName`, `username`, `email`, `phone`,

### How the existing runtime-sensitive plumbing works (M12-005)

The pre-evaluation pre-scan in `Scope.Interpolate` (variable.go:319-343)
records, per dyn-fn call, which **arguments** sourced from sensitive
variables. After `Registry.Evaluate` returns, the dispatcher (lines
432-440) consults `Registry.SensitiveArgIndex(funcName)`; if the named
argument position was flagged sensitive, the **resolved arg value** is
added to `s.runtimeSensitive`. This is an arg-side hook.

For `$faker.ssn` the sensitive value is the **generated return value**,
not an argument. So we need a value-side hook: a new
`sensitiveReturn map[string]bool` on the registry, a setter
`(r *Registry).IsSensitiveReturn(funcName) bool`, and a
post-evaluation branch in `Scope.Interpolate` that calls
`s.runtimeSensitive.AddValue(val)` when the flag is set. This is the
mirror of the existing arg-side hook and keeps all sensitive-policy
state on the registry (no SSN-specific knowledge in the closure or in
the scope).

### The locale behavior (#13)

The task YAML lists a 13th behavior: "Given `--locale de-DE` is passed
on the CLI, when any of the 10 personal-data functions are evaluated,
then the result still uses the en-US data set; the runner emits a
warning that locale support is not yet implemented." The `--locale`
flag does **not** exist in `cmd/curlew/main.go` today, and the scope
section explicitly excludes adding it (no `cmd/curlew/main.go` in
the "Files touched" list; "Not in scope: locale support"). M13-001
plan also confirms the flag is "deferred from M13 entirely". This
behavior is therefore trivially satisfied today (no flag exists →
en-US is always used) and the warning sub-clause cannot be
implemented without scope expansion. The plan documents this as a
deferred behavior with a `t.Skip` test stub so the contract is
visible in code; the actual `--locale` CLI flag and warning will land
in a future locale-support milestone.

```go
type Registry struct {
	funcs           map[string]DynFunc
	rng             *rand.Rand
	now             func() time.Time
	sensitiveArgIdx map[string]int
	// sensitiveReturn[funcName] = true marks the function's *return value*
	// as auto-sensitive: Scope.Interpolate calls runtimeSensitive.AddValue
	// on the result string after a successful Evaluate. Mirrors the
	// arg-side sensitiveArgIdx hook for value-generating helpers like
	// $faker.ssn. No-op when the scope has no runtimeSensitive set.
	sensitiveReturn map[string]bool
}

func NewRegistry(seed *int64) *Registry {
	r := &Registry{
		funcs:           make(map[string]DynFunc),
		sensitiveArgIdx: make(map[string]int),
		sensitiveReturn: make(map[string]bool),
		now:             time.Now,
	}
	if seed != nil {
		r.rng = rand.New(rand.NewPCG(uint64(*seed), uint64(*seed>>32^0xdeadbeef)))
	}
	r.register()
	return r
}

// IsSensitiveReturn reports whether funcName's return value should be
// auto-marked sensitive at evaluation time. The second return value is
// false when the function has no sensitive-return policy.
func (r *Registry) IsSensitiveReturn(funcName string) bool {
	if r == nil || r.sensitiveReturn == nil {
		return false
	}
	return r.sensitiveReturn[funcName]
}
```

## Risks and Edge Cases

- **Risk:** the `Registry` is shared across `Snapshot()` copies of a
  Scope, so two parallel workers calling `$faker.ssn` will both write
  to the same `s.runtimeSensitive` set. → **Mitigation:**
  `SensitiveSet.AddValue` is already `mu.Lock`-guarded
  (sensitive.go:67), so concurrent writes are safe. The set is
  per-run, not per-worker, which is the correct semantics
  (a value generated in one worker should be redacted everywhere).
- **Risk:** memoisation collapse on the same SSN within a request —
  the per-request cache will return the same SSN string for repeated
  `{{$faker.ssn}}` invocations, which is the M12-001 contract. The
  sensitive-return hook fires on the cached return path too because
  the post-`Evaluate` branch in `Scope.Interpolate` runs whether or
  not the value came from cache. → **Mitigation:** add an explicit
  test that two `{{$faker.ssn}}` invocations within one
  `BeginRequest`/`EndRequest` window register the same value once
  (set semantics, not list semantics) — already covered by
  `SensitiveSet.values map[string]struct{}` deduplication.
- **Edge case:** `$faker.username` could in principle produce a
  string starting with a digit (e.g. `aaron.smith0`) — the regex
  `^[a-z0-9._]+$` allows this, matching the SPECIFICATION.md:766
  contract. No action.
- **Edge case:** the unseeded `TestRegistry_FakerPersonal_Unseeded`
  could flake on a 1-in-2500 collision. → **Mitigation:** the test
  re-rolls once on collision (see Step 2 test code) before failing.
- **Edge case:** `intn(rng, 0)` would panic. None of the new closures
  call `intn` with a zero upper bound — `firstNames` (50),
  `lastNames` (49), `namePrefixes` (5), `nameSuffixes` (8) are all
  non-empty constants, and the numeric ranges in `phone` / `ssn` are
  fixed positive constants.
- **Edge case:** legacy `$randomEmail` / `$randomName` behavior must
  remain unchanged — they live in distinct map entries and use the
  same pools. No alias, no deprecation; per the M13 milestone
  description.
- **Risk:** docs/SPECIFICATION.md:766 spec says username may include
  underscore (`_`); the implementation above uses only `[a-z0-9.]`.
  The regex `^[a-z0-9._]+$` permits both — no contract violation.
  Underscore generation can be added in a future enhancement
  without breaking the regex.
- **Risk:** the deferred locale behavior (#13) is left as a
  `t.Skip` stub so reviewers can see the contract is acknowledged
  without false-positive coverage. This is an explicit decision to
  defer rather than over-build a flag whose UX is owned by a future
  milestone.

## Open Decisions Resolved (Auto Mode)

1. **"Auto-sensitive at generation time" mechanism.** Implemented as
   a value-side `sensitiveReturn` registry hook (Option B in the
   exploration), symmetric with the existing M12-005 `sensitiveArgIdx`
   arg-side hook. Closures stay pure functions of the RNG;
   sensitivity policy lives in registry-level metadata rather than
   in the closure body.
2. **`--locale` behavior #13.** Implemented as a `t.Skip` stub
   referencing M13 Open Decision #1. The flag is not added to the
   CLI in this slice (out of scope per the YAML's "Files touched"
   list).
3. **Username format.** `<lower(firstName)>.<lower(lastName)><0-99>` —
   keeps the dot separator for readability, suffix range chosen so
   the format matches the spec example `sarah.johnson92` length.
4. **Phone area / exchange ranges.** `[200, 999]` for area and
   exchange, `[0000, 9999]` for subscriber. NXX in the real NANP
   forbids leading 0/1 in area and exchange; we honour that. Not a
   strict E.164 check since this is fake data.
5. **SSN ranges.** `001-999 / 01-99 / 0001-9999` — non-zero in each
   group to match real SSA issuance (zero-blocks are reserved/invalid).
