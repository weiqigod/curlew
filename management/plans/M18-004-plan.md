# Implementation Plan: M18-004

## Overview

Ship the GDPR per-user data export half of M18 (v4-4): an authenticated user can request a JSON bundle of their own data across the six `InExport` tables identified by the M18-003 manifest. A background builder assembles the bundle, writes it to an `IObjectStore` abstraction (S3-compatible in self-hosted, GCS in SaaS), and returns a 24h signed URL via a polling GET. A SvelteKit `/account/data` page provides the user-facing surface. Per-user rate limit is 1 request per 24h.

## Architectural Decisions

These resolve open questions surfaced during exploration:

1. **`IObjectStore` runtime selection.** Bound via a single config key `ApiTool:ObjectStore:Provider` (`s3` | `gcs` | `in_memory`). `in_memory` is registered in Testing only (mirrors the `FakeSmtpSender` pattern). `s3` is the default and is the only provider exercised in the docker-compose stack via MinIO. `gcs` is wired but only smoke-tested in unit tests with the GCS SDK's fake server — running against real GCS requires real cloud spend and is out of scope per CLAUDE.md hard rule.

2. **Signed-URL semantics.** Pre-signed URL TTL is 24h, embedded in the row's `expires_at` column at write time. For S3 we use `GeneratePresignedUrl`; for GCS, V4 signed URLs via the GCS SDK. The `signed_url` is **not** stored — it's regenerated on each GET so a partially-elapsed TTL is reflected (caller sees `expires_at` from the row, not from the URL).

3. **Status state machine.** `queued → building → ready → failed`. `building` is a transient state set when the builder picks up the row inside a single SaveChanges transaction (claim-by-update with `WHERE status = 'queued'`, takes advantage of EF's optimistic concurrency). On exception, the row transitions to `failed` with `failure_reason`.

4. **Per-user rate limit.** Enforced at the endpoint (not the rate-limiter middleware), via an `AnyAsync(r => r.UserId == userId && r.CreatedAt > now - 24h)` pre-check. Returning `429` with `Retry-After` header set to the integer seconds until the youngest existing request ages out. This avoids partitioning the rate-limiter on user-id JWT claim resolution (which would force the limiter into the post-auth middleware chain).

5. **MinIO is the default in docker-compose.** Adds a `minio` service to `docker-compose.test.yml`. Backend env in compose: `OBJECTSTORE__PROVIDER=s3`, `OBJECTSTORE__S3__ENDPOINT=http://minio:9000`, plus bucket/credentials. No real cloud spend.

6. **Test-hook endpoint.** New `POST /api/v1/internal/test-hooks/run-export-builder` (Dev+Testing only, `InternalAccessFilter` guarded) constructs an ad-hoc `UserExportBuilderHost` and calls `TickOnceAsync(ct)` — mirrors the M18-002 `run-audit-cleanup` endpoint exactly.

7. **Builder schema (per-table query).** Iterates `GdprBundleManifest.InExport` deterministically (entries are already alphabetically ordered by the scanner). For each entry, runs `db.Set<TEntity>().Where("UserId = @0", userId)` projected to a plain dictionary via reflection on the entity properties (no entity-tracker overhead). Output JSON shape:

   ```json
   {
     "user_id": "...",
     "generated_at": "...",
     "schema_version": 1,
     "tables": {
       "users": [ { ... } ],
       "refresh_tokens": [ ... ],
       "organization_members": [ ... ],
       "email_verification_tokens": [ ... ],
       "password_reset_tokens": [ ... ],
       "organization_audit_log": [ ... ]
     }
   }
   ```

   The 6 keys are the `InExport` subset of the M18-003 manifest, exact and exhaustive (the test asserts `tables.Keys.Count == 6` and the set equals the manifest's `InExport` table-names).

8. **`organization_audit_log` UserId column.** The audit-log entity uses `ActorId` (nullable) as the user-attribution column, not `UserId`. The builder special-cases the audit log so the filter is `ActorId == userId` while everything else is `UserId == userId`. We expose this via a per-entry user-id column name on `GdprManifestEntry`. **Decision:** add a new `UserIdColumnName` field to `GdprManifestEntry` populated from a new `[GdprUserAttribution]` property attribute. This makes the builder fully manifest-driven instead of hardcoding entity names.

9. **Web page route.** `/account/data` (user-scoped, not org-scoped — matches the spec scope note). New top-level group `web/src/routes/(app)/account/data/` with `+page.server.ts` and `+page.svelte`. No tier gate. Uses a new `userDataApi` typed API client.

10. **OpenAPI documentation.** Both endpoints are registered via `.Produces<>` calls as in `AuditLogEndpoints`, with the response DTO shape (`UserExportRequestDto`) exposing `id`, `status`, `created_at`, `ready_at?`, `expires_at?`, `signed_url?`, `failure_reason?`.

## Implementation Steps

Ordering principle: smallest-blast-radius-first. EF migration + entity + DI come before the endpoint; the builder host before the GET (which depends on builder output); the test-hook last in backend; the web page last overall.

## Risks and Edge Cases

- **Risk:** The bundle JSON includes sensitive columns (e.g. `users.PasswordHash`). → **Mitigation:** Reflection-based serialiser filters out properties tagged `[JsonIgnore]` AND honours a new `[GdprRedacted]` opt-out attribute. Applied to `User.PasswordHash`. Pinned by a test that asserts the bundle's `users[0]` has no `password_hash` key.

- **Risk:** Reflection-based per-table query construction is fragile across SQLite (test) and Postgres (production). → **Mitigation:** Use `db.Set<T>().FromSqlRaw($"SELECT * FROM {table} WHERE {col} = {{0}}", userId)` for the user-id filter, then `AsNoTracking().ToListAsync()` and project via `IEntityType` metadata into `Dictionary<string,object?>`. This stays in EF Core's `IQueryable` semantics for both providers.

- **Risk:** `expires_at` drift — row says T+24h, but the regenerated signed URL says T+24h-Δ. → **Mitigation:** `GET` recomputes the URL with `ttl = expires_at - now`. If `ttl <= 0`, returns status `expired` (additional state — added to the enum upfront) and a 410 Gone is **not** issued; the row reports `status=expired` so callers can retry with a fresh POST after the 24h window.

- **Edge case:** Two queued rows exist simultaneously (race in the 24h window — should be impossible by the rate-limit, but defence-in-depth). → **Handling:** The builder claim-update has `WHERE status='queued'` so concurrent ticks claim distinct rows; the row's PK is the determining factor.

- **Edge case:** User deletes themselves while an export is queued (M18-005 will exist). → **Handling:** FK cascade on `user_id` deletes the request row. Builder swallows the missing-user case and logs a warning. This task does not depend on M18-005 — the FK behaviour is sufficient.

- **Edge case:** MinIO not yet ready when backend boots. → **Handling:** Bucket-create-if-missing happens on first `PutAsync`, not boot. Production path uses already-provisioned buckets so no creation needed.

- **Edge case:** Object store write fails mid-stream. → **Handling:** Row transitions to `Failed`; `failure_reason` includes the exception type but **not** the message (PII risk — message could leak bucket names or credentials). Full exception is logged structurally.

- **Risk:** Unbounded query result size — `organization_audit_log` rows for a heavy user could be huge. → **Mitigation:** Stream JSON directly to `IObjectStore.PutAsync` via a pipe-based `Stream` (write side feeds JSON serializer, read side is consumed by S3 SDK). The bundle is not held in memory all at once.
