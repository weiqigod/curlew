## Architectural Decisions

1. **C# property type for `requester_ip`**: `string?` (with optional `HasColumnType("inet")` only when running against Npgsql). Same pattern as `RefreshToken.LastUsedIp` — keeps the entity portable across SQLite (dev/test) and Postgres (production). The spec says `INET`; the existing codebase has zero INET column usages and uniformly stores IPs as TEXT/string. Following the established pattern over a one-off divergence.
2. **C# property type for `token_hash`**: `byte[]` (SQLite stores as `BLOB`, Postgres as `BYTEA`). Same pattern as `RefreshToken.TokenHash`.
3. **Index naming**: matches the spec's lowercase snake-case names (`idx_password_reset_tokens_hash`, `idx_password_reset_tokens_user`, `idx_password_reset_tokens_active`, `idx_email_verification_tokens_*`) via `HasDatabaseName(...)`. Matches the existing convention (`idx_signing_keys_current`, `idx_github_installations_org`, etc.).
4. **Partial index on `consumed_at IS NULL AND revoked_at IS NULL`**: declared via `HasFilter(...)` so the SQLite-emitted DDL produces a real partial index. This satisfies behavior #7 and matches the existing `idx_signing_keys_current` / `idx_github_installations_org` patterns.
5. **`email_verified` column on `users`**: added via `AddColumn<bool>` migration (default `false`). Same shape as the existing `is_admin` add in `20260420193328_AddUserBootstrapColumns.cs`.
6. **Spec-vs-EF defaults divergence**: the spec uses Postgres defaults like `gen_random_uuid()` and `NOW()`. EF Core migrations against SQLite cannot emit `gen_random_uuid()`; the C# entity layer assigns `Guid.NewGuid()` and `DateTime.UtcNow` at insert time (consistent with existing entities — `RefreshToken`, `StripeWebhookEvent`, `GithubInstallation` all rely on caller-provided values). No DB-level defaults are added; entity-level assignment is left to the M16-003 / M16-008 service slices.
7. **Placeholder-copy header on new MJML files**: the existing parameterized test `Mjml_starts_with_placeholder_copy_header` runs for every slug in `EmailTemplateInventory.Slugs` and requires the literal string `"placeholder copy; product/design polish in a later non-M14 commit"`. The M16 templates are not M14, but we keep the same header verbatim because (a) the wording explicitly says "non-M14 commit", which is accurate for these files, (b) it preserves a single-source-of-truth invariant, and (c) the alternative — editing the test to skip M16 slugs — would weaken a useful product-quality gate.
8. **Spec-allowlist test extension**: add the two new slugs and their variable lists to the `ExpectedVariables` dictionary in `EmailTemplateInventoryManifestTests`. The existing parameterized tests then run automatically against the new templates with no test-method changes required.
9. **Ordering of `EmailTemplateInventory.Slugs`**: append `password_reset` and `trial_expiring` at the end of the list — preserves the explicit "spec :8926-8933 inventory" ordering of the original six (which a separate test still asserts against the original-six expected array). Update that fixed-array test to include the new slugs.
10. **Forbidden-template assertion**: the existing `Forbidden_templates_are_absent` test asserts `password_reset` and `trial_expiring` files do NOT exist. After this slice they DO exist. Replace the assertion's intent: this test is now obsolete and is removed; the parameterized "each slug has both files" test covers the present-files assertion for the new slugs automatically.
11. **Subject-line copy**: per spec :8586-8587, `password_reset` subject is `"Reset your ApiTool password (expires in 30 minutes)"` and `trial_expiring` subject is `"Your trial of {feature} expires {when}"` — the latter contains literal `{feature}` / `{when}` placeholders in the **subject line itself**. SendGrid Dynamic Templates can interpolate variables in subject lines via Handlebars, but our manifest only declares variables; the subject is a static string in the JSON manifest. We follow the spec literally and put the curly-brace string in the manifest's `subject` field. M16-008 (cron + send) will be responsible for any subject-line interpolation if/when SendGrid template config requires it.
12. **`scope` deviation from observable**: the observable describes running migrations against Postgres (`psql \d`). Local TDD runs against SQLite (the dev DB and test infra). Verification step #1 (entity round-trip via `TestDb.CreateOpen()`) covers behaviors #1, #2, #3 against SQLite. The Postgres-specific check is exercised in CI's docker-compose stack (already wired). No additional postgres-specific test code is required in this slice; the migration code is shared and `Database.IsNpgsql()`-aware where it needs to be.
13. **Migration name**: `AddPasswordResetAndEmailVerificationTokens` (single migration — both tables and the users.email_verified column). One migration is operationally cleaner than three, reverts atomically, and matches the multi-table precedent of `SigningKeysAndRefreshTokens`.

## Implementation Steps

The order is (1) data layer first (entities → DbContext → migration), then (2) inventory and tests, then (3) template files. Smallest blast radius first: entities are leaf types with no callers, the migration just generates DDL, the inventory expansion changes a public list, and the templates are pure content.

```csharp
namespace ApiTool.Backend.Data.Entities;

/// <summary>
/// Hash-stored, time-bound, single-use password-reset token.
/// Refs docs/SPECIFICATION.md:8479-8493 (column shape) and :10964-10985 (DDL).
/// </summary>
/// <remarks>
/// 30-minute lifetime (set by <see cref="ExpiresAt"/> at insert time).
/// <see cref="ConsumedAt"/> is set on successful confirm; <see cref="RevokedAt"/>
/// on explicit user revoke (Devices &amp; Sessions). Either makes the row dead.
/// The raw <c>prst_*</c> token is never persisted — only its SHA-256 hash.
/// </remarks>
public sealed class PasswordResetToken
{
    /// <summary>Primary key — random UUID v4.</summary>
    public Guid Id { get; set; }

    /// <summary>The user this token was issued for.</summary>
    public Guid UserId { get; set; }

    /// <summary>SHA-256 hash of the raw <c>prst_*</c> token.</summary>
    public byte[] TokenHash { get; set; } = [];

    /// <summary>UTC timestamp when the token was issued.</summary>
    public DateTime IssuedAt { get; set; }

    /// <summary>UTC timestamp after which the token must not be accepted.</summary>
    public DateTime ExpiresAt { get; set; }

    /// <summary>UTC timestamp when the token was consumed; null while live.</summary>
    public DateTime? ConsumedAt { get; set; }

    /// <summary>UTC timestamp when the token was revoked; null while live.</summary>
    public DateTime? RevokedAt { get; set; }

    /// <summary>IP address of the requester at issue time, for forensic audit.</summary>
    public string? RequesterIp { get; set; }

    /// <summary>User-Agent of the requester at issue time, for forensic audit.</summary>
    public string? RequesterUa { get; set; }
}
```

```csharp
    public DateTime ExpiresAt { get; set; }

    /// <summary>UTC timestamp when the token was consumed; null while live.</summary>
```

```csharp
using ApiTool.Backend.Data.Entities;
using ApiTool.Backend.Tests.TestInfrastructure;
using Microsoft.EntityFrameworkCore;

namespace ApiTool.Backend.Tests.Auth;

/// <summary>
/// Verifies the PasswordResetToken entity round-trips against SQLite and that
/// the partial active-token index is created.
/// Filter: FullyQualifiedName~PasswordResetTokenEntity
/// </summary>
public sealed class PasswordResetTokenEntityTests
{
    [Fact]
    public async Task Entity_persists_and_round_trips()
    {
        await using var scope = TestDb.CreateOpen();
        await scope.Db.Database.MigrateAsync();
        var userId = await SeedUser(scope.Db);

        var token = new PasswordResetToken
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            TokenHash = new byte[] { 1, 2, 3, 4 },
            IssuedAt = DateTime.UtcNow,
            ExpiresAt = DateTime.UtcNow.AddMinutes(30),
            RequesterIp = "203.0.113.42",
            RequesterUa = "Mozilla/5.0",
        };
        scope.Db.PasswordResetTokens.Add(token);
        await scope.Db.SaveChangesAsync();

        (await scope.Db.PasswordResetTokens.CountAsync()).Should().Be(1);
        var loaded = await scope.Db.PasswordResetTokens.SingleAsync();
        loaded.UserId.Should().Be(userId);
        loaded.TokenHash.Should().Equal(token.TokenHash);
        loaded.RequesterIp.Should().Be("203.0.113.42");
        loaded.ConsumedAt.Should().BeNull();
        loaded.RevokedAt.Should().BeNull();
    }

    [Fact]
    public async Task Token_hash_unique_index_prevents_duplicate()
    {
        await using var scope = TestDb.CreateOpen();
        await scope.Db.Database.MigrateAsync();
        var userId = await SeedUser(scope.Db);

        var hash = new byte[] { 9, 9, 9, 9 };
        scope.Db.PasswordResetTokens.Add(NewRow(userId, hash));
        await scope.Db.SaveChangesAsync();
        scope.Db.ChangeTracker.Clear();

        scope.Db.PasswordResetTokens.Add(NewRow(userId, hash));
        await Assert.ThrowsAsync<DbUpdateException>(
            () => scope.Db.SaveChangesAsync());
    }

    [Fact]
    public async Task Active_partial_index_exists_on_sqlite()
    {
        // The partial-index filter is what proves behavior #7 ("EXPLAIN uses
        // the index on lookup"). On SQLite we assert the index DDL contains
        // the WHERE clause; full EXPLAIN parsing is a Postgres-only concern
        // verified by the migration round-trip in the docker stack.
        await using var scope = TestDb.CreateOpen();
        await scope.Db.Database.MigrateAsync();

        var sql = await ReadIndexSqlAsync(scope.Db,
            "idx_password_reset_tokens_active");
        sql.Should().Contain("consumed_at").And.Contain("revoked_at");
    }

    private static async Task<Guid> SeedUser(AppDbContext db)
    {
        var u = new User { Id = Guid.NewGuid(), Email = $"u-{Guid.NewGuid():N}@example.com", CreatedAt = DateTime.UtcNow };
        db.Users.Add(u);
        await db.SaveChangesAsync();
        return u.Id;
    }

    private static PasswordResetToken NewRow(Guid userId, byte[] hash) => new()
    {
        Id = Guid.NewGuid(),
        UserId = userId,
        TokenHash = hash,
        IssuedAt = DateTime.UtcNow,
        ExpiresAt = DateTime.UtcNow.AddMinutes(30),
    };

    private static async Task<string> ReadIndexSqlAsync(AppDbContext db, string name)
    {
        await using var cmd = db.Database.GetDbConnection().CreateCommand();
        cmd.CommandText =
            "SELECT sql FROM sqlite_master WHERE type='index' AND name=@n";
        var p = cmd.CreateParameter(); p.ParameterName = "@n"; p.Value = name;
        cmd.Parameters.Add(p);
        var result = await cmd.ExecuteScalarAsync();
        return result as string ?? string.Empty;
    }
}
```

## Risks and Edge Cases

- **Risk:** The auto-generated migration may include unwanted operations if the model snapshot has drifted (e.g., a half-finished M16-001 commit). → **Mitigation:** before running `dotnet ef migrations add`, run `dotnet build src/ApiTool.Backend` and inspect `git status --porcelain src/ApiTool.Backend/Migrations/AppDbContextModelSnapshot.cs`. If the snapshot diff outside our two new entities and the email_verified column shows other changes, abort and reconcile; the migration must be a pure additive of the two tables + one column + six indexes.
- **Risk:** `HasFilter("\"consumed_at\" IS NULL AND \"revoked_at\" IS NULL")` uses Postgres-style double-quoted identifiers. SQLite accepts double-quoted identifiers as well (SQLite's CREATE INDEX ... WHERE clause), so the same string works on both. The existing `idx_signing_keys_current` filter uses the same convention. → **Mitigation:** verified by reading existing migration 20260504150157 and the M14-017 github_installations migration; both use double-quoted column names in `HasFilter` strings and apply cleanly on SQLite via `Database.MigrateAsync()`.
- **Risk:** `IsDescending(false, true)` on the composite `(user_id, issued_at DESC)` index is a relatively recent EF Core 9 API. → **Mitigation:** `Microsoft.EntityFrameworkCore` 9.0.4 (per csproj) supports it. Fallback: omit `IsDescending` and accept that SQLite ignores DESC anyway; the spec's DESC requirement is an analyzer hint that matters only on Postgres.
- **Risk:** The `trial_expiring` subject `"Your trial of {feature} expires {when}"` carries literal curly-brace placeholders that are NOT in the manifest variable allowlist (the variable is `feature`, not `{feature}`; the manifest has no `when` variable at all). The current `SendGridSmtpSender` allowlist check applies only to template *body* variables, not subject lines (subject is a static `manifest.Subject` string). → **Mitigation:** acceptable — subject-line interpolation is M16-008's concern (cron + send). If M16-008 needs runtime substitution it can do `subject.Replace("{feature}", feature)` server-side before passing to SendGrid. This slice ships the subject string verbatim per spec.
- **Edge case:** the existing dev DB at `src/ApiTool.Backend/Data/apitool-dev.db` already has an applied migration history. `dotnet ef database update` against it should apply only the new migration. → **Handling:** documented in observable; nothing to do.
- **Edge case:** `User` already has `EmailVerified` set true accidentally on existing rows? Default is `false`; `AddColumn<bool>(... defaultValue: false)` backfills existing rows on SQLite. Tested by `User_email_verified_column_defaults_false`.
- **Edge case:** the Mjml.Net compiler is strict about XML well-formedness. The `&` char in user-agents (`Macintosh; Intel Mac OS X 10_15_7`) lives in the JSON manifest, not the MJML — no escaping concern. → **Handling:** the MJML files use only `{{var}}` Handlebars, no embedded special characters; verified by reading the existing five M14 templates which use identical patterns.
