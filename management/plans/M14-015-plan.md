# Implementation Plan: M14-015

## Overview

Ships the remaining five M14 transactional email templates (auth_device_code, billing_receipt, billing_payment_failed, billing_subscription_canceled, account_security_alert), an `EmailTemplateInventory` static asset that pins the canonical six-slug list, a manifest-validator unit test that round-trips every template through compile + manifest-coverage + variable-allowlist checks, a `templates/email/README.md` documenting the placeholder-copy convention plus the variable-allowlist rule, and a GitHub Actions workflow `.github/workflows/email-templates.yml` that compiles + uploads to a fake SendGrid in CI and writes per-slug template IDs to the secrets-store fixture. ## Architectural Decisions (resolved up-front)

The task YAML is precise; the residual decisions are mechanical. Resolving them up-front so the implementation steps are deterministic.

1. **Inventory pin: a canonical static class `EmailTemplateInventory`.** The behaviors require the test class to be discoverable via `--filter "FullyQualifiedName~EmailTemplateInventory"`. We add a `public static class EmailTemplateInventory` with `Slugs` = a `IReadOnlyList<string>` of the six canonical slugs, ordered to match the spec table at `docs/SPECIFICATION.md:8926-8933`. The class lives at `src/ApiTool.Backend/Notifications/Email/EmailTemplateInventory.cs` (production code, not test code) so that production callers (e.g. a future startup gate) can also enumerate the canonical list. The corresponding test class is `EmailTemplateInventoryTests` in `src/ApiTool.Backend.Tests/Notifications/Email/`.

2. **Variable allowlist per template — exactly the spec table.** No additions, no extensions. The spec at :8926-8933 prescribes the exact variable set per slug; manifests must match.

   | Slug | Variables (manifest-declared) |
   |---|---|
   | `email_verification` | `first_name`, `verification_url` |
   | `auth_device_code` | `user_code`, `verification_url`, `expires_in_minutes` |
   | `billing_receipt` | `first_name`, `billing_period`, `amount_total`, `invoice_url` |
   | `billing_payment_failed` | `first_name`, `amount_total`, `update_payment_url`, `attempt_count` |
   | `billing_subscription_canceled` | `first_name`, `tier`, `effective_date` |
   | `account_security_alert` | `first_name`, `event_time`, `event_ip`, `relogin_url` |

   The `email_verification` row already exists from M14-014; we leave it untouched.

3. **Subject lines.** The spec only fully specifies `billing_receipt` ("Your Curlew receipt for {{billing_period}}", :8908). For the other five, we ship placeholder subjects following the same style. Per Open Decision #8 these are placeholder copy; product/design polishes them in a later non-M14 commit.
   - `email_verification`: "Verify your Curlew email" (already shipped by M14-014)
   - `auth_device_code`: "Your Curlew device-login code"
   - `billing_receipt`: "Your Curlew receipt for {{billing_period}}" (spec-fixed)
   - `billing_payment_failed`: "Payment issue with your Curlew subscription"
   - `billing_subscription_canceled`: "Your Curlew subscription has been canceled"
   - `account_security_alert`: "Security alert on your Curlew account"

4. **Test data values.** Per :8915-8920 the test_data must satisfy the type hints and produce a recognisable preview. We pick stable, recognisable values that round-trip through Handlebars without producing surprising HTML (no `<`, `>`, `&` characters in test data — the XSS test at `EmailPreviewRendererTests.cs:82` already exercises escaping with a separate fixture).
   - Names: `"Alex"` (matches the `email_verification` baseline).
   - URLs: `https://app.apitool.dev/...` (matches the `email_verification` baseline).
   - Dates: ISO 8601 dates (`"2026-05-15"`) and human-friendly periods (`"May 2026"`).
   - Currency: `"$49.00"` (matches the spec example at :8918).
   - IPs: `"203.0.113.42"` (RFC 5737 documentation prefix — never collides with real-world IPs).
   - Codes: `"WDJB-MJHT"` (the canonical Google device-code shape).
   - Counts: `"3"`, `"15"`.

5. **Template content style — all six follow the M14-014 fixture's MJML structure.** Each template ships a single `mj-body` → `mj-section` → `mj-column` block with: header `mj-text` (welcome/heading), body `mj-text`s explaining the action, optional `mj-button` for the primary call-to-action, optional `mj-divider`, and a footer `mj-text` with disclaimer. This keeps Mjml.Net 4.x compatibility tight (we already have the M14-014 contract test that proves these components compile). All six open with the M14-014 placeholder-copy convention header comment: `<!-- placeholder copy; product/design polish in a later non-M14 commit -->`.

6. **Manifest-validator scope.** Behavior #2 prescribes a validator that asserts (a) no required field is missing, (b) every test_data key is also a declared variable. Behavior #3 separately prescribes a compose-time check that raises `EmailTemplateVariableUnknownException` on hand-crafted out-of-list variables. Both ship as **unit tests** (no new production class is required — M14-014 already shipped `EmailTemplateLoader`, the `EmailTemplateManifest` record, and the `SendGridSmtpSender.SendTemplateAsync` allowlist check that throws `EmailTemplateVariableUnknownException`). The validator test is a parameterized xUnit `[Theory]` that drives every slug in `EmailTemplateInventory.Slugs` through the same set of assertions; it doubles as the >=12-test count in `definition_of_done`.

7. **Spec coverage assertion (Behavior #4).** A dedicated `EmailTemplateInventoryTests.Inventory_matches_spec_section_8924_to_8933` test asserts the inventory matches the six listed slugs **exactly**. Implementation: the test holds the canonical list as a literal `string[]` mirroring the spec table, and asserts `EmailTemplateInventory.Slugs` is a permutation of that literal. This guards against future drift if someone adds a slug without updating the spec.

8. **Forbidden-template assertion (Behavior #5).** A dedicated `EmailTemplateInventoryTests.Forbidden_templates_are_absent` test asserts the files `templates/email/password_reset.mjml`, `templates/email/password_reset.json`, `templates/email/trial_expiring.mjml`, and `templates/email/trial_expiring.json` do **not** exist. The reasoning is documented in the assertion's `because:` clause: "password_reset and trial_expiring ship with M16's password-reset and trial cron slices per investigation Decision #10."

9. **Placeholder-copy header comment (Behavior #6).** The validator test asserts every MJML file's first non-blank line contains `placeholder copy; product/design polish in a later non-M14 commit` (the existing M14-014 fixture already contains this exact string). This wires the convention into the build so future templates can't drop it without breaking the test. The check is case-sensitive substring on the raw MJML text (read via `loader.LoadMjml(slug)`).

10. **CI-upload job behavior (Behavior #7).** The task scope says the CI upload job uploads each template to a "fake SendGrid in CI." We ship a GitHub Actions workflow `.github/workflows/email-templates.yml` that:
    - Triggers on `push` to `main` and `pull_request` (so it gates merges that touch `templates/email/**`).
    - Spins up a tiny in-CI fake SendGrid HTTP server (a 30-line Python `http.server` script committed at `scripts/fake-sendgrid.py`) on `localhost:8080`. The fake script implements just `GET /v3/templates?generations=dynamic`, `POST /v3/templates`, and `POST /v3/templates/{id}/versions` — the exact endpoints `SendGridTemplateUploader` calls.
    - Runs `dotnet run --project src/ApiTool.Backend -- dev upload-templates --api-key fake-ci-key` with `SENDGRID_API_BASE=http://localhost:8080` (we add a tiny env-var override hook to `DevCommands.RunUploadTemplatesAsync` for this exact purpose; default remains `https://api.sendgrid.com`).
    - Captures the `CURLEW__SENDGRID__TEMPLATES__<SLUG>=<id>` lines from stdout and writes them to `${{ runner.temp }}/sendgrid-templates.env` (the "secrets-store fixture"). The workflow then `cat`s the file to confirm all six lines are present and asserts `wc -l == 6`. This is the observable "uploads each template and writes a per-slug template ID to the secrets-store fixture."

    Why the env-var override: `DevCommands.RunUploadTemplatesAsync` currently hard-codes `new HttpClient { BaseAddress = new Uri("https://api.sendgrid.com") }`. We inject `Environment.GetEnvironmentVariable("SENDGRID_API_BASE") ?? "https://api.sendgrid.com"` to support the CI-only fake. This is a minimal one-line change.

11. **Fake-SendGrid script — Python `http.server` + 50 lines of routing.** The script lives at `scripts/fake-sendgrid.py`, runs as `python3 scripts/fake-sendgrid.py 8080`, and is invoked from the CI workflow as a backgrounded process. It records each `POST /v3/templates` call, returns a deterministic incrementing ID `d-fake-001`..`d-fake-006`, and accepts version POSTs unconditionally. We do not add a complex test fixture — the goal is just to prove the CLI talks HTTP to a SendGrid-shaped endpoint. The unit test `SendGridTemplateUploaderTests` (M14-014) already covers the wire-format correctness; the workflow proves the end-to-end CLI invocation.

12. **README content (definition_of_done).** `templates/email/README.md` documents:
    - The pair-file convention (`<slug>.mjml` + `<slug>.json`).
    - The manifest schema with a link back to `docs/SPECIFICATION.md:8941+`.
    - The variable-allowlist rule (any variable name not declared in the manifest is rejected at compose time by `SendGridSmtpSender.SendTemplateAsync` per `docs/SPECIFICATION.md:8941-8942`).
    - The placeholder-copy convention header comment requirement.
    - The dev preview command (`dotnet run --project src/ApiTool.Backend -- dev email-preview <slug>`).
    - The list of forbidden slugs (password_reset, trial_expiring) and the M16 deferral note.
    - The :8924-8953 spec citation.

13. **No production code changes beyond the `SENDGRID_API_BASE` env hook and the inventory class.** All other deliverables are content (MJML + JSON), documentation (README), tests, and a workflow file. This keeps the slice surgical.

14. **Test naming convention.** The task observable filters `FullyQualifiedName~EmailTemplateInventory` — we name the new test classes `EmailTemplateInventoryTests` (the spec-coverage and forbidden-templates checks) and `EmailTemplateInventoryManifestTests` (the per-slug parameterized validator). Both share the `EmailTemplateInventory` substring so both are picked up by the filter. Counting: with six slugs and two `[Theory]` validator behaviors plus four `[Fact]` inventory tests, the class produces 6×2 + 4 = 16 tests, comfortably above the >=12 threshold in DoD.

15. **Test count math (Behavior #1).** The behavior says ">=12, one or more tests per template." Concretely:
    - `EmailTemplateInventoryManifestTests.Manifest_round_trips_loader(slug)` — 6 tests (one per slug)
    - `EmailTemplateInventoryManifestTests.Mjml_compiles_to_non_empty_html(slug)` — 6 tests (one per slug)
    - `EmailTemplateInventoryManifestTests.TestData_keys_are_subset_of_variables(slug)` — 6 tests
    - `EmailTemplateInventoryManifestTests.TestData_keys_match_variables_exactly(slug)` — 6 tests (stricter check: equal sets, not just subset; otherwise a manifest with declared-but-undefaulted variables would slip through)
    - `EmailTemplateInventoryManifestTests.Manifest_variables_match_spec_allowlist(slug)` — 6 tests (asserts each slug's manifest declares exactly the spec-prescribed variable set, Decision #2 above)
    - `EmailTemplateInventoryManifestTests.SendGridSmtpSender_rejects_unknown_variable(slug)` — 6 tests (Behavior #3)
    - `EmailTemplateInventoryManifestTests.Mjml_starts_with_placeholder_copy_header(slug)` — 6 tests (Behavior #6)
    - `EmailTemplateInventoryTests.Inventory_matches_spec_section_8924_to_8933` — 1 test
    - `EmailTemplateInventoryTests.Inventory_has_six_slugs` — 1 test
    - `EmailTemplateInventoryTests.Forbidden_templates_are_absent` — 1 test
    - `EmailTemplateInventoryTests.Each_slug_has_both_mjml_and_json_files` — 1 test
    
    Total: 7 × 6 + 4 = **46 tests**. Comfortably above >=12.

16. **The `email_verification` slot.** M14-014 already shipped `templates/email/email_verification.{mjml,json}` and the four-test `EmailVerificationFixtureTests` against it. We **do not modify** that fixture; we add to it. The new `EmailTemplateInventoryManifestTests` covers `email_verification` with the same six per-slug behaviors as the other five (its existing `EmailVerificationFixtureTests` becomes redundant but stays green; we leave the M14-014 tests untouched to avoid coupling slices). The Behavior-#1 count of >=12 is per the inventory tests alone, not counting the M14-014 fixture tests.

17. **Behavior #3 implementation in the parameterized test.** The test instantiates a real `SendGridSmtpSender` (via DI scaffolding from `SendGridSmtpSenderTests` patterns), hands it a hand-crafted variable name guaranteed not to be in any manifest (`"__definitely_not_a_variable"`), and asserts `EmailTemplateVariableUnknownException` is thrown. This proves the M14-014 allowlist mechanism still rejects unknown vars across all six slugs as new manifests are added. Cheaper alternative: load the manifest, build a dict with one allowed key + one disallowed key, run the same allowlist logic by calling `SendGridSmtpSender.SendTemplateAsync` directly with a stub HTTP handler. The stub never gets called because the exception fires first — which is the correctness condition.

18. **Workflow naming and triggers.** `.github/workflows/email-templates.yml`. Triggers: `push` to `main` (so the merge-into-main run captures the upload artifact for the secrets-store fixture) and `pull_request` (so PRs that touch `templates/email/**` are gated). `paths`: `['templates/email/**', 'src/ApiTool.Backend/Notifications/Email/**', 'scripts/fake-sendgrid.py', '.github/workflows/email-templates.yml']`. This matches the e2e-m4.yml pattern of co-locating "what triggers re-run" with the workflow.

19. **CI workflow does NOT run dotnet test.** The unit tests run in `e2e-m4.yml`. The new workflow's job is specifically to prove the CLI talks to a SendGrid-shaped endpoint and emits the env-var lines. Keeping responsibilities narrow.

```csharp
[Fact]
public void Forbidden_templates_are_absent()
{
    var root = Path.Combine(GetRepoRoot(), "templates", "email");
    var forbidden = new[] { "password_reset", "trial_expiring" };
    foreach (var slug in forbidden)
    {
        File.Exists(Path.Combine(root, $"{slug}.mjml")).Should().BeFalse(
            because: $"{slug} ships with M16's slice per investigation Decision #10");
        File.Exists(Path.Combine(root, $"{slug}.json")).Should().BeFalse(
            because: $"{slug} ships with M16's slice per investigation Decision #10");
    }
}

[Fact]
public void Each_slug_has_both_mjml_and_json_files()
{
    var root = Path.Combine(GetRepoRoot(), "templates", "email");
    foreach (var slug in EmailTemplateInventory.Slugs)
    {
        File.Exists(Path.Combine(root, $"{slug}.mjml")).Should().BeTrue(
            because: $"M14 inventory requires {slug}.mjml");
        File.Exists(Path.Combine(root, $"{slug}.json")).Should().BeTrue(
            because: $"M14 inventory requires {slug}.json");
    }
}

private static string GetRepoRoot()
{
    var dir = new DirectoryInfo(AppContext.BaseDirectory);
    while (dir is not null)
    {
        if (Directory.Exists(Path.Combine(dir.FullName, "templates", "email")))
            return dir.FullName;
        dir = dir.Parent;
    }
    throw new InvalidOperationException(
        "Could not locate repo root containing templates/email from " + AppContext.BaseDirectory);
}
```

```csharp
namespace ApiTool.Backend.Tests.Notifications.Email;

public sealed class EmailTemplateInventoryManifestTests

            .LoadManifest(slug);
```

#### New Code (`fake-sendgrid.py` outline)

```python
#!/usr/bin/env python3
"""Fake SendGrid v3 templates API for CI. Implements the three endpoints
SendGridTemplateUploader calls: list templates, create template, create version."""
import http.server, json, sys, threading, itertools

_id_seq = itertools.count(1)

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path.startswith("/v3/templates"):
            self._json(200, {"templates": []})
        else:
            self._json(404, {"error": "not found"})

    def do_POST(self):
        if self.path == "/v3/templates":
            self._json(201, {"id": f"d-fake-{next(_id_seq):03d}"})
        elif self.path.startswith("/v3/templates/") and "/versions" in self.path:
            self._json(201, {"id": "v-1", "active": 1})
        else:
            self._json(404, {"error": "not found"})

    def _json(self, code, body):
        data = json.dumps(body).encode()
        self.send_response(code); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data))); self.end_headers()
        self.wfile.write(data)

    def log_message(self, fmt, *args): pass  # quiet

if __name__ == "__main__":
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8080
    http.server.HTTPServer(("127.0.0.1", port), Handler).serve_forever()
```

## Risks and Edge Cases

- **Risk: Mjml.Net 4.x cannot compile one of the five new templates.** → **Mitigation:** Step 2's `Mjml_compiles_to_non_empty_html` test is parameterized across all six slugs; any compile failure raises `InvalidOperationException` from `MjmlNetCompiler` and fails the test in CI. Each template uses only the canonical `mj-body`/`mj-section`/`mj-column`/`mj-text`/`mj-button`/`mj-divider` set already proven by the M14-014 fixture. If a template fails, we narrow it to the canonical-component set.

- **Risk: A manifest's `test_data` value contains a Handlebars special character (e.g. `{`).** → **Mitigation:** Decision #4 prescribes test data without `{`, `}`, `<`, `>`, or `&`. The `EmailPreviewRendererTests` already covers the XSS case with a separate fixture; the inventory tests do not need to re-cover it.

- **Risk: A workflow flake when the fake-SendGrid Python server takes >1s to start.** → **Mitigation:** the workflow does `curl -fsS http://localhost:18080/...` after `sleep 1` to confirm the server is actually listening before the dotnet step runs. If the curl fails, the job fails fast and surfacing the readiness issue.

- **Risk: `SENDGRID_API_BASE` env-var override leaks into other tests.** → **Mitigation:** the Step 5 test wraps `Environment.SetEnvironmentVariable` in try/finally so the env var is cleared on test exit. Other tests do not read this env var.

- **Risk: Spec-coverage test (`Inventory_matches_spec_section_8924_to_8933`) regresses if someone updates the spec.** → **Mitigation:** the test holds the canonical list as a literal string array. If the spec changes, the test must change too — which is the desired behaviour (intentional friction on inventory drift).

- **Risk: M14-014's `EmailVerificationFixtureTests` becomes redundant with the new parameterized tests.** → **Mitigation:** redundant tests are GREEN tests; we leave them so M14-014's slice boundary isn't disturbed by M14-015.

- **Edge case: `email_verification` already exists.** → **Handling:** Step 3 does not touch `email_verification.{mjml,json}`; only the five new pairs are added. The Step 2 tests cover `email_verification` automatically because `EmailTemplateInventory.Slugs` includes it.

- **Edge case: CI runner Python version doesn't have stdlib `http.server`.** → **Handling:** `http.server` is part of the Python 3 standard library back to Python 3.0; `setup-python@v5` with 3.12 is sufficient.

- **Edge case: `SendGridStubClient` must implement `ISendGridClient`.** → **Handling:** `ISendGridClient` has only one method (`SendEmailAsync`); the stub throws `InvalidOperationException("HTTP call should not be made — variable allowlist must reject first")` from that method, ensuring a regression in the allowlist would fail the test loudly.
