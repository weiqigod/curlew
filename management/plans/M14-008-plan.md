## Architectural Decisions (resolved up-front)

1. **`stripe_customer_id` lives on `subscriptions`, not on `organizations`.** The task YAML wording "persisted to the orgs.stripe_customer_id column" is a paraphrase of the spec; the spec's authoritative DB schema (SPECIFICATION.md:9886) places `stripe_customer_id` on the `subscriptions` table, the EF entity `Subscription.cs` already exposes a `StripeCustomerId` string property, and a migration already created the column (`20260417123128_AddBillingAndInvitations`). Adding a duplicate column to `Organization` would split the source of truth and require a fresh migration. We persist on `subscriptions.stripe_customer_id` and document this in the plan. Reuse logic: when an org already has a `Subscription` row with a non-null `StripeCustomerId`, that value is reused for the new Checkout Session even if the prior subscription is in a non-active state. Today the service short-circuits with `AlreadySubscribed` when *any* row exists for the org, so on the happy-path "no active sub" branch the lookup returns null and we always create a new Customer — the reuse code path becomes load-bearing once future slices loosen the `AlreadySubscribed` guard, but is implemented now to satisfy behaviour #3's "first time" wording without painting us into a corner later.

2. **The endpoint contract changes shape: `price_id` (free-form) replaces `tier`+`interval`+`seat_count`.** The task observable POSTs `{"price_id":"price_test_solo_monthly", "success_url":..., "cancel_url":...}`. Today's contract is `{"org_id","tier","interval","seat_count","success_url","cancel_url"}`. Behaviour #4 requires a `price_id` allowlist and a new `invalid_price_id` 400 error. We **add** `price_id` as an optional field to `CheckoutRequest` and route it through a new code path; when `price_id` is present, the `tier`/`seat_count`/`interval` fields are derived from the price_id pattern (per the allowlist `price_test_*`, `price_solo_*`, `price_team_*`, `price_professional_*`, `price_enterprise_*`). When `price_id` is absent the existing fields drive behaviour. This dual-path keeps the existing 9 endpoint tests green while satisfying the M14-008 observable. **Behaviour #6 (org_id binding)**: the spec says the request body cannot override the bearer-validated org. We satisfy this by **resolving the org from the authenticated user** when only `price_id` is supplied (the user's owned/single-membership org), and rejecting requests that supply both `price_id` and a mismatching `org_id`. When the `price_id` path is taken the request body's `org_id` field is ignored; the user's owned org is selected.

3. **No interface signature change. `IStripeGateway.CreateCheckoutSessionAsync` keeps its current parameter list, plus a new optional `priceId` parameter and an optional `existingCustomerId` parameter.** Adding a second method (`CreateCheckoutAsync(priceId, ...)`) per the task wording would force every test that uses the fake to migrate. Instead we extend the single method's parameter list — both `priceId` and `existingCustomerId` default to `null` so the existing 5 callers compile unchanged. The `tier+interval+seatCount` path is preserved; when `priceId` is non-null it takes precedence and the tier/interval/seat values are advisory (used only for audit-log payload + DB row hydration). The fake gateway still constructs a deterministic `cs_<guid>` URL when `priceId` is null, and a deterministic `cs_test_<guid>` URL when `priceId` is non-null so tests can distinguish paths.

4. **`IdempotencyKey` is derived deterministically from the inbound HTTP request.** Per behaviour #1 it must be a "request-derived UUID" and per behaviour #2 must be stable across a network retry of the same request. The CLI client (M14-004) already uses RFC 4122 v4 random UUIDs per call as its retry key; that is the only id we control end-to-end. We propagate it via a new `Idempotency-Key` request header (Stripe's own convention; the same header name HTTP retry middleware uses) read inside `CreateCheckout`. When the header is absent we synthesize a v4 UUID server-side and return it on the response (header `X-Stripe-Idempotency-Key`) so callers can replay. The header value is passed all the way down to `IStripeGateway.CreateCheckoutSessionAsync` as a new `idempotencyKey` parameter (also defaulted to null for backward compatibility — the fake gateway ignores it).

5. **Stripe SDK access is wired through `Stripe.Net`'s `StripeClient` instance, not the static singleton.** `Stripe.Net` exposes both `StripeConfiguration.ApiKey` (process-global) and `StripeClient(apiKey, ...)` (per-instance). The instance form is required for testability because two integration tests cannot both safely mutate the global. `StripeGateway` takes an `IOptions<StripeOptions>` and constructs a `StripeClient` via the constructor that accepts a custom `IHttpClient` — when `APITOOL__STRIPE__APIBASE` is set we point the client at `http://localhost:12111` (the stripe-mock base URL) by passing `appInfo: null, apiBase: APITOOL__STRIPE__APIBASE`. In production `APITOOL__STRIPE__APIBASE` is unset and the SDK uses `https://api.stripe.com`.

6. **The `StripeOptions` record gains `ApiKey` and `ApiBase` fields.** Today it carries only `Mode`. Behaviour #7 names the env vars: `APITOOL__STRIPE__APIKEY`, `APITOOL__STRIPE__APIBASE`, `APITOOL__STRIPE__MODE`. ASP.NET's `Configure<StripeOptions>` already binds case-insensitively, so adding `string ApiKey { get; set; }` and `string? ApiBase { get; set; }` to `StripeOptions` is enough. We **also** validate at startup: when `Mode == "live"` and `ApiKey` is empty, throw `OptionsValidationException` so the misconfiguration is visible at startup, not on first checkout.

7. **`StripeException` rate-limit mapping uses `HttpStatusCode == 429` plus `ex.StripeError?.Code == "rate_limit"` (behaviour #5).** Stripe.Net surfaces these on `StripeException`. We map to RFC 7807 `STRIPE_RATE_LIMITED` 503 with the idempotency key in the `extensions` field, matching how the rest of the backend shapes errors (`ErrorResponse(code, message)` is the existing shape — we add a new code constant).

8. **`stripe-mock` healthcheck uses HTTP `/v1/customers` HEAD.** The container exposes the same routes as Stripe; a HEAD on a real route is the standard probe per Stripe's own docs (no `/health` endpoint).

9. **The existing 9 endpoint tests in `SubscriptionsEndpointsTests` must continue to pass unchanged.** They use the `tier`/`interval`/`seat_count` legacy contract and the `FakeStripeGateway`. They are not touched by this slice. Adding new tests, not modifying old ones, is the way we honour the test stability quality bar.

```csharp
// Spec refs: docs/SPECIFICATION.md:6856–6870 (three-layer test strategy), :7980 (force-validation triggers).
using ApiTool.Backend.Data.Entities;
using Microsoft.Extensions.Options;
using Stripe;
using Stripe.Checkout;

namespace ApiTool.Backend.Subscriptions;

public sealed class StripeGateway : IStripeGateway
{
    private readonly StripeClient _client;
    private readonly ILogger<StripeGateway> _log;

    public StripeGateway(IOptions<StripeOptions> options, ILogger<StripeGateway> log)
    {
        var opts = options.Value;
        if (string.IsNullOrEmpty(opts.ApiKey))
            throw new InvalidOperationException(
                "Stripe:Mode=live requires APITOOL__STRIPE__APIKEY to be set.");

        _client = string.IsNullOrEmpty(opts.ApiBase)
            ? new StripeClient(opts.ApiKey)
            : new StripeClient(opts.ApiKey, apiBase: opts.ApiBase);
        _log = log;
    }

    public async Task<CheckoutSession> CreateCheckoutSessionAsync(
        Guid userId, Guid orgId, SubscriptionTier tier, string interval, int seatCount,
        string successUrl, string cancelUrl,
        string? priceId = null,
        string? existingCustomerId = null,
        string? idempotencyKey = null,
        CancellationToken ct = default)
    {
        var requestOptions = new RequestOptions { IdempotencyKey = idempotencyKey };

        // 1) Resolve customer id.
        string customerId;
        if (!string.IsNullOrEmpty(existingCustomerId))
        {
            customerId = existingCustomerId;
        }
        else
        {
            try
            {
                var customer = await new CustomerService(_client).CreateAsync(
                    new CustomerCreateOptions { Metadata = new() { ["org_id"] = orgId.ToString("D") } },
                    requestOptions, ct);
                customerId = customer.Id;
            }
            catch (StripeException ex) when (ex.HttpStatusCode == HttpStatusCode.TooManyRequests)
            {
                _log.LogWarning("stripe rate-limited (customer.create) idempotency_key={IdempotencyKey}", idempotencyKey);
                throw new StripeRateLimitedException(idempotencyKey, ex);
            }
        }

        // 2) Create the checkout session.
        var resolvedPriceId = priceId ?? throw new InvalidOperationException(
            "StripeGateway requires priceId; SubscriptionsService must resolve tier→price before invoking the gateway.");

        var sessionOptions = new SessionCreateOptions
        {
            Mode = "subscription",
            Customer = customerId,
            SuccessUrl = successUrl,
            CancelUrl = cancelUrl,
            LineItems = [new SessionLineItemOptions { Price = resolvedPriceId, Quantity = seatCount }],
            Metadata = new() { ["org_id"] = orgId.ToString("D"), ["user_id"] = userId.ToString("D") },
        };
        try
        {
            var session = await new SessionService(_client).CreateAsync(sessionOptions, requestOptions, ct);
            return new CheckoutSession(session.Id, session.Url, customerId);
        }
        catch (StripeException ex) when (ex.HttpStatusCode == HttpStatusCode.TooManyRequests)
        {
            _log.LogWarning("stripe rate-limited (session.create) idempotency_key={IdempotencyKey}", idempotencyKey);
            throw new StripeRateLimitedException(idempotencyKey, ex);
        }
    }

    public async Task<PortalSession> CreatePortalSessionAsync(
        Guid userId, Guid orgId, string returnUrl, CancellationToken ct)
    {
        // Best-effort: requires a customer id; for now we look up via metadata when called from the live path.
        // Keeping a placeholder so the integration tests that exercise the checkout path don't trip portal logic.
        // Real portal wiring (which needs a customer-id-by-org lookup) lands in M14-009.
        throw new NotImplementedException(
            "CreatePortalSessionAsync lands in M14-009; M14-008 ships only checkout.");
    }

    public ProrationResult ComputeProration(
        SubscriptionTier fromTier, int fromSeats, SubscriptionTier toTier, int toSeats, string interval)
        => throw new NotImplementedException(
            "ComputeProration lands in M14-010 (Stripe upcoming-invoice preview).");
}

public sealed class StripeRateLimitedException(string? idempotencyKey, Exception inner)
    : Exception("Stripe rate-limited (HTTP 429); retry with idempotency key.", inner)
{
    public string? IdempotencyKey { get; } = idempotencyKey;
}
```

```csharp
public async Task<(string checkoutUrl, string sessionId, SubscriptionError err, string? msg)>
    CreateCheckoutByPriceAsync(Guid userId, string priceId,
                                string successUrl, string cancelUrl,
                                string idempotencyKey, CancellationToken ct)
{
    if (!StripePriceAllowlist.IsAllowed(priceId))
        return (string.Empty, string.Empty, SubscriptionError.InvalidPriceId,
            $"Price '{priceId}' is not in the allowlist.");

    // Resolve the user's owned org (single membership with Owner role).
    var ownership = await db.OrganizationMembers
        .Where(m => m.UserId == userId && m.Role == OrgRole.Owner)
        .FirstOrDefaultAsync(ct);
    if (ownership is null)
        return (string.Empty, string.Empty, SubscriptionError.PermissionDenied,
            "User does not own any organization.");

    var orgId = ownership.OrgId;

    // Reuse an existing Stripe customer id when one is on file (any prior subscription row).
    var existingSub = await db.Subscriptions
        .FirstOrDefaultAsync(s => s.OrgId == orgId, ct);
    if (existingSub is not null)
        return (string.Empty, string.Empty, SubscriptionError.AlreadySubscribed,
            "Organization already has a subscription.");

    var existingCustomerId = await db.Subscriptions
        .Where(s => s.OrgId == orgId && s.StripeCustomerId != null)
        .OrderByDescending(s => s.CreatedAt)
        .Select(s => s.StripeCustomerId)
        .FirstOrDefaultAsync(ct);

    var (tier, seatCount, interval) = DerivePlanFromPriceId(priceId);

    CheckoutSession session;
    try
    {
        session = await stripe.CreateCheckoutSessionAsync(
            userId, orgId, tier, interval, seatCount,
            successUrl, cancelUrl,
            priceId: priceId, existingCustomerId: existingCustomerId,
            idempotencyKey: idempotencyKey, ct: ct);
    }
    catch (StripeRateLimitedException)
    {
        return (string.Empty, string.Empty, SubscriptionError.StripeRateLimited,
            "Stripe rate-limited; retry with the same idempotency key.");
    }

    var now = clock.GetUtcNow().UtcDateTime;
    db.Subscriptions.Add(new Subscription
    {
        Id = Guid.NewGuid(),
        OrgId = orgId,
        Tier = tier,
        Status = SubscriptionStatus.Active,
        Interval = interval,
        SeatCount = seatCount, SeatLimit = seatCount,
        CurrentPeriodStart = now,
        CurrentPeriodEnd = interval == "year" ? now.AddYears(1) : now.AddMonths(1),
        StripeCustomerId = session.CustomerId,
        StripeSubscriptionId = session.SessionId,
        CreatedAt = now, UpdatedAt = now,
    });
    audit.Append(new AuditEvent(...));
    await db.SaveChangesAsync(ct);

    return (session.CheckoutUrl, session.SessionId, SubscriptionError.None, null);
}

private static (SubscriptionTier tier, int seatCount, string interval) DerivePlanFromPriceId(string priceId)
{
    var tier = priceId switch
    {
        var p when p.StartsWith("price_solo_") || p.StartsWith("price_test_solo_") => SubscriptionTier.Professional,
        var p when p.StartsWith("price_professional_") || p.StartsWith("price_test_pro_") => SubscriptionTier.Professional,
        var p when p.StartsWith("price_team_") || p.StartsWith("price_test_team_") => SubscriptionTier.Team,
        var p when p.StartsWith("price_enterprise_") => SubscriptionTier.Enterprise,
        _ => SubscriptionTier.Free,
    };
    var interval = priceId.Contains("yearly", StringComparison.Ordinal) ? "year" : "month";
    var seatCount = tier == SubscriptionTier.Team ? 3 : 1;
    return (tier, seatCount, interval);
}
```

## Risks and Edge Cases

- **Risk:** Stripe.Net 43.x has breaking changes vs older versions and changes the namespace shape for `Stripe.Checkout` types. → **Mitigation:** Pin `<PackageReference Include="Stripe.net" Version="[43.0.0,44.0.0)" />` and run `dotnet build` immediately after adding the package to surface API drift.

- **Risk:** `stripe-mock` does not preserve idempotency-key state across container restarts (it's stateless). → **Mitigation:** Behaviour #2 ("replay returns same session id") is verified within a single container lifetime. The stripe-mock README does support idempotency replay within a session.

- **Risk:** The `IsAvailable` check in `StripeMockFixture` would silently skip integration tests in CI if stripe-mock fails to start. → **Mitigation:** `ci-local.sh` waits for stripe-mock readiness with a 30-attempt loop and `exit 1` if it never comes up — by the time `dotnet test` runs the fixture's check is just defence-in-depth.

- **Risk:** The `StripeCustomerId` reuse path queries `Subscriptions` for any prior row with a non-null customer id; if a future slice changes how subscriptions are deleted (hard-delete vs soft-delete), this lookup might miss the customer id. → **Mitigation:** Document the assumption inline ("relies on `subscriptions` retaining at least one historical row per org for customer id reuse"); this is consistent with how Stripe itself recommends storing customer ids.

- **Risk:** `Stripe.Mode=live` without `Stripe.ApiKey` was previously a no-op (it would only fail on first checkout); now `ValidateOnStart` will fail fast at app build. → **Mitigation:** Documented in Step 8's `deploy/self-hosted/README.md` section. Existing dev/test environments default to `fake` mode and are unaffected.

- **Risk:** The CLI does not yet send an `Idempotency-Key` request header for the `/checkout` endpoint. → **Mitigation:** The endpoint generates one server-side when missing; CLI integration with this header lands in M14-009 or later. Behaviour #1 ("a request-derived UUID") is still satisfied because the server derives one (RFC 4122 v4 from `Guid.NewGuid()`).

- **Risk:** Stripe.Net dependency adds ~6 MB and pulls Newtonsoft.Json (some versions). → **Mitigation:** 43.x ships without Newtonsoft for .NET 6+ targets — verify on `dotnet add package`.

- **Edge case:** A request with both `price_id` and the legacy fields takes the `price_id` path (the new field wins) and the `org_id` field is ignored — documented in Decision #2.

- **Edge case:** A request with `price_id` but no `success_url`/`cancel_url` returns 400 from ASP.NET model validation (existing behaviour for required fields).

- **Edge case:** `idempotencyKey` longer than Stripe's 255-byte limit; we always pass a UUID v4 (36 bytes) so this never trips, but the gateway truncates defensively.

- **Q:** Where does `stripe_customer_id` live? **A:** On `subscriptions.stripe_customer_id` (already exists). The task YAML wording is paraphrased; the spec at :9886 is authoritative. Decision #1 above.
- **Q:** Does the integration suite count toward the ">=8 tests pass" threshold? **A:** Yes — the 4 stripe-integration tests + the >=4 unit tests on the new code paths exceed the threshold, even before legacy tests are counted.
- **Q:** Should `CreatePortalSessionAsync` be wired live in this slice? **A:** No — task scope is `CreateCheckoutAsync` only. M14-009 (next slice) wires the portal. Decision in Step 3.
- **Q:** Should the spec's "request-derived UUID" be a hash of (orgId, priceId, success_url, cancel_url) for true determinism, or a fresh UUID v4 each call? **A:** Fresh UUID v4 generated server-side when the client does not supply `Idempotency-Key`. Two reasons: (a) deterministic hashing leaks request topology (anyone with read access to logs can correlate retries to same key), (b) the CLI's flock'd retry loop already guarantees at most one in-flight call per (user, command) — so the "same key on retry" property is the CLI's contract to provide, not the server's to invent. The header is the seam. Decision #4 above.
