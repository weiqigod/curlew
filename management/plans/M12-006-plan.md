# Implementation Plan: M12-006

## Overview

## Architectural Decisions

1. **Clock seam lives on `Registry`, not at package level.** A package-level `var nowFn = time.Now` would force all tests sharing a process to coordinate clock state. Putting `now func() time.Time` on `Registry` keeps the seam request-scoped and matches the existing `rng` field's instance-level lifetime — each `NewRegistry()` is a clean slate. The seam will be reused by M12-007's `$formatDate` for frozen-clock golden tests.
2. **Default `now` is `time.Now`, not `time.Now().UTC`.** `.UTC()` is applied at format time (matching existing `$isoTimestamp` behaviour at dynamic.go:169). Keeping the seam in local-time preserves drop-in `time.Now` semantics; tests that inject a frozen clock are responsible for supplying the timezone they want.
3. **No exported clock setter.** The seam is unexported (`r.now`). Tests inside the `variable` package set `reg.now = func() time.Time { ... }` directly. Exporting a `WithClock` would invite production callers to override real time — a foot-gun for a tool whose primary value-add is reproducible test runs. M12-007 will live in the same package and inherit the same access.
4. **`$dateSubtract` is a thin wrapper around the same kernel.** Both functions parse `amount` via `strconv.Atoi`, then dispatch on `unit`. `$dateSubtract` negates the amount before dispatch. Sharing the kernel guarantees byte-for-byte symmetry on `amount='0' unit='second'` (behavior 8).
5. **Integer-only amount, by spec.** `strconv.Atoi("1.5")` rejects with a `strconv.NumError`. We surface this as a structured `[INPUT]` error with code `DYNFN_DATE_BAD_AMOUNT`, naming the offending value and pointing to the integer-only restriction. The MANUAL.md note on decimal hours suggests `$dateAdd('90', 'minute')` as the workaround.
6. **Unknown unit returns the canonical seven-unit allowlist.** The error code is `DYNFN_DATE_BAD_UNIT`, the message lists `second, minute, hour, day, week, month, year`. Callers benefit from the literal list because the unit set is small and stable — no need for fuzzy matching.
7. **Reuse the existing `twoArgs` helper.** Arity validation, error wrapping, and prefix consistency all come from `twoArgs`. Both `$dateAdd` and `$dateSubtract` register through it.
8. **AddDate month-rollover documented, not corrected.** Go's `time.AddDate` rolls Feb 31 forward to March 3 (or 2). The spec explicitly accepts this. We document the behaviour in MANUAL.md §3.7 alongside a warning to use day-arithmetic when end-of-month stability matters.

```go
// Date arithmetic helpers — two args (amount, unit); the resolved
// instant is taken from r.now() (default time.Now, overridable in
// tests). Result is ISO-8601 UTC matching $isoTimestamp shape.
//
// $dateAdd(amount, unit)        — now + amount*unit
// $dateSubtract(amount, unit)   — now - amount*unit
//
// Supported units: second, minute, hour, day, week, month, year.
// Negative amounts are accepted (so $dateAdd('-1', 'day') is valid).
//
// Month and year offsets follow time.AddDate semantics — Feb 31 rolls
// forward to March 3 (or 2). Use day-based arithmetic when end-of-month
// stability matters. See MANUAL.md §3.7.
r.funcs["dateAdd"] = twoArgs("dateAdd", func(amount, unit string) (string, error) {
    return r.applyDateOffset("dateAdd", amount, unit, +1)
})
r.funcs["dateSubtract"] = twoArgs("dateSubtract", func(amount, unit string) (string, error) {
    return r.applyDateOffset("dateSubtract", amount, unit, -1)
})
```

Plus a kernel method:

```go
// applyDateOffset is the shared dispatch kernel for $dateAdd and $dateSubtract.
// sign is +1 for add, -1 for subtract; the kernel multiplies the parsed amount by sign.
// On parse failure, returns DYNFN_DATE_BAD_AMOUNT. On unknown unit, returns DYNFN_DATE_BAD_UNIT.
func (r *Registry) applyDateOffset(funcName, amount, unit string, sign int) (string, error) {
    n, err := strconv.Atoi(amount)
    if err != nil {
        return "", &apierrors.Structured{
            Category: apierrors.CategoryInput,
            Code:     "DYNFN_DATE_BAD_AMOUNT",
            Message:  fmt.Sprintf("invalid amount %q: must be an integer", amount),
            Hint:     "Pass an integer string (e.g. '90'); decimal amounts are not supported — use a smaller unit (e.g. $dateAdd('90', 'minute') instead of '1.5' 'hour').",
            Inner:    err,
        }
    }
    n *= sign
    base := r.now()
    var t time.Time
    switch unit {
    case "second":
        t = base.Add(time.Duration(n) * time.Second)
    case "minute":
        t = base.Add(time.Duration(n) * time.Minute)
    case "hour":
        t = base.Add(time.Duration(n) * time.Hour)
    case "day":
        t = base.AddDate(0, 0, n)
    case "week":
        t = base.AddDate(0, 0, 7*n)
    case "month":
        t = base.AddDate(0, n, 0)
    case "year":
        t = base.AddDate(n, 0, 0)
    default:
        return "", &apierrors.Structured{
            Category: apierrors.CategoryInput,
            Code:     "DYNFN_DATE_BAD_UNIT",
            Message:  fmt.Sprintf("unknown unit %q", unit),
            Hint:     "Allowed units: second, minute, hour, day, week, month, year.",
        }
    }
    return t.UTC().Format("2006-01-02T15:04:05Z"), nil
}
```

## Risks and Edge Cases

- **Risk:** Production callers might depend on `time.Now` being called in a particular goroutine context. **Mitigation:** the seam defaults to `time.Now`, so production behaviour is byte-for-byte identical to a direct `time.Now()` call. The change is observable only in tests that explicitly install a frozen clock.

- **Edge case:** Integer overflow on `time.Duration(n) * time.Second`. A `time.Duration` is `int64` nanoseconds; `int64(math.MaxInt64) / 1e9 ≈ 292 years`. An attacker passing `dateAdd('999999999', 'second')` (~31 years) is well within range, but `dateAdd('99999999999', 'second')` (~3170 years) would overflow `time.Duration` math silently. **Handling:** acceptable risk for the M12 vertical slice — overflow produces an unhelpful but not security-relevant ISO timestamp. Future hardening (M12-007 or beyond) can add a sane upper bound. Documented as a non-goal in the spec ("not in scope: bounds-checked amounts").

- **Edge case:** `strconv.Atoi("-0")` returns 0 with no error — both functions would treat `'-0' second` and `'0' second` identically, which is correct.

- **Edge case:** Empty `amount` (`''`) or empty `unit` (`''`) — `strconv.Atoi("")` returns an error → caught by `DYNFN_DATE_BAD_AMOUNT`; `unit == ""` falls through the switch's default → caught by `DYNFN_DATE_BAD_UNIT`. Both paths produce structured errors with appropriate codes.

- **Edge case:** `amount` with leading whitespace like `' 1'` — `strconv.Atoi` rejects whitespace, producing `DYNFN_DATE_BAD_AMOUNT`. This matches the M12-001 contract that argument values are passed verbatim after literal-quote unescaping; users should not include whitespace inside their argument literals.

- **Risk:** Per-request memoisation cache could mask clock changes. The cache key is `funcName + NUL + args`, which does not include the timestamp. If a single request makes two `$dateAdd('1', 'hour')` calls, the second hits the cache and returns the same instant as the first — even if `r.now()` would have advanced. **Mitigation:** this is the intended behaviour and matches existing `$timestamp` and `$isoTimestamp` caching; documented in §3.7 ("multiple references to the same function return the same value (per-request memoization)"). Frozen-clock tests are unaffected because the clock returns the same value on every call regardless.

- **Risk:** Documenting AddDate rollover surfaces a stdlib oddity that may surprise users coming from JavaScript's `date-fns` (which provides both `addMonths` and `endOfMonth`-aware variants). **Mitigation:** explicit MANUAL.md callout with a workaround pointer (use day-based arithmetic). A future task can add `$dateAddPreserveEOM` if real users hit this; not in scope here.
