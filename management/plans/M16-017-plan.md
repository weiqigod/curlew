## Open Decisions Resolved Up Front

The task references two open decisions that the plan resolves now (per pipeline rule "use best judgment, document"):

- **Open Decision 5 — validator mode toggle.** Implemented as an option object `VaultConfigOptions { ValidatorMode = "reject" | "warn" }` bound from the configuration section `Curlew:VaultConfig:ValidatorMode` (env spelling `CURLEW__VAULTCONFIG__VALIDATORMODE`). The task observable spells the env as `VAULTCONFIG__VALIDATOR_MODE` — we'll bridge that exact spelling in `Program.cs` (same pattern used for `GITHUB__WEBHOOK_SECRETS` etc.) into the canonical key. Default is `reject` (production-safe); the Development environment auto-defaults to `warn` so the observable's dev-mode case works without extra config. `appsettings.Development.json` gets `Curlew:VaultConfig:ValidatorMode = "warn"`.
- **Open Decision 11 — minimum-viable page.** The YAML editor is a `<textarea class="font-mono ...">` — no monaco-editor dependency added. The page is functional (load, edit, save, delete, copy CLI snippet) and uses the existing Tailwind/Skeleton conventions. Polish (syntax highlighting, linting) is deferred.

## Schema Reconciliation

The task observable says columns `id`, `org_id UNIQUE`, `template_jsonb`, `version`, `created_at`, `updated_at`. The spec appendix (`docs/SPECIFICATION.md:10947-10960`) is richer: `org_id UUID PRIMARY KEY` (no surrogate `id`), `template_yaml TEXT NOT NULL`, `template_jsonb JSONB NOT NULL`, `version BIGINT NOT NULL DEFAULT 1`, `created_at`, `created_by`, `updated_at`, `updated_by`, plus `idx_team_vaults_updated`. **The spec is the canonical source.** We follow the appendix. The observable's `id` and `UNIQUE org_id` are an older draft — the spec's `org_id PRIMARY KEY` already enforces uniqueness, and `template_yaml` + `created_by`/`updated_by` are required to (a) preserve YAML comments/ordering and (b) record who touched the row. We will document this divergence in the plan and the task once the migration applies; the spirit of the observable (one row per org, JSONB template, version increment) is preserved.

```csharp
namespace ApiTool.Backend.VaultConfig;

/// <summary>
/// Inspects a parsed vault-config template for fields named password|secret|token|key
/// whose value matches the literal-secret heuristic (^[A-Za-z0-9+/=._-]{16,}$ not also
/// matching a recognized provider coordinate pattern). Spec :5658.
/// </summary>
public static class VaultManifestValidator
{
    private static readonly Regex LiteralSecretRegex =
        new(@"^[A-Za-z0-9+/=._\-]{16,}$", RegexOptions.Compiled);

    private static readonly Regex CoordinateRegex =
        // ARN, vault://, key vault refs — coordinates contain at least one `:`, `/`, or starts with arn:
        new(@"^(arn:|.+://|.+[:/].+)$", RegexOptions.Compiled);

    private static readonly HashSet<string> SensitiveKeyNames = new(StringComparer.OrdinalIgnoreCase)
    { "password", "secret", "token", "key" };

    /// <summary>Walks the parsed JSON tree, returns the JSON-path of every suspect value.</summary>
    public static VaultValidationResult Validate(JsonElement root);
}

public sealed record VaultValidationResult(IReadOnlyList<string> OffendingPaths)
{
    public bool Ok => OffendingPaths.Count == 0;
}
```

#### Endpoint contract

```
GET    /api/v1/organizations/{orgId}/vault-config
    Headers: If-None-Match: "<version>"  (optional)
    200 with body { template: <object>, version, updated_at, updated_by_email } + ETag: "<version>"
    304 when If-None-Match matches version
    402 when tier < team (via TierGateProblemFactory)
    403 when user lacks vault_config.view
    404 when org missing OR row missing
    
PUT    /api/v1/organizations/{orgId}/vault-config
    Body: application/x-yaml or application/yaml or application/json { yaml: "<yaml>" }
    For simplicity we accept text/yaml + application/yaml (Content-Type negotiation) and read
    the raw body as a string; JSON-wrapped body is rejected with 415 to keep the
    contract clean. The web client sends raw YAML; this matches the spec semantics.
    200 with body { ..., version } and ETag: "<new-version>"
    402 / 403 like GET
    422 when validator rejects (problem detail .../vault-template-suspicious-value, payload includes offending_paths)
    
DELETE /api/v1/organizations/{orgId}/vault-config
    204 on success
    402 / 403 / 404 like GET
```

#### ETag semantics

`ETag` value is the literal `"<version>"` string (weak ETag prefix `W/` could be used but version is monotonic so the strong form is correct). `If-None-Match` is compared case-sensitively, stripping surrounding quotes — spec line 5685.

#### RBAC

Service is the gate keeper: `RoleResolver.HasPermissionAsync(userId, orgId, Permissions.VaultConfigView, ct)` for GET, `VaultConfigManage` for PUT/DELETE. The endpoint translates `PermissionDenied` to 403.

## Risks and Edge Cases

- **Risk:** EF Core's SQLite provider does not natively support `jsonb`. The current convention (cf. `pr_checks.annotations`, `signing_keys.public_key_jwk`) is to branch `if (Database.IsNpgsql())` in `OnModelCreating`. The same branch is required for `team_vaults.template_jsonb`. **Mitigation:** copy the existing pattern verbatim; assert SQLite TEXT path via `TeamVaultSchemaTests`.
- **Risk:** YAML round-tripping with comments lost on `YamlToJson → JsonToYaml`. **Mitigation:** Store both `template_yaml` (round-trippable source — exactly what the client sent) AND `template_jsonb` (parsed form). Spec :10962 mandates this.
- **Risk:** YamlDotNet 16.x dependency may not exist in NuGet on `net9.0`. **Mitigation:** pin a known-good version (`16.2.1` is the latest at time of writing; if absent, fall back to `15.x` which already targets net9). Verify at `dotnet restore` time during execute phase.
- **Risk:** The literal-secret regex `^[A-Za-z0-9+/=._-]{16,}$` will also match many legitimate coordinates (e.g., a 16-char Azure Key Vault name). The spec mitigates by exempting "recognized provider coordinate patterns" — we operationalise this as: a value containing `:`, `/`, or starting with `arn:` is a coordinate; otherwise, if it's 16+ alphanumeric chars under a sensitive key name, it's suspect. **Mitigation:** unit-test the coordinate exemption explicitly with all four spec example providers (aws-secrets-manager ARN, azure-key-vault vault_name, hashicorp-vault path, 1password vault id).
- **Edge case:** `If-None-Match: *`. Per HTTP spec, `*` matches any current representation. **Handling:** treat `*` as a 304 when a row exists, 200 otherwise (rarely sent in practice; non-blocking — add to the test matrix).
- **Edge case:** Concurrent PUTs racing the version increment. **Handling:** `db.SaveChangesAsync` with EF Core's default optimistic concurrency catches via `DbUpdateConcurrencyException` only if we mark `Version` as a concurrency token. For v4.3 we accept last-writer-wins (spec doesn't mandate optimistic concurrency). Document as a follow-up if the CLI ever needs it.
- **Edge case:** `template_yaml` is the empty string. **Handling:** reject with `InvalidYaml` — vault-config without `team_secrets:` makes no sense; an explicit `DELETE` is the contract for "remove the config".
- **Edge case:** A free-tier org admin loads the page directly. **Handling:** `requireTeamTier` redirects with `team_tier_required` toast — same as schedules/gitlab.
